## 🔍 相互依赖的未实现功能

### 1. 健康筛查流程接口（关键阻塞）

**问题描述**:
- `diagnosis-service` 的 `WellnessScreeningOrchestrator` 已经准备好调用健康筛查流程的A1-A5接口
- 但 `health-state-assessment-service` 未实现这些API接口

**未实现的接口**:
- ❌ `POST /api/v1/wellness-screening/a1-demand-classification` - A1: 需求分类
- ❌ `POST /api/v1/wellness-screening/a2-health-profile-collection` - A2: 收集健康画像
- ❌ `POST /api/v1/wellness-screening/a3-branch-execution` - A3: 执行分支
- ❌ `POST /api/v1/wellness-screening/a4-unified-result-generation` - A4: 生成统一结果
- ❌ `POST /api/v1/wellness-screening/a5-follow-up-setup` - A5: 设置随访

**影响**:
- 当用户进入健康管理态（wellness_mode）时，`diagnosis-service` 无法执行健康筛查流程
- `WellnessScreeningOrchestrator.executeWellnessScreening()` 会调用失败
- 健康筛查流程完全无法使用

**代码位置**:
- `diagnosis-service/src/main/java/com/aidoctor/diagnosis/service/wellness/WellnessScreeningOrchestrator.java` (已准备好调用)
- `health-state-assessment-service/app/services/wellness-screening/` (业务逻辑未实现，只有TODO框架)

### 2. 健康状态判定响应解析（部分实现）

**问题描述**:
- `diagnosis-service` 调用 `health-state-assessment-service` 后，需要解析响应
- `parseAssessmentResponse()` 方法目前是简化实现（TODO）

**当前实现**:
```java
private Map<String, Object> parseAssessmentResponse(Object response) {
    // TODO: 根据实际响应格式解析
    // 这里假设response是Map类型
    if (response instanceof Map) {
        return (Map<String, Object>) response;
    }
    return new HashMap<>();
}
```

**实际响应格式**:
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "cdpId": "cdp_xxx",
    "needsClinicalMode": true,
    "workMode": "clinical_mode",
    "riskLevel": "L2",
    "assessmentReason": "...",
    "entryAssessment": {...},
    "redFlags": [],
    "wellnessPlan": null
  },
  "timestamp": 1705123456789
}
```

**需要完善**:
- 提取 `data` 字段中的关键信息（workMode, needsClinicalMode, riskLevel等）
- 处理错误响应格式
- 验证响应数据完整性

**影响**:
- 当前可以工作（因为简化实现能处理基本格式）
- 但不够健壮，可能在某些情况下解析失败
- 无法正确提取嵌套的 `entryAssessment` 等复杂字段

**代码位置**:
- `diagnosis-service/src/main/java/com/aidoctor/diagnosis/service/DiagnosisOrchestrationService.java` 第370-377行

## 💡 开发建议

### 建议：先完善这三个服务，再进入诊断引擎服务开发

**理由**：

#### 1. 形成完整的最小闭环

**当前状态**：
- ✅ `diagnosis-service` → `health-state-assessment-service` (启动流程) - 已实现
- ✅ `diagnosis-service` → `clinical-parsing-service` (Step 1) - 已实现
- ⚠️ `diagnosis-service` → `health-state-assessment-service` (健康筛查流程) - 部分阻塞

**完善后**：
- 可以完整测试从启动诊断到Step 1的完整流程
- 可以完整测试健康管理态的流程（如果实现健康筛查）
- 形成可验证的最小闭环

#### 2. 降低后续开发风险

**如果先开发诊断引擎服务**：
- 诊断引擎服务依赖 `diagnosis-service` 的响应解析方法
- 但 `diagnosis-service` 的响应解析方法大部分未实现
- 无法进行端到端测试
- 可能出现接口不匹配的问题

**如果先完善这三个服务**：
- 可以明确接口规范
- 可以验证服务间调用
- 为后续服务开发提供稳定的基础

#### 3. 优先级排序

**P0（必须，阻塞其他功能）**：
1. ✅ `parseParsingResponse()` - 已实现，Step 1可以工作
2. ⚠️ `parseAssessmentResponse()` - 需要完善（当前简化实现可用，但不够健壮）
3. ❌ 健康筛查流程A1-A5接口 - 阻塞健康管理态流程

**P1（重要，但不阻塞核心流程）**：
4. ❌ 健康筛查流程响应解析（A1-A5）- 依赖P0完成
5. ❌ Step 2-5的响应解析 - 依赖诊断引擎服务开发

**P2（可选）**：
6. 其他优化功能

## ✅ 总结

### 相互依赖的未实现功能

1. **健康筛查流程接口**（health-state-assessment-service） - 阻塞健康管理态流程
2. **健康状态判定响应解析**（diagnosis-service） - 需要完善
3. **健康筛查流程响应解析**（diagnosis-service） - 依赖健康筛查接口
4. **Step 2-5响应解析**（diagnosis-service） - 依赖诊断引擎服务

### 开发建议

**建议先完善这三个服务**，原因：
1. 形成完整的最小闭环（启动 → 健康状态判定 → 病例理解）
2. 降低后续开发风险
3. 明确接口规范
4. 为诊断引擎服务开发提供稳定基础

**开发顺序**:
1. 完善 `parseAssessmentResponse()` (1-2天)
2. 实现健康筛查流程接口 (1-2周)
3. 实现健康筛查流程响应解析 (2-3天)
4. 进入诊断引擎服务开发
