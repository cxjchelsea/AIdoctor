# AIdoctor 外部健康数据与设备连接扩展方案

> 文档状态：`FUTURE_EXTENSION_DESIGN`  
> 设计来源：Health / freddy / Fitness AI Connector 等外部产品模式观察  
> 当前 Runtime 影响：`NONE`  
> Shared Contracts v1 影响：`NONE`  
> 当前 Capability 影响：`NONE`  
> 实现授权：`NOT_AUTHORIZED`

---

## 1. 目的

本方案定义 AIdoctor 未来如何接入患者外部健康数据、可穿戴设备、专用医疗/健康设备以及独立算法项目，而不破坏当前重构已经确定的：

- Clinical State 所有权；
- State Committer 唯一受控写入；
- Consent / Permission；
- Evidence Ledger；
- Patient RAG 与 Medical RAG 隔离；
- ToolContext / ToolResult 边界；
- Capability Allowlist；
- Audit / Trace / Replay。

本设计当前只沉淀扩展边界，不要求修改 `contracts/v1`，也不进入当前 A7-NC / A7-CL Scope。

---

## 2. 外部产品带来的核心启发

### 2.1 Health 模式

核心价值不是“增加一个健康聊天入口”，而是：

```text
多个患者数据源
→ 统一授权与连接
→ 标准化健康数据
→ 纵向患者上下文
→ Agent 按最小必要范围查询
```

AIdoctor 应吸收“多源患者数据统一 + 长期记录 + 来源与授权”的思想，而不是复制具体产品形态。

### 2.2 freddy 模式

核心价值是：

```text
多个健康平台 / 设备
→ Connector 层
→ 统一 Agent 可查询接口
```

AIdoctor 应吸收多 Connector 的抽象、连接状态、权限、同步和数据标准化。

### 2.3 Fitness AI Connector 模式

核心价值是“单设备/单平台能力不通过万能查询接口暴露”，而是拆成小而明确的 Tool Surface，例如 summary、activity、trend、refresh 等职责。

AIdoctor 未来的设备 Tool 同样应避免：

```text
call_medical_device(query: string)
```

而应提供可治理、可测试、可授权的明确操作。

## 3. 总体目标架构

```text
External Health Sources
│
├── EHR / Hospital Data
├── Wearables
├── Home Health Devices
├── Pulse Diagnosis Device
└── Tongue Imaging System
        │
        ▼
External Source Adapter / Device Adapter
        │
        ▼
Connector Runtime
│  - authentication
│  - consent
│  - synchronization
│  - normalization
│  - provenance
│  - quality
│  - retry / timeout
│
        ▼
SourceArtifact / Measurement Artifact
        │
        ▼
Parser / Signal Model / Image Model
        │
        ▼
ObservationCandidate / ToolResult
        │
        ▼
State Committer
        │
        ├── Encounter Evidence Ledger
        └── Longitudinal Patient Record（满足写入条件时）
```

关键约束：

> 外部来源、设备模型和算法输出永远不是 Clinical State 的直接写入者。

## 4. 新增的未来平台抽象

以下均为 vNext Candidate，不是当前 Shared Contracts v1 变更。

### 4.1 ConnectorSpec

描述一种可接入外部来源的连接器类型。

```python
class ConnectorSpec(BaseModel):
    connector_id: str
    connector_version: str
    provider_type: Literal[
        "ehr",
        "wearable",
        "home_device",
        "medical_device",
        "internal_device_service",
    ]
    auth_mode: str
    supported_operations: list[str]
    supported_data_types: list[str]
    sync_modes: list[str]
    required_scopes: list[str]
    data_residency_policy_id: str | None
    status: str
```

### 4.2 ExternalHealthSourceConnection

描述患者与一个外部来源之间的实际连接。

```python
class ExternalHealthSourceConnection(BaseModel):
    connection_id: str
    patient_id: str
    connector_id: str
    external_subject_ref: str
    consent_scope_id: str
    authorization_scopes: list[str]
    connection_status: str
    connected_at: datetime
    last_sync_at: datetime | None
    sync_cursor_ref: str | None
    valid_until: datetime | None
```

原则：

- Token / Credential 不进入普通业务 Contract；
- Patient / Tenant / Consent 强绑定；
- Connection 可撤销；
- 每次读取必须重新经过 Policy Check；
- 连接存在不等于本次 Encounter 有权读取全部数据。

### 4.3 MeasurementArtifact / BiosignalArtifact / ImageArtifact

当前 `SourceArtifact v1` 已承担上传、报告、OCR 和知识资产等来源元数据，但未来设备接入需要更明确的数据类型。

候选类型：

```text
DEVICE_MEASUREMENT
BIOSIGNAL
IMAGE
DERIVED_SIGNAL
DERIVED_IMAGE
MULTIMODAL_ANALYSIS
```

候选元数据：

```text
device_id
device_model
firmware_version
acquisition_protocol
observed_at
sampling_rate
unit
calibration_version
quality_score
algorithm_id
algorithm_version
derived_from_artifact_ids
```

这些字段只作为 vNext Contract Candidate 记录，不修改当前 `SourceArtifact 1.0.0`。

## 5. Connector Runtime 职责

Connector Runtime 未来应负责：

### 5.1 Authentication

- OAuth/OIDC/API credential adapter；
- Credential 与临床数据隔离；
- Token rotation；
- 连接撤销；
- 不允许把患者密码交给 Agent。

### 5.2 Consent / Authorization

每次调用都必须同时满足：

```text
Connector 支持该操作
+ Patient 已连接
+ Consent 允许
+ Capability Allowlist 允许
+ 当前 Actor 有权限
+ 当前 Encounter 需要该数据
```

### 5.3 Synchronization

支持未来按来源选择：

```text
pull
webhook
scheduled sync
on-demand refresh
local device upload
```

同步不能静默覆盖历史数据，应保留 source version / observed_at / ingestion time。

### 5.4 Normalization

Connector 负责将厂商字段映射到 AIdoctor 标准候选结构，但不能直接把所有外部数据转成长期患者真值。

```text
Vendor Payload
→ Normalized Measurement
→ Validation / Quality
→ ObservationCandidate
→ State Committer
```

### 5.5 Failure Semantics

统一映射到现有 Tool Result 思路：

```text
SUCCEEDED
NO_RESULT
RETRYABLE_FAILURE
NON_RETRYABLE_FAILURE
TIMED_OUT
POLICY_BLOCKED
```

设备不可用时不得默认解释为“患者指标正常”。

## 6. 数字脉诊项目接入设计

### 6.1 边界

`digital-pulse-diagnosis` 保持独立项目，不将传感器驱动、滤波、特征工程和算法代码直接迁入 AIdoctor。

```text
digital-pulse-diagnosis
│
├── acquisition
├── signal processing
├── feature extraction
└── pulse analysis
        │
        ▼
Pulse Device Adapter
        │
        ▼
AIdoctor Tool Runtime
```

### 6.2 推荐数据链

```text
Raw Pulse Waveform
↓
Acquisition Metadata
↓
Signal Quality Assessment
↓
Filtering / Segmentation
↓
Pulse Features
↓
Pulse Analysis Candidate
↓
ToolResult
↓
ObservationCandidate
↓
State Committer
```

### 6.3 推荐 Tool Surface

未来可评估：

```text
get_pulse_measurement
get_pulse_waveform
get_pulse_signal_quality
get_pulse_features
analyze_pulse_measurement
```

禁止使用一个过宽的 `pulse_diagnosis()` 直接返回正式疾病诊断并写入 Clinical State。

### 6.4 来源与可追溯性

每个脉诊派生结果至少应可追踪：

```text
原始波形 artifact
→ 采集设备 / firmware
→ acquisition protocol
→ preprocessing version
→ feature algorithm version
→ model version
→ output candidate
```

这样以后算法升级可以重放和比较，而不会丢失历史证据。

## 7. 舌象分析项目接入设计

### 7.1 边界

舌象分析同样保持独立算法/设备服务。

```text
Tongue Imaging System
↓
Tongue Device Adapter
↓
Tool Runtime
↓
ObservationCandidate
```

### 7.2 推荐数据链

```text
Raw Tongue Image
↓
Camera / Lighting / Calibration Metadata
↓
Image Quality Assessment
↓
Tongue Segmentation
↓
Color / Shape / Coating Features
↓
Analysis Candidate
↓
ToolResult
↓
ObservationCandidate
↓
State Committer
```

### 7.3 推荐 Tool Surface

```text
get_tongue_image
assess_tongue_image_quality
extract_tongue_features
analyze_tongue_image
```

### 7.4 关键约束

图像质量不足时必须返回显式质量状态，而不能让模型继续产生高置信度医学解释。

未来应把：

```text
camera model
lighting condition
white balance / calibration
capture distance
resolution
segmentation version
model version
```

作为可复现元数据管理。

## 8. 设备数据、Patient RAG 与 Medical RAG 的边界

三者不得混为一层。

### 8.1 设备数据

属于患者来源证据：

```text
Raw Measurement / Image / Signal
→ SourceArtifact
→ Analysis
→ ClinicalObservation Candidate
```

### 8.2 Patient RAG

用于查找患者历史：

```text
历史 Encounter
长期病史
既往检查
既往设备测量
随访记录
```

### 8.3 Medical RAG

用于查找医学证据：

```text
指南
系统综述
研究
监管与患者教育材料
```

禁止把“设备数据向量化后能搜索”误当成 Clinical State 建模。

---

## 9. ToolContext / ToolResult 兼容原则

未来 Connector / Device Tool 应继续遵守现有受限调用思路：

```text
Agent / Runtime
↓
ToolContext（最小必要授权上下文）
↓
Device / Connector Tool
↓
ToolResult
    ├── output
    ├── suggested_patches
    ├── evidence_refs
    └── errors
↓
State Committer
```

外部 Tool 不获得完整 CDP 任意读写能力。

---

## 10. Capability 集成原则

设备存在不等于任何 Capability 都可以调用。

未来 Capability 必须通过 allowlist 声明：

```yaml
allowed_tool_ids:
  - pulse-signal-quality
  - pulse-feature-extraction
```

而不是由 Agent 运行时自由发现所有连接设备。

对于临床证据不足、尚未通过验证的设备能力，可以只进入：

```text
research
shadow
clinician_assist
```

而不能直接进入患者自动化路径。

---

## 11. 安全与隐私门禁

未来实现至少需要：

- Patient/Tenant 强隔离；
- Consent Scope；
- 最小必要读取；
- Credential 与 PHI 分离；
- 数据驻留策略；
- 原始设备数据 Retention；
- 删除与撤回传播；
- Tool invocation audit；
- 设备型号、算法版本和校准版本可追踪；
- Prompt 不默认接收原始大体量生理信号；
- 外部 Provider 不得成为 State Committer。

---

## 12. 未来评估体系

### Connector 层

- auth success rate；
- consent enforcement；
- sync completeness；
- duplicate ingestion rate；
- stale-data detection；
- cross-patient leakage = 0；
- retry / timeout semantics。

### Device 数据层

- acquisition quality；
- calibration repeatability；
- artifact provenance completeness；
- algorithm reproducibility；
- missing/invalid data correctness。

### Agent Tool 层

- tool selection accuracy；
- unauthorized tool call = 0；
- correct no-result behavior；
- correct policy-block behavior；
- state write bypass = 0。

---

## 13. 推荐未来实施顺序

当前不实施。进入未来正式版本时建议：

```text
1. ADR：Connector / Device Extension 是否进入正式 Roadmap
2. 定义 ConnectorSpec / Connection Contract Candidate
3. FakeHealthConnector
4. Synthetic Device Fixture
5. Tool Registry / Allowlist 集成
6. 一个只读真实 Connector
7. Pulse Device Adapter Shadow
8. Tongue Device Adapter Shadow
9. Evidence / State Committer 集成评估
10. Clinician Assist
11. 再决定 Restricted Patient
```

不建议第一步就接真实患者设备数据。

---

## 14. Exit 条件（未来）

某个设备或外部健康数据源只有同时满足以下条件，才有资格进入正式 Capability：

- Connector Contract 稳定；
- Authentication / Consent / Revocation 验证完成；
- Source provenance 可完整追踪；
- 输入质量有明确状态；
- ToolResult 不直接提交 Clinical State；
- State Committer 路径验证通过；
- 专项 Eval 达标；
- 临床 Reviewer 批准其语义边界；
- Privacy / Security Review 完成；
- Rollback / Disconnect / Data Deletion 可执行。
