# 诊断服务 - 架构与逻辑整理

> **文档定位**：本文档全面整理诊断服务（diagnosis-service）的系统架构、核心逻辑、数据流程和技术实现细节。  
> **服务定位**：AI医生系统的流程编排中心，负责协调所有脑区服务，管理CDP生命周期，编排诊断流程和健康筛查流程。  

**文档内容说明**：
- ✅ **完整实现**：已完整实现，符合设计规范的功能
- 🟡 **简化实现**：采用简化实现方式，功能可用但需要进一步优化的功能
- 📋 **设计目标**：设计文档中定义的目标，当前未完全实现

---

## 一、服务概述

### 1.1 服务定位

- **对应脑区**：协调器/编排器（非独立脑区，负责协调所有脑区）
- **在架构中的位置**：双通道推理架构的协调中心，位于所有AI服务的上层，负责流程编排和CDP管理
- **服务职责**：
  1. **CDP管理**：创建、更新、版本控制、回放、回退
  2. **诊断流程编排**：编排5步AI循证诊断流程（临床诊疗态）
  3. **健康筛查流程编排**：编排健康筛查流程（A路径，A1-A5，健康管理态）
  4. **服务协调**：协调各个AI服务的调用顺序和依赖关系
  5. **状态管理**：管理CDP状态流转和诊断流程状态
  6. **执行追踪**：集成execution-trace-service，追踪诊断流程执行过程

### 1.2 核心价值

- **统一流程编排**：将复杂的多服务协作流程统一管理，降低前端调用复杂度
- **CDP生命周期管理**：确保诊断过程可追溯、可审计、可回退
- **状态一致性**：保证CDP状态与诊断流程状态的一致性
- **服务解耦**：前端只需调用diagnosis-service，无需了解底层AI服务的细节
- **可追溯性**：通过CDP版本控制和执行追踪，支持诊断过程的完整追溯

## 三、核心业务流程

### 3.1 完整流程概览

> **重要说明**：诊断服务是**流程编排服务**，不实现具体的诊断逻辑，而是负责协调各个下游AI服务，按照5步AI循证诊断流程的顺序调用相应服务，并管理CDP的状态流转。

```
用户请求
   │
   ▼
┌─────────────────────────────────────┐
│  启动诊断流程（编排层）               │
├─────────────────────────────────────┤
│ 1. 创建CDP（诊断服务内部）           │
│ 2. 调用健康状态判定服务              │
│    └─→ health-state-assessment-service│
│ 3. 根据工作态决定流程                │
└─────────────────────────────────────┘
   │
   ├─→ 健康管理态 → 健康筛查流程（A路径）
   │    └─→ 编排调用 health-state-assessment-service (A1-A5)
   │
   └─→ 临床诊疗态 → 5步AI循证诊断流程（编排层）
        │
        ├─→ Step 1: 识别问题
        │    ├─→ 调用 clinical-parsing-service（脑区A）
        │    └─→ 调用 dialog-service（脑区B）
        │
        ├─→ Step 2: 构建鉴别诊断候选集并分层
        │    ├─→ 调用 diagnosis-engine-service（脑区C）
        │    └─→ 调用 risk-assessment-service（脑区F）
        │
        ├─→ Step 3: 组织候选集并建立分流路径
        │    ├─→ 调用 diagnosis-engine-service（脑区C）
        │    └─→ 调用 dialog-service（脑区B）
        │
        ├─→ Step 4: 采集关键证据并形成排序与验证计划
        │    ├─→ 调用 dialog-service（脑区B）
        │    ├─→ 调用 diagnosis-engine-service（脑区C）
        │    └─→ 调用 workup-planner-service（脑区D）
        │
        └─→ Step 5: 回填证据并输出终点结论包
             ├─→ 调用 clinical-parsing-service（脑区A）
             ├─→ 调用 diagnosis-engine-service（脑区C）
             ├─→ 调用 treatment-engine-service（脑区E）
             ├─→ 调用 risk-assessment-service（脑区F）
             └─→ 调用 explanation-service（脑区G）
```

**编排特点**：
- **不实现诊断逻辑**：诊断服务本身不包含任何诊断算法或医学知识
- **协调服务调用**：按照5步流程的顺序，协调各个脑区服务的调用
- **管理CDP状态**：在每次服务调用后，更新CDP的相应字段和状态
- **容错处理**：当某个下游服务调用失败时，使用默认值或空值继续流程，确保流程不中断

### 3.2 诊断流程启动

#### 3.2.1 启动流程

**功能**：
- 接收前端诊断请求
- 创建CDP（Clinical Decision Process）
- 调用健康状态判定服务
- 根据工作态决定后续流程

**处理逻辑**：
1. **生成会话ID**：为本次诊断会话生成唯一ID
2. **创建CDP**：创建初始版本的CDP，状态为`initial`
3. **调用健康状态判定服务**：
   - 调用`health-state-assessment-service`进行健康状态判定
   - 获取工作态（`clinical_mode` / `wellness_mode`）
   - 获取风险评估结果
   - 容错处理：如果服务不可用，默认进入临床诊疗态
4. **更新CDP**：
   - 保存健康状态判定结果到`healthStateAssessment`字段
   - 保存用户输入、基本信息、症状等到`patientState`字段
   - 更新CDP状态（`clinical_mode_collecting` / `wellness_mode`）
5. **决定后续流程**：
   - 如果`needsClinicalMode = true`：返回CDP ID，等待用户继续（执行Step 1）
   - 如果`needsClinicalMode = false`：执行健康筛查流程（A1-A5）

**输出**：
```json
{
    "cdpId": "cdp_xxx",
    "workMode": "clinical_mode" | "wellness_mode",
    "status": "clinical_mode_collecting" | "wellness_mode",
    "currentStep": "step1_identify_problem",
    "nextAction": {
        "type": "question",
        "question": "请详细描述一下您的症状"
    },
    "completeness": 0.0,
    "riskLevel": "L4",
    "assessmentReason": "..."
}
```

### 3.3 5步AI循证诊断流程（临床诊疗态）

#### 3.3.1 Step 1: 识别问题

**功能**：
- 调用`clinical-parsing-service`（脑区A）进行概念归一化和结构化提取
- 调用`dialog-service`（脑区B）识别信息缺口并生成追问问题
- 构建结构化问题清单
- 更新CDP的`patientState`字段

**处理逻辑**：
1. **概念归一化**：
   - 调用`clinical-parsing-service`的`/api/v1/parsing/parse`接口
   - 提取用户输入文本（从`userAnswers`或`healthStateAssessment`中获取）
   - 解析响应，提取`normalizedConcepts`、`structuredData`等
   - 更新`patientState`字段
2. **信息缺口识别**：
   - 调用`dialog-service`的`/api/v1/dialog/identify-gaps`接口
   - 获取信息完整度（`completeness`）
   - 如果完整度低于阈值，生成追问问题
3. **生成追问问题**：
   - 调用`dialog-service`的`/api/v1/dialog/generate-question`接口
   - 生成自然语言追问问题
   - 保存到`patientState.nextQuestion`字段
4. **更新CDP状态**：
   - 状态更新为`clinical_mode_collecting`
   - 保存`patientState`、`completeness`等信息

**输出**：
- 更新后的CDP（包含`patientState`、`nextQuestion`、`completeness`）
- 如果信息完整度达到最低要求（如61.9%），继续执行后续步骤

#### 3.3.2 Step 2: 构建鉴别诊断候选集并分层

**功能**：
- 调用`diagnosis-engine-service`（脑区C）生成鉴别诊断候选集
- 调用`risk-assessment-service`（脑区F）进行风险评估
- 执行三层分层（首要假设/主要备选/必须排除）
- 更新CDP的`ddx`和`triage`字段

**处理逻辑**：
1. **生成鉴别诊断候选集**：
   - 调用`diagnosis-engine-service`的`/api/v1/engine/generate-ddx-candidates`接口
   - 传入`patientState`作为输入
   - 解析响应，获取诊断候选集列表
   - 容错处理：如果服务调用失败，使用空DDx列表继续流程
2. **风险评估**：
   - 调用`risk-assessment-service`的`/api/v1/risk/assess`接口
   - 传入`ddx`作为输入
   - 解析响应，获取风险评估结果
   - 更新`triage`字段
3. **三层分层**：
   - 由`diagnosis-engine-service`返回的DDx已包含三层分层信息
   - 更新`ddx`字段
4. **更新CDP状态**：
   - 状态更新为`clinical_mode_diagnosing`
   - 保存`ddx`、`triage`等信息

**输出**：
- 更新后的CDP（包含`ddx`、`triage`）

#### 3.3.3 Step 3: 组织候选集并建立分流路径

**功能**：
- 调用`diagnosis-engine-service`（脑区C）组织推理子组
- 调用`dialog-service`（脑区B）设计分流路径
- 生成结构化分流问题清单
- 更新CDP的`ddx`字段

**处理逻辑**：
1. **组织推理子组**：
   - 调用`diagnosis-engine-service`的`/api/v1/engine/organize-reasoning-groups`接口
   - 传入`ddx`作为输入
   - 解析响应，获取组织后的推理子组
   - 更新`ddx`字段
2. **设计分流路径**：
   - 调用`dialog-service`的`/api/v1/dialog/design-routing-path`接口
   - 传入`ddx`作为输入
   - 解析响应，生成分流问题清单
   - 容错处理：如果服务调用失败，不影响流程继续
3. **更新CDP**：
   - 保存更新后的`ddx`（包含推理子组信息）

**输出**：
- 更新后的CDP（包含组织后的`ddx`）

#### 3.3.4 Step 4: 采集关键证据并形成排序与验证计划

**功能**：
- 调用`dialog-service`（脑区B）采集关键证据
- 调用`diagnosis-engine-service`（脑区C）分析证据
- 调用`workup-planner-service`（脑区D）构建验证计划
- 更新CDP的`evidenceGraph`、`ddx`、`workupPlan`字段

**处理逻辑**：
1. **采集关键证据**：
   - 调用`dialog-service`的`/api/v1/dialog/collect-key-evidence`接口
   - 传入`ddx`作为输入
   - 解析响应，获取关键证据列表
   - 更新`evidenceGraph`字段
2. **分析证据**：
   - 调用`diagnosis-engine-service`的`/api/v1/engine/analyze-evidence`接口
   - 传入`evidenceGraph`、`ddx`作为输入
   - 解析响应，获取证据分析结果和更新后的三层排序
   - 更新`ddx`字段
   - 容错处理：如果服务调用失败，不影响流程继续
3. **构建验证计划**：
   - 调用`workup-planner-service`的`/api/v1/workup/build-verification-plan`接口
   - 传入`ddx`作为输入
   - 解析响应，获取检查建议计划
   - 更新`workupPlan`字段
   - 容错处理：如果服务调用失败，不影响流程继续
4. **更新CDP**：
   - 保存`evidenceGraph`、`ddx`、`workupPlan`

**输出**：
- 更新后的CDP（包含`evidenceGraph`、`ddx`、`workupPlan`）

#### 3.3.5 Step 5: 回填证据并输出终点结论包

**功能**：
- 调用`clinical-parsing-service`（脑区A）回填证据
- 调用`diagnosis-engine-service`（脑区C）更新三层排序
- 调用`treatment-engine-service`（脑区E）生成治疗方案
- 调用`risk-assessment-service`（脑区F）进行最终风险评估
- 调用`explanation-service`（脑区G）生成终点结论包
- 更新CDP的`patientState`、`ddx`、`managementPlan`、`triage`字段
- 更新CDP状态为`completed`

**处理逻辑**：
1. **回填证据**：
   - 调用`clinical-parsing-service`的`/api/v1/parsing/backfill-evidence`接口
   - 传入`evidenceGraph`作为输入
   - 解析响应，更新`patientState`
   - 容错处理：如果服务调用失败，不影响流程继续
2. **更新三层排序**：
   - 调用`diagnosis-engine-service`的`/api/v1/engine/update-ranking`接口
   - 传入`patientState`、`evidenceGraph`作为输入
   - 解析响应，获取最终的三层排序结果
   - 更新`ddx`字段
   - 容错处理：如果服务调用失败，不影响流程继续
3. **生成治疗方案**：
   - 调用`treatment-engine-service`的`/api/v1/treatment/generate-plan`接口
   - 传入`ddx`作为输入
   - 解析响应，获取治疗方案
   - 更新`managementPlan`字段
   - 容错处理：如果服务调用失败，不影响流程继续
4. **最终风险评估**：
   - 调用`risk-assessment-service`的`/api/v1/risk/assess-final`接口
   - 传入`ddx`、`managementPlan`作为输入
   - 解析响应，获取最终风险评估结果
   - 更新`triage`字段
   - 容错处理：如果服务调用失败，不影响流程继续
5. **生成终点结论包**：
   - 调用`explanation-service`的`/api/v1/explanation/generate-conclusion-package`接口
   - 传入`ddx`、`evidenceGraph`、`workupPlan`、`managementPlan`作为输入
   - 解析响应，生成终点结论包
   - 容错处理：如果服务调用失败，不影响流程继续
6. **更新CDP状态**：
   - 状态更新为`clinical_mode_managing`（中间状态）
   - 最终状态更新为`completed`

**输出**：
- 更新后的CDP（包含完整的诊断结果，状态为`completed`）

### 3.4 健康筛查流程（健康管理态）

#### 3.4.1 流程概览

健康筛查流程由`WellnessScreeningOrchestrator`编排，调用`health-state-assessment-service`的A1-A5接口：

1. **A1: 需求分类**：分类用户需求类型（筛查建议/健康目标管理/报告解读）
2. **A2: 收集健康画像**：收集用户的健康画像信息，计算完整度
3. **A3: 执行分支**：根据需求类型执行对应的分支
4. **A4: 生成统一结果**：整合分支执行结果，生成统一的结果和摘要
5. **A5: 设置随访**：根据统一结果设置随访计划

**详细实现**：参考`health-state-assessment-service`的架构文档。

### 3.5 继续诊断流程

#### 3.5.1 继续流程

**功能**：
- 接收用户回答（追问问题的回答）
- 更新CDP的`patientState.userAnswers`字段
- 根据当前步骤决定后续流程

**处理逻辑**：
1. **获取CDP**：根据`cdpId`获取当前CDP
2. **更新用户回答**：
   - 将用户回答保存到`patientState.userAnswers`字段
   - 更新CDP版本
3. **判断当前步骤**：
   - 如果当前在Step 1，且信息完整度达到最低要求，执行剩余步骤（Step 2-5）
   - 如果当前在Step 1，且信息完整度未达到最低要求，继续Step 1（生成新的追问问题）
   - 如果当前在其他步骤，根据步骤逻辑决定后续流程
4. **执行后续步骤**：
   - 调用`DiagnosisWorkflowOrchestrator.executeRemainingSteps()`执行Step 2-5

**输出**：
- 更新后的CDP
- 下一步操作（问题/等待/完成）

## 四、数据模型

### 4.1 CDP实体结构

**核心字段**：
- `id`：CDP ID（主键）
- `patientId`：患者ID
- `sessionId`：会话ID
- `version`：版本号（乐观锁）

**JSON字段**（存储在数据库中为JSON字符串）：
- `healthStateAssessment`：健康状态判定结果（Map）
- `wellnessPlan`：健康管理计划（Map，健康管理态时）
- `patientState`：患者状态（Map，包含症状、体征、检查、用户回答等）
- `ddx`：鉴别诊断列表（List，包含三层分层结果）
- `evidenceGraph`：证据图（List）
- `workupPlan`：检查计划（List）
- `managementPlan`：治疗计划（List）
- `triage`：风险评估（Map）
- `uncertainty`：不确定性信息（Map）
- `audit`：审计信息（Map）
- `executionTrace`：执行追踪信息（Map）

### 4.2 CDP版本控制

**版本管理机制**：
- **版本号**：每次更新自增（乐观锁）
- **版本记录**：每次更新创建新版本记录（`cdp_version`表）
- **写时复制**：更新前保存当前版本到版本表
- **版本查询**：支持查询任意历史版本
- **版本回退**：支持回退到指定版本
- **版本回放**：支持回放CDP演变过程

**版本表结构**：
- `id`：版本记录ID
- `cdpId`：CDP ID
- `version`：版本号
- `cdpData`：CDP完整数据（JSON）
- `createdAt`：创建时间

## 六、服务实现

### 6.1 主服务类

#### 6.1.1 DiagnosisOrchestrationService

**文件位置**：`com.aidoctor.diagnosis.service.DiagnosisOrchestrationService`

**核心方法**：
- `startDiagnosis(DiagnosisRequest request) -> DiagnosisResponse`：启动诊断流程
- `continueDiagnosis(UserAnswer answer) -> DiagnosisResponse`：继续诊断流程
- `getDiagnosisStatus(String cdpId) -> DiagnosisResponse`：获取诊断状态
- `getDiagnosisResult(String cdpId) -> DiagnosisResponse`：获取诊断结果

**处理流程**：
1. 启动诊断流程：
   - 创建CDP
   - 调用健康状态判定服务
   - 根据工作态决定后续流程
2. 继续诊断流程：
   - 更新用户回答
   - 判断当前步骤
   - 执行后续步骤

#### 6.1.2 DiagnosisWorkflowOrchestrator

**文件位置**：`com.aidoctor.diagnosis.service.orchestration.DiagnosisWorkflowOrchestrator`

**核心方法**：
- `executeDiagnosisWorkflow(CDP cdp) -> CDP`：执行完整的5步诊断流程
- `executeRemainingSteps(CDP cdp) -> CDP`：执行剩余步骤（Step 2-5）
- `step1IdentifyProblem(CDP cdp) -> CDP`：Step 1: 识别问题
- `step2BuildDDxCandidates(CDP cdp) -> CDP`：Step 2: 构建鉴别诊断候选集并分层
- `step3OrganizeRoutingPath(CDP cdp) -> CDP`：Step 3: 组织候选集并建立分流路径
- `step4CollectEvidenceAndPlan(CDP cdp) -> CDP`：Step 4: 采集关键证据并形成排序与验证计划
- `step5BackfillAndConclude(CDP cdp) -> CDP`：Step 5: 回填证据并输出终点结论包

**处理流程**：
- 按照5步AI循证诊断流程，协调各个脑区服务完成诊断任务
- 每个步骤调用相应的下游服务，更新CDP字段
- 容错处理：下游服务调用失败时，使用默认值或空值继续流程

#### 6.1.3 CDPManager

**文件位置**：`com.aidoctor.diagnosis.service.cdp.CDPManager`

**核心方法**：
- `createCDP(String patientId, String sessionId) -> CDP`：创建CDP
- `updateCDP(String cdpId, Map<String, Object> updates) -> CDP`：更新CDP（使用悲观锁）
- `getCDPById(String cdpId) -> Optional<CDP>`：根据ID获取CDP
- `getCDPsByPatientId(String patientId) -> List<CDP>`：根据患者ID获取CDP列表

**关键特性**：
- **悲观锁机制**：使用`SELECT FOR UPDATE`防止并发更新冲突
- **版本控制**：每次更新前保存当前版本，版本号自增
- **重试机制**：如果CDP刚创建，事务可能还没提交，需要重试（最多3次）

## 九、关键技术点

### 9.1 CDP并发更新控制

**技术难点**：多个服务可能同时更新CDP，需要保证数据一致性

**解决方案**：
- 使用悲观锁机制（`SELECT FOR UPDATE`）
- 更新失败时自动重试（最多3次）
- 使用版本号（乐观锁）作为辅助

**技术风险**：高并发场景下可能出现更新冲突

**应对措施**：
- 实现重试机制
- 监控更新冲突率
- 必要时使用分布式锁

### 9.2 服务间调用超时和熔断

**技术难点**：下游AI服务可能响应慢或不可用，需要保证系统稳定性

**解决方案**：
- 使用Feign配置超时时间（连接超时5s，读取超时30s）
- 实现容错处理（服务调用失败时使用默认值继续流程）
- 记录详细日志，便于问题排查

**技术风险**：下游服务故障可能导致诊断流程中断

**应对措施**：
- 实现服务降级
- 记录详细日志
- 监控服务健康状态

### 9.3 CDP状态流转管理

**技术难点**：CDP状态流转复杂，需要保证状态转换的正确性

**解决方案**：
- 定义明确的状态转换规则
- 状态转换时进行校验
- 记录状态转换日志

**状态流转规则**：
```
initial
  ↓
wellness_mode / clinical_mode_collecting
  ↓
clinical_mode_diagnosing
  ↓
clinical_mode_managing
  ↓
completed
  ↓
follow_up
```

### 9.4 执行追踪集成

**技术难点**：需要在多个服务调用点自动发送追踪事件

**解决方案**：
- 使用AOP切面（`ExecutionTraceAspect`）自动追踪
- 使用Feign拦截器（`FeignTraceInterceptor`）追踪Feign调用
- 通过`TraceContext`传递`cdpId`上下文
