# AI医生系统 - 架构与业务逻辑说明

## 一、系统架构总览

系统采用**四层架构**，实现从用户交互到数据存储的完整闭环：

```
┌─────────────────────────────────────────────────────────────┐
│                   第一层：用户交互层                           │
│  前端界面（React + TypeScript）                               │
│  - 用户输入、结果展示、实时对话                                  │
└─────────────────────────────────────────────────────────────┘
                            ↕ HTTP/WebSocket
┌─────────────────────────────────────────────────────────────┐
│                   第二层：业务流程层                            │
│                    协调器/编排器                               │
│  - CDP管理：创建、更新、版本控制、回退                             │
│  - 流程编排：健康筛查流程 + 临床诊疗流程                           │
│  - 服务协调：统一调度八大脑区服务                                 │
└─────────────────────────────────────────────────────────────┘
                            ↕ 统一调度
┌─────────────────────────────────────────────────────────────┐
│                   第三层：功能模块层（八大脑区）                  │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  通道1：结构化推理通道（决定"该往哪想"）              │   │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐          │   │
│  │  │ 脑区0     │  │ 脑区A    │  │ 脑区C     │          │   │
│  │  │健康状态    │  │病例理解   │  │诊断引擎    │          │   │
│  │  │判定       │  │结构化     │  │多引擎      │          │   │
│  │  └──────────┘  └──────────┘  └──────────┘          │   │
│  │  ┌──────────┐  ┌──────────┐  ┌──────────┐          │   │
│  │  │ 脑区D    │  │ 脑区E    │  │ 脑区F      │          │   │
│  │  │检查建议   │  │治疗推理   │  │风险评估    │          │   │
│  │  │计划生成   │  │方案推荐   │  │分诊评估    │          │   │
│  │  └──────────┘  └──────────┘  └──────────┘          │   │
│  └──────────────────────────────────────────────────────┘   │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  通道2：语言与策略通道（决定"怎么说、怎么问"）          │   │
│  │  ┌──────────┐              ┌──────────┐              │   │
│  │  │ 脑区B     │              │ 脑区G     │              │   │
│  │  │主动问诊   │              │解释生成    │              │   │
│  │  │智能追问   │              │证据链      │              │   │
│  │  └──────────┘              └──────────┘              │   │
│  └──────────────────────────────────────────────────────┘   │
│  注：脑区B、E、G同时具备两个通道的能力                      │
└─────────────────────────────────────────────────────────────┘
                            ↕ 数据读写
┌─────────────────────────────────────────────────────────────┐
│                   第四层：数据与知识层                          │
│  - CDP存储：临床决策包                │
│  - 关系数据库：Oracle/MySQL（业务数据）                         │
│  - 图数据库：Neo4j（知识图谱推理）                              │
│  - 缓存：Redis（会话、临时数据）                                │
└─────────────────────────────────────────────────────────────┘
```

### 1.1 核心设计理念

系统采用**双通道推理架构**作为核心设计理念：
- **通道1：结构化推理通道**（决定"该往哪想"）- 负责临床逻辑推理，生成结构化诊断结果
- **通道2：语言与策略通道**（决定"怎么说、怎么问"）- 负责自然语言表达，将结构化结果转换为用户可理解的语言

两个通道通过**CDP（临床决策包）**连接，实现推理过程可追溯、可审计。八大脑区按照功能划分为两个通道，在第三层功能模块层中协作完成诊断任务。

## 二、业务流程设计

### 2.1 系统入口：智能分流

系统入口采用**智能分流机制**，自动判断用户需求类型：

```
用户输入
    ↓
创建CDP - 临床决策包
    ↓
脑区0：健康状态判定
    ├─→ 入口判定流程（5步）
    ├─→ 工作态判定（wellness_mode / clinical_mode）
    └─→ 危险信号检查（红旗库）
    ↓
    ├─→ 路径A：健康管理态
    └─→ 路径B：临床诊疗态
```

### 2.2 双路径设计

系统根据用户需求自动分流到两个工作态，实现**一系统双模式**：

#### 路径A：健康管理态（健康筛查流程）

**适用场景**：健康体检、报告解读、健康目标管理、计划性健康需求

**流程设计**：5步闭环流程
```
A1: 需求分类
    ↓ 识别用户需求类型
A2: 通用最小健康档案收集
    ↓ 收集必要的基础信息
A3: 进入对应分支
    ├─→ A3-1: 筛查建议分支
    ├─→ A3-2: 体检报告解读分支
    ├─→ A3-3: 健康目标管理分支
    └─→ A3-4: 计划性健康需求分支
    ↓
A4: 统一结果页输出
    ↓ 生成个性化健康管理方案
A5: 随访闭环
    ↓ 设置随访计划，形成闭环
```

**主要服务**：脑区0

#### 路径B：临床诊疗态（5步AI循证诊断流程）

**适用场景**：症状诊断、疾病鉴别、治疗建议

**完整流程**：基于循证医学的5步诊断流程，体现双通道协作

```
Step 1: 识别问题
    【通道1】脑区A：病例理解
        └─→ 医学概念识别与归一化（CUI/ICD/SNOMED）
            └─→ 写入CDP：patient_state（结构化数据）
    【通道2】脑区B：主动问诊
        └─→ 读取CDP：patient_state
        └─→ 生成追问问题（自然语言）
            └─→ 写入CDP：patient_state.nextQuestion

Step 2: 构建鉴别诊断候选集并分层
    【通道1】脑区C：诊断引擎
        ├─→ 读取CDP：patient_state
        ├─→ 知识图谱推理引擎（DR.KNOWS方法）
        ├─→ 五引擎融合诊断（规则/知识图谱/统计/大模型/鉴别）
        └─→ 三层分层分类器（首要假设/主要备选/必须排除）
            └─→ 写入CDP：ddx（结构化诊断结果）
    【通道1】脑区F：风险评估
        ├─→ 读取CDP：ddx
        └─→ 写入CDP：triage（风险评估结果）

Step 3: 组织候选集并建立分流路径
    【通道1】脑区C：推理组织器
        ├─→ 读取CDP：ddx
        └─→ 组织推理子组
            └─→ 更新CDP：ddx.reasoningGroups
    【通道2】脑区B：分流路径设计
        ├─→ 读取CDP：ddx
        └─→ 生成结构化分流问题（自然语言）
            └─→ 写入CDP：patient_state.routingPath

Step 4: 采集关键证据并形成排序与验证计划
    【通道2】脑区B：主动问诊
        ├─→ 读取CDP：patient_state、ddx
        └─→ 生成针对性追问（自然语言）
    【通道1】脑区C：证据分析器
        ├─→ 读取CDP：ddx、patient_state
        └─→ 分析证据支持度
            └─→ 更新CDP：ddx.evidenceAnalysis
    【通道1】脑区D：检查建议
        ├─→ 读取CDP：ddx、triage
        └─→ 生成检查建议计划
            └─→ 写入CDP：workup_plan（结构化检查计划）
    【通道1】脑区F：风险评估
        └─→ 更新CDP：triage（风险等级调整）

Step 5: 回填证据并输出终点结论包
    【通道1】脑区C：证据回填
        └─→ 更新CDP：ddx（回填证据后的诊断结果）
    【通道1】脑区E：治疗推理
        ├─→ 读取CDP：ddx、triage
        └─→ 生成治疗方案
            └─→ 写入CDP：management_plan（结构化治疗计划）
    【通道2】脑区G：解释生成
        ├─→ 读取CDP：ddx、workup_plan、management_plan、triage
        ├─→ 构建证据链（通道1能力）
        └─→ 生成解释和终点结论包（通道2能力）
            └─→ 写入CDP：explanation（自然语言解释）
```

## 三、服务调用决策流程

协调器负责决定调用哪个服务以及何时调用。其决策逻辑如下：

```
用户请求
    ↓
协调器接收请求
    ↓
1. 创建CDP（临床决策包）
    ↓
2. 调用脑区0：健康状态判定服务
    ├─→ 输入：用户输入、基本信息、症状信息
    ├─→ 执行：入口判定流程（5步）
    │   ├─→ Step 1: 接收用户输入
    │   ├─→ Step 2: 识别是否有症状/困扰
    │   ├─→ Step 3: 方向澄清
    │   ├─→ Step 4: 危险信号检查（红旗库）
    │   └─→ Step 5: 路径输出
    └─→ 输出：工作态判定结果（健康 / 诊疗）
    ↓
3. 根据工作态判定结果进行分流
    ├─→ 如果 工作状态是健康
    │   └─→ 调用 健康筛查流程编排器
    │       └─→ 执行路径A：健康管理态流程（A1-A5）
    │
    └─→ 如果 工作状态是诊疗
        └─→ 调用 临床诊疗流程编排器
            └─→ 执行路径B：5步AI循证诊断流程（双通道协作）
                ├─→ Step 1: 识别问题
                │   ├─→ 【通道1】调用脑区A：病例理解服务（结构化提取）
                │   └─→ 【通道2】调用脑区B：主动问诊服务（生成追问）
                ├─→ Step 2: 构建鉴别诊断候选集
                │   ├─→ 【通道1】调用脑区C：诊断引擎服务（结构化推理）
                │   └─→ 【通道1】调用脑区F：风险评估服务（结构化评估）
                ├─→ Step 3: 组织候选集并建立分流路径
                │   ├─→ 【通道1】调用脑区C：推理组织器（结构化组织）
                │   └─→ 【通道2】调用脑区B：分流路径设计（生成分流问题）
                ├─→ Step 4: 采集关键证据并形成验证计划
                │   ├─→ 【通道2】调用脑区B：主动问诊（生成追问）
                │   ├─→ 【通道1】调用脑区C：证据分析器（结构化分析）
                │   ├─→ 【通道1】调用脑区D：检查建议服务（结构化计划）
                │   └─→ 【通道1】调用脑区F：风险评估服务（结构化评估）
                └─→ Step 5: 回填证据并输出终点结论包
                    ├─→ 【通道1】调用脑区C：证据回填（结构化回填）
                    ├─→ 【通道1】调用脑区E：治疗推理服务（结构化推理）
                    └─→ 【通道2】调用脑区G：解释生成服务（生成自然语言解释）
```

## 四、各脑区服务的职责、输入与输出

### 4.1 脑区0：健康状态判定服务

**服务名称**：`health-state-assessment-service`

**所属通道**：通道1（结构化推理通道）

**职责**：
1. 入口判定流程（5步）：识别用户意图、症状、方向、危险信号
2. 工作态判定：决定进入健康管理态还是临床诊疗态
3. 危险信号检查：识别需要紧急处理的危险信号（红旗库）
4. 健康管理计划生成：为健康管理态生成个性化方案

**输入**：
- `userId`：用户ID
- `cdpId`：CDP ID
- `userInput`：用户自然语言输入
- `symptoms`：症状列表（可选）
- `basicInfo`：基本信息（年龄、性别等，可选）
- `vitalSigns`：生命体征（可选）

**输出**（写入CDP的`health_state_assessment`字段）：
- `workMode`：工作态（`"wellness_mode"` / `"clinical_mode"`）
- `needsClinicalMode`：是否需要临床诊疗态（布尔值）
- `riskLevel`：风险等级（L1-L5）
- `assessmentReason`：判定理由
- `redFlags`：危险信号列表
- `entryAssessment`：入口判定流程结果（5步结果）
- `wellnessPlan`：健康管理计划（仅健康管理态）

### 4.2 脑区A：病例理解服务

**服务名称**：`clinical-parsing-service`

**所属通道**：通道1（结构化推理通道）

**职责**：
1. 医学概念识别：从自然语言中识别医学概念（症状、体征、疾病等）
2. 概念归一化：将识别到的概念转换为标准医学编码（CUI/ICD/SNOMED）
3. 结构化提取：将非结构化文本转换为结构化临床要素
4. 多模态理解：支持文本、图片、检查报告等多种输入

**输入**：
- `cdpId`：CDP ID
- `userId`：用户ID
- `sessionId`：会话ID
- `text`：用户输入文本
- `images`：图片列表（可选）
- `examinationReports`：检查报告（可选）

**输出**（写入CDP的`patient_state`字段）：
- `concepts`：识别到的医学概念列表
  - `text`：原始文本
  - `cui`：CUI编码
  - `type`：概念类型（symptom/sign/disease等）
- `structuredData`：结构化数据
  - `chiefComplaint`：主诉
  - `accompanyingSymptoms`：伴随症状
  - `signs`：体征
  - `problemList`：问题清单

### 4.3 脑区B：主动问诊服务

**服务名称**：`dialog-service`

**所属通道**：通道1 + 通道2（结构化推理通道 + 语言与策略通道）
- **通道1能力**：信息缺口识别、信息增益计算
- **通道2能力**：生成问诊问题、自然语言对话

**职责**：
1. 信息缺口识别：识别诊断所需但尚未收集的关键信息
2. 信息缺口分级：将信息缺口分为必填/重要/可选三级
3. 智能追问生成：基于信息缺口生成有针对性的追问问题
4. 自然语言理解：理解用户的自然语言回答
5. 分流路径设计：设计结构化分流问题（Step 3）

**输入**：
- `cdpId`：CDP ID
- `patientState`：患者状态（从CDP读取）
- `ddx`：鉴别诊断候选集（可选，用于生成针对性问题）

**输出**（写入CDP的`patient_state`字段）：
- `nextQuestion`：下一个追问问题（自然语言）
- `questionType`：问题类型（duration/severity/location等）
- `informationGaps`：信息缺口列表
  - `required`：必填信息缺口
  - `important`：重要信息缺口
  - `optional`：可选信息缺口
- `routingPath`：分流路径（Step 3使用）

### 4.4 脑区C：诊断引擎服务

**服务名称**：`diagnosis-engine-service`

**所属通道**：通道1（结构化推理通道）

**职责**：
1. 五引擎融合诊断：融合规则引擎、知识图谱、统计模型、大模型、鉴别诊断五个引擎的结果
2. 三层分层分类：将诊断候选集分为首要假设、主要备选、必须排除三层
3. 知识图谱推理：基于DR.KNOWS方法进行路径检索与推理
4. 推理组织：组织推理子组，建立分流路径（Step 3）
5. 证据分析：分析证据支持度，识别关键证据（Step 4）
6. 证据回填：回填证据并更新诊断结果（Step 5）

**输入**：
- `cdpId`：CDP ID
- `patientState`：患者状态（包含症状、体征等结构化信息）

**输出**（写入CDP的`ddx`字段）：
- `possibilities`：诊断可能性字典（疾病名 -> 概率）
- `threeLayerResult`：三层分层结果
  - `primaryHypothesis`：首要假设（最高可能性诊断）
  - `mainAlternatives`：主要备选（其他可能诊断）
  - `mustExclude`：必须排除（高危诊断，即使可能性低）
- `engineResults`：各引擎结果
  - `ruleEngine`：规则引擎结果
  - `knowledgeGraph`：知识图谱推理结果
  - `statistical`：统计模型结果
  - `llm`：大模型结果
  - `differential`：鉴别诊断结果
- `reasoningPaths`：推理路径列表（DR.KNOWS方法）
- `reasoningGroups`：推理子组（Step 3）
- `evidenceAnalysis`：证据分析结果（Step 4）

### 4.5 脑区D：检查建议服务

**服务名称**：`workup-planner-service`

**所属通道**：通道1（结构化推理通道）

**职责**：
1. 检查价值评估：评估各项检查的信息增益和价值
2. 检查计划生成：生成个性化的检查建议计划
3. 检查优先级排序：根据诊断候选集和风险等级排序检查优先级

**输入**：
- `cdpId`：CDP ID
- `ddx`：鉴别诊断候选集（从CDP读取）
- `triage`：风险评估结果（从CDP读取）

**输出**（写入CDP的`workup_plan`字段）：
- `workupPlan`：检查计划列表
  - `testName`：检查名称
  - `priority`：优先级（high/medium/low）
  - `informationGain`：信息增益（0-1）
  - `purpose`：检查目的（区分哪些诊断）
  - `urgency`：紧急程度

### 4.6 脑区E：治疗推理服务

**服务名称**：`treatment-engine-service`

**所属通道**：通道1 + 通道2（结构化推理通道 + 语言与策略通道）
- **通道1能力**：治疗方案推理、药物推荐
- **通道2能力**：生成治疗方案的自然语言表达

**职责**：
1. 治疗方案推理：基于诊断结果生成个性化治疗方案
2. 药物推荐：推荐合适的药物及用法用量
3. 治疗优先级排序：根据诊断优先级和风险等级排序治疗方案

**输入**：
- `cdpId`：CDP ID
- `ddx`：鉴别诊断候选集（从CDP读取）
- `triage`：风险评估结果（从CDP读取）

**输出**（写入CDP的`management_plan`字段）：
- `managementPlan`：治疗计划
  - `primaryTreatment`：主要治疗方案
  - `alternativeTreatments`：备选治疗方案
  - `medications`：药物推荐列表
    - `name`：药物名称
    - `dosage`：用法用量
    - `duration`：疗程
    - `indication`：适应症
  - `lifestyleRecommendations`：生活方式建议

### 4.7 脑区F：风险评估服务

**服务名称**：`risk-assessment-service`

**所属通道**：通道1（结构化推理通道）

**职责**：
1. 风险识别：识别诊断中的高风险情况
2. 紧急程度评估：评估患者的紧急程度和分诊级别
3. 风险等级调整：根据诊断结果调整风险等级

**输入**：
- `cdpId`：CDP ID
- `ddx`：鉴别诊断候选集（从CDP读取）
- `patientState`：患者状态（可选）

**输出**（写入CDP的`triage`字段）：
- `riskLevel`：风险等级（L1-L5，L1最紧急）
- `urgency`：紧急程度（emergency/urgent/routine）
- `triageLevel`：分诊级别
- `riskFactors`：风险因素列表
- `recommendations`：风险处理建议

### 4.8 脑区G：解释生成服务

**服务名称**：`explanation-service`

**所属通道**：通道1 + 通道2（结构化推理通道 + 语言与策略通道）
- **通道1能力**：证据链构建、推理路径分析
- **通道2能力**：生成解释和说明、推理路径可视化

**职责**：
1. 证据链构建：构建完整的诊断证据链
2. 解释生成：生成可解释的诊断说明
3. 推理路径可视化：可视化推理路径和决策过程
4. 终点结论包生成：生成完整的终点结论包

**输入**：
- `cdpId`：CDP ID
- `ddx`：鉴别诊断候选集（从CDP读取）
- `workupPlan`：检查建议（从CDP读取）
- `managementPlan`：治疗计划（从CDP读取）
- `triage`：风险评估（从CDP读取）

**输出**（写入CDP的`explanation`字段）：
- `evidenceChain`：证据链列表
  - `evidence`：证据内容
  - `type`：证据类型（support/oppose/uncertain）
  - `strength`：证据强度（strong/medium/weak）
  - `affectedDisease`：影响的疾病
- `reasoningPaths`：推理路径（可视化）
- `conclusionPackage`：终点结论包
  - `conclusion`：诊断结论
  - `mustExcludeStatus`：必须排除项状态
  - `keyEvidence`：关键依据
  - `actionAndFollowUp`：行动与随访建议

## 五、CDP（临床决策包）核心数据载体

**CDP（Clinical Decision Package，临床决策包）**是系统的核心数据结构，贯穿整个诊断流程，作为所有脑区服务之间数据共享和状态管理的统一载体。**CDP是双通道推理架构的桥梁**，连接结构化推理通道和语言与策略通道，实现两个通道之间的数据流转和协作。

### 5.1 CDP的核心作用

1. **数据载体**：所有脑区服务通过CDP共享数据，而不是直接传递数据
2. **状态管理**：CDP状态（`cdpStatus`）驱动整个诊断流程的执行
3. **版本控制**：每次更新创建新版本，支持流程回退和数据追溯
4. **可追溯性**：完整记录诊断过程中的所有决策和推理路径

### 5.2 CDP的数据结构

CDP包含以下核心字段，每个字段由对应的脑区服务负责写入：

| 字段名称                  | 说明                     | 负责脑区     | 数据类型   |
| ------------------------- | ------------------------ | ------------ | ---------- |
| `id`                      | CDP唯一标识              | 协调器创建   | String     |
| `patientId`               | 患者ID                   | 协调器创建   | String     |
| `sessionId`               | 会话ID                   | 协调器创建   | String     |
| `version`                 | 版本号                   | 协调器管理   | Integer    |
| `cdpStatus`               | CDP状态                  | 协调器管理   | String     |
| `health_state_assessment` | 健康状态判定结果         | 脑区0        | JSON       |
| `wellness_plan`           | 健康管理计划             | 脑区0        | JSON       |
| `patient_state`           | 患者状态（症状、体征等） | 脑区A、脑区B | JSON       |
| `ddx`                     | 鉴别诊断候选集           | 脑区C        | JSON Array |
| `workup_plan`             | 检查建议计划             | 脑区D        | JSON Array |
| `management_plan`         | 治疗计划                 | 脑区E        | JSON       |
| `triage`                  | 风险评估结果             | 脑区F        | JSON       |
| `explanation`             | 解释生成结果             | 脑区G        | JSON       |

### 5.3 CDP状态流转

CDP状态（`cdpStatus`）反映诊断流程的当前阶段：

```
initial（初始状态）
    ↓ 脑区0判定后
wellness_mode（健康管理态）
    OR
clinical_mode_collecting（临床诊疗态-信息收集中）
    ↓ Step 1完成后，信息完整
clinical_mode_diagnosing（临床诊疗态-诊断中）
    ↓ Step 2-4完成后
clinical_mode_managing（临床诊疗态-处置中）
    ↓ Step 5完成后
completed（已完成）
    OR
follow_up（随访状态）
```

### 5.4 CDP的数据流转机制

**核心原则**：所有脑区服务通过CDP共享数据

**数据流转示例**：
```
1. 协调器创建CDP（初始状态）
    ↓
2. 脑区0读取用户输入，写入 health_state_assessment
    ↓
3. 脑区A读取 health_state_assessment，写入 patient_state
    ↓
4. 脑区B读取 patient_state，更新 patient_state（添加追问问题）
    ↓
5. 脑区C读取 patient_state，写入 ddx
    ↓
6. 脑区F读取 ddx，写入 triage
    ↓
7. 脑区D读取 ddx 和 triage，写入 workup_plan
    ↓
8. 脑区E读取 ddx 和 triage，写入 management_plan
    ↓
9. 脑区G读取所有字段，写入 explanation（终点结论包）
```

**关键特性**：

- **读写分离**：脑区从CDP读取所需数据，将结果写入CDP对应字段
- **版本控制**：每次更新创建新版本，支持回退到任意历史版本
- **状态驱动**：根据CDP状态决定调用哪个脑区服务
- **可追溯性**：完整记录每个脑区的输入输出，支持审计和调试
- **双通道桥梁**：通道1（结构化推理）的输出写入CDP，通道2（语言与策略）基于CDP生成自然语言表达

## 六、双通道在架构中的体现

### 6.1 核心设计理念

系统采用**双通道推理架构**作为核心设计理念，将临床推理分为两个并行通道：
- **通道1：结构化推理通道**（决定"该往哪想"）- 负责临床逻辑推理，生成结构化诊断结果
- **通道2：语言与策略通道**（决定"怎么说、怎么问"）- 负责自然语言表达，将结构化结果转换为用户可理解的语言

两个通道通过**CDP（临床决策包）**连接：通道1的输出写入CDP，通道2基于CDP生成自然语言表达，确保推理过程可追溯、可审计。

### 6.2 第三层：八大脑区的通道划分

**通道1：结构化推理通道**（决定"该往哪想"）

- **脑区0**：健康状态判定（规则推理、风险评估）
- **脑区A**：病例理解（概念归一化、结构化提取）
- **脑区C**：鉴别诊断（知识图谱推理、多引擎融合）
- **脑区D**：检查建议（检查价值评估、信息增益计算）
- **脑区E**：治疗推理（治疗方案推理、药物推荐）
- **脑区F**：风险评估（风险识别、紧急程度评估）

**通道2：语言与策略通道**（决定"怎么说、怎么问"）

- **脑区B**：主动问诊（生成问诊问题、自然语言对话）
- **脑区G**：解释生成（生成解释和说明、推理路径可视化）

**跨通道脑区**（同时具备两个通道的能力）：

- **脑区B**：通道1（信息缺口识别）+ 通道2（自然语言问诊生成）
- **脑区E**：通道1（治疗方案推理）+ 通道2（治疗方案自然语言表达）
- **脑区G**：通道1（证据链构建）+ 通道2（解释生成和可视化）

### 6.3 双通道的协作流程

双通道通过**CDP（临床决策包）**实现协作，形成"推理-表达-再推理"的循环：

```
通道1：结构化推理
   脑区0、A、C、D、E、F执行结构化推理
   ↓ 生成结构化结果（DDx、检查建议、治疗计划等）
   ↓ 写入CDP（结构化数据）
   ↓
通道2：语言与策略
   脑区B、G读取CDP中的结构化数据
   ↓ 基于结构化数据生成自然语言表达
   ↓ 写入CDP（自然语言内容）
   ↓
输出给用户
   前端展示自然语言问诊、解释、建议
```

**关键原则**：

- **通道1决定内容**：生成诊断、检查、治疗等临床决策内容（结构化数据）
- **通道2决定表达**：将结构化内容转换为用户可理解的自然语言
- **CDP作为桥梁**：通道1的输出写入CDP，通道2基于CDP生成自然语言表达
- **可追溯性**：所有推理过程都记录在CDP中，支持审计和调试
