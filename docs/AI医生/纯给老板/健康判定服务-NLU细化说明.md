# AI医生系统 - 健康判定服务 - 自然语言理解细化方案

## 一、当前状态

健康判定服务是AI医生系统的**入口服务**，负责判断用户想要什么、有没有症状、有没有危险信号，并决定用户走哪条路径（健康管理路径或临床诊疗路径）。

**当前实现情况**：
- ✅ **整体框架已搭建完成**：入口判定流程的五个步骤（接收用户输入、识别症状、方向澄清、危险信号检查、路径选择）已经全部实现
- ✅ **基础功能可用**：系统能够处理用户输入，完成基本的需求判断和路径选择
- 🟡 **第一步需要细化**：第一步"接收用户输入"目前使用的是简化的关键词匹配方式，准确率和覆盖面有限，需要细化升级

**本次细化的目标**：
- 在第一步中，将当前的关键词匹配方式升级为基于LLM和知识库的自然语言理解系统
- 提升需求判断和实体提取的准确率
- 为后续步骤提供更准确、更完整的基础数据

---

## 二、第一步要做什么：自然语言理解、需求判断、实体提取

第一步"接收用户输入"需要完成三个动作，这三个动作各有不同的职责，互相配合完成对用户输入的理解。

### 2.1 三个动作的区别和关系

| 动作 | 职责 | 作用 | 例子 |
|------|------|------|------|
| **自然语言理解** | 理解用户说的完整意思，理解上下文和语义关系 | 这是基础能力，为需求判断和实体提取提供语义理解支持 | 用户说"我不疼"，系统要理解"不"是否定词，不能只看"疼"字 |
| **需求判断** | 判断用户想干什么（是想体检，还是看病，还是都有） | 确定用户的整体目标，为后续路径选择提供依据 | 用户说"我想了解一下我的健康状况"，系统要判断出这是体检需求 |
| **实体提取** | 从用户的话中提取具体的关键信息（症状、时间、程度等） | 提取结构化数据，为后续的症状判断、危险信号检查等提供数据 | 用户说"我胸口疼了3天了"，系统要提取出"胸痛"这个症状和"3天"这个时间 |

**三者的关系**：
- 自然语言理解是基础，提供语义理解能力
- 需求判断和实体提取都依赖自然语言理解的结果
- 需求判断关注"用户想干什么"（整体目标）
- 实体提取关注"用户说了什么具体信息"（具体数据）

### 2.2 自然语言理解（NLU）

| 项目 | 内容 |
|------|------|
| **要干什么** | 理解用户说的完整意思，不能只看关键词；理解上下文和语义关系，比如否定词、修饰词等；为需求判断和实体提取提供语义理解支持 |
| **例子** | 用户说："我最近胸口有点疼，想做个全面体检"<br>系统要理解这句话包含两个意思：有症状（胸口疼）和体检需求（想体检） |
| **当前的问题** | 现在系统用的是关键词匹配，比如看到"疼"就认为有症状，看到"体检"就认为要体检<br>但这样理解不准确，比如用户说"我不疼"，系统可能只看"疼"字，误判为有症状<br>或者用户说"心口不舒服"，系统可能识别不出来这是"胸痛"的同义词 |

### 2.3 需求判断

| 项目 | 内容 |
|------|------|
| **要干什么** | 判断用户到底想干什么（整体目标）<br>四种需求类型：<br>- **体检需求**：用户想体检、想检查身体、想做健康评估<br>- **看病需求**：用户有症状，想知道是什么病<br>- **混合需求**：用户既想体检，又有轻微不适<br>- **不确定**：无法判断用户需求 |
| **例子** | 用户说："我想了解一下我的健康状况" → 体检需求<br>用户说："我最近偶尔有点不舒服，想做个全面体检" → 混合需求 |
| **当前的问题** | 现在系统用关键词列表匹配，比如看到"体检"就认为是体检需求<br>但用户可能说"我想了解一下我的健康状况"，没有"体检"这个词，系统就判断不出来<br>或者用户说"最近偶尔有点不舒服，想做个全面体检"，这是混合需求，系统可能判断不准 |

### 2.4 实体提取

| 项目 | 内容 |
|------|------|
| **要干什么** | 从用户的话中提取具体的关键信息<br>提取的内容包括：<br>- **症状实体**：比如"胸痛"、"头痛"、"腹痛"<br>- **基本信息**：比如年龄、性别、体重<br>- **生命体征**：比如血压、心率<br>- **时间信息**：比如"疼了3天了"、"偶尔疼"<br>- **程度信息**：比如"轻微"、"很疼" |
| **例子** | 用户说："我胸口疼了3天了，有点轻微"<br>系统要提取出：症状="胸痛"，时间="3天"，程度="轻微" |
| **当前的问题** | 现在系统用正则表达式匹配，只能识别固定的表达方式<br>用户说"心口疼"，系统可能识别不出来，因为词表里只有"胸痛"<br>用户说"血压有点高"，系统可能提取不出来具体的血压数值<br>用户说"疼了快一周了"，系统可能提取不出来"一周"这个时间信息 |

## 三、为什么第一步要做这件事

### 3.1 这是整个流程的基础

第一步是入口判定流程的**起点**，如果这一步理解错了，后面的步骤都会错。

**举个例子**：
- 用户说："我最近偶尔有点不舒服，想做个全面体检"
- 如果第一步理解错了，认为用户只是想体检，没有症状
- 那么第二步会判断为"明确无症状"
- 第五步会选择路径A（健康筛查路径）
- 但实际上用户有轻微症状，应该走路径B（症状诊断路径）

### 3.2 影响后续所有判断

第一步的输出会传递给后续所有步骤：
- **第二步**：基于第一步提取的症状，判断用户有没有症状
- **第三步**：基于第一步的需求判断，决定是否需要澄清
- **第四步**：基于第一步提取的症状，检查危险信号
- **第五步**：基于前面的所有结果，选择路径

如果第一步提取的症状不准确，或者需求判断错误，后续所有判断都会受影响。

### 3.3 用户体验的关键

用户的第一句话如果系统理解错了，用户会觉得系统不智能，体验很差。

**举个例子**：
- 用户说："我心脏部位有点不舒服"
- 系统如果识别不出来这是"胸痛"，后续的危险信号检查就会漏掉
- 这可能导致系统没有识别出高危信号，给用户带来风险

## 四、要怎么做：实现逻辑

### 4.1 整体思路

不是简单地接一个LLM，而是构建一个**三层架构**，每层都有明确的职责和降级方案：

**第一层：需求判断层**
- **职责**：专门负责理解用户想干什么（体检、看病、还是都有）
- **实现方式**：使用LLM理解用户需求，但要有明确的输出格式（JSON格式）
- **降级方案**：如果LLM调用失败，可以降级到关键词匹配
- **输出**：需求类型（体检/看病/混合/不确定）、置信度、判断理由

**第二层：实体提取层**
- **职责**：专门负责从用户的话中提取关键信息（症状、时间、程度等）
- **实现方式**：
  - 使用LLM提取结构化信息（症状、时间、程度等）
  - 同时调用临床解析服务，利用已有的医学词表进行实体识别
  - 两种方法的结果互相补充和验证
- **输出**：结构化的实体列表，包含原始文本、标准术语、上下文信息等

**第三层：实体归一化层**
- **职责**：将提取的实体转换成标准医学术语，并链接到医学知识库
- **实现方式**：
  - 调用临床解析服务进行归一化
  - 使用同义词库处理新表达方式
  - 链接到医学知识库，获取标准编码
- **输出**：标准化的实体列表，每个实体都有标准术语和标准编码（UMLS编码、ICD编码等）

**数据流转过程**：
1. 用户输入 → 需求判断层 → 得到需求类型
2. 用户输入 + 需求类型 → 实体提取层 → 得到原始实体列表
3. 原始实体列表 → 实体归一化层 → 得到标准化实体列表
4. 需求类型 + 标准化实体列表 → 传递给后续步骤（第二步、第三步、第四步等）

### 4.2 需求判断的实现逻辑

**主流程（详细步骤）**：

1. **准备提示词**
   - 把用户输入和预设的问题模板组合成提示词
   - 提示词包含：任务说明、四种需求类型的定义、输出格式要求、示例

2. **调用LLM**
   - 发送提示词给LLM
   - 设置超时时间（比如30秒）
   - 如果超时或网络错误，进入降级流程

3. **解析LLM返回结果**
   - LLM返回结构化的结果（JSON格式），包含：
     - 需求类型：体检/看病/混合/不确定
     - 置信度：0-1之间的数值
     - 判断理由：为什么判断为这个类型
     - 关键词列表：识别到的关键词

4. **验证结果格式**
   - 检查JSON格式是否正确
   - 检查必需字段是否存在
   - 检查需求类型是否在允许的范围内
   - 检查置信度是否在0-1之间

5. **判断是否使用LLM结果**
   - 如果格式正确且置信度≥0.5，使用LLM的结果
   - 如果格式错误或置信度<0.5，进入降级流程

6. **降级到关键词匹配**
   - 使用预设的关键词列表匹配
   - 体检关键词：体检、筛查、检查、健康管理、预防等
   - 看病关键词：痛、疼、不适、难受、不舒服、异常等
   - 根据匹配结果判断需求类型

**提示词设计要点**：
- **任务说明**：明确告诉LLM要做什么（判断用户需求类型）
- **需求类型定义**：
  - 体检需求：用户想体检、想检查身体、想做健康评估，没有明确的症状描述
  - 看病需求：用户有明确的症状、不适或困扰，想知道可能的原因或诊断
  - 混合需求：用户既有体检需求，又有轻微症状描述
  - 不确定：无法明确判断用户需求
- **输出格式要求**：严格要求返回JSON格式，包含所有必需字段
- **示例**：给LLM提供2-3个示例，帮助它理解任务

**降级机制（详细说明）**：
- **触发条件**：
  - LLM调用失败（网络问题、超时、API错误等）
  - LLM返回格式错误（不是有效的JSON）
  - LLM返回的置信度很低（低于0.5）
- **降级流程**：
  - 自动切换到关键词匹配
  - 记录降级原因（用于后续分析和优化）
  - 返回降级结果，保证系统可用
- **保证**：无论LLM是否可用，系统都能返回需求判断结果

### 4.3 实体提取的实现逻辑

**主流程（详细步骤）**：

1. **并行调用两种方法**
   - **方法1：LLM提取**
     - 把用户输入和预设的提取模板组合成提示词
     - 调用LLM，让LLM提取结构化信息
     - LLM返回JSON格式的结果
   - **方法2：临床解析服务**
     - 同时调用临床解析服务API
     - 传入用户输入文本
     - 临床解析服务利用医学词表识别医学概念
     - 返回识别到的概念列表（包含标准术语、CUI编码等）

2. **解析LLM返回结果**
   - LLM返回的JSON包含：
     - 症状列表：每个症状包含原始文本、标准术语、位置、程度、持续时间、频率等
     - 基本信息：年龄、性别、BMI等（如果提及）
     - 生命体征：血压、心率、体温等（如果提及）
     - 时间信息：症状开始时间、持续时间、频率等
   - 验证JSON格式是否正确

3. **解析临床解析服务返回结果**
   - 临床解析服务返回的概念列表包含：
     - 标准术语：标准化的医学术语
     - CUI编码：UMLS概念唯一标识符
     - ICD编码：国际疾病分类编码（如果是疾病）
     - 置信度：识别置信度

4. **合并两种方法的结果**
   - **合并策略**：
     - 如果LLM提取的症状和临床解析服务识别的概念一致（通过标准术语或CUI编码匹配），合并为一个实体，保留两者的信息
     - 如果LLM提取的症状在临床解析服务中没有找到，也保留（可能是新表达方式，LLM能理解但词表中没有）
     - 如果临床解析服务识别的概念在LLM结果中没有，也保留（可能是LLM漏掉的，但词表中有）
   - **去重**：基于标准术语或CUI编码去重
   - **排序**：按置信度或重要性排序

5. **输出最终结果**
   - 返回完整的实体列表，每个实体包含：
     - 原始文本：用户在输入中使用的表达
     - 标准术语：标准化的医学术语
     - CUI编码：UMLS编码（如果有）
     - 上下文信息：时间、程度、位置等（从LLM提取）
     - 置信度：综合两种方法的置信度

**提示词设计要点**：
- **任务说明**：明确告诉LLM要提取哪些信息
- **提取内容定义**：
  - 症状实体：症状名称、位置、程度、持续时间、频率等
  - 基本信息：年龄、性别、体重、BMI等
  - 生命体征：血压、心率、体温等
  - 时间信息：症状开始时间、持续时间、频率等
- **输出格式要求**：严格要求返回JSON格式，每个字段都有明确定义
- **示例**：给LLM提供2-3个示例，展示如何提取和格式化信息

**结果合并逻辑（详细说明）**：
- **匹配规则**：
  - 优先使用标准术语匹配（如果LLM返回了标准术语）
  - 其次使用CUI编码匹配（如果临床解析服务返回了CUI编码）
  - 如果都没有，使用文本相似度匹配
- **信息合并**：
  - LLM提取的上下文信息（时间、程度等）优先保留
  - 临床解析服务提供的标准编码优先保留
  - 两者结合，得到最完整的实体信息
- **冲突处理**：
  - 如果两种方法的结果冲突，优先使用置信度高的
  - 如果置信度相同，优先使用临床解析服务的结果（因为它有标准编码）

### 4.4 实体归一化的实现逻辑

**主流程（详细步骤）**：

1. **遍历实体列表**
   - 对于实体提取层返回的每个实体，逐一进行归一化处理
   - 如果实体已经有标准术语和CUI编码（来自临床解析服务），跳过归一化

2. **调用临床解析服务**
   - 对于需要归一化的实体，调用临床解析服务的归一化接口
   - 传入实体的原始文本或标准术语
   - 临床解析服务会：
     - 在医学词表中查找匹配的标准术语
     - 返回标准术语和标准编码（UMLS编码、ICD编码、SNOMED编码等）
     - 返回匹配置信度

3. **处理归一化结果**
   - **如果找到匹配**：
     - 更新实体的标准术语和标准编码
     - 记录匹配置信度
   - **如果找不到匹配**：
     - 进入同义词扩展流程

4. **同义词扩展（如果临床解析服务找不到匹配）**
   - 在同义词库中查找实体的同义词
   - 同义词库维护常见表达方式的映射关系，比如：
     - "心口疼" → "胸痛"
     - "胸口痛" → "胸痛"
     - "胸闷" → "胸痛"
   - 如果找到同义词，用同义词再次调用临床解析服务查询标准编码
   - 如果还是找不到，保留原始文本，标记为"未归一化"

5. **输出最终结果**
   - 返回归一化后的实体列表
   - 每个实体都有：
     - 原始文本：用户在输入中使用的表达
     - 标准术语：标准化的医学术语（如果有）
     - 标准编码：UMLS编码、ICD编码等（如果有）
     - 归一化状态：已归一化/未归一化

**同义词库设计**：
- **维护方式**：维护一个同义词映射表，包含常见表达方式到标准术语的映射
- **更新机制**：定期更新，根据实际使用情况添加新的同义词
- **匹配策略**：
  - 精确匹配：完全匹配同义词库中的表达
  - 模糊匹配：使用文本相似度匹配（如果精确匹配失败）
- **优先级**：同义词库匹配的优先级低于临床解析服务，只在临床解析服务找不到时才使用

**错误处理**：
- **临床解析服务调用失败**：
  - 记录错误日志
  - 保留原始实体信息，标记为"归一化失败"
  - 不影响整体流程，继续处理其他实体
- **同义词库查找失败**：
  - 保留原始文本
  - 标记为"未归一化"
  - 记录日志，用于后续优化同义词库

## 五、为什么不直接接LLM：两种方式的对比

### 5.1 直接接LLM的方式

**实现方式**：
- 用户输入 → 直接调用LLM → LLM一次性返回需求和实体 → 解析结果 → 继续后续流程

**特点**：
- 简单直接，代码量少
- 依赖LLM，LLM失败整个流程就断
- 输出不稳定，需要大量解析和验证代码
- 无法利用现有资源（临床解析服务、医学词表等）

**存在的问题**：

1. **输出不稳定**
   - LLM的输出格式可能每次都不一样
   - 有时候返回JSON，有时候返回文本，有时候格式错误
   - 系统需要花很多精力去解析和验证LLM的输出

2. **无法利用现有资源**
   - 系统已经有临床解析服务，里面有完整的医学词表
   - 直接接LLM就浪费了这些资源
   - 而且临床解析服务的识别准确率可能比LLM更高（因为它有专门的医学词表）

3. **成本高**
   - 每次用户输入都要调用LLM，成本很高
   - 如果LLM调用失败，整个流程就断了
   - 没有降级方案，系统可靠性差

4. **难以优化**
   - 如果发现某个场景识别不准，很难针对性地优化
   - 只能调整提示词，但提示词调整的效果有限
   - 无法利用规则和知识库进行精确控制

### 5.2 我们的方式：分层架构

**实现方式**：
- 用户输入 → 需求判断层（LLM + 降级方案）→ 实体提取层（LLM + 临床解析服务）→ 实体归一化层（临床解析服务 + 同义词库）→ 继续后续流程

**特点**：
- 架构清晰，每层职责明确
- 有降级方案，LLM失败不影响系统可用
- 输出格式固定，解析简单可靠
- 充分利用现有资源，提高准确率
- 可以针对性地优化每个环节

**三层架构的优势**：

**第一层：需求判断层**
- 使用LLM理解用户需求，但输出格式固定（JSON）
- 有降级方案（关键词匹配），保证系统可用
- 可以针对性地优化提示词，提高准确率

**第二层：实体提取层**
- LLM提取灵活信息（时间、程度、上下文等）
- 临床解析服务提取标准医学概念（有标准编码）
- 两者结合，既灵活又准确

**第三层：实体归一化层**
- 利用临床解析服务的医学词表进行归一化
- 利用同义词库处理新表达方式
- 最终所有实体都有标准术语和标准编码

**这样做的优势**：
1. **准确率高**：LLM理解灵活表达，知识库保证标准术语
2. **成本可控**：可以缓存常见问题，减少LLM调用
3. **可靠性强**：有降级方案，LLM失败不影响系统可用
4. **可优化**：可以针对性地优化每个环节，提高整体效果

### 5.3 两种方式的具体对比

| 对比维度 | 直接接LLM | 我们的方式：分层架构 |
|---------|----------|---------------------|
| **需求判断** | LLM一次性返回需求和实体，格式可能不稳定 | 专门设计需求判断提示词，要求LLM返回固定格式的JSON，有降级方案 |
| **实体提取** | LLM提取所有信息，但可能不准确，没有标准编码 | LLM提取灵活信息，临床解析服务提取标准概念，两者合并 |
| **实体归一化** | LLM可能返回非标准术语，后续处理困难 | 利用临床解析服务的医学词表，所有实体都有标准术语和编码 |
| **可靠性** | LLM失败，整个流程就断 | 有降级方案，LLM失败可以切换到规则匹配 |
| **成本** | 每次都要调用LLM，成本高 | 可以缓存，可以降级，成本可控 |
| **可优化性** | 只能调整提示词，优化空间有限 | 可以优化提示词、规则、知识库，优化空间大 |
| **资源利用** | 无法利用现有资源（临床解析服务、医学词表等） | 充分利用现有资源，提高准确率 |
