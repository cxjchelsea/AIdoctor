> **文档定位**：本文档详细设计AI医生系统知识演化与维护的业务逻辑，包括知识查询业务逻辑、知识演化触发业务逻辑、知识演化流程等。这是理解知识演化业务逻辑的必读文档。

## 一、知识演化业务逻辑概述

### 1.1 业务逻辑定位

**知识演化业务逻辑定位**：
- **知识查询业务逻辑**：在线层知识查询服务的业务逻辑
- **知识演化触发业务逻辑**：知识演化提案的触发条件和处理流程
- **知识演化流程**：知识从抽取到发布的完整业务流程

### 1.2 核心原则

**核心原则**：
- **诊断决策单点负责**：主Agent仍是诊断与临床动作的唯一责任主体
- **知识演化多点自治**：知识演化Agent集群可以自动运行，最大化研究空间
- **发布单点门禁**：知识演化不能直接改生产知识，必须通过Publish Gate
- **可追溯性**：所有知识变更可追溯，支持审计和回滚

## 二、知识查询服务业务逻辑

### 2.1 知识库优先查询

**业务逻辑**：

1. **确定知识版本**：如果未指定kgVersion，使用当前生产版本
2. **查询知识库**：根据查询类型（主诉/疾病/关系）查询知识库
3. **返回结果**：返回知识对象列表、版本信息、来源信息

**流程**：

```
接收查询请求
  ↓
确定知识版本（默认当前生产版本）
  ↓
根据查询类型查询知识库
  ├─ 主诉知识图谱查询
  ├─ 疾病知识图谱查询
  └─ 关系查询
  ↓
返回知识对象列表
```

**关键点**：
- 默认使用当前生产版本
- 支持查询指定版本（用于审计和对比）
- 知识库优先原则：优先使用知识库中的权威医学内容

### 2.2 Neo4j路径检索验证

**业务逻辑**：

1. **路径检索**：根据症状CUI列表检索多跳推理路径（2-4跳）
2. **版本过滤**：根据kgVersion过滤路径
3. **路径验证**：验证知识库候选是否有路径支持

**流程**：

```
接收路径检索请求
  ↓
构建Cypher查询（包含版本过滤）
  ↓
执行Neo4j查询
  ↓
返回路径列表
  ↓
（可选）验证知识库候选
  ↓
返回验证结果
```

**关键点**：
- 路径检索用于验证知识库候选
- 路径约束推理：LLM在路径约束下推理，避免自由联想
- 路径用于补充知识库候选（如果路径指向知识库候选外的疾病）

### 2.3 版本化知识访问

**业务逻辑**：

1. **获取当前版本**：从ReleaseMetadata表获取当前生产版本
2. **版本过滤**：在查询中添加版本过滤条件
3. **版本切换支持**：支持查询指定版本的知识

**关键点**：
- 默认使用当前生产版本
- 支持查询历史版本（用于审计和对比）
- 版本切换通过修改current_release指针实现

## 三、知识演化触发业务逻辑

### 3.1 在线触发：主Agent触发知识演化提案

**触发场景**：
- tool_3鉴别诊断候选为空/很弱（知识覆盖缺口）
- 冲突复核反复失败（图谱路径无法验证、证据互斥）
- 反复"证据不足"仍无法满足停止条件中的"证据链完整"

**业务逻辑**：

1. **主Agent在Evaluate阶段检测触发条件**
2. **构建知识演化提案**：
   - 触发原因
   - 变更内容（diff）
   - 风险等级
   - 去重键（dedupe_key）
   - 证据快照
3. **去噪/节流处理**：应用去噪/节流机制，避免提案风暴
4. **异步提交提案**：向knowledge-ops-service提交提案（不阻塞当前会话）
5. **记录到CDP**：在CDP的knowledge_refs中记录知识缺口信息

**流程**：

```
主Agent运行循环（Evaluate阶段）
  ↓
检测知识演化触发条件
  ├─ 知识覆盖缺口？
  ├─ 冲突复核失败？
  └─ 证据不足？
  ↓
构建知识演化提案
  ├─ 生成dedupe_key
  ├─ 检查cooldown_window
  ├─ 检查节流限制
  └─ 生成evidence_snapshot
  ↓
去噪/节流处理
  ├─ 相同dedupe_key在cooldown_window内？
  │   ├─ 是：合并proposal（更新trigger_count）
  │   └─ 否：创建新proposal
  ├─ 超出节流限制？
  │   ├─ 是：标记为"节流"，记录日志
  │   └─ 否：继续处理
  ↓
异步提交到knowledge-ops-service
  ↓
不阻塞当前会话，继续诊断流程
```

### 3.2 去噪/节流机制

**问题**：真实运行中会出现"提案风暴"（同类缺口重复触发）

**解决方案**：

**1. dedupe_key（去重键）生成规则**：

- 按病种/概念/缺口类型聚合
- 格式：`{gap_type}_{disease_concept_id}_{symptom_concept_id}`
- 示例：
  - `knowledge_gap_ICD_I20_0_SYMP_001`：心绞痛的知识缺口
  - `conflict_resolution_failed_ICD_I21_0`：急性心肌梗死冲突解决失败
  - `evidence_insufficient_ICD_J18_0`：肺炎证据不足

**去重逻辑**：
- 相同`dedupe_key`的proposal在`cooldown_window`内只保留第一个
- 后续相同key的proposal会被合并或丢弃
- 合并时更新`trigger_count`（触发次数）和`latest_evidence_snapshot`

**2. cooldown_window（冷却时间窗口）配置规则**：

- 默认冷却时间：3600秒（1小时）
- 可根据gap_type调整：
  - 知识缺口：3600秒（1小时）
  - 冲突解决失败：7200秒（2小时）
  - 证据不足：1800秒（30分钟）

**冷却逻辑**：
- 在冷却窗口内，相同`dedupe_key`的proposal会被拒绝
- 冷却窗口外，允许新的proposal
- 冷却窗口可以动态调整（根据触发频率）

**3. evidence_snapshot（证据快照）**：

**快照内容**：
- 触发时的CDP状态（关键字段）
- 触发时的工具调用结果
- 触发时的知识查询结果
- 触发时的错误信息

**作用**：
- **便于复现**：可以复现触发场景，用于知识演化Agent分析
- **问题诊断**：可以分析为什么触发，是否误触发
- **审计追溯**：记录触发时的完整上下文

**4. 节流策略**：

**触发频率限制**：
- 单个`dedupe_key`：每小时最多触发1次
- 单个会话：每小时最多触发5次proposal
- 全局：每小时最多触发100个proposal

**超出限制处理**：
- 超出限制的proposal会被标记为"节流"
- 记录到日志，但不提交到knowledge-ops
- 可以人工查看被节流的proposal

**5. Proposal合并策略**：

**合并条件**：
- 相同`dedupe_key`
- 在`cooldown_window`内
- 触发原因相同或相似

**合并方式**：
- 保留第一个proposal
- 更新`trigger_count`（触发次数）
- 更新`latest_evidence_snapshot`（最新证据快照）
- 合并`diff`（如果有多个KO变更）

### 3.3 离线触发：周期性扫描

**触发场景**：
- 新指南/新共识发布
- 内部规则变更
- 线上监控发现某类case回归

**业务逻辑**：

1. **定时任务扫描知识源**
2. **检测更新**：对比新旧版本，识别变更
3. **自动生成提案**：根据变更内容生成知识演化提案
4. **提交到知识演化流程**

**流程**：

```
定时任务启动
  ↓
扫描知识源（指南/文献/规则）
  ↓
检测更新（版本对比）
  ↓
生成知识演化提案
  ↓
提交到knowledge-ops-service
```

## 四、知识演化Agent集群业务逻辑

### 4.1 Extractor Agent（抽取Agent）

**业务逻辑**：

1. **接收知识源**：指南/文献/内部规则文本
2. **构建提取Prompt**：根据KO schema构建提取指令
3. **调用LLM提取**：使用大模型提取结构化知识
4. **构建知识对象**：生成KO草稿，绑定provenance
5. **保存到Sandbox**：将KO保存到Sandbox区域

**流程**：

```
接收知识源
  ↓
构建提取Prompt
  ↓
调用LLM提取结构化知识
  ↓
构建知识对象（KO）
  ├─ ko_id生成
  ├─ 绑定provenance
  └─ 标记status=proposed
  ↓
保存到Sandbox
```

### 4.2 Verifier Agent（验证Agent）

**业务逻辑**：

1. **证据一致性验证**：检查KO是否被原文支持
2. **冲突检测**：检测与现有KO的冲突
3. **验证通过**：如果通过验证，移动到Staging
4. **验证失败**：标记问题，需要人工审核

**流程**：

```
从Sandbox读取KO
  ↓
证据一致性验证
  ├─ provenance完整性检查
  └─ 内容与证据匹配检查
  ↓
冲突检测
  ├─ 查询现有KO（Staging和Production）
  └─ 检查冲突
  ↓
验证通过？
  ├─ 是：移动到Staging（status=verified）
  └─ 否：标记问题，需要人工审核
```

### 4.3 Conflict Resolver Agent（冲突解决Agent）

**业务逻辑**：

1. **分析冲突类型和严重程度**
2. **选择解决策略**：
   - 覆盖：新知识覆盖旧知识（新指南证据等级更高）
   - 并存：多个版本并存（机构政策差异）
   - 分支：按不同场景分支（不同人群适用不同标准）
   - 降级：降级为"需人工审阅"（复杂冲突无法自动解决）
3. **执行解决策略**
4. **生成冲突解决记录**

**流程**：

```
检测到冲突
  ↓
分析冲突类型和严重程度
  ↓
选择解决策略
  ├─ 覆盖？
  ├─ 并存？
  ├─ 分支？
  └─ 降级？
  ↓
执行解决策略
  ↓
生成冲突解决记录
  ↓
更新KO状态
```

### 4.4 Release Builder Agent（打包发布候选Agent）

**业务逻辑**：

1. **收集通过验证的KO**
2. **生成diff**：与当前生产版本对比，生成变更diff
3. **生成测试计划**：根据diff确定需要测试的范围
4. **准备发布材料**：打包候选发布包
5. **创建candidate_release**：生成候选发布对象

**流程**：

```
收集通过验证的KO
  ↓
生成diff（与当前生产版本对比）
  ├─ 新增的KO
  ├─ 修改的KO
  └─ 删除的KO
  ↓
生成测试计划
  ├─ 核心回归集
  ├─ 受影响疾病的测试
  └─ 删除影响测试
  ↓
准备发布材料
  ↓
创建candidate_release
  ↓
保存到Staging
```

### 4.5 Shadow Evaluator Agent（影子评测Agent）

**业务逻辑**：

1. **加载测试用例集**：
   - 固定小集（Core Regression Set）：100个固定测试用例
   - 抽样大集（Sampling Set）：500个随机抽样病例
2. **运行评测**：在离线环境运行测试用例
3. **计算指标**：
   - 硬阈值：红旗召回率、关键路径断裂、总体性能下降、新增错误率
   - 软阈值：平均响应时间、证据完整性、路径可追溯性
4. **生成评测报告**：包含评测结果、指标对比、报告hash
5. **保存评测结果**：记录到EvaluationResultDatabase

**流程**：

```
接收candidate_release
  ↓
加载测试用例集
  ├─ 核心回归集（100个固定用例）
  └─ 抽样大集（500个随机抽样）
  ↓
获取基线版本
  ↓
运行评测
  ↓
计算指标
  ├─ 硬阈值检查
  └─ 软阈值检查
  ↓
生成评测报告
  ├─ 测试集结果
  ├─ 指标对比
  └─ 报告hash
  ↓
保存评测结果
```

**评测通过条件**：

1. **所有硬阈值必须满足**：
   - 红旗召回率 ≥ 基线
   - 关键路径断裂 = 0
   - 总体性能下降 ≤ 5%
   - 新增错误率 ≤ 2%

2. **至少80%的软阈值满足**：
   - 响应时间、证据完整性、路径可追溯性等

3. **评测报告必须完整**：
   - 报告hash已记录
   - 所有测试用例都有结果
   - 对比基线数据完整

### 4.6 Rollback & Drift Monitor Agent（回滚与漂移监控Agent）

**业务逻辑**：

1. **监控生产环境**：
   - DDx波动（新版本上线后是否出现DDx波动）
   - 风险评估异常（风险评估是否异常）
   - 特定人群退化（特定人群的诊断性能是否下降）
2. **检测异常**：识别生产环境中的异常情况
3. **评估回滚需求**：判断是否需要回滚
4. **触发回滚**：如果需要，触发回滚流程
5. **生成监控报告**：记录监控结果

**流程**：

```
监控生产环境
  ↓
收集生产环境指标
  ├─ DDx分布
  ├─ 风险评估结果
  └─ 特定人群诊断性能
  ↓
检测异常
  ├─ DDx波动？
  ├─ 风险评估异常？
  └─ 特定人群退化？
  ↓
评估回滚需求
  ├─ 需要回滚？
  │   ├─ 是：触发回滚流程
  │   └─ 否：继续监控
  ↓
生成监控报告
  ↓
保存监控记录
```

## 五、知识演化完整流程

### 5.1 知识演化流程总览

**完整流程**：

```
新知识源（指南/文献/规则）
  ↓
Extractor Agent（抽取）→ Sandbox
  ↓
Verifier Agent（验证）→ Staging
  ↓
Conflict Resolver Agent（冲突解决）→ Staging
  ↓
Release Builder Agent（打包）→ candidate_release
  ↓
Shadow Evaluator Agent（影子评测）→ 评测报告
  ↓
Publish Gate（门禁）→ Production
  ↓
Rollback & Drift Monitor Agent（监控）→ 持续监控
```

### 5.2 知识演化流程详细步骤

**步骤1：知识抽取（Sandbox）**
- Extractor Agent从知识源中抽取结构化知识
- 生成KO草稿，绑定provenance
- 保存到Sandbox区域

**步骤2：知识验证（Sandbox → Staging）**
- Verifier Agent验证知识的正确性和一致性
- 检测与现有KO的冲突
- 通过验证的KO移动到Staging

**步骤3：冲突解决（Staging）**
- Conflict Resolver Agent解决知识冲突
- 选择解决策略（覆盖/并存/分支/降级）
- 生成冲突解决记录

**步骤4：候选构建（Staging）**
- Release Builder Agent打包发布候选
- 生成diff（与当前生产版本对比）
- 生成测试计划
- 创建candidate_release

**步骤5：影子评测（Staging）**
- Shadow Evaluator Agent在离线环境进行评测
- 运行测试用例集（核心回归集 + 抽样大集）
- 计算指标（硬阈值 + 软阈值）
- 生成评测报告

**步骤6：发布门禁（Publish Gate）**
- Gate-1：结构合法性检查
- Gate-2：证据可追溯性检查
- Gate-3：回归评测与影子评测通过
- Gate-4：风险分级审批（可选人工）

**步骤7：发布到生产（Production）**
- 通过Publish Gate后，生成kg_version
- 发布到Production区域
- 更新current_release指针

**步骤8：监控与回滚（Production）**
- Rollback & Drift Monitor Agent监控生产环境
- 检测异常（DDx波动、风险评估异常、特定人群退化）
- 如果需要，触发回滚流程
