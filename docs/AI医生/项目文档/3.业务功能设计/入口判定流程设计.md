## 一、入口判定流程概述

### 1.1 流程定位

**入口判定流程定位**：
- **核心职责**：判断"这个人，现在需要被当成'病人'对待吗？"这是医生的第一职责，发生在"诊断之前"
- **流程目标**：通过五个步骤完成用户意图识别、症状识别、方向澄清、危险信号检查和路径输出
- **关键原则**：宁可误报，不能漏报

### 1.2 流程总览

**入口判定流程（P0模块）**：

```
Step 1: 接收用户输入
  ↓
Step 2: 识别用户是否"有症状/困扰"
  ↓
Step 3: 方向澄清（仅对"情况C"触发一次）
  ↓
Step 4: 危险信号检查（安全兜底，所有用户都要过一次）
  ↓
Step 5: 输出路径结果并跳转
```

**流程特点**：
- **无感判定**：尽量在用户无感知的情况下完成判定
- **安全第一**：危险信号检查是安全兜底，所有用户都要过一次
- **明确输出**：输出必须明确：进入 A / 进入 B / 退出线上流程

## 二、Step 1：接收用户输入

### 2.1 功能

接收用户自然语言描述本次来访目的。

### 2.2 输入

- 用户自然语言输入（文本/语音）

### 2.3 处理

**处理逻辑**：
- 支持自然语言理解（NLU）
- 允许混合诉求（既想体检又有轻微不适）
- 不依赖选择题入口

**业务逻辑**：

```java
/**
 * Step 1：接收用户输入
 */
public UserIntent step1ReceiveInput(String userInput) {
    // 1. 使用NLU引擎理解用户意图
    NLUResult nluResult = nluEngine.parse(userInput);
    
    // 2. 提取实体（症状、疾病、检查等）
    List<Entity> entities = nluResult.getEntities();
    
    // 3. 判断是否为混合诉求
    boolean isMixed = detectMixedRequest(nluResult);
    
    return UserIntent.builder()
        .text(userInput)
        .intent(nluResult.getIntent())
        .entities(entities)
        .isMixed(isMixed)
        .build();
}
```

### 2.4 输出

结构化的用户意图表达，包含：
- 原始文本
- 用户意图
- 提取的实体（症状、疾病、检查等）
- 是否为混合诉求

### 2.5 需求清单

**输入接收能力**：
- 支持用户用自然语言描述需求（不依赖选择题入口）
- 允许用户输入"混合诉求"（既想体检又有轻微不适）

## 三、Step 2：识别用户是否"有症状/困扰"

### 3.1 功能

系统对用户输入做一次判断，识别用户是否有症状/困扰。

### 3.2 判断结果

**情况 A：明确无症状**
- 用户表达的是"健康管理/体检规划/筛查/预防"
- 且没有任何不适描述
- **处理**：进入 Step 4（危险信号兜底）后，准备进入健康筛查路径（A）

**情况 B：存在症状/困扰**
- 用户描述任何身体不适、异常感觉、功能变化、心理困扰等（不论轻重）
- **处理**：进入 Step 4（危险信号兜底）后，准备进入症状诊断路径（B）

**情况 C：不确定/模糊/混合诉求**
- 用户说不清是否算不适
- 或同时说"想体检 + 有点不舒服"
- **处理**：进入 Step 3 做一次方向澄清

### 3.3 业务逻辑

**业务逻辑**：

```java
/**
 * Step 2：识别用户是否"有症状/困扰"
 */
public SymptomStatus step2IdentifySymptom(UserIntent userIntent) {
    // 1. 识别症状/困扰表达
    List<String> symptoms = symptomRecognizer.recognize(userIntent.getText());
    
    // 2. 识别健康管理/体检规划表达
    boolean hasWellnessIntent = hasWellnessKeywords(userIntent.getText());
    
    // 3. 判断情况
    String status;
    if (symptoms.isEmpty() && hasWellnessIntent) {
        // 情况A：明确无症状
        status = "no_symptom";
    } else if (!symptoms.isEmpty()) {
        // 情况B：存在症状/困扰
        status = "has_symptom";
    } else {
        // 情况C：不确定/模糊/混合诉求
        status = "uncertain";
    }
    
    return SymptomStatus.builder()
        .status(status)
        .symptoms(symptoms)
        .hasWellnessIntent(hasWellnessIntent)
        .isMixed(userIntent.isMixed())
        .build();
}
```

### 3.4 需求清单

**症状/困扰识别规则**：
- 能识别"症状/不适/困扰/异常感觉/功能变化"等表达
- 轻微问题也算"有困扰"，不要求严重程度
- 能识别"明确无症状"的表达（纯筛查/纯体检规划）

## 四、Step 3：方向澄清（仅对"情况C"触发一次）

### 4.1 功能

通过最小澄清确认用户当前的主要目标。

### 4.2 触发条件

仅当 Step 2 判断为"情况C"时触发。

### 4.3 澄清目标

确认用户主要目标是：
- **A**：健康筛查/体检规划
- **B**：症状咨询/问题排查

### 4.4 处理原则

- 澄清后不得反复追问，避免入口卡顿
- 澄清结果只能落到两类：进入 A 或进入 B

### 4.5 处理流程

- 生成最小澄清问题（仅一次）
- 根据用户回答确定方向（A 或 B）
- 澄清完成后，继续进入 Step 4

### 4.6 业务逻辑

**业务逻辑**：

```java
/**
 * Step 3：方向澄清（仅对"情况C"触发一次）
 */
public ClarificationResult step3Clarification(UserIntent userIntent) {
    // 1. 生成最小澄清问题
    String clarificationQuestion = clarificationEngine.generateQuestion(userIntent);
    
    // 2. 等待用户回答（在实际实现中，这里是异步的）
    String userResponse = waitForUserResponse(clarificationQuestion);
    
    // 3. 根据用户回答确定方向
    String direction = clarificationEngine.determineDirection(userResponse);
    // direction = "A"（健康筛查）或 "B"（症状诊断）
    
    return ClarificationResult.builder()
        .question(clarificationQuestion)
        .direction(direction)
        .clarified(userResponse != null)
        .build();
}
```

### 4.7 需求清单

**方向澄清机制（仅一次）**：
- 当用户表达模糊或混合诉求时，触发一次澄清
- 澄清结果只能落到两类：进入 A 或进入 B
- 澄清后不得反复追问，避免入口卡顿

## 五、Step 4：危险信号检查（安全兜底，所有用户都要过一次）

### 5.1 功能

无论用户走 A 还是 B，都必须判断是否存在危险信号。

### 5.2 检查逻辑

**如果命中危险信号**：
- 不进入线上流程
- 输出"优先线下就医/急诊"的安全提示（结束）

**如果未命中危险信号**：
- 进入 Step 5 输出选路结果

### 5.3 危险信号库

维护一份危险信号清单（红旗库），包含：
- 急危重症状组合
- 高危体征
- 紧急情况触发条件

### 5.4 检查原则

- 入口判定阶段只做"是否命中"，不做解释诊断
- 命中后输出固定的安全提示并结束线上流程

### 5.5 业务逻辑

**业务逻辑**：

```java
/**
 * Step 4：危险信号检查（安全兜底）
 */
public RedFlagsCheck step4RedFlagCheck(UserIntent userIntent, BasicInfo basicInfo) {
    // 1. 检测危险信号
    List<RedFlag> redFlags = redFlagDetector.detect(
        userIntent.getText(), 
        basicInfo
    );
    
    // 2. 判断是否命中危险信号
    boolean redFlagsHit = !redFlags.isEmpty();
    
    // 3. 生成安全提示消息
    String safetyMessage = null;
    if (redFlagsHit) {
        safetyMessage = generateSafetyMessage(redFlags);
    }
    
    return RedFlagsCheck.builder()
        .redFlagsHit(redFlagsHit)
        .redFlags(redFlags)
        .safetyMessage(safetyMessage)
        .shouldExit(redFlagsHit)
        .build();
}
```

### 5.6 需求清单

**危险信号检查机制**：
- 维护一份危险信号清单（红旗库）
- 入口判定阶段只做"是否命中"，不做解释诊断
- 命中后输出固定的安全提示并结束线上流程

## 六、Step 5：输出路径结果并跳转

### 6.1 功能

根据前面的判断结果，输出明确的路径选择并跳转。

### 6.2 输出规则

- **无症状 + 无危险信号** → 进入健康筛查路径（A）
- **有症状/困扰 + 无危险信号** → 进入症状诊断路径（B）
- **危险信号命中** → 退出线上流程（安全提示）

### 6.3 跳转规则

- 跳转到对应路径的第一个步骤
- **A路径**：进入健康筛查流程的起点（A1｜需求分类）
- **B路径**：进入症状诊断流程的起点（阶段1｜问诊，即Step 1：识别问题）

### 6.4 业务逻辑

**业务逻辑**：

```java
/**
 * Step 5：输出路径结果并跳转
 */
public PathResult step5PathSelection(
        SymptomStatus symptomStatus, 
        ClarificationResult clarificationResult, 
        RedFlagsCheck redFlagsCheck) {
    
    // 1. 如果命中危险信号，退出线上流程
    if (redFlagsCheck.isRedFlagsHit()) {
        return PathResult.builder()
            .path("exit")
            .pathName("退出线上流程")
            .reason("危险信号命中")
            .message(redFlagsCheck.getSafetyMessage())
            .build();
    }
    
    // 2. 确定路径
    String path;
    String nextStep;
    
    if ("no_symptom".equals(symptomStatus.getStatus())) {
        path = "A";  // 健康筛查路径
        nextStep = "A1｜需求分类";
    } else if ("has_symptom".equals(symptomStatus.getStatus())) {
        path = "B";  // 症状诊断路径
        nextStep = "阶段1｜问诊";
    } else if ("uncertain".equals(symptomStatus.getStatus())) {
        // 根据澄清结果确定路径
        if (clarificationResult != null) {
            path = clarificationResult.getDirection();
            nextStep = "A".equals(path) ? "A1｜需求分类" : "阶段1｜问诊";
        } else {
            // 默认进入症状诊断路径（宁可误报，不能漏报）
            path = "B";
            nextStep = "阶段1｜问诊";
        }
    } else {
        path = "B";
        nextStep = "阶段1｜问诊";
    }
    
    return PathResult.builder()
        .path(path)
        .pathName("A".equals(path) ? "健康筛查路径" : "症状诊断路径")
        .nextStep(nextStep)
        .build();
}
```

### 6.5 需求清单

**选路输出与跳转规则**：
- 输出必须明确：进入 A / 进入 B / 退出线上流程
- 跳转到对应路径的第一个步骤
- A：进入健康筛查流程的起点
- B：进入症状诊断流程的起点

## 七、路径切换支持（防止误入）

### 7.1 功能

允许用户在路径中切换，防止误入错误路径。

### 7.2 切换规则

**A路径 → B路径切换**：
- **触发条件**：若用户在 A 路径中后续出现症状描述
- **处理**：应允许切换到 B（症状诊断路径）

**B路径 → A路径切换**：
- **触发条件**：若用户在 B 路径中明确只是想筛查
- **处理**：应允许切换到 A（健康筛查路径）

### 7.3 需求清单

**路径切换支持（防止误入）**：
- 若用户在 A 路径中后续出现症状描述，应允许切换到 B
- 若用户在 B 路径中明确只是想筛查，应允许切换到 A

## 八、关键原则

### 8.1 核心原则

**宁可误报，不能漏报**：
- 不确定时优先进入临床诊疗态
- 避免漏诊高危情况

**及时升级**：
- 健康管理态中发现风险信号，立即升级到临床诊疗态
- 症状加重或出现新症状，立即升级到临床诊疗态

### 8.2 安全原则

**安全第一**：
- 危险信号检查是安全兜底，所有用户都要过一次
- 命中危险信号后，必须退出线上流程，建议立即就医

**无感判定**：
- 尽量在用户无感知的情况下完成判定
- 避免不必要的追问和澄清
