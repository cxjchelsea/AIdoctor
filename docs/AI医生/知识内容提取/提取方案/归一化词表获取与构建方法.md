## 一、归一化词表概述

### 1.1 什么是归一化词表

**归一化词表**（基础层第1项）用于将用户的各种表达方式映射到标准术语，支持：

1. **标准术语映射**：将同义词、别名、常用名映射到标准医学术语
   - 示例：`胸口闷`、`胸闷`、`胸憋气` → `胸闷样不适(C0232118)`

2. **用户口语化表达映射**：将用户的口语化表达映射到标准术语
   - 示例：`走几步就喘` → `活动后气促(C0030193)`
   - 示例：`血压高` → `高血压病(I10)`

3. **错别字映射**：将常见的错别字映射到标准术语
   - 示例：`胸疼`（错别字）→ `胸痛(C0232118)`

4. **编码映射**：将标准术语映射到医学编码（CUI、ICD、SNOMED等）
   - 示例：`胸闷样不适` → `C0232118`（CUI编码）

### 1.2 归一化词表的两种映射类型

| 映射类型 | 定义 | 来源 | 特点 |
|---------|------|------|------|
| **标准术语映射** | 医学标准术语库中已有的同义词、别名、常用名等映射关系 | UMLS、ICD-10、SNOMED CT等标准术语库 | 有权威来源、准确性高、主要覆盖医学术语之间的映射 |
| **用户口语化表达映射** | 用户在实际使用中产生的口语化表达与标准术语的映射关系 | 实际应用数据、AI生成 | 无权威来源、需要补充、覆盖用户日常表达 |

**示例对比**：
- **标准术语映射**：UMLS中 `Chest Pain` 的同义词包括 `Thoracic Pain`、`Chest Discomfort`
- **用户口语化表达映射**：用户说 `走几步就喘` → 标准术语：`活动后气促(C0030193)`

## 二、归一化方案

**最佳实践**：**词表映射（覆盖高频）+ NLP模型（处理长尾）**

**混合方案架构**：

```
用户输入："我最近胸口闷，走几步就喘"
    ↓
【第一层：词表映射（快速路径）】
    ├─ 查询归一化词表（倒排索引）
    ├─ "胸口闷" → 匹配成功 → "胸闷样不适(C0232118)" ✓
    ├─ "走几步就喘" → 匹配成功 → "活动后气促(C0030193)" ✓
    └─ 如果全部匹配成功 → 直接返回（快速、准确）
    
    如果有未匹配的表达 → 进入第二层
        ↓
【第二层：NLP模型推理（兜底路径）】
    ├─ 使用医疗BERT模型进行语义理解
    ├─ 识别未匹配的医学概念
    ├─ 映射到标准术语（基于语义相似度）
    └─ 返回标准术语（可能准确率略低，但能处理未覆盖的表达）
```

**混合方案的优势**：
1. **兼顾准确率和覆盖率**：词表覆盖高频表达（准确率高），NLP模型处理长尾表达（覆盖率高）
2. **兼顾效率和灵活性**：词表查找快速（O(log n)），NLP模型灵活处理新表达
3. **可迭代优化**：将NLP模型识别到的新表达补充到词表中，持续优化

**词表映射的定位**：
- **不是唯一方案**：不需要覆盖所有用户表达
- **是优化方案**：覆盖高频表达，提升准确率和效率
- **是基础方案**：为NLP模型提供训练数据和参考标准

**词表映射的目标**：
- **覆盖80%的高频表达**：根据帕累托原则，80%的用户会使用20%的高频表达
- **提供标准参考**：为NLP模型提供标准术语参考，提升模型准确性
- **持续优化**：将NLP模型识别到的新表达补充到词表中，形成良性循环

## 三、用户口语化表达映射的获取方法

### 两种生成方式：正向生成 vs 反向收集

**问题**：在生成用户口语映射的时候，是针对每一个标准用语去找对应的口语吗？

**答案**：**有两种方式，推荐混合使用**。

### 3.1 方式1：正向生成（标准术语 → 用户表达）

**定义**：针对每个标准术语，生成可能的用户口语表达。

**流程**：
```
标准术语列表
    ↓
针对每个标准术语
    ↓
生成可能的用户口语表达（AI生成或人工编写）
    ↓
映射关系：标准术语 → [用户表达1, 用户表达2, ...]
```

**优点**：
- **系统化**：可以覆盖所有标准术语，不遗漏
- **可控性强**：可以控制生成的数量和质量
- **适合AI生成**：AI可以针对标准术语生成对应的用户表达

**缺点**：
- **可能不贴近实际**：生成的表达可能不是用户真实使用的
- **可能遗漏真实表达**：用户实际使用的表达可能与生成的不同

**适用场景**：
- **初始词表构建**：在词表为空时，快速生成基础映射关系
- **补充低频标准术语**：为低频标准术语生成用户表达
- **AI批量生成**：使用AI批量生成候选映射关系

**示例**：
```
输入：标准术语：胸闷样不适(C0232118)

AI生成（正向生成）：
- 胸口闷
- 胸闷
- 胸憋气
- 胸部不适
- 胸口不舒服
- 胸憋
- 胸闷感
- 胸部闷胀
```

### 3.2 方式2：反向收集（用户表达 → 标准术语）

**定义**：从实际应用数据中收集用户表达，然后映射到标准术语。

**流程**：
```
实际应用数据（电子病历、在线问诊等）
    ↓
提取用户表达
    ↓
映射到标准术语（NLP模型或人工标注）
    ↓
映射关系：用户表达 → 标准术语
```

**优点**：
- **贴近实际**：收集的是用户真实使用的表达
- **覆盖高频表达**：优先覆盖高频表达，符合帕累托原则
- **质量高**：来自真实数据，质量可靠

**缺点**：
- **可能遗漏低频标准术语**：低频标准术语可能没有对应的用户表达数据
- **需要大量数据**：需要收集大量实际应用数据
- **映射成本高**：需要将用户表达映射到标准术语（NLP模型或人工标注）

**适用场景**：
- **高频表达收集**：收集高频用户表达，建立基础词表
- **持续优化**：从实际应用中持续收集新表达
- **质量保证**：作为正向生成的验证和补充

**示例**：
```
实际数据：电子病历主诉："胸口闷，走几步就喘"

反向收集：
- "胸口闷" → 映射到 → "胸闷样不适(C0232118)"
- "走几步就喘" → 映射到 → "活动后气促(C0030193)"
```

### 3.3 推荐方案：混合方式

**最佳实践**：**正向生成（初始构建）+ 反向收集（持续优化）**

**阶段1：初始构建（正向生成）**
- 针对每个标准术语，使用AI生成可能的用户口语表达
- 快速建立基础词表，覆盖所有标准术语
- 作为初始映射关系

**阶段2：持续优化（反向收集）**
- 从实际应用数据中收集用户表达
- 将收集到的用户表达映射到标准术语
- 补充和优化词表，优先覆盖高频表达

**阶段3：迭代优化（混合）**
- 将反向收集到的新表达补充到词表中
- 对于反向收集中发现的新标准术语，使用正向生成补充用户表达
- 形成良性循环

**数据存储结构**：

归一化词表的数据结构（CSV格式）：
```
standard_term,synonym,alias,common_name,cui
胸闷样不适,胸口闷,胸闷,胸憋气,C0232118
活动后气促,走几步就喘,活动后气喘,运动后气短,C0030193
```

**重要说明**：
- **统一存储**：无论正向生成还是反向收集，都存储在同一个CSV表中
  - 正向生成：`标准术语 → [用户表达1, 用户表达2, ...]` → 存储到CSV的同一行
  - 反向收集：`用户表达 → 标准术语` → 也存储到CSV的同一行（如果标准术语已存在，追加到同义词字段；如果不存在，新建一行）
- **一行一个标准术语**：每个标准术语占一行，该行的所有同义词字段（synonym、alias、common_name等）存储该标准术语的所有表达方式
- **索引构建时机**：索引在**服务启动时（加载阶段）**构建，不是查询时构建
  - 服务启动时：读取CSV文件 → 构建正向索引和倒排索引 → 加载到内存
  - 查询阶段：直接使用内存中的索引进行快速查找（O(1)时间复杂度）

## 四、归一化词表的存储方式

### 4.1 存储格式

**主要格式**：**CSV文件**（逗号分隔值）

**选择CSV格式的原因**：
1. **简单易编辑**：可以使用Excel、文本编辑器等工具直接编辑
2. **版本控制友好**：Git等版本控制系统可以很好地跟踪CSV文件的变更
3. **批量导入导出**：便于批量管理和数据迁移
4. **跨平台兼容**：所有操作系统和编程语言都支持CSV格式
5. **轻量级**：文件体积小，加载速度快

**辅助格式**：**JSON文件**（用于特殊规则）

- 用于存储复杂的规则配置（如歧义规则）
- 示例：`ambiguity_rules.json`（歧义表达判定规则）

### 4.2 存储位置和文件组织

**存储位置**：
```
clinical-parsing-service/
  └── data/
      └── vocabularies/          # 归一化词表目录
          ├── symptom_normalization.csv        # 症状归一化词表
          ├── disease_normalization.csv        # 疾病归一化词表
          ├── medication_normalization.csv     # 药物归一化词表
          ├── allergy_normalization.csv        # 过敏源归一化词表
          ├── examination_normalization.csv    # 检查项目归一化词表
          ├── indicator_normalization.csv      # 指标归一化词表
          └── ambiguity_rules.json             # 歧义规则（JSON格式）
```

**文件命名规范**：
- 格式：`{类型}_normalization.csv`
- 类型包括：`symptom`（症状）、`disease`（疾病）、`medication`（药物）、`allergy`（过敏源）、`examination`（检查）、`indicator`（指标）

### 4.3 CSV文件结构

**标准字段定义**：

| 字段名 | 数据类型 | 是否必填 | 说明 | 示例 |
|--------|---------|---------|------|------|
| standard_term | String | 是 | 标准术语（唯一） | 胸闷样不适 |
| synonym | String | 否 | 同义词（多个用逗号分隔） | 胸口闷,胸闷 |
| alias | String | 否 | 别名（多个用逗号分隔） | 胸憋气,胸闷感 |
| common_name | String | 否 | 常用名（多个用逗号分隔） | 憋气,气闷 |
| variant | String | 否 | 变体表达（多个用逗号分隔） | 胸憋,胸部不适 |
| cui | String | 否 | UMLS CUI编码 | C0232118 |
| icd | String | 否 | ICD-10编码 | R06.0 |
| snomed | String | 否 | SNOMED CT编码 | 29857009 |
| loinc | String | 否 | LOINC编码 | 12345-6 |
| atc | String | 否 | ATC编码（药物） | B01AC06 |

**实际CSV文件示例**：

```csv
standard_term,synonym,alias,common_name,cui
胸闷样不适,胸口闷,胸闷,胸憋,C0232118
活动后气促,走几步就喘,活动后气喘,运动后气短,C0030193
胸痛,胸部疼痛,胸口疼,胸痛不适,C0232118
```

**字段说明**：
- **standard_term**：标准医学术语，作为主键
- **synonym/alias/common_name/variant**：支持多种类型的同义词表达
  - 多个同义词用逗号分隔：`"胸口闷,胸闷,胸憋气"`
  - 空值表示该类型无同义词
- **编码字段**：根据词表类型选择相应的编码字段
  - 症状：主要使用 `cui`（UMLS编码）
  - 疾病：主要使用 `icd`（ICD-10编码）
  - 药物：主要使用 `atc`（ATC编码）
  - 检查：主要使用 `loinc`（LOINC编码）

### 4.4 内存索引结构

**加载策略**：**启动时全量加载到内存**

**数据结构设计**：

1. **正向索引**（标准术语 → 详细信息）：
   ```python
   vocabularies = {
       'symptom': {
           '胸闷样不适': {
               'cui': 'C0232118',
               'icd': 'R06.0',
               'synonyms': ['胸口闷', '胸闷', '胸憋气', ...]
           },
           ...
       }
   }
   ```

2. **倒排索引**（同义词 → 标准术语集合）：
   ```python
   indexes = {
       'symptom': {
           '胸口闷': {'胸闷样不适'},
           '胸闷': {'胸闷样不适'},
           '胸憋气': {'胸闷样不适'},
           ...
       }
   }
   ```

**索引构建流程**：
```
【服务启动时（加载阶段）】
CSV文件读取
    ↓
逐行解析
    ↓
提取标准术语和所有同义词
    ↓
构建正向索引：standard_term → {cui, icd, synonyms, ...}
    ↓
构建倒排索引：synonym → {standard_term1, standard_term2, ...}
    ↓
加载到内存（字典结构）
    ↓
【查询阶段】
用户输入 → 直接使用内存中的索引进行查找（O(1)时间复杂度）
```

**重要说明**：
- **索引构建时机**：在**服务启动时（加载阶段）**一次性构建，不是查询时构建
- **索引用途**：用于**查询阶段**快速查找，提升查询性能
- **存储与索引的关系**：
  - **存储**：CSV文件存储原始数据（正向生成和反向收集的结果都存这里）
  - **索引**：内存中的数据结构（启动时从CSV构建，用于查询）

**完整流程总结**：
```
【数据构建阶段】
正向生成：标准术语 → 用户表达 → 写入CSV
反向收集：用户表达 → 标准术语 → 写入CSV（追加到已有行或新建行）
    ↓
【服务启动阶段（加载）】
读取CSV文件 → 构建正向索引和倒排索引 → 加载到内存
    ↓
【查询阶段（运行时）】
用户输入"胸口闷" → 查询内存中的倒排索引 → 快速返回标准术语
```

**索引优势**：
- **查询速度快**：O(1) 时间复杂度（字典查找）
- **支持多对一映射**：一个同义词可以映射到多个标准术语（处理歧义）
- **大小写不敏感**：统一转换为小写进行索引

### 4.5 查询性能优化

**查询流程**：

```
用户输入："胸口闷"
    ↓
1. 转换为小写："胸口闷"
    ↓
2. 查询倒排索引：indexes['symptom']['胸口闷']
    ↓
3. 获取标准术语集合：{'胸闷样不适'}
    ↓
4. 从正向索引获取详细信息：vocabularies['symptom']['胸闷样不适']
    ↓
5. 返回结果：{
       'standard_term': '胸闷样不适',
       'cui': 'C0232118',
       'synonyms': [...]
   }
```

**性能指标**：
- **查询速度**：O(1) 平均时间复杂度（字典查找）
- **内存占用**：约 10-50MB（取决于词表大小）
- **加载时间**：< 1秒（启动时一次性加载）

**优化策略**：
1. **预加载**：服务启动时一次性加载所有词表到内存
2. **倒排索引**：构建同义词到标准术语的快速映射
3. **大小写归一化**：统一转换为小写，避免重复索引
4. **内存缓存**：词表常驻内存，无需重复读取文件

### 4.6 数据更新机制

**更新方式**：

1. **文件更新**：
   - 直接编辑CSV文件（使用Excel、文本编辑器等）
   - 支持批量导入（从其他数据源导入）
   - 版本控制（使用Git跟踪变更）

2. **热更新**（可选）：
   - 提供API接口重新加载词表
   - 支持增量更新（只更新变更的部分）
   - 更新时保持服务可用（零停机）

3. **版本管理**：
   - 在CSV文件中添加版本号字段（可选）
   - 使用Git进行版本控制
   - 记录每次更新的变更日志

**更新流程**：

```
1. 编辑CSV文件
    ↓
2. 提交到版本控制系统（Git）
    ↓
3. 部署到生产环境
    ↓
4. 服务重启或热更新
    ↓
5. 重新加载词表到内存
    ↓
6. 验证更新结果
```

**注意事项**：
- **备份**：更新前备份原始文件
- **验证**：更新后验证数据格式和完整性
- **测试**：在测试环境验证后再部署到生产环境
- **回滚**：保留旧版本，支持快速回滚

### 4.7 与代码实现的对应关系

**代码实现位置**：
- **词表加载器**：`clinical-parsing-service/app/utils/vocabulary_loader.py`
- **词表数据目录**：`clinical-parsing-service/data/vocabularies/`

**核心类和方法**：

```python
class VocabularyLoader:
    def __init__(self, base_path: str = "data/vocabularies")
        # 初始化词表加载器，指定词表文件目录
    
    def load_vocabulary(self, vocab_type: str) -> bool
        # 加载指定类型的归一化词表
        # 构建正向索引和倒排索引
    
    def load_all_vocabularies(self) -> bool
        # 加载所有类型的归一化词表
    
    def find_match(self, text: str, vocab_type: str) -> Optional[Dict]
        # 查找匹配的标准术语
        # 支持精确匹配和模糊匹配
```

**使用示例**：

```python
# 初始化加载器
loader = VocabularyLoader(base_path="data/vocabularies")

# 加载所有词表
loader.load_all_vocabularies()

# 查询匹配
result = loader.find_match("胸口闷", vocab_type="symptom")
# 返回: {
```

## 五、混合方案实现建议（词表映射 + NLP模型）

### 5.1 混合方案架构

**推荐架构**：

```
用户输入："我最近胸口闷，走几步就喘"
    ↓
【第一层：词表映射（快速路径）】
    ├─ 查询归一化词表（倒排索引）
    ├─ "胸口闷" → 匹配成功 → "胸闷样不适(C0232118)" ✓
    ├─ "走几步就喘" → 匹配成功 → "活动后气促(C0030193)" ✓
    └─ 如果全部匹配成功 → 直接返回（快速、准确）
    
    如果有未匹配的表达 → 进入第二层
        ↓
【第二层：NLP模型推理（兜底路径）】
    ├─ 使用医疗BERT模型进行语义理解
    ├─ 识别未匹配的医学概念
    ├─ 映射到标准术语（基于语义相似度）
    └─ 返回标准术语（可能准确率略低，但能处理未覆盖的表达）
```

### 5.2 词表映射的实现

**实现方式**：
1. **倒排索引**：构建 `用户表达 → 标准术语` 的倒排索引，提升查找效率
2. **模糊匹配**：支持编辑距离、相似度计算，处理轻微变体
3. **优先级排序**：精确匹配 > 模糊匹配，高频表达优先

**性能指标**：
- **查找速度**：O(log n)，n为词表大小
- **准确率**：接近100%（经过医学专家审核）
- **覆盖率**：目标覆盖80%的高频表达

### 5.3 NLP模型的实现

**模型选择**：
1. **医疗BERT模型**：如医疗BERT、BioBERT、中文医疗BERT等
2. **命名实体识别（NER）**：识别医学概念（症状、疾病、药物等）
3. **语义相似度计算**：将识别的概念映射到标准术语

**实现方式**：
1. **模型训练**：
   - 使用归一化词表作为训练数据
   - 训练模型识别医学概念并映射到标准术语
2. **推理流程**：
   - 输入：用户原始文本
   - 输出：识别的医学概念 + 标准术语映射 + 置信度
3. **置信度阈值**：
   - 高置信度（>0.9）：直接使用
   - 中置信度（0.7-0.9）：需要人工审核
   - 低置信度（<0.7）：拒绝或要求用户澄清

**性能指标**：
- **准确率**：85-95%（取决于模型质量）
- **覆盖率**：接近100%（能处理未覆盖的表达）
- **推理速度**：较慢（需要GPU加速）

### 5.4 决策流程

**决策流程**：

```
1. 首先尝试词表映射
   ├─ 如果匹配成功 → 直接返回（快速、准确）
   └─ 如果匹配失败 → 进入步骤2

2. 使用NLP模型推理
   ├─ 如果置信度 > 0.9 → 直接返回
   ├─ 如果置信度 0.7-0.9 → 返回结果 + 标记需要审核
   └─ 如果置信度 < 0.7 → 要求用户澄清或拒绝

3. 持续优化
   ├─ 将NLP模型识别到的新表达补充到词表中
   ├─ 将高置信度的映射关系加入词表
   └─ 持续提升词表覆盖率和模型准确性
```

### 5.5 词表映射的优化策略

**优化目标**：用最小的词表覆盖最大的用户表达

**策略**：
1. **高频优先**：优先收集高频表达，覆盖80%的用户
2. **模式提取**：提取表达模式，而非枚举所有表达
   - 示例：`XX痛` → `XX疼痛`（模式：`痛` → `疼痛`）
3. **语义聚类**：将语义相似的表达聚类，减少词表大小
4. **动态更新**：将NLP模型识别到的新表达补充到词表中

**示例**：
```
词表映射（优化前）：
- "胸口闷" → "胸闷样不适"
- "胸部闷" → "胸闷样不适"
- "胸憋气" → "胸闷样不适"
- "胸闷感" → "胸闷样不适"
- ...（需要枚举所有表达）

词表映射（优化后）：
- 模式："胸" + "闷" → "胸闷样不适"
- 模式："胸" + "憋" → "胸闷样不适"
- 模式："胸" + "不适" → "胸闷样不适"
- ...（提取模式，减少词表大小）
```

## 六、归一化词表的构建流程

### 6.1 数据收集阶段

**步骤1：从标准术语库提取**
- 下载UMLS、ICD-10、SNOMED CT等标准术语库
- 提取标准术语、CUI编码、ICD编码、SNOMED编码
- 提取同义词、别名、常用名等映射关系（标准术语之间的映射）

**步骤2：从中文医学词表提取**
- 下载中文医学主题词表、中国医学术语标准
- 提取中文标准术语和同义词
- 建立中文表达与标准术语的映射

**步骤3：从实际应用数据提取（反向收集）**
- 收集电子病历数据、在线问诊平台数据、医学文献数据
- 提取实际表达和常用同义词
- 建立口语化表达与标准术语的映射（用户口语化表达映射）

**步骤4：AI生成补充（正向生成，可选）**
- 使用大语言模型生成用户口语化表达与标准术语的映射关系
- 针对每个标准术语，生成可能的用户口语表达
- 作为医学专家审核的候选映射关系

### 6.2 数据清洗阶段

**步骤1：去重处理**
- 去除重复的映射关系
- 合并相同的标准术语

**步骤2：标准化处理**
- 统一术语格式（大小写、空格、标点等）
- 统一编码格式（CUI、ICD、SNOMED等）

**步骤3：质量检查**
- 检查映射关系的准确性
- 检查编码的正确性
- 检查同义词的完整性

### 6.3 数据组织阶段

**步骤1：按类别组织**
- 症状归一化词表
- 疾病归一化词表
- 检查归一化词表
- 指标归一化词表
- 药物归一化词表
- 体征归一化词表

**步骤2：按格式组织**
- 标准术语（standard_term）
- 同义词（synonym_1, synonym_2, ...）
- 别名（alias_1, alias_2, ...）
- 常用名（common_name_1, common_name_2, ...）
- 用户表达（user_expression_1, user_expression_2, ...）
- 编码（cui, icd, snomed, loinc, rxnorm等）

### 6.4 数据验证阶段

**步骤1：医学专家审核**
- 邀请医学专家审核映射关系的准确性
- 特别关注用户口语化表达映射的准确性
- 补充遗漏的同义词和别名
- 修正错误的映射关系

**步骤2：实际应用测试**
- 在实际应用中测试归一化词表的效果
- 收集用户反馈，优化映射关系
- 持续更新和完善词表
