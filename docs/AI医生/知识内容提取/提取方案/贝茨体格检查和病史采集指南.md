你可以把这件事做成一条**可重复运行的“PDF → 主诉候选集 → 主诉最小字段（CC-MDK）”流水线**。核心思路是：**先用目录/标题把书切成结构化章节 → 只抽取“Health History”相关段落 → 在这些段落里自动发现“主诉候选词” → 再用 LLM 按固定规则产出每个主诉的最小字段**，最后加一层质检与回归测试

## 0）你最终要产出的“标准数据结构”

建议你把结果固化成两张表/两个 JSON：

### A. 主诉词表（CC Catalog）

- `cc_id`
- `cc_name_zh` / `cc_name_en`（可选）
- `system`（呼吸/心血管/腹部…）
- `source_chapter`（如 Ch8）
- `source_span`（原文定位：页码+段落hash/offset）
- `evidence_text`（可选，保存原文片段用于审计）

### B. 主诉最小诊断核（CC-MDK）

- `cc_id`
- `required_fields[]`（必填字段列表）
- `optional_fields[]`
- `why_required`（每个字段1句话说明：用于分流/危险识别/进入鉴别）
- `next_step_gate`（进入下一步诊断的“门槛规则”描述，如“能区分急性/慢性、能做危险信号初筛”）
- `confidence`（LLM给的自信度）
- `review_status`（待审/已审/驳回）

## 1）流水线总览（自动化分 6 步）

### Step 1：PDF 解析为“带页码的文本块”

- 目标：得到 `page_no + text` 的结构化输出，保留页码用于溯源。
- 注意：医学书的标题常见大写、换行、缩进；**不要只做纯拼接**，要保留换行。

### Step 2：构建“文档结构树”（Unit/Chapter/Section）

两条路（建议都做，互相校验）：

1. **基于目录页**（Contents）解析出层级树（Unit → Chapter → Section）
2. **基于正文标题模式**做二次定位（例如 `CHAPTER 8`、`THE HEALTH HISTORY` 等）

产物：`doc_outline.json`，每个节点包含：

- `title`
- `level`
- `start_page` / `end_page`（或 start_offset/end_offset）

> 《Bates》的目录里明确出现了 Unit 2 各章并且多章含 “THE HEALTH HISTORY / TECHNIQUES / RECORDING YOUR FINDINGS”等稳定节名，非常适合规则匹配切分。

### Step 3：只抽取“主诉信息密集区”的文本

你要的不是全书，优先抽这些 Section：

- Unit 1：Interviewing / Health History（用于“字段定义与访谈维度”）
- Unit 2：每章的 **THE HEALTH HISTORY**（用于“主诉候选集合 + 追问维度”）
- （可选）Unit 3：特殊人群的 Health History（用于“人群覆盖差异”）

产物：`health_history_corpus/`（按系统分文件或按章节分块）

### Step 4：自动发现“主诉候选词/短语”（CC candidates）

做法建议“两段式”：

1. **规则/统计初筛**：
   - 从 “Health History” 文本中提取高频名词短语（中文可用分词，英文可用名词短语提取）
   - 过滤：器官名、检查名、泛化词（“pain” 单独保留，但像 “the patient” 过滤）
2. **LLM 精筛**：
   - 让模型把候选短语分类为：`可作为主诉 / 伴随症状 / 体征 / 风险因素 / 其他`
   - 输出“可作为主诉”的规范名（合并同义词：dyspnea=呼吸困难=气促）

产物：`cc_catalog_draft.json`

### Step 5：对每个主诉生成“最小字段（CC-MDK）”

核心是固定一个**很严格的提示词与判定准则**：

**判定准则（写进 prompt）**

> “最小字段”必须满足：
>
> 1. 仅凭这些字段就能进入下一步诊断（至少能做急危重分流/初步鉴别方向）
> 2. 去掉任意一个“必填字段”都会导致下一步决策显著不确定
> 3. 不把 HPI 全量维度都塞进去（字段数建议 3–6）

**输出格式强约束**：JSON Schema（强烈建议）

产物：`cc_mdk_draft.json`

### Step 6：自动质检 + 抽样人工审核（必须做）

自动质检规则示例：

- 必填字段数量 < 2 或 > 7 → 标红
- 必填字段包含“具体检查/化验” → 标红（主诉阶段不该依赖）
- `why_required` 为空 → 标红
- 同一主诉在不同章节生成结果冲突 → 标红

人工审核策略：

- 先审高风险主诉（胸痛、呼吸困难、意识障碍等）
- 每个系统抽样 20% 审核
- 审核反馈回写为“训练/提示词修订依据”

## 2）你需要的 3 个关键 Prompt 模板（可直接落地）

### 模板 A：从 Health History 段落提取主诉候选

输入：某章节 “THE HEALTH HISTORY” 文本块
输出：候选列表 + 分类 + 证据句

要求模型输出：

- `cc_candidates[]`（主诉候选）
- `excluded[]`（为何不是主诉：体征/风险因素/检查）
- 每个候选附 `evidence_quote`（<=25词）

### 模板 B：为单个主诉生成 CC-MDK（最小字段）

输入：`cc_name` + 相关证据文本（同章节或跨章节聚合）
输出：严格 JSON：

- `required_fields[]`
- `optional_fields[]`
- `why_required{field: reason}`
- `gate_to_next_step`（一句话）

### 模板 C：一致性对齐（跨章节合并）

输入：同一主诉从不同系统/章节得到的多个 MDK
输出：最终合并版 + 差异说明 + 选择理由

## 3）工程实现建议（让它“自动跑起来”）

### 运行形态

- 做成一个 CLI 或流水线（Airflow/Dagster 也行）
- 每次输入：`pdf_path + config.yaml`
- 输出：`cc_catalog.json + cc_mdk.json + qa_report.html`

### 配置文件（config.yaml）建议包含

- `section_whitelist`: ["THE HEALTH HISTORY", "Interviewing", ...]
- `chapter_scope`: [4..17]（先做 Unit2）
- `language`: "en"（本书为英文目录/正文为主，中文翻译后置）
- `llm_models`: {extract: xxx, mdk: xxx, judge: xxx}
- `synonym_map`: 同义词表（dyspnea/shortness of breath 等）

### 版本化与回归测试（非常重要）

- 每次跑完保存：
  - prompt 版本号
  - 模型版本号
  - 输入文本哈希
- 建一个小型“黄金集”（golden set）：
  - 20 个主诉、每个主诉一份你认可的 MDK
- 新提示词/新模型上线前跑回归：差异超过阈值就拦截

> 你之前提到想用 deepseek API 做回答评估，这里正好可以用作 **judge 模型**：对 MDK 的“字段是否过多/过少、是否能分流”做二次评分。

## 4）中文翻译放在哪一步做最稳

不要一开始就翻译全文（成本高、引入噪声）。推荐：

- CC 候选和字段先用英文（原书语义稳定）
- 最后对：
  - `cc_name`
  - `field_name`
  - `why_required`
    做“受控翻译”（固定术语表 + 同义词映射）

这样能保证一致性，避免“呼吸困难/气促/气短”乱飞。
