# AI医生系统 - 知识内容与映射关系说明

> **文档定位**：清晰说明19项知识内容中哪些是**分立的知识实体**，哪些是**映射关系**，以及这些知识如何通过映射相互联系。同时说明知识图谱的工程层和语义层设计。

---

## 一、什么是分立知识？什么是映射关系？

**分立知识** = **实体** = **节点**
- 就像字典里的词条，每个都是独立的医学概念
- 例如："胸痛"、"心绞痛"、"心电图"、"硝酸甘油"
- 它们是**静态的**，代表"是什么"

**映射关系** = **连接** = **边/规则**
- 就像词条之间的关联，说明它们如何相互联系
- 例如："胸痛" → "心绞痛"（症状提示疾病）、"心口疼" → "胸痛"（口语映射标准词）
- 它们是**动态的**，代表"如何关联"

## 三、分立知识详解（5项）

### 3.1 什么是分立知识？

**分立知识**是独立的医学概念实体，就像字典里的词条，每个都是完整的、独立的概念。

**存储位置**：根据使用场景，可以存储在：
- **知识图谱节点**：需要建立复杂关系的实体（如症状、疾病）
- **表格文件**：大量同类型数据，便于批量管理（如标准目录的源数据）

### 3.2 分立知识清单

| 编号 | 内容名称 | 包含的实体类型 | 存储位置 | 示例 |
|------|---------|--------------|---------|------|
| **0** | 医学概念本体与编码规范 | 编码属性 | 表格+知识图谱节点属性 | ICD-10编码、SNOMED CT编码 |
| **3** | 标准目录主数据 | 症状、主诉、疾病、检查、治疗等 | 表格（源数据）→ 知识图谱节点 | "胸痛"、"心绞痛"、"心电图" |
| **5** | 主诉模板（实体部分） | 主诉节点 | 知识图谱节点 | "胸痛"主诉节点 |
| **6** | 疾病模板（实体部分） | 疾病节点 | 知识图谱节点 | "心绞痛"疾病节点 |
| **7** | 证据条目模板（实体部分） | 证据节点 | 知识图谱节点 | "胸痛伴大汗"证据节点 |

**实体示例**：
- `Symptom`（症状）："胸痛"、"气短"、"发热"
- `ChiefComplaint`（主诉）："胸痛"、"呼吸困难"
- `Disease`（疾病）："心绞痛"、"急性心肌梗死"
- `Examination`（检查）："心电图"、"胸部X光"
- `Treatment`（治疗）："硝酸甘油"、"阿司匹林"
- `Evidence`（证据）："胸痛伴大汗"、"心电图ST段抬高"

## 四、映射关系详解（15项）

### 4.1 什么是映射关系？

**映射关系**是连接不同知识实体的关系，说明它们如何相互关联。就像地图上的路线，告诉你从A到B怎么走。

**存储位置**：根据关系类型，可以存储在：
- **知识图谱关系**：实体之间的直接关系（如"胸痛" → "心绞痛"）
- **配置文件**：流程控制和规则（如"症状组合[胸痛+气短] → 主诉候选"）
- **表格文件**：简单的映射表（如"心口疼" → "胸痛"）

### 4.2 映射关系分类

#### 4.2.1 归一化映射（1项）- 输入标准化

| 编号 | 内容名称 | 映射类型 | 存储位置 | 示例 |
|------|---------|---------|---------|------|
| **1** | 归一化词表 | 口语→标准词 | 表格文件 | "心口疼" → "胸痛"<br>"心梗" → "急性心肌梗死" |

**作用**：将用户输入的口语表达转换为标准医学概念

**存储形式**：7个表格文件（症状、主诉、疾病、检查、指标、药物、体征各一个）

#### 4.2.2 核心映射关系（4项）- 诊断核心

这些映射关系存储在**知识图谱**中，是诊断流程的核心：

| 编号 | 内容名称 | 映射关系 | 关系类型 | 存储位置 | 示例 |
|------|---------|---------|---------|---------|------|
| **5** | 主诉模板（映射部分） | 主诉↔症状 | `CONTAINS` | 知识图谱关系 | 主诉"胸痛"包含症状"胸痛" |
| **5** | 主诉模板（映射部分） | 主诉→疾病 | `HAS_CANDIDATE_DISEASE` | 知识图谱关系 | 主诉"胸痛"关联疾病"心绞痛" |
| **6** | 疾病模板（映射部分） | 症状→疾病 | `HAS_CANDIDATE_DISEASE` | 知识图谱关系 | 症状"胸痛"提示疾病"心绞痛" |
| **7** | 证据条目模板（映射部分） | 证据→疾病 | `SUPPORTS`/`OPPOSES` | 知识图谱关系 | 证据"胸痛伴大汗"支持疾病"急性心肌梗死" |

**作用**：建立主诉、症状、疾病、证据之间的医学关系

#### 4.2.3 扩展映射关系（11类）- 诊断支持

这些映射关系也存储在**知识图谱**中，属于疾病模板（6）的映射部分：

| 映射关系 | 关系类型 | 说明 | 示例 |
|---------|---------|------|------|
| 疾病→检查 | `REQUIRES_EXAMINATION` | 疾病需要哪些检查 | "心绞痛"需要"心电图" |
| 疾病→治疗 | `REQUIRES_TREATMENT` | 疾病需要哪些治疗 | "心绞痛"需要"硝酸甘油" |
| 疾病↔疾病 | `DIFFERENTIAL_WITH` | 需要鉴别的疾病对 | "心绞痛"与"急性心肌梗死"需要鉴别 |
| 主诉→推理子组 | `HAS_REASONING_SUBGROUP` | 主诉关联的推理子组 | - |
| 主诉→鉴别诊断框架 | `HAS_DIFFERENTIAL_SUBCLASS` | 主诉关联的鉴别诊断框架 | - |
| 主诉→关键差异点 | `HAS_DIFFERENTIAL_POINT` | 主诉的关键差异点 | - |
| 主诉→检查建议 | `RECOMMENDS_EXAMINATION` | 主诉建议的检查 | - |
| 疾病→支持证据 | `SUPPORTED_BY` | 疾病的支持证据 | - |
| 疾病→反对证据 | `OPPOSED_BY` | 疾病的反对证据 | - |
| 疾病→必需证据 | `REQUIRES` | 疾病的必需证据 | - |
| 疾病→鉴别点 | `HAS_DIFFERENTIAL_POINT` | 疾病的鉴别点 | - |

**作用**：扩展诊断支持信息，如检查建议、治疗建议、鉴别诊断等

#### 4.2.4 规则映射关系（11项）- 流程控制

这些映射关系存储在**配置文件**中，是流程控制和规则定义：

| 编号 | 内容名称 | 映射关系 | 存储位置 | 说明 |
|------|---------|---------|---------|------|
| **8** | 症状到主诉映射规则 | 症状组合→主诉候选 | 配置文件 | 如果出现[胸痛+气短]，则触发主诉候选[心血管疾病] |
| **9** | 主诉候选生成与排序规则 | 主诉→疾病候选 | 配置文件 | 如何从主诉生成和排序疾病候选 |
| **10** | 回填与重排规则 | 证据→候选调整 | 配置文件 | 新证据出现后如何重新排序疾病候选 |
| **11** | 收效与升级规则 | 条件→动作 | 配置文件 | 什么时候停止诊断，什么时候升级 |
| **12** | 风险与急症识别规则 | 症状组合→风险等级 | 配置文件 | 如何识别高危情况 |
| **13** | 输出规则 | 风险等级→处置建议 | 配置文件 | 风险等级如何给出处置建议 |
| **14-18** | 其他规则 | 各种流程规则 | 配置文件 | 健康管理、风险评估等规则 |

**作用**：控制诊断流程，如症状组合如何触发主诉、如何排序疾病候选等

**关键区别**：
- **知识图谱中的映射**：实体之间的**直接关系**，如"胸痛" → "心绞痛"（这是医学事实）
- **配置文件中的映射**：**规则和流程**，如"如果出现[胸痛+气短]，则触发主诉候选"（这是业务规则）

#### 4.2.5 来源引用映射（跨所有项）- 合规追溯

| 映射关系 | 关系类型 | 存储位置 | 说明 |
|---------|---------|---------|------|
| **任何节点→来源** | `SOURCED_FROM` | 知识图谱关系 | 任何知识实体都可以引用来源，用于合规追溯 |

**作用**：追溯所有知识的来源，满足医疗合规要求

**说明**：这是**工程层**的核心映射关系，用于追溯所有知识的来源（详见第六章）

## 五、知识如何通过映射相互联系

### 5.1 完整的连接链路

以一个完整的诊断流程为例，说明知识如何通过映射连接：

```
用户输入："心口疼，还有点喘不上气"
    ↓
【步骤1：归一化映射】
    口语"心口疼" → 标准症状"胸痛"（映射1：归一化词表）
    口语"喘不上气" → 标准症状"气短"（映射1：归一化词表）
    ↓
【步骤2：规则映射】
    症状组合[胸痛+气短] → 主诉候选[心血管疾病]（映射8：症状到主诉映射规则）
    ↓
【步骤3：核心映射】
    主诉"心血管疾病" -[CONTAINS]-> 症状"胸痛"、"气短"（映射5：主诉模板）
    主诉"心血管疾病" -[HAS_CANDIDATE_DISEASE]-> 疾病"心绞痛"（映射5：主诉模板）
    症状"胸痛" -[HAS_CANDIDATE_DISEASE]-> 疾病"心绞痛"（映射6：疾病模板）
    ↓
【步骤4：扩展映射】
    疾病"心绞痛" -[REQUIRES_EXAMINATION]-> 检查"心电图"（映射6：疾病模板）
    疾病"心绞痛" -[REQUIRES_TREATMENT]-> 治疗"硝酸甘油"（映射6：疾病模板）
    ↓
【步骤5：规则映射】
    症状组合[胸痛+大汗] → 风险等级"高危"（映射12：风险识别规则）
    风险等级"高危" → 处置建议"立即就医"（映射13：输出规则）
```

### 5.2 映射关系的层次结构

映射关系按照**抽象层次**可以分为4层：

| 层次 | 映射类型 | 存储位置 | 特点 | 示例 |
|------|---------|---------|------|------|
| **L1：输入标准化层** | 归一化映射 | 表格文件 | 一对一映射，简单直接 | "心口疼" → "胸痛" |
| **L2：语义关系层** | 核心映射、扩展映射 | 知识图谱关系 | 多对多关系，支持推理 | "胸痛" → "心绞痛" |
| **L3：流程控制层** | 规则映射 | 配置文件 | 条件判断，流程控制 | "症状组合[胸痛+气短] → 主诉候选" |
| **L4：合规追溯层** | 来源映射 | 知识图谱关系 | 跨层追溯，合规保障 | "任何节点" → "来源节点" |

## 六、知识图谱的工程层与语义层设计

### 6.1 双层架构设计

AI医生系统的知识图谱采用**双层架构**设计：

```
┌─────────────────────────────────────────────────────────────┐
│                      语义层（Semantic Layer）                 │
│  存储医学知识的实体和关系，支持诊断推理                        │
│  - 实体节点：主诉、症状、疾病、证据、检查、治疗等               │
│  - 语义关系：CONTAINS、HAS_CANDIDATE_DISEASE、SUPPORTS等      │
└────────────────────┬──────────────────────────────────────┘
                     │
                     │ 通过 SOURCED_FROM 关系连接
                     │
┌────────────────────▼──────────────────────────────────────┐
│                      工程层（Engineering Layer）             │
│  存储来源信息，支持合规追溯和知识管理                         │
│  - 来源节点：Source（医学文献、指南、专家共识等）              │
│  - 追溯关系：SOURCED_FROM（任何节点都可以引用来源）            │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 语义层（Semantic Layer）

**定义**：语义层是知识图谱的**核心业务层**，存储医学知识的实体和关系，支持诊断推理。

**存储内容**：
- **实体节点**（分立知识）：主诉、症状、疾病、证据、检查、治疗等
- **语义关系**（映射关系）：CONTAINS、HAS_CANDIDATE_DISEASE、SUPPORTS等

**功能**：
- 支持推理：通过图遍历发现隐含关系
- 支持查询：使用Cypher查询语言进行复杂查询
- 支持更新：可以动态添加、修改、删除实体和关系

### 6.3 工程层（Engineering Layer）

**定义**：工程层是知识图谱的**管理支撑层**，存储来源信息，支持合规追溯、版本管理和知识审核。

**存储内容**：
- **来源节点**：Source（医学文献、临床指南、专家共识等）
- **追溯关系**：SOURCED_FROM（任何语义层节点都可以通过此关系连接到来源节点）

**功能**：
- 合规追溯：每个知识实体都可以追溯其来源
- 版本管理：通过版本号管理知识的变更历史
- 审核流程：通过状态字段管理知识的审核流程

### 6.4 双层架构的连接方式

语义层的**任何节点**都可以通过`SOURCED_FROM`关系连接到工程层的**来源节点**：

```cypher
// 示例：主诉节点引用来源
(主诉节点) -[SOURCED_FROM {chapter, page, citation}]-> (Source节点)
```

**示例**：
- 主诉"胸痛" -[SOURCED_FROM]-> "Murtagh's General Practice Chapter 5"
- 症状→疾病关系 -[SOURCED_FROM]-> "Harrison's Principles of Internal Medicine Chapter 237"
