# 知识图谱设计-第5项-主诉模板

> **设计目标**：为主诉模板设计知识图谱结构，支持主诉的存储、查询和推理路径管理。  
> **创建日期**：2026-01-28  
> **文档版本**：v1.0  
> **基础文档**：基于"知识图谱设计-第3项-标准目录主数据"和"主诉知识图谱-字段分析"

---

## 📋 设计总览

**主诉知识图谱的特点**：
- **存储形式**：在第3项已有的ChiefComplaint节点基础上扩展
- **核心内容**：主诉定义、包含/排除范围、适用人群/场景、候选疾病、推理子组、检查建议等
- **设计重点**：支持主诉澄清、诊断推理、检查建议等业务场景

**设计原则**：
- 在第3项已有的ChiefComplaint节点基础上扩展属性
- 实体和关系存储在知识图谱中，支持推理和查询
- 流程规则存储在配置文件中（本文档不涉及）
- 支持与疾病知识图谱的关联和复用

**职责划分**：
- **第3项（标准目录主数据）**：提供基础主诉信息（编号、名称、分类、编码）
- **第5项（主诉模板）**：在第3项基础上扩展主诉的详细属性（定义、适用人群、适用场景）和关系（主诉与疾病、推理子组、检查等）

## 步骤0：双层Schema定义

### 0.1 语义层（Ontology/Concept Schema）

**定义**：语义层定义主诉领域的核心概念、实体类型和关系类型，关注临床语义的正确性。

**核心实体类型**：
- **ChiefComplaint**（主诉）：标准主诉实体（基于第3项扩展）
- **Disease**（疾病）：候选疾病实体（复用疾病知识图谱）
- **ReasoningSubgroup**（推理子组）：线索簇/推进组（复用疾病知识图谱）
- **DifferentialFrameworkSubclass**（鉴别诊断框架子类）：Step2分组实体
- **DifferentialPoint**（关键差异点）：Step4差异点实体（可选）
- **Examination**（检查）：检查建议实体（复用第3项）

**关系类型**：
- **HAS_CANDIDATE_DISEASE**：主诉有候选疾病（三层候选）
- **HAS_REASONING_SUBGROUP**：主诉有推理子组
- **HAS_DIFFERENTIAL_SUBCLASS**：主诉有鉴别诊断框架子类
- **HAS_DIFFERENTIAL_POINT**：主诉有关键差异点（可选）
- **RECOMMENDS_EXAMINATION**：主诉推荐检查
- **CONTAINS_DISEASE**：子类/子组包含疾病
- **AFFECTS**：差异点影响子组/疾病

**属性定义**：主诉定义、包含/排除范围、适用人群/场景、候选疾病层级、推理路径等

### 0.2 工程层（Ingestion & Retrieval Schema）

**定义**：工程层定义主诉知识抽取、存储、检索所需的技术结构，关注可追溯性和可维护性。

**核心节点类型**：
- **Document**：源文档（主诉模板文档、指南等）
- **Chunk**：文档片段（含向量嵌入），用于GraphRAG
- **Mention**：实体提及（在文本中的出现位置）
- **Evidence**：证据节点（链接到chunk）
- **Source**：数据来源（文档、版本、作者等）
- **Version**：版本信息（主诉模板版本、更新日期等）
- **ExtractionRun**：抽取运行记录（时间、模型、参数等）

**核心关系类型**：
- **Document → Chunk**：文档包含词块
- **Chunk → Mention**：词块包含实体提及
- **Mention → Entity**：提及指向实体
- **Edge → Evidence**：关系边链接到证据chunk
- **Entity → Source**：实体链接到来源文档

**设计要点**：
- 每个三元组（实体-关系-实体）必须能追溯到源chunk
- 支持版本管理和多来源合并
- 支持GraphRAG检索（chunk含向量嵌入）

### 0.3 两层Schema的关联

**关联方式**：
- 语义层的ChiefComplaint实体通过`Mention`节点链接到工程层的`Chunk`
- 语义层的关系边通过`Evidence`节点链接到工程层的`Chunk`
- 工程层的`Source`和`Version`节点为语义层实体提供来源和版本信息

**示例结构**：
```
语义层：ChiefComplaint(水肿) --[HAS_CANDIDATE_DISEASE]--> Disease(深静脉血栓)
         ↓                                    ↓
工程层：Mention --[IN_CHUNK]--> Chunk --[FROM_DOC]--> Document(主诉模板v1.0)
```

## 步骤1：业务场景 & Query Set

### 1.1 业务目标

**需要回答的问题**：
- 如何根据用户输入的主诉推理候选疾病？
- 如何确定主诉的适用人群和场景？
- 如何管理主诉的澄清流程？
- 如何组织主诉的推理子组和鉴别诊断框架？
- 如何根据主诉推荐检查项目？

### 1.2 业务场景

| 场景编号 | 场景描述 | 涉及的实体 | 涉及的关系 |
|---------|---------|-----------|-----------|
| **场景1** | 用户输入"我水肿"，系统识别主诉并推理候选疾病 | ChiefComplaint, Disease | HAS_CANDIDATE_DISEASE |
| **场景2** | 系统根据主诉确定适用人群和场景 | ChiefComplaint | 节点属性（applicable_populations, applicable_scenarios） |
| **场景3** | 用户输入多个症状，系统进行主诉澄清 | ChiefComplaint | 澄清规则（配置文件） |
| **场景4** | 系统根据主诉组织推理子组 | ChiefComplaint, ReasoningSubgroup | HAS_REASONING_SUBGROUP |
| **场景5** | 系统根据主诉推荐检查项目 | ChiefComplaint, Examination | RECOMMENDS_EXAMINATION |
| **场景6** | 系统根据主诉确定鉴别诊断框架子类 | ChiefComplaint, DifferentialFrameworkSubclass | HAS_DIFFERENTIAL_SUBCLASS |

### 1.3 查询需求（Query Set）

| 查询ID | 查询描述 | 期望返回字段 | 示例 |
|--------|---------|------------|------|
| **Q5-1** | 根据主诉查询候选疾病（三层候选） | 疾病列表、层级、优先级、支持/反对线索 | 主诉"水肿" → 候选疾病列表（Tier1/Tier2/Tier3） |
| **Q5-2** | 根据主诉查询推理子组 | 推理子组列表、进入触发、推进目标 | 主诉"水肿" → 推理子组列表 |
| **Q5-3** | 根据主诉查询鉴别诊断框架子类 | 子类列表、候选疾病、must-not-miss | 主诉"水肿" → 鉴别诊断框架子类列表 |

| **Q5-7** | 查询主诉的定义和范围 | 主诉定义、包含范围、排除范围 | 主诉"水肿" → 定义和范围信息 |
| **Q5-8** | 根据候选疾病查询详细信息 | 疾病、默认层级、入选依据、支持/反对线索、待补齐缺口 | 主诉"水肿" + 疾病"深静脉血栓" → 详细信息 |

## 步骤3：抽取设计

### 3.1 数据来源

**主要数据来源**：
1. **主诉模板文档**：结构化表格文件，包含主诉的详细属性
2. **主诉知识图谱表格**：主诉表1-10的表格数据
3. **疾病知识图谱**：复用已有的疾病和推理子组节点
4. **第3项标准目录**：复用已有的ChiefComplaint和Examination节点

### 3.2 抽取方法

**方法1：表格文件直接导入**
- 从主诉模板表格文件直接读取数据
- 批量创建和更新ChiefComplaint节点属性
- 建立主诉与其他实体的关系

**方法2：关系建立**
- 根据候选疾病列表建立HAS_CANDIDATE_DISEASE关系
- 根据推理子组列表建立HAS_REASONING_SUBGROUP关系
- 根据检查建议列表建立RECOMMENDS_EXAMINATION关系

**方法3：实体复用**
- 复用疾病知识图谱中的Disease和ReasoningSubgroup节点
- 复用第3项中的ChiefComplaint和Examination节点
- 通过display_id关联

### 3.3 抽取流程

```
步骤1：读取主诉模板表格源数据
  ↓
步骤2：查找或创建ChiefComplaint节点（基于第3项的display_id）
  ↓
步骤3：更新ChiefComplaint节点属性（定义、包含/排除范围、适用人群/场景等）
  ↓
步骤4：创建鉴别诊断框架子类节点（DifferentialFrameworkSubclass）
  ↓
步骤5：创建关键差异点节点（DifferentialPoint，可选）
  ↓
步骤6：建立主诉与候选疾病的关系（HAS_CANDIDATE_DISEASE，含三层候选属性）
  ↓
步骤7：建立主诉与推理子组的关系（HAS_REASONING_SUBGROUP，复用疾病知识图谱）
  ↓
步骤8：建立主诉与鉴别诊断框架子类的关系（HAS_DIFFERENTIAL_SUBCLASS）
  ↓
步骤9：建立主诉与关键差异点的关系（HAS_DIFFERENTIAL_POINT，可选）
  ↓
步骤10：建立主诉与检查的关系（RECOMMENDS_EXAMINATION）
  ↓
步骤11：建立子类/子组与疾病的关系（CONTAINS_DISEASE）
  ↓
步骤12：建立差异点与子组/疾病的关系（AFFECTS，可选）
  ↓
步骤13：链接到来源文档
  ↓
步骤14：验证数据完整性
```

## 步骤4：实体归并/去重 + 标准编码对齐

### 4.1 实体归并策略

**归并场景**：
- 主诉节点基于第3项已有的ChiefComplaint节点，通过display_id关联，无需归并
- 疾病节点复用疾病知识图谱，通过display_id关联
- 推理子组复用疾病知识图谱，通过display_id关联
- 鉴别诊断框架子类和关键差异点为新节点，需要检查重复

**归并方法**：
1. **名称精确匹配**：完全相同的名称归并为同一实体
2. **display_id匹配**：相同display_id的实体归并
3. **语义匹配**：语义相似的实体归并（用于鉴别诊断框架子类和关键差异点）

### 4.2 标准编码对齐

**对齐策略**：
- ChiefComplaint节点：与第3项的编码对齐（chief_complaint_code）
- Disease节点：复用疾病知识图谱的编码对齐（icd10_code、icd11_code、snomed_code）
- Examination节点：复用第3项的编码对齐（examination_code）

### 4.3 归并对齐流程


## 步骤7：图模型设计

### 7.1 节点设计

**节点类型**：

1. **语义层实体节点**：
   - **ChiefComplaint**：主诉节点（基于第3项扩展）
   - **Disease**：疾病节点（复用疾病知识图谱）
   - **ReasoningSubgroup**：推理子组节点（复用疾病知识图谱）
   - **DifferentialFrameworkSubclass**：鉴别诊断框架子类节点（新增）
   - **DifferentialPoint**：关键差异点节点（新增，可选）
   - **Examination**：检查节点（复用第3项）

2. **工程层节点**：
   - **Document**：源文档节点
   - **Chunk**：文档片段节点（含向量嵌入）
   - **Mention**：实体提及节点
   - **Evidence**：证据节点
   - **Source**：数据来源节点
   - **Version**：版本信息节点
   - **ExtractionRun**：抽取运行记录节点

**节点标签设计**：
- 使用英文标签：`ChiefComplaint`、`Disease`、`ReasoningSubgroup`、`DifferentialFrameworkSubclass`、`DifferentialPoint`、`Examination`
- 标签清晰、简洁、符合命名规范

### 7.2 边设计

**边类型**：

1. **语义层关系边**：
   - **HAS_CANDIDATE_DISEASE**：主诉有候选疾病
   - **HAS_REASONING_SUBGROUP**：主诉有推理子组
   - **HAS_DIFFERENTIAL_SUBCLASS**：主诉有鉴别诊断框架子类
   - **HAS_DIFFERENTIAL_POINT**：主诉有关键差异点（可选）
   - **RECOMMENDS_EXAMINATION**：主诉推荐检查
   - **CONTAINS_DISEASE**：子类/子组包含疾病
   - **AFFECTS**：差异点影响子组/疾病

2. **工程层关系边**：
   - **Document → Chunk**：文档包含词块
   - **Chunk → Mention**：词块包含实体提及
   - **Mention → Entity**：提及指向实体
   - **Edge → Evidence**：关系边链接到证据chunk
   - **Entity → Source**：实体链接到来源文档

**设计要点**：
- 边的方向性明确，确保关系语义准确
- 每条语义层关系边必须链接到证据chunk（通过Evidence节点）
- 支持GraphRAG检索（chunk含向量嵌入）

### 7.3 子图设计（语义子图 + 证据子图 + 运行子图）

#### 7.3.1 语义子图（Semantic Subgraph）

**包含内容**：
- **节点**：ChiefComplaint、Disease、ReasoningSubgroup、DifferentialFrameworkSubclass、DifferentialPoint、Examination
- **边**：HAS_CANDIDATE_DISEASE、HAS_REASONING_SUBGROUP、HAS_DIFFERENTIAL_SUBCLASS、RECOMMENDS_EXAMINATION、CONTAINS_DISEASE、AFFECTS
- **用途**：支持主诉澄清、诊断推理、检查建议等业务场景

**示例结构**：
```
ChiefComplaint(水肿) --[HAS_CANDIDATE_DISEASE {tier_level: "Tier2"}]--> Disease(深静脉血栓)
ChiefComplaint(水肿) --[HAS_REASONING_SUBGROUP]--> ReasoningSubgroup(血栓风险线索组)
ChiefComplaint(水肿) --[HAS_DIFFERENTIAL_SUBCLASS]--> DifferentialFrameworkSubclass(单侧)
DifferentialFrameworkSubclass(单侧) --[CONTAINS_DISEASE]--> Disease(深静脉血栓)
```

#### 7.3.2 证据子图（Evidence Subgraph）

**包含内容**：
- **节点**：Document、Chunk（含向量嵌入）、Mention、Evidence
- **边**：Document→Chunk、Chunk→Mention、Mention→Entity、Edge→Evidence
- **用途**：支持证据追溯、GraphRAG检索、可解释性查询

**示例结构**：
```
Document(主诉模板v1.0) --[CONTAINS]--> Chunk(chunk_001, embedding)
Chunk(chunk_001) --[CONTAINS]--> Mention(mention_001)
Mention(mention_001) --[REFERS_TO]--> ChiefComplaint(水肿)
Edge(HAS_CANDIDATE_DISEASE) --[HAS_EVIDENCE]--> Chunk(chunk_001)
```

#### 7.3.3 运行子图（Run Subgraph）

**包含内容**：
- **节点**：ExtractionRun、Model、PromptVersion、Metrics
- **边**：ExtractionRun→Model、ExtractionRun→PromptVersion、ExtractionRun→Entity/Edge
- **用途**：支持抽取运行管理、质量评估、版本控制

### 7.4 图数据库结构设计

**存储模式选择**：
- **单一图数据库**：选择一个单一的图数据库存储整个知识图谱（推荐Neo4j）
- **与疾病知识图谱共享**：主诉知识图谱与疾病知识图谱共享同一个图数据库实例

**图数据库选择考虑**：
- **数据规模**：根据数据规模选择合适的图数据库（Neo4j、ArangoDB、JanusGraph等）
- **查询需求**：根据查询需求选择合适的查询语言（Cypher、Gremlin、SPARQL等）
- **扩展性**：考虑图数据库的水平扩展能力
- **向量支持**：考虑是否支持向量嵌入存储和检索（Neo4j 5.x支持向量索引）

**索引设计**：

| 索引类型 | 索引字段 | 用途 |
|---------|---------|------|
| **节点属性索引** | `display_id`、`name` | 加速节点查询 |
| **节点属性索引** | `chief_complaint_uuid`、`disease_uuid` | 加速UUID查询 |
| **关系属性索引** | `tier_level`、`priority` | 加速关系查询和过滤 |
| **关系属性索引** | `source_chunk_id`、`confidence` | 加速关系查询和过滤 |

## 步骤8：子图设计考虑

### 8.1 子图的必要性

**子图的作用**：

| 作用 | 说明 |
|------|------|
| **性能优化** | 随着知识图谱规模的增长，查询性能可能会受到影响。通过将图谱划分为子图，可以针对不同子图优化查询性能 |
| **模块化设计** | 主诉知识图谱与疾病知识图谱可以划分为不同的子图，使图谱更具模块化，便于维护和扩展 |
| **业务隔离** | 通过子图，可以实现不同业务领域的数据隔离和权限控制 |

### 8.2 子图的划分依据

**划分方式**：

1. **主题或领域划分**：根据知识图谱覆盖的领域或主题，将图谱拆分成多个子图
   - **主诉子图**：包含主诉相关的实体和关系
   - **疾病子图**：包含疾病相关的实体和关系（复用）
   - **推理子图**：包含推理子组和鉴别诊断框架子类

2. **实体类型划分**：根据实体的类型将图谱划分为子图
   - **主诉实体子图**：ChiefComplaint节点及其关系
   - **疾病实体子图**：Disease节点及其关系（复用）
   - **推理实体子图**：ReasoningSubgroup、DifferentialFrameworkSubclass节点及其关系

3. **来源类型划分**：根据数据来源的类型和证据等级划分子图
   - **主诉模板子图**：来自主诉模板的实体和关系
   - **指南子图**：来自指南的实体和关系（复用疾病知识图谱）

**示例：主诉知识图谱子图划分**：

| 子图名称 | 包含内容 | 划分依据 |
|---------|---------|---------|
| **主诉子图** | ChiefComplaint节点及其关系 | 主题划分 |
| **推理子图** | ReasoningSubgroup、DifferentialFrameworkSubclass节点及其关系 | 主题划分 |
| **疾病子图** | Disease节点及其关系（复用） | 主题划分 |
| **检查子图** | Examination节点及其关系（复用） | 主题划分 |

### 8.3 版本与合规隔离设计

**设计原则**：

1. **版本并行存储**：
   - 同一主诉在不同版本下可能有不同属性值
   - 通过`version`属性区分，查询时指定版本

2. **版本冲突检测**：
   - 检测同一主诉关系在不同版本下的冲突
   - 标记冲突，需要人工审核

3. **版本合并策略**：
   - **最新版本优先**：使用最新版本的主诉模板
   - **人工指定**：人工指定使用哪个版本

**版本隔离设计**：

| 隔离维度 | 设计方式 | 示例 |
|---------|---------|------|
| **来源类型** | 通过`source_type`属性标记 | `chief_complaint_template`、`guideline` |
| **版本号** | 通过`version`属性标记 | `v1.0`、`v2.0` |
| **子图标签** | 通过子图标签隔离 | `ChiefComplaintSubgraph`、`DiseaseSubgraph` |

**设计原则**：
- **唯一性**：确保每个节点主键唯一
- **稳定性**：主键一旦生成，永不改变
- **可读性**：展示ID便于理解和调试
- **规范性**：使用统一的命名规范
- **可追溯性**：保留来源信息，支持追溯

## 📊 设计总结

### 核心设计要点

1. **基于第3项扩展**：主诉节点基于第3项已有的ChiefComplaint节点扩展，通过display_id关联
2. **实体复用**：疾病节点和推理子组节点复用疾病知识图谱，避免重复创建
3. **关系设计**：通过关系属性支持三层候选（Tier1/Tier2/Tier3）和详细属性
4. **证据追溯**：每条关系边必须链接到证据chunk，支持可解释性查询
5. **版本管理**：节点和关系都包含版本信息，支持版本管理和更新

### 与其他知识内容的关联

- **与第3项的关联**：主诉节点（ChiefComplaint）基于第3项扩展，通过display_id关联
- **与疾病知识图谱的关联**：疾病节点（Disease）和推理子组节点（ReasoningSubgroup）复用疾病知识图谱，通过display_id关联
- **与检查知识图谱的关联**：检查节点（Examination）复用第3项，通过display_id关联
