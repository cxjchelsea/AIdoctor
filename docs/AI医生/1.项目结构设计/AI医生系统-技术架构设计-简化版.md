# AI医生系统 - 技术架构设计（简化版）

> **文档定位**：本文档是AI医生系统技术架构的**简化版**，面向非技术背景的同事，用通俗易懂的语言介绍系统的核心架构和工作流程。  
> **完整技术文档**：如需了解详细技术实现，请参考《AI医生系统-技术架构设计.md》

---

## 📖 核心概念快速理解

在深入了解架构之前，先理解几个核心概念：

| 概念 | 通俗解释 |
|------|---------|
| **智能体（Agent）** | 就像医院里的不同科室医生，每个智能体负责一个专业领域，比如有的负责理解病情，有的负责诊断，有的负责开检查单 |
| **协调器（Orchestrator）** | 就像医院的"总调度室"，负责安排哪个医生（智能体）什么时候工作，协调大家配合 |
| **双通道推理** | 系统有两个"大脑"：一个负责"想什么"（临床逻辑推理），一个负责"怎么说"（自然语言表达） |
| **CDP（临床决策包）** | 就像患者的"病历本"，记录整个诊疗过程中的所有信息：症状、诊断、检查、治疗方案等 |
| **工作态** | 系统有两种工作模式：**健康管理态**（面向健康人群）和**临床诊疗态**（面向患者） |

## 一、系统整体架构

### 1.1 双通道推理架构

AI医生系统采用**双通道推理架构**，就像人类医生有两个大脑：

```
┌─────────────────────────────────────────────────────────────┐
│                    通道1：结构化推理通道                      │
│              （决定"该往哪想" - 临床逻辑）                    │
│                                                              │
│  这个通道负责：                                               │
│  • 理解医学概念（把"头痛"标准化为医学编码）                   │
│  • 在知识图谱中查找可能的疾病路径                            │
│  • 运用医学规则和概率模型进行诊断推理                         │
│  • 生成可能的诊断列表                                        │
│                                                              │
│  输出：可能的疾病诊断 + 推理依据                              │
└─────────────────────────────────────────────────────────────┘
                            ↓
                    写入CDP（病历本）
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                    通道2：语言与策略通道                      │
│            （决定"怎么说、怎么问" - 医生表达）               │
│                                                              │
│  这个通道负责：                                               │
│  • 生成问诊问题（"您头痛多久了？"）                          │
│  • 把诊断结果用通俗语言解释给患者                            │
│  • 生成治疗方案的自然语言描述                                │
│  • 组织整个对话流程                                          │
│                                                              │
│  输出：自然语言问诊、解释、建议                              │
└─────────────────────────────────────────────────────────────┘
```

**核心原则**：
> **让结构化通道决定"该往哪想"（医学推理），让语言通道决定"怎么说、怎么问"（医患沟通）**

这样设计的好处是：
- **准确性**：医学推理基于严谨的知识图谱和规则，不会"胡说"
- **可解释性**：每一步推理都有依据，可以追溯
- **人性化**：用自然语言与患者交流，就像真实医生一样

### 1.2 多智能体系统架构

系统由**8个智能体**组成，每个智能体就像医院里的一个专业科室：

```
┌─────────────────────────────────────────────────────────────┐
│                    协调器（总调度室）                         │
│  负责：任务分配、流程编排、冲突解决                            │
└─────────────────────────────────────────────────────────────┘
                            ↓
        ┌───────────────────┼───────────────────┐
        │                   │                   │
        ▼                   ▼                   ▼
┌───────────────┐  ┌───────────────┐  ┌───────────────┐
│  智能体0      │  │  智能体1      │  │  智能体2      │
│  健康状态判定 │  │  病例理解     │  │  主动问诊     │
│  （分诊台）   │  │  （理解病情）  │  │  （问诊医生）  │
└───────────────┘  └───────────────┘  └───────────────┘
        │                   │                   │
        ▼                   ▼                   ▼
┌───────────────┐  ┌───────────────┐  ┌───────────────┐
│  智能体3      │  │  智能体4      │  │  智能体5      │
│  鉴别诊断     │  │  检查建议     │  │  治疗建议     │
│  （诊断医生）  │  │  （开检查单）  │  │  （开处方）   │
└───────────────┘  └───────────────┘  └───────────────┘
        │                   │                   │
        ▼                   ▼                   ▼
┌───────────────┐  ┌───────────────┐
│  智能体6      │  │  智能体7      │
│  风险评估     │  │  证据链       │
│  （评估风险）  │  │  （整理证据）  │
└───────────────┘  └───────────────┘
```

#### 八大智能体职责说明

| 智能体 | 通俗比喻 | 主要职责 |
|--------|---------|---------|
| **智能体0：健康状态判定** | 分诊台护士 | 判断用户是健康人群还是患者，决定走哪个流程 |
| **智能体1：病例理解** | 病历录入员 | 理解用户输入的症状，标准化为医学概念 |
| **智能体2：主动问诊** | 问诊医生 | 主动提问，收集关键信息，填补信息缺口 |
| **智能体3：鉴别诊断** | 诊断医生 | 分析可能的疾病，生成诊断列表并排序 |
| **智能体4：检查建议** | 开检查单的医生 | 建议需要做什么检查来验证诊断 |
| **智能体5：治疗建议** | 开处方的医生 | 根据诊断结果，制定治疗方案 |
| **智能体6：风险评估** | 风险评估专家 | 评估病情紧急程度，判断是否需要紧急处理 |
| **智能体7：证据链** | 病历整理员 | 整理所有证据，生成完整的诊疗报告 |

## 二、核心工作流程

### 2.1 系统入口：健康状态判定

当用户发起咨询时，系统首先由**智能体0（健康状态判定）**判断用户属于哪类人群：

```
用户："我最近有点头痛"
        ↓
┌─────────────────────────────────────┐
│  智能体0：健康状态判定                │
│  • 评估症状严重程度                   │
│  • 判断是否有危险信号                 │
│  • 决定工作模式                       │
└───────────┬─────────────────────────┘
            │
    ┌───────┴───────┐
    │               │
    ▼               ▼
健康管理态        临床诊疗态
（健康人群）      （患者）
```

**判定结果**：
- **健康管理态（wellness_mode）**：面向无症状的健康人群，提供健康筛查、体检规划等服务
- **临床诊疗态（clinical_mode）**：面向有症状的患者，执行完整的诊疗流程

---

### 2.2 健康管理态流程

**适用场景**：用户没有明显症状，只是想了解健康状况、做体检规划等

**流程步骤**：

```
1. 需求分类
   └─ 智能体1（病例理解）：理解用户想要什么
        ↓
2. 补充信息
   └─ 智能体2（主动问诊）：如果信息不足，补充提问
        ↓
3. 生成健康管理计划
   └─ 智能体5（治疗建议）：制定健康管理方案
        ↓
4. 制定随访计划
   └─ 智能体6（风险评估）：确定多久复查一次
        ↓
5. 输出结果
   └─ 智能体7（证据链）：生成统一的结果报告
```

**示例**：
- 用户："我想做个体检，应该查什么？"
- 系统：理解需求 → 询问年龄、性别、既往病史 → 推荐体检项目 → 制定随访计划 → 输出体检建议

---

### 2.3 临床诊疗态流程（5步AI循证诊断）

**适用场景**：用户有症状，需要诊断和治疗

**核心流程**：5步AI循证诊断流程

```
Step 1: 识别问题
  └─ 理解用户症状，标准化为医学概念
        ↓
Step 2: 构建鉴别诊断候选集并分层
  └─ 列出所有可能的疾病，分为三层：
     • 首要假设（最可能的）
     • 主要备选（次可能的）
     • 必须排除（危险但可能性低的）
        ↓
Step 3: 组织候选集并建立分流路径
  └─ 找出关键差异点，形成问诊路径
        ↓
Step 4: 采集关键证据并形成验证计划
  └─ 沿着路径问诊，制定检查计划
        ↓
Step 5: 回填证据并输出终点结论包
  └─ 综合分析，输出最终诊断和治疗方案
```

#### 详细流程说明

**Step 1: 识别问题**
- **智能体1（病例理解）**：把"头痛"标准化为医学概念
- **智能体2（主动问诊）**：补充关键信息（头痛多久了？什么性质？）
- **输出**：完整的问题清单

**Step 2: 构建鉴别诊断候选集并分层**
- **智能体3（鉴别诊断）**：在知识图谱中查找可能的疾病
- **智能体6（风险评估）**：评估哪些疾病需要优先排除
- **输出**：三层诊断列表
  - 首要假设：偏头痛（概率70%）
  - 主要备选：紧张性头痛（概率20%）
  - 必须排除：脑肿瘤（概率5%，但必须排除）

**Step 3: 组织候选集并建立分流路径**
- **智能体3（鉴别诊断）**：找出区分不同疾病的关键问题
- **输出**：分流路径
  - 路径A：如果头痛是搏动性的 → 偏头痛
  - 路径B：如果头痛是持续性的 → 紧张性头痛
  - 路径C：如果有神经系统症状 → 需要排除脑肿瘤

**Step 4: 采集关键证据并形成验证计划**
- **智能体2（主动问诊）**：沿着分流路径提问
- **智能体3（鉴别诊断）**：根据回答更新诊断概率
- **智能体4（检查建议）**：制定检查计划（如需要）
- **输出**：验证计划（需要做什么检查）

**Step 5: 回填证据并输出终点结论包**
- **智能体4（检查建议）**：回填检查结果
- **智能体3（鉴别诊断）**：更新最终诊断
- **智能体5（治疗建议）**：制定治疗方案
- **智能体7（证据链）**：生成终点结论包（四要素）
  - 诊断结论
  - 诊断依据
  - 治疗方案
  - 随访建议

## 三、智能体协作机制

### 3.1 协作方式

智能体之间通过**消息传递**进行协作，就像医生之间会互相沟通：

```
智能体A → 发送消息 → 协调器 → 转发消息 → 智能体B
```

### 3.2 协商机制

当多个智能体对同一问题有不同看法时，系统会进行**协商**：

**示例场景**：
- **智能体3（鉴别诊断）**：认为可能是心绞痛（概率70%）
- **智能体4（检查建议）**：建议做心电图，但需要排除心梗
- **智能体6（风险评估）**：认为风险等级较高，需要优先排除心梗

**协商过程**：
1. 协调器收集各方观点
2. 根据各智能体的专业权重进行加权投票
3. 达成共识：优先排除心梗
4. 更新CDP（病历本）

### 3.3 冲突解决

如果智能体之间产生冲突，协调器会执行冲突解决策略：

**示例场景**：
- **智能体3**：诊断A概率80%
- **智能体4**：诊断A概率50%（基于检查结果）
- **智能体6**：诊断A概率90%（基于风险分析）

**解决方式**：
1. 检测到冲突
2. 根据优先级规则和证据强度进行加权
3. 执行专家投票
4. 得出最终结论：诊断A概率65%，标记为"需要进一步验证"

## 四、CDP（临床决策包）核心概念

### 4.1 什么是CDP？

**CDP（Clinical Decision Package）**就像患者的"电子病历本"，记录整个诊疗过程中的所有信息。

### 4.2 CDP包含什么？

CDP包含以下核心信息：

| 字段 | 通俗解释 | 由哪个智能体填写 |
|------|---------|----------------|
| **健康状态判定** | 用户是健康人群还是患者 | 智能体0 |
| **患者状态** | 患者的基本信息和症状 | 智能体1 |
| **鉴别诊断列表** | 可能的疾病列表（三层排序） | 智能体3 |
| **检查计划** | 建议做什么检查 | 智能体4 |
| **治疗计划** | 治疗方案 | 智能体5 |
| **风险评估** | 病情紧急程度 | 智能体6 |
| **证据链** | 所有诊断依据的整理 | 智能体7 |

### 4.3 CDP的流转

CDP在整个诊疗过程中不断更新，就像病历本不断被填写：

```
创建CDP（空病历本）
    ↓
智能体0填写：健康状态判定
    ↓
智能体1填写：患者状态
    ↓
智能体2填写：问诊信息
    ↓
智能体3填写：诊断列表
    ↓
智能体4填写：检查计划
    ↓
智能体5填写：治疗方案
    ↓
智能体7整理：最终报告
```

### 4.4 CDP版本管理

每次更新CDP时，系统会创建新版本，这样可以：
- **追溯历史**：可以看到每一步的变化
- **回退机制**：如果诊断有误，可以回退到之前的版本
- **审计追踪**：记录每一步是谁（哪个智能体）做的，为什么这样做
