## 一、服务逻辑关系

### 1.1 服务分类

AI医生系统共有**11个服务**，分为三类：

#### 1.1.1 协调器服务（1个）

- **diagnosis-service** (Java)
  - **定位**：系统协调中心，非脑区
  - **职责**：流程编排、CDP管理、任务分配、冲突解决
  - **特点**：不直接处理业务逻辑，而是协调其他服务

#### 1.1.2 智能体服务（8个，对应8个脑区）

| 服务名称 | 智能体 | 脑区 | 主要职责 |
|---------|--------|------|---------|
| `health-state-assessment-service` | 智能体0 | 脑区0 | 健康状态判定、入口判定流程 |
| `clinical-parsing-service` | 智能体1 | 脑区A | 病例理解、概念归一化 |
| `dialog-service` | 智能体2 | 脑区B | 主动问诊、智能追问 |
| `diagnosis-engine-service` | 智能体3 | 脑区C | 鉴别诊断、多引擎融合 |
| `workup-planner-service` | 智能体4 | 脑区D | 检查建议、验证计划 |
| `treatment-engine-service` | 智能体5 | 脑区E | 治疗推理、药物推荐 |
| `risk-assessment-service` | 智能体6 | 脑区F | 风险评估、紧急程度分级 |
| `explanation-service` | 智能体7 | 脑区G | 证据链构建、解释生成 |

#### 1.1.3 辅助服务（2个）

- **ocr-service** (Python)
  - **定位**：通用能力服务
  - **职责**：图像识别、报告OCR、结构化数据提取
  - **被调用**：被 `clinical-parsing-service` 调用

- **examination-service** (Java)
  - **定位**：业务服务层
  - **职责**：检查管理、检查结果处理
  - **特点**：提供检查相关的业务逻辑

### 1.3 服务调用关系详解

#### 1.3.1 协调器服务（diagnosis-service）的调用关系

**调用所有智能体服务**：
- 作为协调中心，`diagnosis-service` 负责调用所有8个智能体服务
- 根据流程需要，按顺序或并行调用相应的服务
- 管理服务间的数据流转和状态同步

**调用特点**：
- **同步调用**：关键路径服务（如健康状态判定、病例理解、诊断引擎）
- **异步调用**：非关键路径服务（如检查建议、治疗建议、解释生成）

#### 1.3.2 智能体服务间的调用关系

**直接调用关系**：

1. **clinical-parsing-service → ocr-service**
   - 当需要处理图片输入时调用
   - 调用方式：同步HTTP调用
   - 调用场景：多模态理解（文本+图片）

2. **dialog-service → clinical-parsing-service**
   - 获取结构化信息，用于生成追问问题
   - 调用方式：同步HTTP调用
   - 调用场景：信息缺口识别、问题生成

3. **dialog-service → diagnosis-engine-service**
   - 获取DDx信息，用于生成有针对性的追问
   - 调用方式：同步HTTP调用
   - 调用场景：基于诊断候选集生成追问

4. **diagnosis-engine-service → clinical-parsing-service**
   - 获取结构化病例数据，用于诊断推理
   - 调用方式：同步HTTP调用
   - 调用场景：诊断推理前需要结构化输入

5. **diagnosis-engine-service → risk-assessment-service**
   - 获取风险评估结果，用于调整诊断优先级
   - 调用方式：同步HTTP调用
   - 调用场景：高危诊断需要优先处理

6. **workup-planner-service → diagnosis-engine-service**
   - 获取DDx列表，用于评估检查价值
   - 调用方式：同步HTTP调用
   - 调用场景：检查建议生成

7. **workup-planner-service → risk-assessment-service**
   - 获取风险等级，用于调整检查优先级
   - 调用方式：同步HTTP调用
   - 调用场景：紧急情况需要优先检查

8. **treatment-engine-service → diagnosis-engine-service**
   - 获取诊断结果，用于生成治疗方案
   - 调用方式：同步HTTP调用
   - 调用场景：治疗建议生成

9. **treatment-engine-service → risk-assessment-service**
   - 获取风险等级，用于调整治疗方案
   - 调用方式：同步HTTP调用
   - 调用场景：高危患者需要特殊治疗方案

10. **risk-assessment-service → diagnosis-engine-service**
    - 获取DDx列表，用于评估风险
    - 调用方式：同步HTTP调用
    - 调用场景：风险评估需要诊断信息

11. **explanation-service → diagnosis-engine-service**
    - 获取推理路径，用于生成解释
    - 调用方式：同步HTTP调用
    - 调用场景：证据链构建

12. **explanation-service → workup-planner-service**
    - 获取检查建议，用于生成解释
    - 调用方式：同步HTTP调用
    - 调用场景：解释检查建议的原因

13. **explanation-service → treatment-engine-service**
    - 获取治疗方案，用于生成解释
    - 调用方式：同步HTTP调用
    - 调用场景：解释治疗方案的原因

**间接调用关系**（通过CDP）：
- 所有服务通过CDP（临床决策包）共享数据
- 服务间不直接传递数据，而是通过CDP读写
- 这保证了数据的一致性和可追溯性

### 1.4 服务执行顺序

#### 1.4.1 系统入口流程

```
用户输入
    ↓
diagnosis-service（创建CDP）
    ↓
health-state-assessment-service（健康状态判定）
    ├─→ 入口判定流程（Step 1-5）
    ├─→ 工作态判定（wellness_mode / clinical_mode）
    └─→ 危险信号检查
```

#### 1.4.2 健康管理态流程（路径A）

```
health-state-assessment-service
    ↓
[主要在health-state-assessment-service内部完成]
    ├─→ A1: 需求分类
    ├─→ A2: 通用最小健康档案
    ├─→ A3: 进入对应分支
    ├─→ A4: 统一结果页输出
    └─→ A5: 随访闭环
```

**涉及服务**：
- `health-state-assessment-service`（主要执行）
- `diagnosis-service`（流程编排，可选）

#### 1.4.3 临床诊疗态流程（路径B）- 5步AI循证诊断流程

```
Step 1: 识别问题
    ├─→ clinical-parsing-service（病例理解）
    └─→ dialog-service（主动问诊）

Step 2: 构建鉴别诊断候选集并分层
    └─→ diagnosis-engine-service（诊断引擎）
        └─→ risk-assessment-service（风险评估）

Step 3: 组织候选集并建立分流路径
    ├─→ diagnosis-engine-service（推理组织器）
    └─→ dialog-service（分流路径设计）

Step 4: 采集关键证据并形成排序与验证计划
    ├─→ dialog-service（主动问诊）
    ├─→ diagnosis-engine-service（证据分析器）
    ├─→ workup-planner-service（检查建议）
    └─→ risk-assessment-service（风险评估）

Step 5: 回填证据并输出终点结论包
    ├─→ diagnosis-engine-service（证据回填）
    ├─→ explanation-service（解释生成）
    ├─→ treatment-engine-service（治疗推理）
    └─→ diagnosis-service（流程编排与回退）
```

### 1.5 服务协作模式

#### 1.5.1 顺序协作

**特点**：服务按顺序执行，前一个服务的输出作为后一个服务的输入

**示例**：
```
clinical-parsing-service → diagnosis-engine-service → treatment-engine-service
```

#### 1.5.2 并行协作

**特点**：多个服务并行执行，最后汇总结果

**示例**：
```
diagnosis-engine-service ──┐
workup-planner-service   ──┼→ explanation-service（等待所有结果）
treatment-engine-service ──┘
```

#### 1.5.3 循环协作

**特点**：服务间形成循环，直到满足条件

**示例**：
```
dialog-service → diagnosis-engine-service → dialog-service
（问诊 → 诊断 → 再问诊，直到信息完整）
```

## 二、脑区逻辑关系

### 2.1 脑区分类

AI医生系统共有**8个脑区**，分为两类：

#### 2.1.1 通道1：结构化推理通道（决定"该往哪想"）

**主要脑区**：
- **脑区0**：健康状态判定（规则推理、风险评估）
- **脑区A**：病例理解（概念归一化、结构化提取）
- **脑区C**：鉴别诊断（知识图谱推理、多引擎融合）
- **脑区D**：检查建议（检查价值评估、信息增益计算）
- **脑区E**：治疗推理（治疗方案推理、药物推荐）
- **脑区F**：风险评估（风险识别、紧急程度评估）

**技术实现**：
- 知识图谱路径检索与排序（DR.KNOWS方法）
- 规则引擎、统计模型、贝叶斯推理
- 多引擎融合诊断
- 医学概念标准化（CUI/ICD/SNOMED）

**输出**：DDx候选 + 证据结构 + 推理路径（写入CDP）

#### 2.1.2 通道2：语言与策略通道（决定"怎么说、怎么问"）

**主要脑区**：
- **脑区B**：主动问诊（生成问诊问题、自然语言对话）
- **脑区G**：解释生成（生成解释和说明、推理路径可视化）

**技术实现**：
- LLM（大语言模型）
- NLG（自然语言生成）
- 对话生成、解释生成
- 自然语言理解（NLU）

**输出**：自然语言问诊、解释、建议

#### 2.1.3 双通道协作

**协作机制**：
```
通道1智能体（结构化推理）
    ↓
生成结构化结果（DDx、检查建议等）
    ↓
写入CDP（结构化数据）
    ↓
通道2智能体（语言与策略）
    ↓
读取CDP
    ↓
生成自然语言表达
    ↓
输出给用户
```

**关键原则**：
- **通道1决定"该往哪想"**：结构化推理通道负责临床逻辑推理
- **通道2决定"怎么说"**：语言与策略通道负责将结构化结果转换为自然语言
- **CDP作为桥梁**：通道1的输出写入CDP，通道2基于CDP生成自然语言表达

### 2.4 脑区协作模式

#### 2.4.1 顺序协作

**特点**：脑区按顺序执行，前一个脑区的输出作为后一个脑区的输入

**示例**：
```
脑区A（病例理解） → 脑区C（鉴别诊断） → 脑区E（治疗推理）
```

#### 2.4.2 并行协作

**特点**：多个脑区并行执行，最后汇总结果

**示例**：
```
脑区C（鉴别诊断） ──┐
脑区D（检查建议） ──┼→ 脑区G（解释生成，等待所有结果）
脑区E（治疗推理） ──┘
```

#### 2.4.3 循环协作

**特点**：脑区间形成循环，直到满足条件

**示例**：
```
脑区B（主动问诊） → 脑区C（鉴别诊断） → 脑区B（再问诊）
（问诊 → 诊断 → 再问诊，直到信息完整）
```

#### 2.4.4 双通道协作

**特点**：通道1生成结构化结果，通道2生成自然语言表达

**示例**：
```
通道1：脑区C（鉴别诊断） → 生成DDx（结构化）
    ↓
写入CDP
    ↓
通道2：脑区G（解释生成） → 生成解释（自然语言）
```

---

### 2.5 脑区功能互补关系

#### 2.5.1 信息收集阶段

**脑区A + 脑区B**：
- **脑区A**：将非结构化输入转换为结构化数据
- **脑区B**：识别信息缺口，生成追问问题
- **协作**：脑区A提供结构化基础，脑区B基于此生成有针对性的追问

#### 2.5.2 诊断推理阶段

**脑区C + 脑区F**：
- **脑区C**：生成诊断候选集
- **脑区F**：评估风险，调整诊断优先级
- **协作**：脑区F的风险评估结果影响脑区C的诊断排序

#### 2.5.3 检查建议阶段

**脑区C + 脑区D + 脑区F**：
- **脑区C**：提供诊断候选集
- **脑区D**：评估检查价值，生成检查建议
- **脑区F**：提供风险等级，影响检查优先级
- **协作**：三个脑区共同决定检查建议

#### 2.5.4 治疗建议阶段

**脑区C + 脑区E + 脑区F**：
- **脑区C**：提供诊断结果
- **脑区E**：生成治疗方案
- **脑区F**：提供风险等级，影响治疗方案
- **协作**：三个脑区共同决定治疗方案

#### 2.5.5 解释生成阶段

**脑区G + 其他脑区**：
- **脑区G**：生成解释和说明
- **其他脑区**：提供推理路径、检查建议、治疗方案
- **协作**：脑区G整合所有脑区的输出，生成完整的解释

## 三、服务与脑区的映射关系

### 3.1 一对一映射

**原则**：一个服务对应一个脑区，一个脑区对应一个服务

| 服务 | 脑区 | 映射关系 |
|------|------|---------|
| `health-state-assessment-service` | 脑区0 | 一对一 |
| `clinical-parsing-service` | 脑区A | 一对一 |
| `dialog-service` | 脑区B | 一对一 |
| `diagnosis-engine-service` | 脑区C | 一对一 |
| `workup-planner-service` | 脑区D | 一对一 |
| `treatment-engine-service` | 脑区E | 一对一 |
| `risk-assessment-service` | 脑区F | 一对一 |
| `explanation-service` | 脑区G | 一对一 |

### 3.2 协调器与脑区的关系

**diagnosis-service（协调器）**：
- **不是脑区**：协调器不属于8个脑区之一
- **协调所有脑区**：负责协调所有8个脑区的执行
- **流程编排**：决定脑区的执行顺序和协作方式

### 3.3 辅助服务与脑区的关系

**ocr-service**：
- **不是脑区**：辅助服务不属于8个脑区之一
- **被脑区A调用**：被 `clinical-parsing-service`（脑区A）调用
- **提供能力**：为脑区A提供多模态理解能力

**examination-service**：
- **不是脑区**：业务服务不属于8个脑区之一
- **独立服务**：提供检查相关的业务逻辑
- **与脑区关系**：可能被多个脑区间接使用（通过业务层）

## 四、数据流转关系

### 4.1 CDP（临床决策包）作为数据载体

**核心原则**：所有服务通过CDP共享数据，而不是直接传递数据

**CDP结构**：
```json
{
  "id": "cdp_123",
  "version": 1,
  "health_state_assessment": {},  // 脑区0写入
  "patient_state": {},            // 脑区A写入
  "ddx": [],                      // 脑区C写入
  "workup_plan": {},              // 脑区D写入
  "management_plan": {},          // 脑区E写入
  "triage": {},                   // 脑区F写入
  "explanation": {}               // 脑区G写入
}
```

### 4.2 数据流转路径

#### 4.2.1 健康管理态数据流转

```
用户输入
    ↓
diagnosis-service（创建CDP）
    ↓
health-state-assessment-service
    ├─→ 读取：用户输入
    └─→ 写入：CDP.health_state_assessment
    ↓
[主要在health-state-assessment-service内部完成]
    ↓
health-state-assessment-service
    └─→ 写入：CDP.wellness_plan
    ↓
返回结果给用户
```

#### 4.2.2 临床诊疗态数据流转

```
用户输入
    ↓
diagnosis-service（创建CDP）
    ↓
health-state-assessment-service
    └─→ 写入：CDP.health_state_assessment
    ↓
clinical-parsing-service
    ├─→ 读取：CDP.health_state_assessment
    └─→ 写入：CDP.patient_state
    ↓
dialog-service
    ├─→ 读取：CDP.patient_state
    └─→ 写入：CDP.patient_state（更新）
    ↓
diagnosis-engine-service
    ├─→ 读取：CDP.patient_state
    └─→ 写入：CDP.ddx
    ↓
risk-assessment-service
    ├─→ 读取：CDP.ddx
    └─→ 写入：CDP.triage
    ↓
workup-planner-service
    ├─→ 读取：CDP.ddx, CDP.triage
    └─→ 写入：CDP.workup_plan
    ↓
treatment-engine-service
    ├─→ 读取：CDP.ddx, CDP.triage
    └─→ 写入：CDP.management_plan
    ↓
explanation-service
    ├─→ 读取：CDP.ddx, CDP.workup_plan, CDP.management_plan
    └─→ 写入：CDP.explanation
    ↓
返回结果给用户
```

## 五、协作模式总结

### 5.1 服务协作模式

| 协作模式 | 特点 | 示例 |
|---------|------|------|
| **顺序协作** | 服务按顺序执行 | clinical-parsing → diagnosis-engine → treatment-engine |
| **并行协作** | 多个服务并行执行 | diagnosis-engine + workup-planner + treatment-engine |
| **循环协作** | 服务间形成循环 | dialog-service ↔ diagnosis-engine-service |
| **协调协作** | 通过协调器协调 | diagnosis-service协调所有服务 |

### 5.2 脑区协作模式

| 协作模式 | 特点 | 示例 |
|---------|------|------|
| **顺序协作** | 脑区按顺序执行 | 脑区A → 脑区C → 脑区E |
| **并行协作** | 多个脑区并行执行 | 脑区C + 脑区D + 脑区E |
| **循环协作** | 脑区间形成循环 | 脑区B ↔ 脑区C |
| **双通道协作** | 通道1生成结构化，通道2生成自然语言 | 脑区C（通道1）→ 脑区G（通道2） |

### 5.3 关键设计原则

1. **单一职责原则**：每个服务/脑区只负责一个功能领域
2. **依赖最小化**：服务间依赖关系尽可能简单
3. **数据共享**：通过CDP共享数据，保证一致性
4. **可追溯性**：所有推理过程可追溯、可审计
5. **可扩展性**：支持服务/脑区的独立演进和升级

## 六、总结

### 6.1 服务逻辑关系总结

- **11个服务**：1个协调器 + 8个智能体服务 + 2个辅助服务
- **服务依赖**：协调器调用所有智能体服务，智能体服务间有直接调用关系
- **数据流转**：通过CDP共享数据，保证一致性和可追溯性
- **协作模式**：顺序、并行、循环、协调四种模式

### 6.2 脑区逻辑关系总结

- **8个脑区**：6个结构化推理通道 + 2个语言与策略通道
- **脑区依赖**：脑区0为入口，其他脑区按流程顺序执行
- **双通道协作**：通道1生成结构化结果，通道2生成自然语言表达
- **协作模式**：顺序、并行、循环、双通道四种模式

### 6.3 服务与脑区的对应关系

- **一对一映射**：一个服务对应一个脑区
- **协调器**：不属于脑区，但协调所有脑区
- **辅助服务**：不属于脑区，但为脑区提供能力支持
