### 服务与智能体的对应关系

实际上是一个智能体对应一个服务：

| 服务                              | 对应智能体 | 对应脑区 | 主要功能 |
| --------------------------------- | ---------- | -------- | -------- |
| `health-state-assessment-service` | 智能体0    | 脑区0    | 健康状态判定、入口判定流程、工作态判定、危险信号检查、健康管理计划生成 |
| `clinical-parsing-service`        | 智能体1    | 脑区A    | 病例理解、医学概念识别与归一化、结构化提取、多模态理解、歧义表达判定 |
| `dialog-service`                  | 智能体2    | 脑区B    | 主动问诊、信息缺口识别、智能追问生成、自然语言理解与生成 |
| `diagnosis-engine-service`        | 智能体3    | 脑区C    | 五引擎融合诊断（规则/知识图谱/统计模型/LLM/鉴别诊断）、知识图谱推理、证据分析 |
| `workup-planner-service`          | 智能体4    | 脑区D    | 检查价值评估、信息增益计算、验证计划构建 |
| `treatment-engine-service`        | 智能体5    | 脑区E    | 治疗方案推理、药物推荐、非药物治疗建议 |
| `risk-assessment-service`         | 智能体6    | 脑区F    | 高危识别、紧急程度分级、复评与升级规则、终点结论包构建 |
| `explanation-service`             | 智能体7    | 脑区G    | 证据链构建、推理路径可视化、自然语言解释生成 |

除了8个智能体服务，还有：

#### 协调器服务（非脑区）
- `diagnosis-service` (Java) - 协调器（Orchestrator）
  - **主要功能**：流程编排、CDP管理、任务分配、冲突解决
  - **具体职责**：
    - CDP（临床决策包）的创建、更新、版本控制、回放、回退
    - 编排5步AI循证诊断流程（临床诊疗态）
    - 编排健康筛查流程（健康管理态）
    - 协调各个AI服务的调用顺序和依赖关系
    - 管理CDP状态流转和诊断流程状态
  - 不是脑区，而是协调所有智能体的服务

#### 辅助服务
- `ocr-service` (Python) - OCR服务
  - **主要功能**：图像识别、报告OCR、结构化数据提取
  - **具体职责**：
    - 报告图片识别
    - 多模态理解支持
    - 从图片中提取结构化数据
  - 被 `clinical-parsing-service` 调用

- `examination-service` (Java) - 检查服务
  - **主要功能**：检查相关的业务逻辑
  - **具体职责**：
    - 检查管理
    - 检查结果处理
    - 业务服务层功能

```
┌─────────────────────────────────────┐
│  协调器层（Orchestrator）            │
│  diagnosis-service (Java)           │  ← 流程编排、CDP管理
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│  智能体服务层（8个智能体服务）        │
│  - health-state-assessment-service  │  ← 智能体0
│  - clinical-parsing-service         │  ← 智能体1
│  - dialog-service                   │  ← 智能体2
│  - diagnosis-engine-service         │  ← 智能体3
│  - workup-planner-service           │  ← 智能体4
│  - treatment-engine-service         │  ← 智能体5
│  - risk-assessment-service          │  ← 智能体6
│  - explanation-service               │  ← 智能体7
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│  辅助服务层（通用能力）               │
│  - ocr-service                       │  ← OCR能力
│  - examination-service               │  ← 业务服务
└─────────────────────────────────────┘
```

- 8个智能体对应8个服务（按脑区拆分）
- 协调器服务（`diagnosis-service`）负责编排和CDP管理
- 辅助服务（`ocr-service`、`examination-service`）提供通用能力

设计依据：
1. 按脑区拆分，职责单一
2. 独立演进，便于升级
3. 微服务原则，独立部署
4. 协调器模式，统一编排

因此，服务设计遵循"一个智能体一个服务"的原则，同时增加了协调器和辅助服务以支撑整体架构。

## 各服务与智能体功能详细说明

### 智能体服务（8个脑区）

#### 1. health-state-assessment-service（智能体0，脑区0）- 健康状态判定服务

**核心目标**：判断"这个人，现在需要被当成'病人'对待吗？"

**主要功能**：
- **入口判定流程（P0模块）**：执行5步入口判定（接收输入、识别症状、方向澄清、危险信号检查、路径选择）
- **工作态判定**：区分健康管理态（wellness_mode）和临床诊疗态（clinical_mode）
- **风险评估**：症状严重程度评估、早期风险信号识别、红旗信号识别、风险等级计算（L1/L2/L3/L4）
- **健康管理计划生成**：在健康管理态时生成包含风险识别、生活方式建议、随访计划的健康管理方案

**在系统中的位置**：系统入口服务，所有用户请求的第一站

---

#### 2. clinical-parsing-service（智能体1，脑区A）- 病例理解服务

**核心目标**：将非结构化的患者信息转换为结构化的临床要素

**主要功能**：
- **医学概念识别**：从文本中提取症状、疾病、药物等医学概念
- **概念归一化**：将用户自然语言描述转换为医学标准概念（CUI/ICD/SNOMED）
- **结构化提取**：提取症状、体征、检查等结构化数据
- **多模态理解**：支持文本、图片等多种输入形式（调用OCR服务）
- **歧义表达判定与追问**：识别歧义表达，生成追问问题

**在系统中的位置**：结构化推理通道的起点，为后续诊断提供标准化输入

---

#### 3. dialog-service（智能体2，脑区B）- 对话服务

**核心目标**：提供像医生一样的主动对话、智能追问能力

**主要功能**：
- **信息缺口识别**：识别诊断所需但尚未收集的关键信息
- **智能追问生成**：基于信息缺口和诊断需求，生成有针对性的追问问题
- **自然语言理解（NLU）**：理解用户的自然语言输入，提取关键信息
- **自然语言生成（NLG）**：将结构化问题转换为自然语言表达
- **对话上下文管理**：维护对话历史，支持多轮对话

**在系统中的位置**：主动问诊通道，与病例理解服务配合完成信息收集

---

#### 4. diagnosis-engine-service（智能体3，脑区C）- 诊断引擎服务

**核心目标**：执行多引擎融合的鉴别诊断推理

**主要功能**：
- **五引擎融合诊断**：
  - 规则引擎：基于医学规则进行推理
  - 知识图谱引擎：基于知识图谱路径进行推理
  - 统计模型引擎：基于机器学习模型进行推理
  - LLM引擎：基于大语言模型进行推理（使用LangChain）
  - 鉴别诊断引擎：执行鉴别诊断分析
- **知识图谱推理**：基于DR.KNOWS知识图谱进行路径推理
- **三层分层分类器**：对疾病进行分层分类
- **证据分析**：分析支持诊断的证据，评估证据强度
- **结果融合**：融合多个引擎的诊断结果，生成最终诊断候选集（DDx）

**在系统中的位置**：诊断推理的核心，结构化推理通道的核心引擎

---

#### 5. workup-planner-service（智能体4，脑区D）- 检查建议服务

**核心目标**：基于当前DDx和已有证据，建议下一步检查，并评估检查的价值

**主要功能**：
- **检查价值评估**：评估各项检查对诊断的价值和必要性
- **信息增益计算**：计算检查结果对诊断的信息增益
- **检查优先级排序**：根据价值和信息增益对检查进行排序
- **验证计划构建**：制定验证诊断假设的检查计划

**在系统中的位置**：诊断流程中的检查建议环节，帮助确定下一步需要进行的检查

---

#### 6. treatment-engine-service（智能体5，脑区E）- 治疗推理服务

**核心目标**：基于诊断结果，生成治疗方案和处置建议

**主要功能**：
- **治疗方案推理**：基于诊断结果和患者情况，推理合适的治疗方案
- **药物推荐**：推荐合适的药物（研发阶段不涉及具体剂量）
- **非药物治疗建议**：提供生活方式、康复训练等非药物治疗建议
- **治疗计划构建**：构建完整的治疗计划

**在系统中的位置**：诊断流程的后续环节，提供治疗建议

---

#### 7. risk-assessment-service（智能体6，脑区F）- 风险评估服务

**核心目标**：识别高危情况，评估紧急程度，决定是否需要立即升级处理

**主要功能**：
- **高危识别**：识别高危疾病和危险信号
- **严重程度评估**：评估疾病的严重程度
- **紧急程度分级**：评估紧急程度，决定处理优先级
- **复评与升级规则**：制定复评计划，确定升级处理规则
- **终点结论包构建**：构建包含诊断、风险、建议的完整结论包

**在系统中的位置**：贯穿诊断流程，在多个环节进行风险评估

---

#### 8. explanation-service（智能体7，脑区G）- 解释生成服务

**核心目标**：生成完整的证据链，让系统的"结论"能被复核

**主要功能**：
- **证据链构建**：构建支持诊断的完整证据链
- **推理路径可视化**：可视化展示诊断推理路径
- **自然语言解释生成**：将证据链和推理路径转换为自然语言解释
- **可解释性增强**：提高系统诊断结果的可解释性和可信度

**在系统中的位置**：语言与策略通道，为诊断结果提供可解释性支持

---

### 协调器服务

#### diagnosis-service（协调器，非脑区）

**核心目标**：协调所有智能体服务，管理诊断流程

**主要功能**：
- **CDP管理**：创建、更新、版本控制、回放、回退临床决策包（CDP）
- **流程编排**：
  - 编排5步AI循证诊断流程（临床诊疗态）
  - 编排健康筛查流程（健康管理态，A路径A1-A5）
- **任务分配**：根据流程需要，调用相应的智能体服务
- **冲突解决**：处理多个服务之间的冲突和矛盾
- **状态管理**：管理CDP状态流转和诊断流程状态

**在系统中的位置**：位于所有AI服务的上层，作为协调中心

---

### 辅助服务

#### ocr-service（OCR服务）

**主要功能**：
- **图像识别**：识别医疗报告图片
- **报告OCR**：从图片中提取文字信息
- **结构化数据提取**：将OCR结果转换为结构化数据

**使用场景**：被 `clinical-parsing-service` 调用，支持多模态输入

---

#### examination-service（检查服务）

**主要功能**：
- **检查管理**：管理检查相关的业务逻辑
- **检查结果处理**：处理检查结果的存储和查询
- **业务服务层功能**：提供检查相关的业务服务

**技术栈**：Java服务
