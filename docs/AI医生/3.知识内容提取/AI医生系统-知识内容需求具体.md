# AI医生系统 - 知识内容需求

---

**说明**：本文档仅包含AI医生系统相关的知识内容需求。检查报告的详细解析功能（报告格式识别、指标提取、正常值判定、异常判定等）已独立为报告解读系统，详见《报告解读系统-知识内容需求.md》。

---

## 零、与《系统功能设计》《技术架构设计》的对齐补充（新增）

> **目的**：把“知识内容建设”与**八大脑区功能、两种工作态、CDP数据结构、微服务拆分与落库方式**对齐，避免知识建设与工程落地脱节。

### 0.1 范围与边界（必须明确）

- **本文件覆盖**：AI医生系统在健康管理态（A路径）与临床诊疗态（B路径）中，为“识别/归一化/结构化/推理/分流/验证/风险/解释/随访”提供支撑的知识内容。
- **本文件不覆盖**：检查报告的详细解析（格式识别、指标提取、正常值/异常判定等）——该能力归属“报告解读系统”。

### 0.2 架构对齐：八大脑区 ⇄ 微服务/智能体（工程落点）

| 微服务 | 对应脑区 | 说明（知识消费侧） |
|------|---------|------------------|
| `health-state-assessment-service` | 脑区0 | 消费：红旗信号库、工作态判定规则、入口判定规则、A路径升级条件等 |
| `clinical-parsing-service` | 脑区A | 消费：归一化词表（症状/疾病/药物/过敏/检查/指标）、歧义表达与追问规则 |
| `dialog-service` | 脑区B | 消费：主诉字段模板、伴随症状清单、缺口分级、追问题库、线索库、差异点词库等 |
| `diagnosis-engine-service` | 脑区C | 消费：DDx Universe、分层/子组/分流路径模板、证据条目库、KG/贝叶斯相关数据等 |
| `workup-planner-service` | 脑区D | 消费：检查项目库、验证计划库（含判定与回填规则） |
| `treatment-engine-service` | 脑区E | 消费：治疗方案推理规则库、非药物建议库 |
| `risk-assessment-service` | 脑区F | 消费：高危识别/严重度/紧急分级/复评与升级规则 |
| `explanation-service` | 脑区G | 消费：证据链构建/来源标注/不确定性表达/终点结论包模板 |
| `diagnosis-service`（Java） | 协调器 | 负责编排流程；在CDP层面读取/写入各脑区输出，确保可审计 |

### 0.3 CDP与知识版本审计（必须落到可追溯）

- **CDP是系统内部的唯一推理载体**：各脑区对CDP“读/写”，形成可回放轨迹。
- **知识版本必须可审计**：CDP的 `audit.knowledge_version` 必须能追溯到本文件所定义的知识内容版本（例如：`knowledge_version = YYYYMMDD-<tag>`）。

**CDP字段与落库形态（建议口径）**：

| CDP字段 | 建议落库形态 | 说明 |

| `wellness_plan` | `cdp.wellness_plan`（JSON） | 健康管理计划 |
| `patient_state` | `cdp.patient_state`（JSON） | 患者状态（结构化要素） |
| `ddx` | `cdp.ddx`（JSON） | 鉴别诊断列表 |
| `evidence_graph` | `cdp.evidence_graph`（JSON） | 证据图/证据清单 |
| `workup_plan` | `cdp.workup_plan`（JSON） | 检查/验证计划 |
| `management_plan` | `cdp.management_plan`（JSON） | 处置/治疗建议 |
| `triage` | `cdp.triage`（JSON） | 风险评估/升级条件 |
| `uncertainty` | `cdp.uncertainty`（JSON） | 不确定性来源与关键缺口 |
| `audit` | `cdp.audit`（JSON） | 模型/提示词/知识版本与推理轨迹 |

### 0.4 知识交付形态（内容组交付物要工程可用）

- **表类知识**：词表/规则库/模板库/映射表（建议以CSV/Excel维护，发布时固化为数据库表或配置文件）。
- **图谱类知识**：Neo4j知识图谱（节点/关系/权重/置信度），用于DR.KNOWS路径推理。
- **结构化模板**：用于对话追问、证据链、终点结论包的JSON模板（工程侧可直接序列化入CDP）。

### 0.6 知识生产与发布流程（建议写入执行规范）

- **内容建设**：内容组产出（词表/规则/模板/图谱数据）→ 医学专家审核 → 工程侧格式校验（字段、枚举、编码映射）  
- **发布**：生成版本号 → 写入数据库/图谱 → 回归评测（静态病例集/交互问诊集/轨迹回放集）→ 上线  
- **回滚**：发现风险（红旗漏识别、Must-not-miss缺失、证据链错误）可按 `knowledge_version` 快速回滚

## 一、脑区0：健康状态判定服务（Health State Assessment Service）

**服务说明**：判断"这个人，现在需要被当成'病人'对待吗？"，这是医生的第一职责，发生在"诊断之前"。

| 序号 | 知识内容名称 | 作用说明 |
|-----|------------|---------|
| **0.1** | **红旗信号库（主诉特异）** | **作用**：定义每个主诉下出现哪些症状组合时必须立即就医，不能继续在线诊断。<br>**举例**：对于"胸痛"，如果同时出现"意识模糊"或"生命体征异常"（如血压很低、心率很快），就触发红旗条件，立即进入临床诊疗态并建议急诊。<br>**内容组需要准备**：为每个常见主诉列出高危症状组合清单，比如"胸痛+意识改变"、"发热+呼吸困难"等。 |
| **0.2** | **工作态判定规则库** | **作用**：定义什么情况下进入健康管理态，什么情况下进入临床诊疗态。<br>**举例**：出现红旗信号 → 立即进入临床诊疗态；症状严重程度高或风险等级≥L2 → 进入临床诊疗态；症状在正常范围且风险等级低（L3/L4） → 进入健康管理态。<br>**内容组需要准备**：定义工作态判定的具体规则和阈值，包括症状严重程度、风险等级、信息完整度等维度的判定标准。 |
| **0.3** | **症状/困扰识别规则库** | **作用**：定义如何识别用户是否有症状/困扰，用于入口判定Step 2。<br>**举例**：能识别"症状/不适/困扰/异常感觉/功能变化"等表达；轻微问题也算"有困扰"，不要求严重程度；能识别"明确无症状"的表达（纯筛查/纯体检规划）。<br>**内容组需要准备**：整理症状/困扰识别的关键词库、识别规则（如何判断用户是否有症状/困扰）、健康管理/体检规划的关键词库（如何判断用户是否无症状）。 |
| **0.4** | **方向澄清模板库** | **作用**：定义如何对"不确定/模糊/混合诉求"进行方向澄清，用于入口判定Step 3。<br>**举例**：用户说不清是否算不适，或同时说"想体检 + 有点不舒服"，系统需要生成最小澄清问题（仅一次），根据用户回答确定方向（A健康筛查或B症状诊断）。<br>**内容组需要准备**：整理方向澄清问题模板（用于不确定/模糊/混合诉求场景）、答案选项、方向映射规则（答案到方向的映射：进入A或进入B）。 |
| **0.5** | **入口判定路径选择规则库** | **作用**：定义入口判定Step 5的路径选择规则，决定进入A路径（健康筛查）还是B路径（症状诊断）或退出线上流程。<br>**举例**：无症状 + 无危险信号 → 进入健康筛查路径（A）；有症状/困扰 + 无危险信号 → 进入症状诊断路径（B）；危险信号命中 → 退出线上流程（安全提示）。<br>**内容组需要准备**：定义路径选择规则（基于症状状态、危险信号检查结果的路径选择逻辑）、跳转规则（A路径跳转到A1需求分类，B路径跳转到Step 1识别问题）。 |

## 一（续）、健康管理态（A路径）知识内容需求

**服务说明**：健康管理态面向无症状或不确定健康状态的人群，提供健康筛查、体检规划、健康管理等服务。

| 序号 | 知识内容名称 | 作用说明 |
|-----|------------|---------|
| **0.6** | **需求分类规则库（A1）** | **作用**：定义如何将用户需求归入三类之一（筛查建议/健康目标管理/计划性健康需求），用于A1需求分类。<br>**举例**：用户说"我想做个体检" → 归类为筛查建议（需求1）；用户说"我想减肥" → 归类为健康目标管理（需求2）；用户说"我要备孕" → 归类为计划性健康需求（需求3）。<br>**内容组需要准备**：整理三类需求的关键词库、用户常见表达归类示例、不确定时的引导话术、需求分类规则（如何判断用户需求属于哪一类）。 |
| **0.7** | **健康档案字段清单（A2）** | **作用**：定义通用最小健康档案需要采集的字段，用于A2通用最小健康档案。<br>**举例**：基本信息（年龄、性别、身高、体重）、既往史（疾病史、手术史、过敏史）、家族史（遗传疾病史）、生活习惯（吸烟、饮酒、运动、饮食）、用药史（当前用药、既往用药）。<br>**内容组需要准备**：定义健康档案采集字段清单（字段名称、字段类型、是否必填、标准问法）、低信息模式兜底话术（缺失不阻塞仍能输出）、缺失字段提示与补充策略（可选）。 |
| **0.8** | **筛查建议规则库（A3-1）** | **作用**：定义筛查建议分支的规则，用于A3-1筛查建议分支。<br>**举例**：按年龄段、性别、风险因素推荐筛查项目；包含筛查频率和时机；反过度筛查理由和替代建议。<br>**内容组需要准备**：整理条件触发筛查规则库（什么条件→建议哪些筛查→大致频率/时机）、推荐筛查清单（按年龄段、性别、风险因素）、不推荐筛查清单（反过度筛查理由与替代建议）、输出数量与排序规则（推荐/不推荐各输出多少条）、强烈要求检查时的标准回应话术。 |
| **0.10** | **健康目标管理模板库（A3-3）** | **作用**：定义健康目标管理分支的模板，用于A3-3健康目标管理分支。<br>**举例**：目标类型（减脂/睡眠/运动/精力）、行动计划模板、追踪指标建议（2-3个关键指标）、复盘节点。<br>**内容组需要准备**：整理健康目标类型清单、固定追问清单（目标/现状/资源/周期）、目标计划模板库（按目标类型复用）、追踪指标建议库（2-3个关键指标即可）、复盘节点设置规则、失败兜底调整话术。 |
| **0.11** | **计划性健康需求场景库（A3-4）** | **作用**：定义计划性健康需求分支的场景清单，用于A3-4计划性健康需求分支。<br>**举例**：场景类型（备孕/疫苗/差旅/材料等）、检查清单、时间表、注意事项。<br>**内容组需要准备**：整理场景类型清单、固定追问清单（场景/时间点/禁忌信息）、场景清单库（每个场景的检查清单+时间表+注意事项）、场景节点提醒规则（什么时候提醒更新）。 |
| **0.12** | **统一结果页模板库（A4）** | **作用**：定义统一结果页的输出格式，用于A4统一结果页输出。<br>**举例**：一句话总结、现在建议做的事（清单）、暂时不建议做的事（清单）、下一次复查/更新时间点、退出A路径条件提示（出现不适/危险信号→线下评估）。<br>**内容组需要准备**：整理一句话总结模板（按需求类型）、推荐/不推荐展示话术模板、退出A路径提醒文案（出现不适/危险信号→线下评估）。 |
| **0.13** | **健康管理态随访规则库（A5）** | **作用**：定义健康管理态的随访节奏规则，用于A5随访闭环。<br>**举例**：筛查建议 → 周期性更新档案；目标管理 → 按复盘节点回访更新；计划性需求 → 按场景节点提醒更新/完成任务。<br>**内容组需要准备**：整理随访节奏规则（按需求类型：筛查建议/目标管理/计划性需求的随访规则）、随访提醒话术（按节点提醒用户更新/复查/复盘）。 |
| **0.14** | **健康管理态升级条件库** | **作用**：定义健康管理态升级到临床诊疗态的条件，用于持续监控和升级判断。<br>**举例**：症状加重、出现新症状、识别到风险信号（红旗信号）、生命体征异常。<br>**内容组需要准备**：整理升级触发条件清单（症状加重、新症状出现、风险信号、生命体征异常等）、升级判断规则（什么情况下需要升级到临床诊疗态）、升级处理方式（如何切换到临床诊疗态流程）。 |

## 二、脑区A：病例理解与结构化服务（Clinical Parsing Service）

**服务说明**：将非结构化的患者信息转换为结构化的临床要素，包括医学概念识别、概念归一化、结构化提取。

| 序号 | 知识内容名称 | 作用说明 |
|-----|------------|---------|
| **1.1** | **症状归一化词表** | **作用**：将患者说的各种口语化表达转换成医学标准术语，让系统能理解患者的意思。<br>**举例**：患者说"胸口闷"、"走几步就喘"，系统要能识别出这是"胸闷样不适"和"活动后气促"。如果患者说"胸痛"这种模糊词，系统要知道需要进一步追问疼痛的性质。<br>**内容组需要准备**：整理常见症状的口语化表达和标准医学术语的对应关系，包括同义表达、歧义表达的判定规则，映射到CUI/ICD/SNOMED编码。 |
| **1.2** | **疾病名称归一化词表** | **作用**：将患者说的疾病名称转换成标准医学术语，用于既往史、家族史的识别。<br>**举例**：患者说"血压高"、"血糖高"，系统要识别为"高血压病"、"2型糖尿病"；患者说"心脏病"需要进一步追问是哪种心脏病。<br>**内容组需要准备**：整理疾病名称的常见表达和标准术语的对应关系，包括同义词、别名、口语化表达等，映射到CUI/ICD/SNOMED编码。 |
| **1.3** | **药物名称归一化词表** | **作用**：将患者说的药物名称、商品名/俗称统一为标准药物名称（用于用药史识别、风险提示与处置建议的禁忌校验）。<br>**举例**：患者说"阿司匹林肠溶片"、"拜阿司匹灵"、"吃了抗生素（头孢）"，系统要能识别为标准药物概念，并尽量映射到通用名/ATC（或可选：RxNorm/CUI）。<br>**内容组需要准备**：整理常见药物的商品名/别名/缩写与标准名映射；整理药物类别（抗生素/NSAIDs/降压药等）与关键禁忌提示字段（可后续扩展）。 |
| **1.4** | **过敏源归一化词表** | **作用**：将患者说的过敏源转换成标准医学术语，用于过敏史的识别。<br>**举例**：患者说"青霉素过敏"、"海鲜过敏"，系统要识别为"青霉素类抗生素过敏"、"海产品过敏"等标准术语。<br>**内容组需要准备**：整理过敏源的常见表达和标准术语的对应关系，包括药物过敏、食物过敏、环境过敏等。 |
| **1.5** | **检查项目归一化词表** | **作用**：将不同医院使用的不同检查项目名称统一成标准名称，确保系统能正确识别检查项目（用于检查建议和验证计划）。<br>**举例**：不同医院可能用"血常规"、"血象"、"血细胞分析"等不同名称，系统都要能识别为"血常规检查"这个标准名称。<br>**内容组需要准备**：整理每个检查项目的标准名称、标准编码、同义名称（包括不同医院、不同地区的用法）。<br><br>**注意**：检查报告的详细解析（报告格式识别、指标提取等）由独立的报告解读系统负责，详见《报告解读系统-知识内容需求.md》。 |
| **1.6** | **指标名称归一化词表** | **作用**：将不同医院使用的不同指标名称统一成标准名称，确保系统能正确识别检查指标（用于理解检查结果和验证计划）。<br>**举例**：不同医院可能用"白细胞"、"白细胞计数"、"WBC"、"White Blood Cell"等不同名称，系统都要能识别为"白细胞"这个标准名称。<br>**内容组需要准备**：整理每个检查指标的标准名称、标准编码、同义名称（包括不同医院、不同地区的用法），以及单位映射关系。<br><br>**注意**：检查报告的详细解析（报告格式识别、指标提取、正常值判定、异常判定等）由独立的报告解读系统负责，详见《报告解读系统-知识内容需求.md》。 |
| **1.7** | **歧义表达判定与追问规则库** | **作用**：定义如何识别歧义表达，以及如何追问澄清。<br>**举例**：患者说"胸闷"，可能是"呼吸困难"、"心悸"、"压迫感"等，系统需要追问："您说的胸闷是指呼吸费力、心跳快还是感觉有压迫感？"；患者说"胸痛"这种模糊词，系统要知道需要进一步追问疼痛的性质、部位、持续时间等。对于"肚子疼"，需要追问具体位置（上腹/下腹/全腹）、性质（绞痛/钝痛/胀痛）等。<br>**内容组需要准备**：整理常见歧义表达及其可能的含义，定义判定规则（什么情况下判定为歧义），以及对应的追问策略和标准问法。包括：歧义表达识别规则（如何判断一个表达是歧义的）、可能含义列表（每个歧义表达可能的2-5种含义）、追问策略（如何追问澄清）、标准澄清问法（针对每个歧义表达的标准追问方式）。 |

## 三、脑区B：主动问诊与信息补全服务（Interview / Gap-Filling Service）

**服务说明**：像医生一样问"关键问题"，补齐鉴别诊断所需证据，基于信息增益决定问什么问题。

| 序号 | 知识内容名称 | 作用说明 |
|-----|------------|---------|
| **2.1** | **主诉关键字段模板（主诉特异）** | **作用**：定义每个主诉（如胸痛、发热）需要收集哪些关键信息，以及如何问这些问题。<br>**举例**：对于"胸痛"，必须收集的信息包括：起病时间（"疼痛持续多久了？"）、起病方式（"是突然出现的还是慢慢加重的？"）、严重程度（"0-10分，您觉得疼痛是几分？"）、症状性质（"疼痛是什么性质的？是钝痛、刺痛还是压榨感？"）等。<br>**内容组需要准备**：为每个常见主诉列出必须收集的字段清单，以及每个字段的标准问法。字段包括：起病时间、起病方式、持续时间、严重程度、症状性质、部位/范围/放射、诱因/缓解因素等。 |
| **2.2** | **伴随症状清单（主诉特异）** | **作用**：定义与主诉相关的、最能帮助判断疾病方向的伴随症状，以及如何询问这些症状。<br>**举例**：对于"胸痛"，需要询问是否伴有"出汗"、"恶心"、"呼吸困难"、"咳血"等。如果患者说"胸痛伴出汗"，这提示可能是心血管疾病（如心梗、心绞痛）。<br>**内容组需要准备**：为每个主诉列出重要的伴随症状清单，每个症状的标准问法，以及这个症状对诊断方向的影响（支持哪些疾病方向）。 |
| **2.3** | **关键背景字段（主诉特异 + 全局通用）** | **作用**：定义需要收集的患者背景信息，包括年龄、性别、既往史、用药史、过敏史、暴露史、家族史等，以及如何询问这些信息。<br>**举例**：对于"胸痛"，需要询问年龄（"您今年多大年纪？"）、性别、既往史（"您有没有高血压、冠心病、糖尿病等疾病？"）、用药史（"您最近在吃什么药？"）、暴露史（"最近有没有旅行、接触过感染病人、做过手术、长时间坐着或躺着、受过外伤？"）等。<br>**内容组需要准备**：列出全局通用字段（年龄、性别）和主诉特定字段（既往史、用药史等）的标准问法，以及这些信息对诊断的影响。 |
| **2.4** | **信息缺口分级规则（主诉特异）** | **作用**：定义哪些信息是必须的（缺失就不能诊断），哪些是重要的（缺失会影响准确性），哪些是可选的（后续补充即可）。<br>**举例**：对于所有主诉，"主诉"、"起病时间"、"严重程度"都是必填的；"伴随症状"、"既往史"是重要的；"详细生活方式信息"是可选的。<br>**内容组需要准备**：定义通用必填项、主诉特定必填项、重要项、可选项的清单，以及信息完整度计算规则（例如：≥60%且无必填缺口才能进入诊断分析）。 |
| **2.5** | **智能追问题库（按缺口映射）** | **作用**：当发现患者信息不完整时，系统知道如何追问，以及如何处理患者说"不知道"、"记不清"等不确定回答。<br>**举例**：如果患者没有说疼痛持续多久，系统会问"疼痛持续多久了？"；如果患者说"记不清"，系统会标记为不确定，但继续问其他必填项；如果患者拒绝回答，系统会提示风险并建议线下就医。<br>**内容组需要准备**：定义每个必填/重要字段的标准问法（引用主诉关键字段模板），以及处理不确定回答的方式（标记为缺口、继续追问、建议线下就医等）。 |
| **2.6** | **主诉关键线索库** | **作用**：为每个主诉沉淀可复用的关键线索，用于问诊和证据分析。包括差异点线索、阳性线索、关键阴性线索。<br>**举例**：对于"胸痛"和"急性心肌梗死"这个方向，"胸痛伴大汗"是强阳性线索（权重1.0），出现这个线索应该推动心梗方向前移；"无明显出汗"是中等阴性线索（权重0.7），出现这个线索应该推动心梗方向后移；"症状持续时间短（<5分钟）"是强阴性线索（权重1.0），因为心梗通常持续时间>30分钟。<br>**内容组需要准备**：为每个主诉和疾病方向整理三种类型的线索：差异点线索（能最快区分诊断方向）、阳性线索（能显著支持某一方向）、关键阴性线索（能显著削弱某一方向）。每条线索包含：线索名称、类型、获取方式（追问：通过问诊获得；观察：通过观察患者状态获得；设备测量：通过设备测量获得，如体温、血压；线下检查：通过线下检查获得，如心电图、血常规）、标准问法、答案选项、判定规则、推理动作。 |
| **2.7** | **差异点词库与问法规范** | **作用**：统一差异点的问法和答案选项，保证不同用户输入可比。<br>**举例**：差异点"是否突发"，标准问法："症状是突然出现的还是慢慢加重的？"，答案选项：["突然出现", "慢慢加重", "不确定"]，判定规则：突然出现 → 支持急性疾病；慢慢加重 → 支持慢性疾病。阈值表达：<1周为急性、≥1周为慢性。<br>**内容组需要准备**：整理差异点词库，包括差异点名称、标准问法、答案选项、阈值表达（如<1周为急性、≥1周为慢性），确保不同用户输入可比。 |
| **2.8** | **生命体征正常值范围库** | **作用**：定义血压、心率、体温、血氧饱和度等生命体征的正常值范围，用于判断患者体征是否异常。<br>**举例**：成人血压正常范围是收缩压90-140mmHg、舒张压60-90mmHg；心率正常范围是60-100次/分；体温正常范围是36.0-37.2℃；血氧饱和度正常范围是95-100%。<br>**内容组需要准备**：整理各种生命体征在不同年龄、性别下的正常值范围，以及异常判定标准。 |
| **2.9** | **临床决策分析驱动的问诊规则库** | **作用**：定义基于临床决策理论（Clinical Decision Analysis, CDA）的问诊策略，包括信息增益、风险增益、成本效益的计算规则，用于临床决策分析驱动的问诊。<br>**举例**：临床决策增益计算公式：IG_clinical(q|DDx, E) = IG_information(q|DDx, E) + α · IG_risk(q|DDx, E) + β · IG_cost(q|DDx, E)，其中IG_information是信息论的信息增益，IG_risk是风险相关的信息增益（优先问能排除高危诊断的问题），IG_cost是成本效益相关的信息增益。权重设置：α = 0.5（风险权重较高），β = 0.2（成本权重较低），信息增益权重 = 0.3（基础权重）。<br>**内容组需要准备**：定义临床决策增益计算公式、信息增益计算规则（如何计算问题能减少多少诊断不确定性）、风险增益计算规则（如何计算问题能排除多少高危诊断）、成本效益计算规则（如何计算问题的成本效益比）、权重设置规则（α、β、信息增益权重的设置依据和标准值）。 |

## 四、脑区C：鉴别诊断引擎（Differential Diagnosis Engine）

**服务说明**：生成Top-K鉴别诊断列表，包括多引擎融合、推理子组组织、分流路径设计、证据分析等。

| 序号 | 知识内容名称 | 作用说明 |
|-----|------------|---------|
| **3.1** | **规则引擎 - 症状组合规则库** | **作用**：定义"出现哪些症状组合，可能是什么疾病"的规则，让系统能快速匹配可能的疾病方向。<br>**举例**：如果患者有"胸痛+出汗+气短"这个症状组合，系统会匹配到"急性心肌梗死"这个疾病方向，置信度0.9；如果患者有"胸痛+活动后加重"，系统会匹配到"心绞痛"，置信度0.7。<br>**内容组需要准备**：整理常见症状组合与疾病的对应关系，包括症状组合、疾病名称、置信度、典型体征、典型背景等。<br><br>**症状-疾病对应关系要求**：内容组需要建立症状-疾病映射表，明确列出每个症状或症状组合可能对应的疾病。格式要求：<br>- **症状/症状组合**：单个症状（如"胸痛"）或症状组合（如"胸痛+出汗+气短"）<br>- **对应疾病列表**：该症状或症状组合可能对应的疾病，按置信度/权重排序<br>- **典型体征**：该症状组合在该疾病中的典型体征表现<br>- **典型背景**：该症状组合在该疾病中的典型患者背景（年龄、性别、既往史等）<br><br>**示例**：<br>- 症状组合："胸痛+出汗+气短" → 急性心肌梗死、心绞痛<br>- 症状组合："胸痛+活动后加重" → 心绞痛、急性心肌梗死<br>- 单个症状："胸痛" → 心绞痛、胃食管反流、急性心肌梗死、焦虑症等<br><br>**填写要求**：<br>1. 为常见症状和症状组合建立症状-疾病映射表<br>2. 每个症状组合至少列出1-3个最可能的疾病方向<br>4. 需要同时考虑正向映射（症状→疾病）和反向映射（疾病→典型症状组合） |
| **3.2** | **知识图谱引擎 - Neo4j知识图谱** | **作用**：建立症状、疾病、检查、体征、药物等医学概念之间的关系网络，让系统能通过关系推理发现可能的疾病。<br>**举例**：在知识图谱中，"胸痛"这个症状节点与"心绞痛"、"急性心肌梗死"、"胃食管反流"等疾病节点有"引起"关系，权重和置信度不同。系统可以根据这些关系推理出可能的疾病方向。<br>**内容组需要准备**：整理症状、疾病、检查、体征、药物等概念之间的关系，包括关系类型（引起、诊断、治疗、相关等）、权重、置信度等。需要构建Neo4j知识图谱。 |
| **3.2.1** | **疾病患病率数据库** | **作用**：存储疾病的患病率数据，用于知识图谱推理引擎的贝叶斯评分体系中的先验概率评分（Prior Probability Score）。<br>**举例**：心绞痛在55岁男性中的患病率约为3%，急性心肌梗死在55岁男性中的患病率约为0.5%。系统根据疾病患病率和患者特征（年龄、性别、地区等）计算先验概率。<br>**内容组需要准备**：整理各种疾病在不同年龄组、性别、地区下的患病率数据，包括疾病CUI编码、年龄组、性别、地区、患病率、数据来源等。数据需要来自流行病学调查或权威医学数据库。 |
| **3.2.2** | **诊断试验敏感性/特异性数据库** | **作用**：存储诊断试验的敏感性和特异性数据，用于知识图谱推理引擎的贝叶斯评分体系中的似然评分（Likelihood Score）。<br>**举例**：心电图ST段抬高对急性心肌梗死的敏感性约为90%，特异性约为95%；"胸痛伴出汗"对急性心肌梗死的敏感性约为70%，特异性约为80%。系统根据诊断试验的敏感性和特异性计算似然评分。<br>**内容组需要准备**：整理各种证据（症状组合、体征、检查结果）对不同疾病的敏感性和特异性数据，包括证据名称、疾病CUI编码、敏感性、特异性、证据类型（客观检查异常/典型症状组合/主观描述）、数据来源等。数据需要来自临床研究或医学指南。 |
| **3.2.3** | **贝叶斯更新规则库** | **作用**：定义如何基于贝叶斯定理计算后验概率，用于知识图谱推理引擎的贝叶斯评分体系中的后验概率评分（Posterior Probability Score）。<br>**举例**：当患者有"胸痛伴出汗"这个证据时，系统根据贝叶斯定理P(D|E) = (P(E|D) · P(D)) / P(E)计算急性心肌梗死的后验概率，其中P(D)是先验概率，P(E|D)是似然（敏感性），P(E)是证据的边际概率。<br>**内容组需要准备**：定义贝叶斯更新计算公式、多证据联合似然的计算规则、证据边际概率的计算方法、权重设置规则（先验概率权重0.2、似然权重0.3、后验概率权重0.5）。 |
| **3.3** | **统计模型引擎 - 历史诊断数据** | **作用**：基于大量历史诊断数据训练统计模型，当输入患者症状、体征、背景信息时，模型能预测可能的疾病及其概率。<br>**举例**：如果历史数据中，有1000个"55岁男性+胸痛+出汗+气短+高血压史"的案例，其中800个最终诊断为"心绞痛"，那么当遇到类似患者时，模型会预测"心绞痛"的概率较高。<br>**内容组需要准备**：提供历史诊断数据，包括症状、体征、检查结果、最终诊断、患者画像（年龄、性别、既往史）等，数据量建议≥10000条，需要经过医学专家审核。 |
| **3.4** | **鉴别诊断引擎 - 鉴别诊断规则库** | **作用**：定义如何区分相似的疾病，提供鉴别诊断的要点，帮助系统区分容易混淆的疾病。<br>**举例**：对于"心绞痛"和"急性心肌梗死"这对容易混淆的疾病，鉴别要点包括：疼痛持续时间（心绞痛<30分钟，心梗>30分钟）、严重程度（心绞痛中等，心梗剧烈）、伴随症状（心绞痛出汗气短轻度，心梗大汗恶心气短重度）、心电图（心绞痛ST段压低或正常，心梗ST段抬高）等。<br>**内容组需要准备**：整理常见疾病对的鉴别要点，包括每个要点在两个疾病中的不同特征，以及每个要点的权重。 |
| **3.6** | **主诉级鉴别诊断模板库（DDx Universe）** | **作用**：为常见主诉（如胸痛、发热）预先定义**默认三层候选集（DDx Universe）**，要求覆盖三类：常见原因、易混淆原因、严重但不能漏诊原因（must-not-miss）。对每个主诉都要能输出：首要假设（1-2）、主要备选（2-5）、必须排除（1-3）。<br>**举例**：对于"胸痛"，默认三层候选集包括：首要假设可能是"心绞痛"（如果症状典型）、"胃食管反流"（如果症状不典型）；主要备选可能是"焦虑症"、"胸膜炎"、"肺炎"等；必须排除的是"急性心肌梗死"（即使概率不高，但一旦漏诊后果严重，必须优先排除）。每个候选需要明确：入选依据（来自问题清单哪些线索）、典型症状组合、典型体征、典型背景、当前缺口（推进/排除所需的关键缺失）。<br>**内容组需要准备**：为每个常见主诉整理**DDx Universe（鉴别诊断全集）**，包括：三层诊断方向的默认候选集合（首要假设1-2、主要备选2-5、必须排除1-3），每个疾病的入选依据（来自问题清单哪些线索）、典型症状组合、典型体征、典型背景、当前缺口（推进/排除所需的关键缺失）。要求覆盖：常见原因、易混淆原因、严重但不能漏诊原因（must-not-miss）。<br><br>**主诉-疾病对应关系要求**：内容组需要为每个主诉建立主诉-疾病映射表，明确列出该主诉对应的所有候选疾病。格式要求：<br>- **主诉名称**：标准主诉术语（如"胸痛"、"发热"、"腹痛"等）<br>- **首要假设（1-2个疾病）**：最可能的方向，症状典型时优先考虑<br>- **主要备选（2-5个疾病）**：常见备选方向，症状不典型时考虑<br>- **必须排除（1-3个疾病）**：高危疾病，即使概率不高也必须优先排除<br>- **疾病总数**：该主诉对应的所有候选疾病数量（首要假设+主要备选+必须排除，建议控制在6-12个）<br>- **优先级**：高/中/低，用于确定填写顺序<br><br>**示例**：对于"胸痛"主诉，主诉-疾病映射表如下：<br>- 首要假设：心绞痛、胃食管反流<br>- 主要备选：焦虑症、胸膜炎、肺炎、肌肉拉伤、胸壁炎<br>- 必须排除：急性心肌梗死、主动脉夹层、肺栓塞<br>- 疾病总数：10个疾病<br>- 优先级：高<br><br>**填写要求**：<br>1. 每个主诉必须建立完整的主诉-疾病映射表<br>2. 三层候选集必须覆盖：常见原因、易混淆原因、严重但不能漏诊原因（must-not-miss）<br>3. 所有疾病必须使用标准医学术语，并映射到ICD/SNOMED/CUI编码<br>4. 填写完成后需经过医学专家审核验证 |
| **3.7** | **分层规则库** | **作用**：定义什么情况下一个疾病可以进入"首要假设"（最可能方向），什么情况下必须进入"必须排除"（高危方向）。<br>**举例**：一个疾病要成为"首要假设"，需要满足：可能性分数最高、症状组合匹配度≥70%、支持证据数量≥3、关键背景匹配。一个疾病要进入"必须排除"，需要满足：一旦漏诊后果严重、即使概率不高（≥0.1）也必须纳入、存在高危线索或高危背景。<br>**内容组需要准备**：定义首要假设规则、主要备选诊断规则、必须排除的高危诊断规则的具体条件。 |
| **3.8** | **推理子组组织规则库** | **作用**：定义如何将候选方向按维度（系统来源、病程、诱因等）组织为推理子组。<br>**举例**：对于"胸痛"，可以按系统来源组织为：心血管相关（心绞痛、心梗）、呼吸系统相关（肺炎、胸膜炎）、消化系统相关（胃食管反流）、其他（焦虑症）。一条关键问题（如"疼痛是否活动后加重？"）能推动整个心血管子组前移或后移。<br>**内容组需要准备**：为每个主诉定义推理子组的组织方式（按哪个维度组织最有效），包括子组名称、包含的候选方向、子组入选依据、子组的关键差异点、子组的高危触发条件等。 |
| **3.9** | **分流路径模板库** | **作用**：为每个高频主诉沉淀分流路径模板，定义如何通过分叉式问诊快速区分诊断方向，逐步缩小候选疾病范围。<br>**举例**：对于"胸痛"，第一个分叉问题是"疼痛是急性还是慢性？"（<1周为急性，≥1周为慢性）。如果答案是"急性"，系统会继续问"疼痛是否活动后加重？"；如果答案是"慢性"，系统会问"疼痛是否与进食有关？"。通过这样的分叉问题，系统能快速区分是心血管疾病还是消化系统疾病等。<br>**内容组需要准备**：为每个高频主诉设计分流路径模板，包括推理子组结构、第一层分叉问题、高危触发条件与优先路径、继续收缩步骤、每个分叉结果对应的诊断方向等。 |
| **3.10** | **关键分岔点（Pivotal Points）清单** | **作用**：定义保证"任何主诉都能分流推进"的关键分岔点，这些分岔点是互斥的（如急性vs慢性），用于快速分流诊断方向。<br>**举例**：对于"胸痛"，关键分岔点包括："急性vs慢性"（<1周为急性，≥1周为慢性）、"活动诱发vs静息也发生"、"单侧vs双侧"、"发热vs无发热"、"进行性加重vs稳定/波动"等。如果患者是"急性胸痛"，系统会优先考虑急性心血管事件；如果是"慢性胸痛"，系统会优先考虑非急性疾病。<br>**内容组需要准备**：为每个主诉整理关键分岔点清单，包括分岔点名称、互斥对、判定条件、标准问法、命中后推动的方向等。 |
| **3.11** | **证据条目库（支持证据清单 + 反对证据清单）** | **作用**：为每个疾病方向定义支持证据和反对证据条目，用于证据分析和诊断推理。把证据做成可复用条目，每条包含：证据名称、证据类型、证据强度、权重、特异性、证据来源、影响对象等。<br>**举例**：对于"急性心肌梗死"，支持证据包括：<br>• "胸痛伴出汗"<br>• "心电图ST段抬高"<br>• "老年男性"<br>反对证据包括：<br>• "无出汗"<br>• "症状持续时间短（<5分钟）"<br>• "心电图正常"<br>**内容组需要准备**：为每个疾病方向整理支持证据清单和反对证据清单，每条证据包含：证据名称、证据类型（症状组合/检查结果/体征/用户画像）、特异性（高/中/低）、证据来源（追问/观察/设备测量/线下检查）、获取方式（如何获取该证据）、影响对象（推动哪个方向上移/下移）、判定规则（什么情况下该证据生效）。<br><br>**格式要求**：<br>- **支持证据清单**：列出所有能支持该疾病的证据条目<br>- **反对证据清单**：列出所有能削弱或排除该疾病的证据条目<br>- **特异性分级**：极高（仅见于该疾病）、高（多见于该疾病）、中（多个疾病都可能出现）、低（非特异性，多个疾病都可能出现） |
| **3.12** | **鉴别诊断差异点表（Diff Table：A vs B）** | **作用**：用于"最快分清两个方向"的差异点表，针对疾病对（如"心绞痛 vs 急性心肌梗死"）定义最能区分的3-5个差异点，以及对应问法/体征/测量/检查项。<br>**举例**：对于"心绞痛 vs 急性心肌梗死"这对疾病，差异点表包括：差异点1-疼痛持续时间（心绞痛<30分钟，心梗>30分钟，对应问法："疼痛持续多久了？"）；差异点2-严重程度（心绞痛中等，心梗剧烈，对应问法："疼痛程度如何？0-10分"）；差异点3-伴随症状程度（心绞痛出汗气短轻度，心梗大汗恶心气短重度，对应问法："是否伴有大汗、恶心？"）；差异点4-心电图表现（心绞痛ST段压低或正常，心梗ST段抬高，对应检查：心电图）。<br>**内容组需要准备**：为每对容易混淆的疾病整理差异点表（Diff Table），包括：差异点名称、两个疾病在该差异点上的不同特征、对应问法/体征/测量/检查项、判定规则（如何根据差异点区分两个疾病）。每个疾病对至少需要3-5个差异点，优先选择最能快速区分的高权重差异点。 |

## 五、脑区D：检查/检验建议与价值评估服务（Workup Planner Service）

**服务说明**：基于当前DDx和已有证据，建议下一步检查，并评估检查的价值，制定验证计划。

| 序号 | 知识内容名称 | 作用说明 |
|-----|------------|---------|
| **4.1** | **检查项目库** | **作用**：定义所有可用的检查项目，包括检查名称、检查类型、检查目的、适用疾病等。<br>**举例**：心电图（检查类型：辅助检查，检查目的：诊断心血管疾病，适用疾病：心绞痛、心梗、心律失常等）。<br>**内容组需要准备**：整理所有检查项目的标准信息，包括检查名称、类型、目的、适用疾病、检查成本、检查风险等。 |
| **4.2** | **验证计划库** | **作用**：定义如何验证某个疾病方向，包括是否需要验证、需要做什么检查、需要问什么问题、如何判定验证结果。<br>**举例**：对于"急性心肌梗死"这个必须排除的方向，验证计划包括：优先检查"心电图"和"心肌酶"，关键问题"疼痛是否持续不缓解？"、"是否伴有大汗、恶心？"。如果心电图显示ST段抬高或心肌酶升高，则支持心梗诊断，必须升级处理；如果心电图正常且心肌酶正常且症状已缓解，则不支持心梗诊断，可以排除。<br>**内容组需要准备**：为每个疾病方向（特别是最可能方向和必须排除方向）设计验证计划，包括查不查（是否需要验证）、查什么（检查/问题/观察）、判定标准（什么结果支持/不支持/不确定）、结果回填规则（如何更新三层排序）。<br><br>**注意**：检查报告的详细解析（报告格式识别、指标提取、正常值判定、异常判定等）由独立的报告解读系统负责，详见《报告解读系统-知识内容需求.md》。 |

## 六、脑区E：治疗/处置建议引擎（Management Planner Service）

**服务说明**：基于诊断结果，生成治疗方案和处置建议，包括对症处理、用药建议、非药物治疗建议等。

| 序号 | 知识内容名称 | 作用说明 |
|-----|------------|---------|
| **5.1** | **治疗方案推理规则库** | **作用**：定义如何基于疾病类型、严重程度推理治疗方向。<br>**举例**：对于"心绞痛"，治疗方案方向包括：抗心绞痛药物（硝酸甘油、β受体阻滞剂等）、生活方式改善（避免剧烈活动、控制危险因素）、必要时介入治疗等。<br>**内容组需要准备**：为每个疾病整理治疗方案推理规则，包括疾病类型、严重程度、治疗方案方向（不涉及具体用药剂量，研发阶段）。 |
| **5.2** | **非药物治疗建议库** | **作用**：定义生活方式、饮食、运动等非药物治疗建议。<br>**举例**：对于"心绞痛"，非药物治疗建议包括：避免剧烈活动、控制体重、戒烟限酒、规律作息、低盐低脂饮食等。<br>**内容组需要准备**：为每个疾病整理非药物治疗建议，包括生活方式改善、饮食建议、运动建议、环境调整等。 |

## 七、脑区F：风险与急症识别服务（Triage / Safety Brain Service）

**服务说明**：识别高危情况，评估紧急程度，决定是否需要立即升级处理，包括复评与升级规则。

| 序号 | 知识内容名称 | 作用说明 |
|-----|------------|---------|
| **6.1** | **高危识别规则库** | **作用**：定义需要立即就医的高危情况，识别红旗信号。<br>**举例**：对于"胸痛"，如果出现"持续剧烈胸痛+大汗+恶心+气短"，识别为极高危，必须立即就医；如果出现"胸痛+意识改变"，识别为极高危，必须立即拨打120。<br>**内容组需要准备**：整理各种高危症状组合，包括症状组合、体征异常、检查结果异常等，以及对应的风险等级和处理建议。 |
| **6.2** | **严重程度评估规则库** | **作用**：定义如何评估疾病的严重程度，包括轻度/中度/重度的判定标准。<br>**举例**：对于"心绞痛"，轻度：症状轻微，不影响日常活动；中度：症状影响日常活动，但不影响基本生活；重度：症状严重影响基本生活，需要立即就医。<br>**内容组需要准备**：为每个疾病整理严重程度评估规则，包括轻度/中度/重度的判定标准和对应的处理建议。 |
| **6.3** | **紧急程度分级规则库** | **作用**：定义L1到L4的紧急程度分级标准。<br>**举例**：L1（极紧急）：需要立即就医，可能危及生命；L2（紧急）：需要尽快就医，24小时内；L3（一般）：可以预约就医，3-7天内；L4（非紧急）：可以观察，1-2周内复诊即可。<br>**内容组需要准备**：定义L1到L4的判定标准和对应的处理建议。 |
| **6.4** | **复评与升级规则库** | **作用**：定义建议患者多久后复评，以及什么情况下需要立即升级处理（建议就医）。<br>**举例**：对于"心绞痛"，默认复评时间窗是"3天后"；但如果症状加重或出现新症状（如出汗、气短），需要立即复评；如果症状完全缓解，可以延迟到1周后复评。升级触发条件包括：症状突然加重、出现高危症状（大汗、恶心、气短等）、处理无效等，一旦触发需要立即就医。<br>**内容组需要准备**：为每个疾病方向定义复评时间窗（默认复评时间）、提前复评条件（症状加重、出现新症状等）、延迟复评条件（症状完全缓解等）、升级触发条件（需要立即就医的情况）、升级处理方式等。 |

## 八、脑区G：可解释性与证据链服务（Evidence & Rationale Service）

**服务说明**：生成完整的证据链，让系统的"结论"能被复核，包括证据清单结构化、终点结论包生成等。

| 序号 | 知识内容名称 | 作用说明 |
|-----|------------|---------|
| **7.1** | **证据链构建规则库** | **作用**：定义如何将分散的证据组织成完整的证据链。<br>**举例**：对于"急性心梗"的诊断，证据链包括：症状证据（胸痛+2天+活动后加重）、体征证据（ST段抬高）、背景证据（有高血压史）、KG路径证据（胸痛→心血管疾病→急性心梗）等。<br>**内容组需要准备**：定义证据链的构建规则，包括证据类型、证据来源、证据关联关系等。 |
| **7.2** | **推理路径可视化规则库** | **作用**：定义如何可视化展示从症状到疾病的推理路径。<br>**举例**：展示"胸痛 → 心血管疾病（知识图谱路径） → 急性心梗（支持证据：ST段抬高）"这个推理路径。<br>**内容组需要准备**：定义推理路径的可视化格式，包括节点表示、边表示、路径权重等。 |

## 十、回退机制引擎（Rollback Engine）

**服务说明**：定义什么情况下需要回退到之前的诊断阶段，重新收集信息或重新分析。

| 序号 | 知识内容名称 | 作用说明 |
|-----|------------|---------|
| **9.1** | **回退条件清单** | **作用**：定义什么情况下需要回退到之前的诊断阶段，重新收集信息或重新分析。每个主诉都要定义回退迭代条件，明确不同回退条件对应的具体回退目标阶段。<br>**举例**：回退条件分类：1）**症状恶化/出现新高危** → 回退到触发诊断或阶段1（健康状态判定），例如症状突然加重、出现意识改变等；2）**证据冲突/信息不足** → 回退到阶段2（信息补全），例如症状说发热但体温测量正常、关键信息缺失无法判断；3）**症状演变** → 回退到阶段3（可能性分析），例如疼痛性质从钝痛变为刺痛，需要重新组织分流路径；4）**处理无效/病程演变** → 回退到阶段4（鉴别诊断），例如按照建议处理后症状未改善或加重，需要重新采集证据与制定验证计划；5）**必须排除项未完成排除** → 回退到阶段4（鉴别诊断），例如高危诊断的验证计划未执行或未完成排除。<br>**内容组需要准备**：为每个主诉定义各种回退条件，包括：回退条件名称、触发规则（什么情况下触发）、回退目标阶段（触发诊断/阶段1/阶段2/阶段3/阶段4）、回退原因（为什么回退）、回退后的动作（回退后需要执行的具体动作，如重新收集信息、重新组织分流路径、重新制定验证计划等）。 |
