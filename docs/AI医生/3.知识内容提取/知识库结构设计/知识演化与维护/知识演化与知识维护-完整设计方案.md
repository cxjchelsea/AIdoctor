# 知识演化与知识维护 - 完整设计方案

> **设计目标**：在保持诊断责任链清晰的前提下，实现知识的自治演化与安全发布  
> **设计原则**：诊断决策单点负责；知识演化多点自治，但发布单点门禁  
> **文档版本**：v1.0

---

## 📋 设计概述

### 1.1 核心思想

**双层决策架构**：
- **诊断域（Clinical Decision Domain）**：主Agent是唯一决策者，负责诊断结论、检查、治疗、升级、拒答等临床动作
- **知识域（Knowledge Evolution Domain）**：知识演化Agent集群负责知识的抽取、验证、冲突处理，但必须通过发布门禁才能进入生产

**权限分离**：
- **Read (生产知识)**：所有诊断相关组件可读
- **Write (候选区)**：知识演化Agent可写
- **Publish (生产发布)**：由Publish Gate（规则+评测+可选人工）控制
- **Rollback (生产回滚)**：由Gate控制且可追溯

### 1.2 设计目标

1. **保持诊断责任链清晰**：诊断与临床动作的唯一责任主体仍是主Agent
2. **实现知识自治演化**：允许知识演化Agent集群自动运行，最大化研究空间
3. **确保生产安全**：知识演化不能直接改生产知识，必须通过版本化与发布门禁
4. **支持可追溯性**：所有知识变更可追溯，支持审计和回滚

### 1.3 设计优势

**优点**：
- ✅ 能真正做"知识演化"研究（触发策略、演化规则、漂移检测）
- ✅ 不会把生产知识库暴露给无门禁的自动更新
- ✅ 诊断责任链仍清晰（决策在主Agent，知识变更可追溯）
- ✅ 支持版本化管理和灰度发布
- ✅ 支持回滚和依赖分析

**缺点**：
- ⚠️ 需要完整的治理设施（版本、影子评测、回滚、依赖分析）
- ⚠️ 系统复杂度上升

## 🏗️ 总体架构

### 2.1 架构分层

#### 2.1.1 在线层：Knowledge Query（只读）

**定位**：服务于通道1结构化推理

**功能**：
- 知识库优先查询
- Neo4j路径检索验证
- 路径约束推理

**实现方式**：
- 新增工具服务：`knowledge-query-service`
- 或作为 `diagnosis-engine-service` 的可插拔retriever模块

**特点**：
- 只读访问生产知识库
- 不参与知识演化流程
- 响应主Agent的工具调用请求

#### 2.1.2 离线层：Knowledge Evolution（写候选/跑评测/提发布）

**定位**：知识演化的核心子系统

**功能**：
- 知识抽取
- 知识验证
- 冲突处理
- 候选构建
- 回归评测
- 发布提议

**实现方式**：
- 新增独立子系统：`knowledge-ops-service`
- 内部由多个"知识维护Agent"组成
- 通过消息队列异步运行（复用现有调度层能力）

**特点**：
- 异步运行，不阻塞在线诊断流程
- 工作在候选区，不直接修改生产知识
- 通过Publish Gate控制发布

### 2.2 数据层设计

**复用现有数据层**：
- Neo4j（知识图谱）
- MySQL/Oracle（持久化）
- Redis（缓存/队列）

**新增概念**：
- **候选区/版本区**：Sandbox、Staging、Production三个知识库区
- **版本化管理**：类似CDP的写时复制思想

## 🔐 三个知识库区：Production / Staging / Sandbox

### 3.1 Sandbox（实验/构建区）

**定位**：知识演化的起点，实验和构建区域

**功能**：
- 抽取Agent、解析Agent在这里生成结构化知识对象（KO）
- 与证据绑定
- 不影响任何线上推理

**特点**：
- 完全隔离，不影响生产环境
- 支持快速迭代和实验
- 可以随时清理和重建

**数据流向**：
```
新知识源（指南/文献/规则）
  ↓
Extractor Agent
  ↓
Sandbox（KO草稿 + provenance）
```

### 3.2 Staging（候选验证区）

**定位**：知识验证和候选构建区域

**功能**：
- 验证Agent工作：证据一致性、冲突检测
- 冲突处理Agent工作：解决知识冲突
- 回归评测Agent工作：影子评测
- 产出"候选release（candidate_release）"

**特点**：
- 通过验证的知识才能进入Staging
- 支持完整的验证和测试流程
- 生成候选发布包

**数据流向**：
```
Sandbox（KO草稿）
  ↓
Verifier Agent（验证）
  ↓
Conflict Resolver Agent（冲突解决）
  ↓
Shadow Evaluator Agent（影子评测）
  ↓
Staging（candidate_release）
```

### 3.3 Production（线上只读发布区）

**定位**：生产环境的知识库，只读访问

**功能**：
- 只有通过Publish Gate的release才进入Production
- 生成 `kg_version`（v1, v2, v3...）
- 支持版本化管理和回滚

**特点**：
- 只读访问，不直接修改
- 版本化管理，支持回滚
- 对应CDP的写时复制思想

**数据流向**：
```
Staging（candidate_release）
  ↓
Publish Gate（四道门禁）
  ↓
Production（kg_version）
  ↓
在线推理使用
```

### 3.4 知识库区的关系

```
┌─────────────┐
│  Sandbox    │  实验/构建区
│  (实验区)    │  抽取、解析、草稿
└──────┬──────┘
       │ 验证通过
       ↓
┌─────────────┐
│  Staging    │  候选验证区
│  (候选区)    │  验证、冲突处理、影子评测
└──────┬──────┘
       │ 通过Publish Gate
       ↓
┌─────────────┐
│ Production  │  生产发布区
│  (生产区)    │  只读、版本化、可回滚
└─────────────┘
```

### 3.5 存储实现方案

**核心问题**：三个知识库区在存储层的实现方式

**方案对比**：

| 方案 | 实现方式 | 优点 | 缺点 | 适用场景 |
|------|---------|------|------|---------|
| **方案X：三套物理库** | Sandbox/Staging/Production各一套Neo4j实例 | 完全隔离，安全性高 | 运维复杂，数据同步成本高，存储成本高 | 大型企业，严格隔离要求 |
| **方案Y：一套库+分区** | 一套Neo4j + release/label分区 + current_release指针 | 运维简单，回滚快（改指针），查询一致性好 | 需要严格的分区管理 | **推荐方案** |
| **方案Z：一套库+diff** | 一套生产库 + Staging只存diff，发布时生成快照 | 存储成本低 | 发布速度慢，回滚需要重建快照 | 存储受限场景 |

**推荐方案：方案Y（一套物理库 + release/label分区 + current_release指针）**

#### 3.5.1 实现细节

**存储架构**：
- **一套Neo4j物理库**：所有知识数据存储在同一个Neo4j实例中
- **release/label分区**：通过Neo4j的label机制实现分区
  - Sandbox：`(:KnowledgeObject:Release_Sandbox)`
  - Staging：`(:KnowledgeObject:Release_Staging)`
  - Production：`(:KnowledgeObject:Release_v1)`、`(:KnowledgeObject:Release_v2)`等
- **current_release指针**：在元数据表中维护当前生产版本指针
  ```cypher
  (:ReleaseMetadata {
    release_id: "v2.1",
    status: "active",
    created_at: timestamp,
    is_current: true
  })
  ```

**查询方式**：
- 生产查询：`MATCH (ko:KnowledgeObject:Release_v2.1) WHERE ko.status = 'published'`
- 或通过current_release指针：`MATCH (rm:ReleaseMetadata {is_current: true}) MATCH (ko:KnowledgeObject) WHERE ko.release_id = rm.release_id`

**发布流程**：
1. Staging中的KO标记为`Release_Staging`
2. 通过Publish Gate后，创建新release（如`Release_v2.1`）
3. 将Staging中的KO复制并标记为新release（写时复制）
4. 更新`current_release`指针指向新release
5. 旧release保留，支持回滚

**回滚机制**：
- **全局回滚**：只需修改`current_release`指针，指向旧release
- **局部回滚**：按ko_id在新release中标记为deprecated，查询时fallback到旧release
- **优势**：回滚速度快（O(1)），不需要重建数据

**运维优势**：
- 查询一致性：所有查询在同一库中，保证ACID特性
- 回滚成本低：只需改指针，不需要数据迁移
- 运维简单：只需管理一套Neo4j实例
- 存储效率：通过label分区，不需要数据复制（发布时才复制）

**注意事项**：
- 需要严格的分区管理，避免跨分区污染
- 需要维护release元数据表
- 需要定期清理过期的Sandbox数据

## 📦 知识对象（KO）与提案（Proposal）

### 4.1 Knowledge Object（KO）数据结构

**最小字段定义**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `ko_id` | string | 唯一ID |
| `ko_type` | enum | rule / relation / pathway_template / contraindication / threshold / ddx_feature |
| `content` | object | 结构化表达（规则条件、三元组、路径模板等） |
| `concept_ids` | array | CUI/ICD/SNOMED（概念标准化） |
| `provenance[]` | array | 证据来源（doc_id、段落定位、发布日期/版本） |
| `status` | enum | proposed / verified / published / deprecated |
| `kg_version` | string | 发布版本号（仅对published） |
| `impact_scope` | array | 影响模块（DDx / workup / treatment / risk） |
| `downstream_bindings[]` | array | 下游绑定：被哪些工具/规则引擎/路径模板引用（详见3.5.2） |

**设计原则**：
- 每条知识必须可追溯到来源（provenance）
- 比ToolResult的evidence引用更严格
- 支持版本化管理
- 支持依赖分析和局部回滚

#### 4.1.1 downstream_bindings字段详解

**字段结构**：
```json
{
  "downstream_bindings": [
    {
      "binding_type": "tool",           // tool / rule_engine / pathway_template
      "binding_id": "tool_3",          // 工具ID或规则引擎ID
      "binding_name": "鉴别诊断工具",    // 名称
      "usage_context": "ddx_candidate_generation",  // 使用上下文
      "binding_strength": "required"   // required / optional / conditional
    },
    {
      "binding_type": "pathway_template",
      "binding_id": "pathway_acute_mi",
      "binding_name": "急性心肌梗死路径",
      "usage_context": "workup_planning",
      "binding_strength": "required"
    }
  ]
}
```

**作用**：
- **依赖分析**：明确知道哪些组件依赖这条KO
- **影响范围评估**：评估KO变更的影响范围
- **局部回滚**：回滚时可以精确知道需要更新哪些组件
- **变更通知**：KO变更时可以通知相关组件

**维护方式**：
- 在KO发布时自动分析依赖关系
- 在工具/规则引擎注册时建立绑定
- 在KO变更时更新绑定关系

### 4.2 Knowledge Proposal（更新提案）

**字段定义**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `proposal_id` | string | 提案ID |
| `trigger` | string | 触发原因（缺口/冲突/新指南/错误回归） |
| `diff` | object | 对哪些ko做新增/修改/删除 |
| `required_tests` | array | 需要跑哪些回归/影子评测 |
| `risk_level` | enum | 影响面、是否触发人工审批（high/medium/low） |
| `dedupe_key` | string | 去重键：按病种/概念/缺口类型聚合（详见8.1.1） |
| `cooldown_window` | int | 冷却时间窗口（秒）：同类触发的冷却时间 |
| `evidence_snapshot` | string | 触发当时的关键证据快照hash，便于复现 |

**触发场景**：
- 知识覆盖缺口（tool_3鉴别诊断候选为空/很弱）
- 冲突复核反复失败（图谱路径无法验证、证据互斥）
- 反复"证据不足"仍无法满足停止条件
- 新指南/新共识发布
- 内部规则变更
- 线上监控发现某类case回归

## 🤖 知识演化Agent集群

### 5.1 Agent职责划分

知识演化Agent集群由多个专门的Agent组成，每个Agent负责知识演化的特定环节。

#### 5.1.1 Extractor Agent（抽取Agent）

**职责**：从知识源中抽取结构化知识

**输入**：
- 指南/文献/内部规则文本
- 触发的缺口描述

**输出**：
- KO草稿
- provenance（段落级证据）

**工作区域**：Sandbox

**特点**：
- 支持多种知识源格式
- 自动提取结构化知识
- 必须绑定证据来源

#### 5.1.2 Verifier Agent（验证Agent）

**职责**：验证知识的正确性和一致性

**验证内容**：
1. **证据一致性**：KO是否被原文支持
2. **冲突检测**：与现有KO的冲突（逻辑/术语/路径断裂）

**工作区域**：Sandbox → Staging

**特点**：
- 自动验证和冲突检测
- 生成验证报告
- 标记需要人工审核的项

#### 5.1.3 Conflict Resolver Agent（冲突解决Agent）

**职责**：解决知识冲突

**冲突策略**：
- **覆盖**：新知识覆盖旧知识
- **并存**：多个版本并存（机构政策差异）
- **分支**：按不同场景分支
- **降级**：降级为"需人工审阅"

**工作区域**：Staging

**特点**：
- 支持多种冲突解决策略
- 自动解决简单冲突
- 复杂冲突提交人工审核

**冲突解决产物**：
每个冲突解决必须生成以下信息：
- `conflict_case_id`：冲突实例ID，便于审计和追溯
- `resolution_rationale`：解决理由，说明为什么选择覆盖/并存/分支/降级
- `resolution_strategy`：采用的解决策略
- `resolution_timestamp`：解决时间
- `resolved_by`：解决者（Agent ID或人工审核者）

**冲突解决记录结构**：
```json
{
  "conflict_case_id": "CONFLICT_20260128_001",
  "conflicting_ko_ids": ["KO_001", "KO_002"],
  "conflict_type": "value_conflict",
  "conflict_description": "新旧指南对心绞痛诊断标准不一致",
  "resolution_strategy": "覆盖",
  "resolution_rationale": "新指南（2026版）证据等级更高（A级），且发布时间更新，采用新指南标准",
  "resolution_timestamp": "2026-01-28T10:00:00Z",
  "resolved_by": "ConflictResolverAgent_v1.0",
  "resolution_evidence": {
    "new_guide_version": "2026",
    "old_guide_version": "2020",
    "evidence_level_comparison": "A > B"
  }
}
```

**作用**：
- **责任链追溯**：明确知道谁解决了冲突，为什么这样解决
- **研究价值**：冲突解决策略可以作为实验变量进行研究
- **审计支持**：支持完整的审计追溯
- **策略优化**：可以分析不同策略的效果，优化解决策略

#### 5.1.4 Release Builder Agent（打包发布候选Agent）

**职责**：打包发布候选

**功能**：
- 把通过验证的KO集合打包成 `candidate_release`
- 生成diff与测试计划
- 准备发布材料

**工作区域**：Staging

**特点**：
- 生成完整的发布包
- 包含变更摘要和测试计划
- 准备提交Publish Gate

#### 5.1.5 Shadow Evaluator Agent（影子评测Agent）

**职责**：在离线环境进行评测

**评测内容**：
- 下游诊断性能
- 路径可追溯性
- 失败模式分布

**工作区域**：Staging（离线环境）

**特点**：
- 在离线病例集/仿真环境运行
- 不影响生产环境
- 生成评测报告

#### 5.1.6 Rollback & Drift Monitor Agent（回滚与漂移监控Agent）

**职责**：监控生产环境的知识使用情况

**监控内容**：
- 新版本上线后是否出现DDx波动
- 风险评估异常
- 特定人群退化

**工作区域**：Production（监控）

**特点**：
- 实时监控生产环境
- 自动触发回滚
- 生成监控报告

### 5.2 Agent协作流程

```
新知识源
  ↓
Extractor Agent（抽取）→ Sandbox
  ↓
Verifier Agent（验证）→ Staging
  ↓
Conflict Resolver Agent（冲突解决）→ Staging
  ↓
Release Builder Agent（打包）→ candidate_release
  ↓
Shadow Evaluator Agent（影子评测）→ 评测报告
  ↓
Publish Gate（门禁）→ Production
  ↓
Rollback & Drift Monitor Agent（监控）→ 持续监控
```

### 5.3 Agent实现特点

**并行/异步**：
- 多个Agent可以并行工作
- 通过消息队列异步运行
- 支持超时、重试、限流

**职责边界**：
- Agent的职责边界是知识域
- 不参与诊断决策
- 通过门禁发布控制

**复用现有能力**：
- 复用消息队列调度层
- 复用现有工具服务架构
- 复用CDP版本管理思想

## 🚪 Publish Gate：发布门禁机制

### 6.1 门禁定位

Publish Gate是**非LLM、规则/测试驱动的发布控制器**，可以是独立服务，也可以是knowledge-ops-service中的模块。

**核心作用**：
- 确保只有通过验证的知识才能进入生产
- 控制知识发布的权限
- 支持风险分级审批

### 6.2 四道门禁

#### Gate-1：结构合法性

**检查内容**：
- KO schema完整
- concept标准化字段齐全
- 避免脏数据

**通过条件**：
- 所有必需字段存在
- 字段格式符合规范
- 数据类型正确

#### Gate-2：证据可追溯性

**检查内容**：
- 每条KO必须绑定provenance
- 没有证据不允许进入发布候选

**通过条件**：
- 所有KO都有provenance
- provenance信息完整（doc_id、段落定位、发布日期/版本）
- 与线上ToolResult必须携带evidence的原则一致

#### Gate-3：回归评测与影子评测通过

**检查内容**：
- 必须跑最小回归集
- 核心DDx场景测试
- 红旗病种测试
- 关键路径断裂测试

**测试契约（Test Contract）**：

**必跑测试集**：
1. **固定小集（Core Regression Set）**：
   - 核心DDx场景：50个标准病例（覆盖前10大常见疾病）
   - 红旗病种：20个急危重病例（急性心肌梗死、脑卒中、肺栓塞等）
   - 关键路径：30个关键诊疗路径（覆盖主要诊疗流程）
   - **总计：100个固定测试用例**

2. **抽样大集（Sampling Set）**：
   - 从历史病例库中随机抽样500个病例
   - 覆盖不同病种、不同严重程度、不同人群
   - 每次发布都重新抽样，确保覆盖全面

**硬阈值（Hard Thresholds）**：
- **红旗召回率**：不得下降（与基线版本对比，红旗病种召回率 ≥ 基线）
- **关键路径断裂**：必须为0（关键路径断裂数 = 0）
- **总体性能下降**：不超过5%（总体诊断准确率下降 ≤ 5%）
- **新增错误**：不超过2%（新增错误病例数 / 总测试病例数 ≤ 2%）

**软阈值（Soft Thresholds）**：
- **平均响应时间**：增加不超过10%
- **证据完整性**：证据链完整性得分 ≥ 基线 - 3%
- **路径可追溯性**：路径可追溯性得分 ≥ 基线 - 5%

**评测输出要求**：
- **评测报告**：必须生成完整的评测报告
- **报告摘要hash**：评测报告的hash值必须记录到candidate_release中
- **审计记录**：评测过程必须记录到AuditTrail
- **对比基线**：必须与当前生产版本（基线）进行对比

**评测报告结构**：
```json
{
  "evaluation_id": "EVAL_20260128_001",
  "candidate_release_id": "RELEASE_20260128_001",
  "baseline_version": "v2.0",
  "test_sets": {
    "core_regression": {
      "total_cases": 100,
      "passed": 98,
      "failed": 2,
      "pass_rate": 0.98
    },
    "sampling_set": {
      "total_cases": 500,
      "passed": 485,
      "failed": 15,
      "pass_rate": 0.97
    }
  },
  "metrics": {
    "red_flag_recall": {
      "baseline": 0.95,
      "candidate": 0.96,
      "delta": 0.01,
      "threshold_met": true
    },
    "critical_path_breaks": {
      "count": 0,
      "threshold_met": true
    },
    "overall_accuracy": {
      "baseline": 0.92,
      "candidate": 0.91,
      "delta": -0.01,
      "threshold_met": true
    },
    "new_errors": {
      "count": 10,
      "rate": 0.0167,
      "threshold_met": true
    }
  },
  "report_hash": "sha256:abc123...",
  "evaluation_timestamp": "2026-01-28T10:00:00Z",
  "evaluator": "ShadowEvaluatorAgent_v1.0"
}
```

**通过条件（明确契约）**：
1. **所有硬阈值必须满足**：
   - 红旗召回率 ≥ 基线
   - 关键路径断裂 = 0
   - 总体性能下降 ≤ 5%
   - 新增错误率 ≤ 2%

2. **至少80%的软阈值满足**：
   - 响应时间、证据完整性、路径可追溯性等

3. **评测报告必须完整**：
   - 报告hash已记录
   - 所有测试用例都有结果
   - 对比基线数据完整

4. **评测结果必须入审计**：
   - candidate_release的评测报告hash已记录
   - 评测过程已记录到AuditTrail

**不通过处理**：
- 如果硬阈值不满足：直接拒绝，不允许进入Gate-4
- 如果软阈值不满足：标记为"需要人工审核"，进入Gate-4但需要人工审批
- 如果评测报告不完整：拒绝，要求重新评测

**与主Agent的"停止条件必须证据链完整"思想一致**：
- Gate-3的评测也要求证据链完整
- 评测报告必须包含证据链完整性评估
- 证据链不完整的测试用例视为失败

#### Gate-4：风险分级审批（可选人工）

**风险分级**：

| 风险等级 | 场景 | 审批方式 |
|---------|------|---------|
| **低风险** | 新增解释性关系、不影响处置 | 自动发布 |
| **中风险** | 调整阈值/禁忌/关键路径 | 需要人工审批或双人签署 |
| **高风险** | 改变红旗/急危重路径 | 必须人工审批+灰度发布 |

**审批流程**：
- 低风险：自动通过
- 中风险：提交人工审批队列
- 高风险：必须人工审批，且需要灰度发布

### 6.3 门禁决策流程

```
candidate_release
  ↓
Gate-1: 结构合法性检查
  ↓ (通过)
Gate-2: 证据可追溯性检查
  ↓ (通过)
Gate-3: 回归评测与影子评测
  ↓ (通过)
Gate-4: 风险分级审批
  ↓ (通过)
生成 kg_version
  ↓
发布到 Production
```

## 🎯 知识演化触发机制

### 8.1 在线触发：只产生Proposal

**触发场景**：
- tool_3鉴别诊断候选为空/很弱（知识覆盖缺口）
- 冲突复核反复失败（图谱路径无法验证、证据互斥）
- 反复"证据不足"仍无法满足停止条件中的"证据链完整"

**处理方式**：
- 主Agent在Evaluate阶段可决定：向knowledge-ops提交 `proposal`（异步）
- **不阻塞当前会话闭环**
- 只产生提案，不直接更新生产知识

**特点**：
- 异步处理，不影响诊断流程
- 只产生提案，不直接修改知识
- 由知识演化Agent集群后续处理

#### 8.1.1 去噪/节流机制

**问题**：真实运行中会出现"提案风暴"（同类缺口重复触发）

**解决方案**：

**1. dedupe_key（去重键）**

**生成规则**：
- 按病种/概念/缺口类型聚合
- 格式：`{gap_type}_{disease_concept_id}_{symptom_concept_id}`
- 示例：
  - `knowledge_gap_ICD_I20_0_SYMP_001`：心绞痛的知识缺口
  - `conflict_resolution_failed_ICD_I21_0`：急性心肌梗死冲突解决失败
  - `evidence_insufficient_ICD_J18_0`：肺炎证据不足

**去重逻辑**：
- 相同`dedupe_key`的proposal在`cooldown_window`内只保留第一个
- 后续相同key的proposal会被合并或丢弃
- 合并时更新`trigger_count`（触发次数）和`latest_evidence_snapshot`

**2. cooldown_window（冷却时间窗口）**

**配置规则**：
- 默认冷却时间：3600秒（1小时）
- 可根据gap_type调整：
  - 知识缺口：3600秒（1小时）
  - 冲突解决失败：7200秒（2小时）
  - 证据不足：1800秒（30分钟）

**冷却逻辑**：
- 在冷却窗口内，相同`dedupe_key`的proposal会被拒绝
- 冷却窗口外，允许新的proposal
- 冷却窗口可以动态调整（根据触发频率）

**3. evidence_snapshot（证据快照）**

**快照内容**：
- 触发时的CDP状态（关键字段）
- 触发时的工具调用结果
- 触发时的知识查询结果
- 触发时的错误信息

**快照格式**：
```json
{
  "evidence_snapshot": {
    "snapshot_hash": "sha256:abc123...",
    "cdp_snapshot": {
      "patient_state": {...},
      "ddx": [...],
      "evidence_graph": {...}
    },
    "tool_results": [
      {
        "tool_id": "tool_3",
        "result": {...},
        "error": "knowledge_gap: no candidate found"
      }
    ],
    "knowledge_queries": [
      {
        "query": "...",
        "result_count": 0
      }
    ],
    "trigger_context": {
      "session_id": "...",
      "timestamp": "2026-01-28T10:00:00Z",
      "agent_state": {...}
    }
  }
}
```

**作用**：
- **便于复现**：可以复现触发场景，用于知识演化Agent分析
- **问题诊断**：可以分析为什么触发，是否误触发
- **审计追溯**：记录触发时的完整上下文

**4. 节流策略**

**触发频率限制**：
- 单个`dedupe_key`：每小时最多触发1次
- 单个会话：每小时最多触发5次proposal
- 全局：每小时最多触发100个proposal

**超出限制处理**：
- 超出限制的proposal会被标记为"节流"
- 记录到日志，但不提交到knowledge-ops
- 可以人工查看被节流的proposal

**5. Proposal合并策略**

**合并条件**：
- 相同`dedupe_key`
- 在`cooldown_window`内
- 触发原因相同或相似

**合并方式**：
- 保留第一个proposal
- 更新`trigger_count`（触发次数）
- 更新`latest_evidence_snapshot`（最新证据快照）
- 合并`diff`（如果有多个KO变更）

**合并后的Proposal结构**：
```json
{
  "proposal_id": "PROP_20260128_001",
  "dedupe_key": "knowledge_gap_ICD_I20_0_SYMP_001",
  "trigger": "知识覆盖缺口",
  "trigger_count": 5,
  "first_trigger_time": "2026-01-28T09:00:00Z",
  "latest_trigger_time": "2026-01-28T10:00:00Z",
  "cooldown_window": 3600,
  "evidence_snapshot": {
    "snapshot_hash": "sha256:abc123...",
    "first_snapshot": {...},
    "latest_snapshot": {...}
  },
  "diff": {...},
  "risk_level": "medium"
}
```

## 🔙 回滚与灰度发布

### 9.1 版本化管理

**版本生成**：
- 每次发布生成 `kg_version`（v1, v2, v3...）
- 对应CDP的写时复制思想
- 新版本、旧版本保留用于审计回滚

**版本特点**：
- 生产库只读
- 线上推理绑定某个版本
- 支持版本切换

### 9.2 回滚机制

**回滚方式**：
- **全局回滚**：把默认kg_version指针回退（通过修改current_release指针）
- **局部回滚**：按ko_id局部回滚（利用downstream_bindings进行精确回滚）

**回滚触发**：
- Rollback & Drift Monitor Agent检测到问题
- 人工触发回滚
- 自动回滚（配置阈值）

**局部回滚的依赖分析**：

**基于downstream_bindings的精确回滚**：
1. **识别受影响组件**：
   - 根据KO的`downstream_bindings`字段，识别所有依赖该KO的组件
   - 包括：工具、规则引擎、路径模板等

2. **影响范围评估**：
   - 评估回滚对每个组件的影响
   - 评估是否需要更新组件配置
   - 评估是否需要通知组件重新加载

3. **回滚执行**：
   - 在新release中标记KO为deprecated
   - 查询时fallback到旧release的KO
   - 通知相关组件（通过downstream_bindings）
   - 更新组件配置（如果需要）

4. **回滚验证**：
   - 验证回滚后的KO是否可用
   - 验证相关组件是否正常工作
   - 验证诊断流程是否恢复正常

**局部回滚示例**：
```cypher
// 1. 识别需要回滚的KO
MATCH (ko:KnowledgeObject {ko_id: "KO_001"})
WHERE ko.release_id = "v2.1"

// 2. 获取下游绑定
WITH ko, ko.downstream_bindings as bindings

// 3. 标记为deprecated
SET ko.status = "deprecated"
SET ko.deprecated_at = timestamp()
SET ko.deprecated_reason = "性能回归"

// 4. 通知相关组件（通过bindings）
// - tool_3: 需要重新加载知识
// - pathway_acute_mi: 需要更新路径配置
```

**回滚特点**：
- 可追溯：回滚操作记录到AuditTrail
- 支持审计：回滚原因、影响范围都有记录
- 不影响其他版本：只影响当前版本
- 精确控制：基于downstream_bindings实现精确回滚

### 9.3 灰度发布

**灰度方式**：
- 按会话分流
- 按机构分流
- 按病种分流

**灰度策略**：
- 可借用现有work_mode、risk_level_limit等约束字段
- 逐步扩大灰度范围
- 监控灰度效果

**灰度特点**：
- 降低发布风险
- 支持A/B测试
- 快速回滚

## 📊 系统优势与挑战

### 11.1 系统优势

1. **责任链清晰**：
   - 诊断决策单点负责（主Agent）
   - 知识演化多点自治，但发布单点门禁
   - 便于审计和追溯

2. **研究空间最大化**：
   - 支持知识演化的完整研究（触发策略、演化规则、漂移检测）
   - 不影响诊断流程
   - 支持实验和迭代

3. **生产安全**：
   - 知识演化不能直接改生产知识
   - 必须通过版本化与发布门禁
   - 支持回滚和灰度发布

4. **可追溯性**：
   - 所有知识变更可追溯
   - 支持审计
   - 支持版本化管理

### 11.2 系统挑战

1. **系统复杂度上升**：
   - 需要完整的治理设施（版本、影子评测、回滚、依赖分析）
   - 需要多个Agent协作
   - 需要Publish Gate机制

2. **实施成本**：
   - 需要开发knowledge-ops-service
   - 需要实现多个Agent
   - 需要实现Publish Gate

3. **运维复杂度**：
   - 需要管理三个知识库区
   - 需要监控知识演化流程
   - 需要处理冲突和回滚

### 11.3 应对策略

1. **分阶段实施**：
   - 先实现核心功能
   - 逐步完善治理设施
   - 持续优化和迭代

2. **复用现有能力**：
   - 复用消息队列调度层
   - 复用CDP版本管理思想
   - 复用现有工具服务架构

3. **自动化优先**：
   - 尽可能自动化检测和维护
   - 减少人工干预
   - 提高效率

## 📚 总结

### 14.1 核心设计

**双层决策架构**：
- 诊断域：主Agent是唯一决策者
- 知识域：知识演化Agent集群自治，但发布单点门禁

**三个知识库区**：
- Sandbox：实验/构建区
- Staging：候选验证区
- Production：生产发布区（只读）

**知识演化Agent集群**：
- Extractor、Verifier、Conflict Resolver、Release Builder、Shadow Evaluator、Rollback & Drift Monitor

**Publish Gate门禁**：
- 四道门禁：结构合法性、证据可追溯性、回归评测、风险分级审批

### 14.2 设计原则

1. **诊断决策单点负责**：保持责任链清晰
2. **知识演化多点自治**：最大化研究空间
3. **发布单点门禁**：确保生产安全
4. **版本化管理**：支持追溯和回滚
5. **可追溯性**：支持审计和追溯
