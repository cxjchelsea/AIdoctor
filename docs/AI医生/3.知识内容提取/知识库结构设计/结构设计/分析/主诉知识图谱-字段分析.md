# 主诉知识图谱 - 字段存储方式分析

> **分析目标**：基于已有的"知识图谱设计-第3项-标准目录主数据"设计，逐条分析"主诉知识图谱.md"中每个表和字段的存储方式  
> **创建日期**：2026-02-03  
> **文档版本**：v1.0

---

## 📋 分析原则

基于混合存储方案的设计原则：
- **关系用图谱**：实体和关系存储在知识图谱中，支持推理和查询
- **配置用文件**：流程规则、判定标准、输出规则等存储在配置文件中，便于维护
- **已有实体扩展**：在第3项已有的ChiefComplaint节点基础上扩展属性
- **新增节点**：需要独立查询和推理的实体创建新节点
- **新增关系**：需要表达实体间关系的创建关系边

## 主诉表4｜鉴别诊断框架子类表（Step2 分组）

### 字段说明

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 鉴别诊断框架的子类（框架类型、子类名称、子类边界、候选疾病集合、must-not-miss、后续优先差异点） |
| **存储方式** | **新增节点 + 关系** |
| **具体设计** | 创建节点类型`DifferentialFrameworkSubclass`（鉴别诊断框架子类），建立关系：`ChiefComplaint -[:HAS_DIFFERENTIAL_SUBCLASS]-> DifferentialFrameworkSubclass`，`DifferentialFrameworkSubclass -[:CONTAINS_DISEASE]-> Disease` |
| **说明** | 鉴别诊断框架子类是独立的实体，可以组织多个疾病，便于推理路径管理 |
| **节点属性** | `subclass_uuid`, `display_id`, `framework_type: String`（框架类型）, `subclass_name: String`（子类名称）, `subclass_boundary: String`（子类边界）, `must_not_miss_diseases: String[]`（必须优先除外的疾病ID列表） |
| **关系属性** | `priority: Integer`（优先级）, `created_at`, `version` |
| **示例** | `(ChiefComplaint {display_id: "CC_001"}) -[:HAS_DIFFERENTIAL_SUBCLASS]-> (DifferentialFrameworkSubclass {framework_type: "分布分叉", subclass_name: "单侧"})` |

## 主诉表7｜推理子组清单表（Step3 线索簇）

### 字段说明

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 推理子组信息（子组名称、覆盖疾病、子组进入触发、推进目标、优先补齐缺口、推进路径） |
| **存储方式** | **新增节点 + 关系**（与疾病知识图谱中的推理子组复用） |
| **具体设计** | 使用疾病知识图谱中已有的`ReasoningSubgroup`节点，建立关系：`ChiefComplaint -[:HAS_REASONING_SUBGROUP]-> ReasoningSubgroup`，`ReasoningSubgroup -[:CONTAINS_DISEASE]-> Disease` |
| **说明** | 推理子组是独立的实体，可以组织多个疾病，便于推理路径管理。与疾病知识图谱中的推理子组复用，避免重复 |
| **节点属性** | 使用疾病知识图谱中已有的`ReasoningSubgroup`节点属性（`subgroup_uuid`, `display_id`, `name`, `description`），新增属性：`entry_triggers: String[]`（子组进入触发线索标题）, `promotion_target: String`（推进目标）, `priority_gaps: String[]`（优先补齐缺口线索标题）, `promotion_path: String`（推进路径：追问/检查/混合） |
| **关系属性** | `priority: Integer`（优先级）, `created_at`, `version` |
| **示例** | `(ChiefComplaint {display_id: "CC_001"}) -[:HAS_REASONING_SUBGROUP]-> (ReasoningSubgroup {display_id: "SG_血栓风险线索组"})` |

## 主诉表8｜关键差异点配置表（Step4）

### 字段说明

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 关键差异点信息（差异点名称、标准问法、答案选项、影响子组/疾病、动作、阴性限制、不确定处理） |
| **存储方式** | **新增节点 + 关系**（可选）或**配置文件** |
| **具体设计** | **方案1（推荐）**：创建节点类型`DifferentialPoint`（关键差异点），建立关系：`ChiefComplaint -[:HAS_DIFFERENTIAL_POINT]-> DifferentialPoint`，`DifferentialPoint -[:AFFECTS]-> ReasoningSubgroup`，`DifferentialPoint -[:AFFECTS]-> Disease`<br>**方案2（简化）**：存储在配置文件`chief_complaint_differential_points.yaml`中 |
| **说明** | 关键差异点是独立的实体，可以影响多个子组和疾病。如果差异点需要独立查询和推理，采用方案1；如果仅作为配置，采用方案2 |
| **节点属性（方案1）** | `differential_point_uuid`, `display_id`, `name: String`（差异点名称）, `standard_question: String`（标准问法）, `answer_options: String[]`（答案选项）, `negative_restriction: String`（阴性限制）, `uncertain_handling: String`（不确定处理） |
| **关系属性** | `action: String`（动作：前移/后移/保留/触发检查/触发升级）, `affected_entity_type: String`（影响实体类型：子组/疾病）, `created_at`, `version` |
| **配置文件结构（方案2）** | 存储在`chief_complaint_differential_points.yaml`中，格式：<br>```yaml<br>chief_complaint_differential_points:<br>  CC_001:<br>    differential_points:<br>      - point_id: "DP_单侧vs双侧"<br>        standard_question: "是一侧明显还是两侧差不多？"<br>        answer_options: ["单侧", "双侧", "不确定"]<br>        affects:<br>          - entity_type: "subgroup"<br>            entity_id: "SG_血栓风险组"<br>            action: "前移"<br>``` |
| **示例** | `(ChiefComplaint {display_id: "CC_001"}) -[:HAS_DIFFERENTIAL_POINT]-> (DifferentialPoint {name: "单侧 vs 双侧"})` |

## 📝 注意事项

1. **与第3项的关联**：主诉编号（display_id）必须与第3项中的ChiefComplaint节点对应，通过`display_id`关联
2. **与疾病知识图谱的关联**：推理子组（ReasoningSubgroup）与疾病知识图谱中的节点复用，避免重复创建
3. **与主诉澄清规则的关联**：主诉澄清规则基于《主诉澄清规则.md》的通用规则框架，特定主诉组合的规则是对通用规则的优化和细化
4. **配置文件索引**：所有配置文件都应按主诉ID（display_id）索引，便于查询和维护
5. **关系属性**：关系上应存储必要的元数据（priority、created_at、version等）
6. **版本管理**：节点和关系都应包含版本信息，支持版本管理和更新
