# 疾病知识图谱 - 字段存储方式分析

> **分析目标**：基于已有的"知识图谱设计-第3项-标准目录主数据"设计，逐条分析"疾病知识图谱.md"中每个字段的存储方式  
> **创建日期**：2026-02-03  
> **文档版本**：v1.0

---

## 📋 分析原则

基于混合存储方案的设计原则：
- **关系用图谱**：实体和关系存储在知识图谱中，支持推理和查询
- **配置用文件**：流程规则、判定标准、输出规则等存储在配置文件中，便于维护
- **已有实体扩展**：在第3项已有的Disease节点基础上扩展属性
- **新增节点**：需要独立查询和推理的实体创建新节点
- **新增关系**：需要表达实体间关系的创建关系边

## 逐条字段分析

### 字段1：疾病ID

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 与基础层疾病主数据关联的唯一键 |
| **存储方式** | **已有实体属性扩展** |
| **具体设计** | 作为Disease节点的`display_id`属性（第3项已有） |
| **说明** | 第3项中Disease节点已有`display_id`字段，格式为`DIS_XXX_001`，与此字段对应 |
| **示例** | `display_id: "DIS_DVT"` |

---

### 字段2：疾病标准名（可选）

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 基础层可直接取名则可不填；内容填写更直观时保留 |
| **存储方式** | **已有实体属性扩展** |
| **具体设计** | 作为Disease节点的`name`属性（第3项已有） |
| **说明** | 第3项中Disease节点已有`name`字段，存储标准名称 |
| **示例** | `name: "深静脉血栓形成"` |

---

### 字段3：疾病定义与边界

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 1-2句：这是什么病；与最相近疾病边界是什么 |
| **存储方式** | **已有实体属性扩展** |
| **具体设计** | 作为Disease节点的新增属性`definition`（String类型） |
| **说明** | 这是疾病的描述性信息，作为节点属性存储，便于查询和展示 |
| **示例** | `definition: "静脉内血栓形成致回流受阻；不等同表浅静脉炎"` |

---

### 字段4：典型表现模式

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 条目化：最常见的症状组合、部位特征、时间特征 |
| **存储方式** | **已有实体属性扩展** |
| **具体设计** | 作为Disease节点的新增属性`typical_manifestations`（String[]类型） |
| **说明** | 这是疾病的典型特征描述，作为节点属性存储。如果需要建立与具体症状的关系，可通过关系边实现 |
| **示例** | `typical_manifestations: ["单侧下肢肿胀", "疼痛/紧绷", "近期风险因素"]` |

---

### 字段5：非典型与易漏点

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 条目化：不典型但仍可能；提示不要因缺失就否定 |
| **存储方式** | **已有实体属性扩展** |
| **具体设计** | 作为Disease节点的新增属性`atypical_manifestations`（String[]类型） |
| **说明** | 这是疾病的非典型特征描述，作为节点属性存储 |
| **示例** | `atypical_manifestations: ["早期体征不明显", "可无明显疼痛"]` |

---

### 字段6：关键支持证据条目ID列表

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 引用证据条目库中最能支持本病的条目（分号分隔） |
| **存储方式** | **新增关系** |
| **具体设计** | 创建关系：`Disease -[:SUPPORTED_BY {evidence_type: "support"}]-> Evidence` |
| **说明** | 证据条目（Evidence）是独立实体（第7项），需要建立关系而非仅存储ID列表。关系属性`evidence_type`标识为支持证据 |
| **关系属性** | `evidence_type: "support"`, `priority: Integer`（优先级）, `created_at`, `version` |
| **示例** | `(Disease {display_id: "DIS_DVT"}) -[:SUPPORTED_BY {evidence_type: "support"}]-> (Evidence {display_id: "E_单侧肿胀"})` |

---

### 字段7：关键反对证据条目ID列表

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 引用明显不支持本病、会推动后移的条目 |
| **存储方式** | **新增关系** |
| **具体设计** | 创建关系：`Disease -[:OPPOSED_BY {evidence_type: "oppose"}]-> Evidence` |
| **说明** | 与支持证据类似，但关系类型为OPPOSED_BY，关系属性`evidence_type`标识为反对证据 |
| **关系属性** | `evidence_type: "oppose"`, `priority: Integer`（优先级）, `created_at`, `version` |
| **示例** | `(Disease {display_id: "DIS_DVT"}) -[:OPPOSED_BY {evidence_type: "oppose"}]-> (Evidence {display_id: "E_双侧对称性水肿"})` |

---

### 字段8：必须补齐的关键信息条目ID列表

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 若缺失就无法确认/排除本病的关键信息（缺口清单） |
| **存储方式** | **新增关系** |
| **具体设计** | 创建关系：`Disease -[:REQUIRES {evidence_type: "required"}]-> Evidence` |
| **说明** | 这是疾病诊断所需的关键证据，建立关系便于查询和推理 |
| **关系属性** | `evidence_type: "required"`, `is_critical: Boolean`（是否关键）, `created_at`, `version` |
| **示例** | `(Disease {display_id: "DIS_DVT"}) -[:REQUIRES {evidence_type: "required"}]-> (Evidence {display_id: "E_起病速度"})` |

---

### 字段9：易混疾病ID列表

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 最容易混淆、需要重点鉴别的疾病（分号分隔） |
| **存储方式** | **新增关系** |
| **具体设计** | 创建关系：`Disease -[:DIFFERENTIAL_WITH]-> Disease` |
| **说明** | 这是疾病与疾病之间的关系，表示需要鉴别诊断的疾病对 |
| **关系属性** | `priority: Integer`（鉴别优先级）, `created_at`, `version` |
| **示例** | `(Disease {display_id: "DIS_DVT"}) -[:DIFFERENTIAL_WITH]-> (Disease {display_id: "DIS_蜂窝织炎"})` |

---

### 字段10：关键鉴别点

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 条目化：用"维度：谁更支持谁"写清（不写问法） |
| **存储方式** | **新增节点 + 关系** |
| **具体设计** | 创建节点类型`DifferentialPoint`（鉴别点），建立关系：`Disease -[:HAS_DIFFERENTIAL_POINT]-> DifferentialPoint`，`DifferentialPoint -[:SUPPORTS]-> Disease` |
| **说明** | 鉴别点是独立的实体，可以复用。一个鉴别点可能涉及多个疾病，需要建立多对多关系 |
| **节点属性** | `differential_point_uuid`, `display_id`, `dimension: String`（维度）, `description: String`（描述） |
| **关系属性** | `supports_disease: String`（支持哪个疾病）, `created_at`, `version` |
| **示例** | `(Disease {display_id: "DIS_DVT"}) -[:HAS_DIFFERENTIAL_POINT]-> (DifferentialPoint {dimension: "皮肤红热痛", description: "蜂窝织炎更支持"})` |

**替代方案（简化）**：如果鉴别点不需要独立查询，可以存储在关系属性中：
- 关系：`Disease -[:DIFFERENTIAL_WITH {differential_points: String[]}]-> Disease`
- 关系属性：`differential_points: ["皮肤红热痛：蜂窝织炎更支持", "超声血栓：本病更支持"]`

---

### 字段11：输出依据口径

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 统一输出时证据条目数量与组织方式（简短） |
| **存储方式** | **配置文件** |
| **具体设计** | 存储在配置文件`disease_output_rules.yaml`中，按疾病ID索引 |
| **说明** | 这是输出格式规则，属于流程配置，不涉及实体关系，适合存储在配置文件中 |
| **配置文件结构** | 存储在`disease_output_rules.yaml`中，格式：<br>```yaml<br>disease_output_rules:<br>  DIS_DVT:<br>    evidence_count: "3-6条"<br>    organization: "关键依据"<br>``` |
| **示例** | `evidence_count: "输出列3-6条关键依据"` |

---

### 字段12：下一步建议（结构化写法）

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 固定写法：追问要点；建议检查；处置建议；升级就医条件 |
| **存储方式** | **已有实体属性扩展 + 新增关系** |
| **具体设计** | 部分作为属性：`next_steps: {追问: String[], 检查: String[], 处置: String[], 升级: String[]}`；检查建议建立关系：`Disease -[:REQUIRES_EXAMINATION]-> Examination` |
| **说明** | 追问要点和处置建议作为属性存储；检查建议建立与Examination节点的关系；升级条件可存储在配置文件中 |
| **属性示例** | `next_steps: {追问: ["血栓风险"], 检查: ["下肢静脉超声"], 处置: [], 升级: ["胸痛气促立即就医"]}` |
| **关系示例** | `(Disease {display_id: "DIS_DVT"}) -[:REQUIRES_EXAMINATION]-> (Examination {display_id: "EXAM_下肢静脉超声_001"})` |

---

### 字段13：验证判定标准（成立/排除阈值）

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 用规则/条目口径写清"满足什么算成立/基本排除"；必须包含"适用前提/阴性限制" |
| **存储方式** | **配置文件** |
| **具体设计** | 存储在配置文件`disease_validation_rules.yaml`中，按疾病ID和规则ID索引 |
| **说明** | 这是判定规则，属于流程配置，需要经常调整，适合存储在配置文件中 |
| **配置文件结构** | 存储在`disease_validation_rules.yaml`中，格式：<br>```yaml<br>disease_validation_rules:<br>  DIS_DVT:<br>    JD_DVT_成立_超声阳性:<br>      condition: "超声检查阳性"<br>      threshold: "成立"<br>      prerequisites: []<br>    JD_DVT_排除_满足前提下阴性:<br>      condition: "满足前提下阴性"<br>      threshold: "排除"<br>      prerequisites: []<br>``` |
| **示例** | `JD_DVT_成立_超声阳性`, `JD_DVT_排除_满足前提下阴性` |

---

| **存储方式** | **配置文件** |
| **具体设计** | 存储在配置文件`disease_feedback_rules.yaml`中，按疾病ID和规则ID索引 |
| **说明** | 这是流程控制规则，属于配置，适合存储在配置文件中 |
| **配置文件结构** | 存储在`disease_feedback_rules.yaml`中，格式：<br>```yaml<br>disease_feedback_rules:<br>  DIS_DVT:<br>    FB_DVT_超声阳性置顶:<br>      trigger: "超声阳性"<br>      action: "置顶"<br>    FB_DVT_阴性后移并转向替代组:<br>      trigger: "阴性"<br>      action: "后移并转向替代组"<br>      target_group: "SG_感染炎症组"<br>``` |
| **示例** | `FB_DVT_超声阳性置顶`, `FB_DVT_阴性后移并转向替代组` |

### 字段15：升级触发条件（疾病级红旗）

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 命中即中断常规推理→安全兜底/升级 |
| **存储方式** | **配置文件 + 新增关系（可选）** |
| **具体设计** | 主要存储在配置文件`disease_escalation_rules.yaml`中；如果升级条件涉及具体证据，可建立关系：`Disease -[:ESCALATION_TRIGGER]-> Evidence` |
| **说明** | 升级规则是流程控制，主要存储在配置文件；如果升级条件涉及具体证据条目，可以建立关系便于查询 |
| **配置文件结构** | 存储在`disease_escalation_rules.yaml`中，格式：<br>```yaml<br>disease_escalation_rules:<br>  DIS_DVT:<br>    ESC_DVT_胸痛或明显气促:<br>      conditions: ["胸痛", "明显气促"]<br>      action: "立即就医"<br>      priority: "high"<br>    ESC_DVT_晕厥或咯血:<br>      conditions: ["晕厥", "咯血"]<br>      action: "立即就医"<br>      priority: "critical"<br>``` |
| **关系示例（可选）** | `(Disease {display_id: "DIS_DVT"}) -[:ESCALATION_TRIGGER]-> (Evidence {display_id: "E_胸痛"})` |

### 字段16：来源条目ID（可选）

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 只填内部来源条目ID（不写书目） |
| **存储方式** | **已有实体属性扩展** |
| **具体设计** | 作为Disease节点的新增属性`source_entry_ids`（String[]类型） |
| **说明** | 这是来源追溯信息，作为节点属性存储。如果需要建立与来源文档的关系，可通过工程层的Document节点实现 |
| **示例** | `source_entry_ids: ["REF_DVT_001"]` |

### 字段17：推理子组归属

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 该病主要归入哪个"线索簇/推进组"（用于挂接主诉Step3） |
| **存储方式** | **新增节点 + 关系** |
| **具体设计** | 创建节点类型`ReasoningSubgroup`（推理子组），建立关系：`Disease -[:BELONGS_TO_SUBGROUP]-> ReasoningSubgroup` |
| **说明** | 推理子组是独立的实体，可以组织多个疾病，便于推理路径管理 |
| **节点属性** | `subgroup_uuid`, `display_id`, `name: String`, `description: String` |
| **关系属性** | `priority: Integer`（在子组中的优先级）, `created_at`, `version` |
| **示例** | `(Disease {display_id: "DIS_DVT"}) -[:BELONGS_TO_SUBGROUP]-> (ReasoningSubgroup {display_id: "SG_血栓风险线索组"})` |

---

### 字段18：分流路径中的位置

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 标注默认分层/阶段（如Tier2必须优先除外） |
| **存储方式** | **已有实体属性扩展** |
| **具体设计** | 作为Disease节点的新增属性`tier_level: String`和`priority_tag: String` |
| **说明** | 这是疾病的分层和优先级标记，作为节点属性存储，便于查询和排序 |
| **示例** | `tier_level: "Tier2"`, `priority_tag: "must-not-miss"` |

---

### 字段19：验证计划

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 优先验证路径（追问/检查的组合路径ID列表） |
| **存储方式** | **配置文件** |
| **具体设计** | 存储在配置文件`disease_validation_plans.yaml`中，按疾病ID和计划ID索引 |
| **说明** | 这是验证路径的配置，属于流程规则，适合存储在配置文件中 |
| **配置文件结构** | 存储在`disease_validation_plans.yaml`中，格式：<br>```yaml<br>disease_validation_plans:<br>  DIS_DVT:<br>    VP_DVT_超声优先:<br>      path: ["追问: 血栓风险", "检查: 下肢静脉超声"]<br>      priority: 1<br>    VP_DVT_高危先兜底:<br>      path: ["检查: 下肢静脉超声", "追问: 高危因素"]<br>      priority: 2<br>``` |
| **示例** | `VP_DVT_超声优先`, `VP_DVT_高危先兜底` |

### 字段20：检查价值评估

| 分析项 | 内容 |
|--------|------|
| **字段含义** | 必要/可选/低价值 + 适用前提一句话 |
| **存储方式** | **新增关系属性** |
| **具体设计** | 在关系`Disease -[:REQUIRES_EXAMINATION]-> Examination`上添加属性：`value_level: String`（必要/可选/低价值）, `prerequisite: String`（适用前提） |
| **说明** | 这是疾病与检查关系的属性，描述检查的价值和适用条件 |
| **关系属性** | `value_level: "必要"`, `prerequisite: "Tier2触发"`, `created_at`, `version` |
| **示例** | `(Disease {display_id: "DIS_DVT"}) -[:REQUIRES_EXAMINATION {value_level: "必要", prerequisite: "Tier2触发"}]-> (Examination {display_id: "EXAM_下肢静脉超声_001"})` |

### 2. 新增关系类型

```cypher
// 疾病与证据的关系
(Disease)-[:SUPPORTED_BY {evidence_type: "support", priority: Integer}]->(Evidence)
(Disease)-[:OPPOSED_BY {evidence_type: "oppose", priority: Integer}]->(Evidence)
(Disease)-[:REQUIRES {evidence_type: "required", is_critical: Boolean}]->(Evidence)
(Disease)-[:ESCALATION_TRIGGER]->(Evidence)  // 可选

(Disease)-[:DIFFERENTIAL_WITH {priority: Integer, differential_points: String[]}]->(Disease)
```

## 📝 注意事项

1. **与第3项的关联**：疾病ID（display_id）必须与第3项中的Disease节点对应，通过`display_id`关联
2. **与第7项的关联**：证据条目（Evidence）是独立实体，需要通过关系建立关联，而不是仅存储ID列表
3. **配置文件索引**：所有配置文件都应按疾病ID（display_id）索引，便于查询和维护
4. **关系属性**：关系上应存储必要的元数据（confidence、priority、created_at、version等）
5. **版本管理**：节点和关系都应包含版本信息，支持版本管理和更新
