# 知识图谱设计-第6项-疾病模板

> **设计目标**：基于"知识图谱设计-第3项-标准目录主数据"和"疾病知识图谱-字段分析"，设计疾病模板（第6项）的知识图谱结构  
> **创建日期**：2026-01-28  
> **文档版本**：v1.0

---

## 📋 设计总览

**设计范围**：
- 在第3项已有的Disease节点基础上扩展属性
- 新增疾病与证据、疾病与疾病、疾病与检查、疾病与推理子组的关系
- 新增推理子组节点类型（可选：鉴别点节点）
- 配置文件部分不在本文档范围内

**设计原则**：
- 与第3项无缝集成：通过`display_id`关联已有Disease节点
- 关系用图谱：实体和关系存储在知识图谱中，支持推理和查询
- 支持证据追溯：关系边链接到证据chunk（工程层）
- 版本管理：节点和关系都包含版本信息

## 步骤0：双层Schema定义

### 0.1 语义层（Ontology/Concept Schema）

**核心实体类型**（基于第3项扩展）：
- **Disease**（疾病）：标准疾病目录中的疾病实体（第3项已有，第6项扩展属性）
- **Evidence**（证据条目）：证据条目库中的证据实体（第7项）
- **Examination**（检查）：检验项目目录中的检查实体（第3项已有）
- **ReasoningSubgroup**（推理子组）：线索簇/推进组实体（第6项新增）
- **DifferentialPoint**（鉴别点）：疾病鉴别点实体（第6项新增，可选）

**关系类型**：
- **SUPPORTED_BY**：疾病被证据支持
- **OPPOSED_BY**：疾病被证据反对
- **REQUIRES**：疾病需要证据
- **DIFFERENTIAL_WITH**：疾病需要与另一疾病鉴别
- **REQUIRES_EXAMINATION**：疾病需要检查
- **BELONGS_TO_SUBGROUP**：疾病属于推理子组
- **HAS_DIFFERENTIAL_POINT**：疾病有鉴别点（可选）
- **ESCALATION_TRIGGER**：疾病升级触发条件（可选）

### 0.2 工程层（Ingestion & Retrieval Schema）

**核心节点类型**（继承自通用设计）：
- **Document**：源文档（指南、论文、教材等）
- **Chunk**：文档片段（含向量嵌入），用于GraphRAG
- **Mention**：实体提及（在文本中的出现位置）
- **Evidence**：证据节点（链接到chunk）
- **Source**：数据来源（文档、版本、作者等）
- **Version**：版本信息（指南版本、更新日期等）

**核心关系类型**：
- **Document → Chunk**：文档包含词块
- **Chunk → Mention**：词块包含实体提及
- **Mention → Entity**：提及指向实体
- **Edge → Evidence**：关系边链接到证据chunk
- **Entity → Source**：实体链接到来源文档

### 0.3 两层Schema的关联

**关联方式**：
- 语义层的Disease节点通过`Mention`节点链接到工程层的`Chunk`
- 语义层的关系边通过`Evidence`节点链接到工程层的`Chunk`
- 工程层的`Source`和`Version`节点为语义层实体提供来源和版本信息

**示例结构**：
```
语义层：Disease(深静脉血栓) --[SUPPORTED_BY]--> Evidence(单侧肿胀)
         ↓                                    ↓
工程层：Mention --[IN_CHUNK]--> Chunk --[FROM_DOC]--> Document(指南v2.0)
```

## 步骤1：业务场景 & Query Set

### 1.1 业务目标

**需要回答的问题**：
- 如何根据症状推理候选疾病？
- 如何查询疾病的支持证据和反对证据？
- 如何查询疾病需要的关键信息？
- 如何查询需要鉴别诊断的疾病？
- 如何查询疾病需要的检查？
- 如何查询疾病所属的推理子组？
- 如何查询疾病的鉴别点？

### 1.2 业务场景

| 场景编号 | 场景描述 | 涉及的实体 | 涉及的关系 |
|---------|---------|-----------|-----------|
| **场景1** | 用户说"单侧下肢肿胀"，系统推理可能的疾病 | Disease, Evidence | Disease -[:SUPPORTED_BY]-> Evidence |

| **场景5** | 系统需要查询"深静脉血栓"所属的推理子组 | Disease, ReasoningSubgroup | Disease -[:BELONGS_TO_SUBGROUP]-> ReasoningSubgroup |
| **场景6** | 系统需要查询"深静脉血栓"需要的关键信息 | Disease, Evidence | Disease -[:REQUIRES]-> Evidence |

## 步骤2：本体设计

### 2.1 核心实体类型（Classes）

**实体层次结构**：

```
医学实体（第3项已有）
├── 疾病类（Disease）- 第3项已有，第6项扩展
│   ├── 急性疾病
│   └── 慢性疾病
├── 证据类（Evidence）- 第7项
│   ├── 支持证据
│   ├── 反对证据
│   └── 必需证据
├── 检查类（Examination）- 第3项已有
│   ├── 实验室检查
│   ├── 影像检查
│   └── 功能检查
└── 推理子组类（ReasoningSubgroup）- 第6项新增
    ├── 线索簇
    └── 推进组
```

### 2.2 关系类型设计

**关系层级结构**：

```
医学关系
├── 证据关系
│   ├── SUPPORTED_BY（疾病被证据支持）
│   ├── OPPOSED_BY（疾病被证据反对）
│   └── REQUIRES（疾病需要证据）
├── 疾病关系
│   ├── DIFFERENTIAL_WITH（疾病需要与另一疾病鉴别）
│   └── HAS_DIFFERENTIAL_POINT（疾病有鉴别点）
├── 检查关系
│   └── REQUIRES_EXAMINATION（疾病需要检查）
└── 组织关系
    └── BELONGS_TO_SUBGROUP（疾病属于推理子组）
```

### 2.3 关系规范化字典（Relation Canonicalization）

| 规范关系名称 | 同义表达 | 方向 | 允许头节点类型 | 允许尾节点类型 | 默认置信度 |
|------------|---------|------|--------------|--------------|-----------|
| `SUPPORTED_BY` | 支持、有利于、增强、提示 | Disease → Evidence | Disease | Evidence | 0.7 |
| `OPPOSED_BY` | 反对、不利于、削弱、排除 | Disease → Evidence | Disease | Evidence | 0.7 |
| `REQUIRES` | 需要、必须、要求、关键 | Disease → Evidence | Disease | Evidence | 0.8 |
| `DIFFERENTIAL_WITH` | 鉴别诊断、需要区分、需排除、易混淆 | Disease ↔ Disease | Disease | Disease | 0.75 |
| `REQUIRES_EXAMINATION` | 需要检查、应做检查、建议检查 | Disease → Examination | Disease | Examination | 0.9 |
| `BELONGS_TO_SUBGROUP` | 属于、归入、属于子组 | Disease → ReasoningSubgroup | Disease | ReasoningSubgroup | 0.85 |
| `HAS_DIFFERENTIAL_POINT` | 有鉴别点、鉴别要点 | Disease → DifferentialPoint | Disease | DifferentialPoint | 0.7 |
| `ESCALATION_TRIGGER` | 升级触发、红旗信号 | Disease → Evidence | Disease | Evidence | 0.9 |

## 步骤3：抽取设计

> **说明**：疾病模板是结构化数据，主要通过表格文件导入，不需要LLM抽取。本节主要说明数据导入流程。

### 3.1 数据来源

**主要数据来源**：
1. **疾病模板表格文件**：包含疾病详细属性（定义、典型表现、非典型表现等）
2. **证据条目库**：证据条目实体（第7项）
3. **标准目录主数据**：疾病、检查实体（第3项）

### 3.2 导入方法

**方法1：表格文件直接导入**
- 从疾病模板表格文件读取疾病详细属性
- 更新已有Disease节点（通过`display_id`关联）
- 设置新增属性

**方法2：关系建立**
- 根据证据条目ID列表建立疾病与证据的关系
- 根据易混疾病ID列表建立疾病与疾病的关系
- 根据检查建议建立疾病与检查的关系
- 根据推理子组归属建立疾病与推理子组的关系

### 3.3 导入流程

```
步骤1：读取疾病模板表格文件
  ↓
步骤2：通过display_id查找已有Disease节点（第3项）
  ↓
步骤3：更新Disease节点属性（新增第6项属性）
  ↓
步骤4：创建推理子组节点（如果不存在）
  ↓
步骤5：建立疾病与证据的关系（SUPPORTED_BY、OPPOSED_BY、REQUIRES）
  ↓
步骤6：建立疾病与疾病的关系（DIFFERENTIAL_WITH）
  ↓
步骤7：建立疾病与检查的关系（REQUIRES_EXAMINATION）
  ↓
步骤8：建立疾病与推理子组的关系（BELONGS_TO_SUBGROUP）
  ↓
步骤9：创建鉴别点节点和关系（可选）
  ↓
步骤10：链接到来源文档（工程层）
  ↓
步骤11：验证数据完整性
```

## 步骤4：实体归并/去重 + 标准编码对齐

### 4.1 实体归并策略

**归并场景**：
- 疾病模板中的疾病ID（display_id）必须与第3项中的Disease节点对应
- 证据条目ID必须与第7项中的Evidence节点对应
- 检查项目ID必须与第3项中的Examination节点对应

**归并方法**：
1. **ID精确匹配**：通过`display_id`精确匹配已有实体
2. **名称匹配**：如果ID不匹配，通过名称匹配（备用方案）
3. **编码匹配**：通过标准编码（ICD-10、SNOMED等）匹配

### 4.2 标准编码对齐

**对齐策略**：
- 疾病编码：与第3项中的Disease节点编码对齐（ICD-10、ICD-11、SNOMED CT）
- 检查编码：与第3项中的Examination节点编码对齐
- 证据编码：与第7项中的Evidence节点编码对齐

### 4.3 归并对齐流程

```
步骤1：读取疾病模板数据
  ↓
步骤2：通过display_id查找已有Disease节点
  ↓
步骤3：验证实体存在性（如果不存在，记录错误）
  ↓
步骤4：通过证据ID查找Evidence节点（第7项）
  ↓
步骤5：通过检查ID查找Examination节点（第3项）
  ↓
步骤6：标准编码对齐验证
  ↓
步骤7：生成稳定ID（如果使用UUID）
  ↓
最终实体列表（已归并对齐、有稳定ID）
```

## 步骤7：图模型设计

### 7.1 节点设计

**节点类型**：
- **Disease**：疾病节点（第3项已有，第6项扩展属性）
- **Evidence**：证据条目节点（第7项）
- **Examination**：检查节点（第3项已有）
- **ReasoningSubgroup**：推理子组节点（第6项新增）
- **DifferentialPoint**：鉴别点节点（第6项新增，可选）

**节点标签设计**：
- 使用英文标签：`Disease`、`Evidence`、`Examination`、`ReasoningSubgroup`、`DifferentialPoint`
- 标签清晰、简洁、符合命名规范

### 7.2 边设计

**关系类型**：
- **SUPPORTED_BY**：疾病被证据支持
- **OPPOSED_BY**：疾病被证据反对
- **REQUIRES**：疾病需要证据
- **DIFFERENTIAL_WITH**：疾病需要与另一疾病鉴别
- **REQUIRES_EXAMINATION**：疾病需要检查
- **BELONGS_TO_SUBGROUP**：疾病属于推理子组
- **HAS_DIFFERENTIAL_POINT**：疾病有鉴别点（可选）
- **ESCALATION_TRIGGER**：疾病升级触发条件（可选）

**边类型定义**：
- 关系边清晰表达语义关系
- 支持证据追溯（通过`source_chunk_id`属性）

### 7.3 索引设计

**索引类型**：

| 索引类型 | 索引字段 | 用途 |
|---------|---------|------|
| **节点属性索引** | `display_id`、`name` | 加速节点查询 |
| **节点属性索引** | `tier_level`、`priority_tag` | 加速分层和优先级查询 |
| **关系属性索引** | `evidence_type`、`priority` | 加速关系查询和过滤 |
| **关系属性索引** | `source_chunk_id` | 加速证据追溯查询 |
| **关系属性索引** | `value_level` | 加速检查价值查询 |
| **复合索引** | `(display_id, version)` | 加速版本查询 |

### 7.4 图结构示例

```
// 疾病与证据的关系
(Disease {display_id: "DIS_DVT"})
  -[:SUPPORTED_BY {evidence_type: "support", priority: 1}]-> (Evidence {display_id: "E_单侧肿胀"})
  -[:OPPOSED_BY {evidence_type: "oppose", priority: 1}]-> (Evidence {display_id: "E_双侧对称性水肿"})
  -[:REQUIRES {evidence_type: "required", is_critical: true}]-> (Evidence {display_id: "E_起病速度"})

// 疾病与疾病的关系
(Disease {display_id: "DIS_DVT"})
  -[:DIFFERENTIAL_WITH {priority: 1, differential_points: ["皮肤红热痛：蜂窝织炎更支持"]}]-> 
  (Disease {display_id: "DIS_蜂窝织炎"})

// 疾病与检查的关系
(Disease {display_id: "DIS_DVT"})
  -[:REQUIRES_EXAMINATION {value_level: "必要", prerequisite: "Tier2触发"}]-> 
  (Examination {display_id: "EXAM_下肢静脉超声_001"})

// 疾病与推理子组的关系

  -[:BELONGS_TO_SUBGROUP {priority: 1}]->
```

### 10.2 查询路径验证

**查询路径示例**：

```cypher
// 查询路径1：查询疾病的支持证据
MATCH (d:Disease {display_id: "DIS_DVT"})-[:SUPPORTED_BY]->(e:Evidence)
RETURN d.name, e.display_id, e.name
ORDER BY e.priority

// 查询路径2：查询疾病的反对证据
MATCH (d:Disease {display_id: "DIS_DVT"})-[:OPPOSED_BY]->(e:Evidence)
RETURN d.name, e.display_id, e.name
ORDER BY e.priority

// 查询路径3：查询疾病需要的关键信息
MATCH (d:Disease {display_id: "DIS_DVT"})-[:REQUIRES {is_critical: true}]->(e:Evidence)
RETURN d.name, e.display_id, e.name

// 查询路径4：查询需要鉴别诊断的疾病
MATCH (d1:Disease {display_id: "DIS_DVT"})-[:DIFFERENTIAL_WITH]->(d2:Disease)
RETURN d1.name, d2.display_id, d2.name, d2.priority
ORDER BY d2.priority

// 查询路径5：查询疾病需要的检查
MATCH (d:Disease {display_id: "DIS_DVT"})-[:REQUIRES_EXAMINATION]->(e:Examination)
RETURN d.name, e.display_id, e.name, e.value_level, e.prerequisite
ORDER BY e.value_level

// 查询路径6：查询疾病所属的推理子组
MATCH (d:Disease {display_id: "DIS_DVT"})-[:BELONGS_TO_SUBGROUP]->(sg:ReasoningSubgroup)
RETURN d.name, sg.display_id, sg.name, sg.priority
ORDER BY sg.priority

// 查询路径7：查询关系的证据来源（证据追溯）
MATCH (d:Disease {display_id: "DIS_DVT"})-[r:SUPPORTED_BY]->(e:Evidence)
MATCH (c:Chunk) WHERE c.chunk_id IN r.source_chunk_id
MATCH (c)-[:FROM_DOC]->(doc:Document)
RETURN d.name, e.display_id, e.name, c.text, doc.name, doc.version

// 查询路径8：根据证据查询支持的疾病
MATCH (e:Evidence {display_id: "E_单侧肿胀"})<-[:SUPPORTED_BY]-(d:Disease)
RETURN d.display_id, d.name, d.tier_level, d.priority_tag
ORDER BY d.priority_tag, d.tier_level
```

## 📊 设计总结

### 核心设计要点

1. **与第3项无缝集成**：通过`display_id`关联已有Disease节点，扩展属性而非创建新节点
2. **关系用图谱**：所有实体关系存储在知识图谱中，支持推理和查询
3. **支持证据追溯**：每条关系边都包含`source_chunk_id`，支持证据追溯
4. **版本管理**：节点和关系都包含版本信息，支持版本管理和更新
5. **新增节点类型**：推理子组（ReasoningSubgroup）和鉴别点（DifferentialPoint，可选）

### 与其他知识内容的关联

- **与第3项的关联**：通过`display_id`关联Disease和Examination节点
- **与第7项的关联**：通过`display_id`关联Evidence节点，建立支持/反对/需要关系
- **与工程层的关联**：通过`source_chunk_id`链接到Chunk节点，支持证据追溯
