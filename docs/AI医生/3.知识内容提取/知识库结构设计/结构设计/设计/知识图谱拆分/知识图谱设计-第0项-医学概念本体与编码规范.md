# 知识图谱设计 - 第0项：医学概念本体与编码规范

> **设计目标**：为医学概念本体与编码规范设计知识图谱结构，支持编码信息的存储、查询和关联。  
> **创建日期**：2026-01-28  
> **文档版本**：v1.0

---

## 📋 设计总览

**第0项的特点**：
- **存储形式**：表格文件（源数据）+ 知识图谱（节点属性）
- **核心内容**：医学概念的标准名称和各类编码（症状编码、疾病编码、检查编码、治疗编码等）
- **设计重点**：编码信息作为节点属性存储，便于查询和关联

**设计原则**：
- 编码信息作为节点属性，不单独创建编码节点
- 支持多编码体系并存（ICD-10、ICD-11、SNOMED CT等）
- 编码信息与实体节点紧密绑定，便于查询和关联

## 步骤0：双层Schema定义

### 0.1 语义层（Ontology/Concept Schema）

**核心实体类型**：
- **Symptom**（症状）：包含症状编码
- **Disease**（疾病）：包含疾病编码
- **Examination**（检查）：包含检查编码
- **Treatment**（治疗）：包含治疗编码
- **Sign**（体征）：包含体征编码
- **Indicator**（指标）：包含指标编码
- **Drug**（药物）：包含药物编码
- **ChiefComplaint**（主诉）：包含主诉编码

**编码属性设计**：
- 每个实体节点包含对应的编码属性
- 支持多编码体系并存
- 编码作为节点属性，不创建独立的编码节点

### 0.2 工程层（Ingestion & Retrieval Schema）

**编码数据的来源**：
- **Document**：编码标准文档（ICD-10、ICD-11、SNOMED CT等）
- **Chunk**：编码定义和说明的文本片段
- **Source**：编码来源（标准体系、版本等）

**编码数据的追溯**：
- 每个编码属性可以链接到来源文档
- 支持编码版本管理和更新历史

### 0.3 两层Schema的关联

**关联方式**：
- 语义层实体的编码属性通过`Source`节点链接到工程层的`Document`
- 编码的更新历史通过`Version`节点管理

### 2.3 编码对齐关系设计

**编码对齐关系**：
- **ALIGNED_WITH**：不同编码体系之间的对齐关系
- 关系属性：`alignment_confidence`（对齐置信度）、`alignment_method`（对齐方法）

**示例**：
```
Disease(心绞痛) 
  - icd10_code: "I20.9"
  - icd11_code: "BA40.Z"
  - snomed_code: "194828000"
  
关系：ICD-10编码"I20.9" ALIGNED_WITH ICD-11编码"BA40.Z" (confidence: 0.95)
```

## 步骤3：抽取设计

### 3.1 数据来源

**主要数据来源**：
1. **标准编码表格文件**：包含所有医学概念的编码信息
2. **编码标准文档**：ICD-10、ICD-11、SNOMED CT等标准文档
3. **医学词典**：标准医学术语词典

### 3.2 抽取方法

**方法1：表格文件导入**
- 从表格文件直接读取编码信息
- 批量导入到知识图谱节点属性

**方法2：标准文档抽取**
- 从ICD-10、ICD-11等标准文档中抽取编码定义
- 使用规则抽取或LLM抽取

**方法3：编码对齐**
- 通过名称匹配、语义匹配等方法对齐不同编码体系

### 3.3 抽取流程

```
步骤1：读取表格源数据
  ↓
步骤2：创建/更新实体节点
  ↓
步骤3：设置编码属性
  ↓
步骤4：建立编码对齐关系
  ↓
步骤5：链接到来源文档
  ↓
步骤6：验证编码完整性
```

## 步骤4：实体归并/去重 + 标准编码对齐

### 4.1 编码对齐策略

**两级对齐策略**：

**第一批（MVP阶段）**：
- 使用内部临时编码
- 快速验证MVP，不依赖外部编码体系
- 格式：`TEMP_SYM_001`、`TEMP_DIS_001`等

**第二批（增强阶段）**：
- 对齐到ICD-10、ICD-11、SNOMED CT等标准编码
- 保留未对齐原因和候选编码
- 支持多编码体系并存

### 4.2 对齐方法

**方法1：精确匹配**
- 实体名称与标准编码体系的名称完全匹配

**方法2：模糊匹配**
- 使用编辑距离、同义词库进行匹配

**方法3：语义匹配**
- 使用向量嵌入计算语义相似度

**方法4：人工审核**
- 对于高价值实体，进行人工审核对齐

### 4.3 对齐结果存储

**对齐结果属性**：

| 属性名 | 数据类型 | 说明 | 示例 |
|--------|---------|------|------|
| `icd10_code` | String | ICD-10编码 | `I20.9` |
| `icd11_code` | String | ICD-11编码 | `BA40.Z` |
| `snomed_code` | String | SNOMED CT编码 | `194828000` |
| `alignment_confidence` | Float | 对齐置信度 | `0.95` |
| `alignment_method` | String | 对齐方法 | `exact_match`、`semantic_match` |
| `unmapped_reason` | String | 未对齐原因 | `not_found_in_icd10` |

## 📊 设计总结

### 核心设计要点

1. **编码作为节点属性**：编码信息直接存储在实体节点属性中，不创建独立的编码节点
2. **多编码体系支持**：支持ICD-10、ICD-11、SNOMED CT等多种编码体系并存
3. **编码对齐机制**：支持不同编码体系之间的对齐和映射
4. **编码来源追溯**：每个编码都可以追溯到来源文档和版本

### 与表格文件的协同

- **表格文件**：作为源数据，便于批量管理和导入
- **知识图谱**：编码作为节点属性存储，支持高效查询和关联
- **数据流转**：表格文件 → 导入脚本 → 知识图谱节点属性
