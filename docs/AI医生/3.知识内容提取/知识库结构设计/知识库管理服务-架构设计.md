# 知识库管理服务 - 架构设计

> **设计目标**：为知识库的导入、清洗、管理设计完整的架构方案  
> **创建日期**：2026-01-28  
> **文档版本**：v1.0

---

## 📋 架构总览

### 服务定位说明

**knowledge-management-service是独立的管理服务，不参与诊断流程**：

- ✅ **独立管理服务**：knowledge-management-service是独立的管理服务，专门负责知识库的导入、清洗、验证、版本管理
- ✅ **不参与诊断流程**：知识库管理服务不参与主Agent的诊断流程，只负责知识库的维护和管理
- ✅ **与诊断服务分离**：知识库管理服务与diagnosis-engine-service、clinical-parsing-service等诊断服务分离，职责清晰
- ✅ **数据提供者角色**：知识库管理服务是知识库数据的提供者，诊断服务是知识库数据的使用者

**架构关系**：

```
知识库管理服务（knowledge-management-service）
  ↓ 导入知识库内容
知识图谱（Neo4j）
配置文件（文件系统）
表格文件（文件系统）
  ↓ 知识库内容更新
诊断服务（diagnosis-engine-service、clinical-parsing-service等）
  ↓ 重新加载知识库
工具（Tools）内部调用知识库
  ↓ 返回结构化结果
主Agent写入CDP
```

### 推荐方案：独立后端服务 + 管理端界面

**架构组成**：
1. **knowledge-management-service**（后端服务）：负责知识库的导入、清洗、验证、管理
2. **frontend-admin**（管理端界面）：提供可视化的知识库管理界面
3. **数据存储**：知识图谱（Neo4j）、表格文件（CSV/Excel）、配置文件（YAML）

**架构优势**：
- ✅ **职责清晰**：后端专注业务逻辑，前端专注展示交互
- ✅ **独立部署**：知识库管理服务可独立部署和扩展
- ✅ **易于维护**：代码组织清晰，便于长期维护
- ✅ **可扩展性强**：后续可增加API接口供其他服务调用
- ✅ **统一管理**：在管理端统一管理所有知识内容
- ✅ **服务分离**：管理服务与诊断服务分离，不影响诊断流程

### 1. 后端服务：knowledge-management-service

#### 1.1 服务定位

**服务职责**：
- 知识图谱数据导入、清洗、验证
- 表格文件解析、转换、导入
- 配置文件验证、管理
- 知识库版本管理
- 数据质量检查
- 导入任务调度和监控

**技术栈**：
- **框架**：FastAPI（与现有服务保持一致）
- **图数据库**：Neo4j（与diagnosis-engine-service共用）
- **文件处理**：pandas、openpyxl、PyYAML
- **任务调度**：Celery（可选，用于异步导入任务）

## 🔄 数据流转

### 导入流程

```
1. 用户上传文件（前端）
   ↓
2. 文件上传到后端（POST /api/v1/import/...）
   ↓
3. 后端保存文件到 data/source/
   ↓
4. 执行数据清洗（DataCleaner）
   ↓
5. 执行导入（Importer）
   ↓
6. 数据验证（Validator）
   ↓
7. 返回导入结果（前端显示）
```

### 版本管理流程

```
1. 创建版本快照（VersionService）
   ↓
2. 保存到版本库
   ↓
3. 版本对比（可选）
   ↓
4. 版本回滚（如需要）
```

## 🔗 与其他服务的关系

### 1. 与diagnosis-engine-service的关系

**关系说明**：
- **数据提供者与使用者**：knowledge-management-service是知识库数据的提供者，diagnosis-engine-service是知识库数据的使用者
- **共享Neo4j数据库**：两个服务连接同一个Neo4j实例，knowledge-management-service写入，diagnosis-engine-service读取
- **数据同步机制**：
  - knowledge-management-service导入数据后，diagnosis-engine-service自动可用（共享数据库）
  - 配置文件更新后，需要通知diagnosis-engine-service重新加载配置文件
- **版本控制**：导入新版本时，可通知diagnosis-engine-service重新加载，或通过配置版本号控制

**协作流程**：
```
1. knowledge-management-service导入知识库内容
   ↓
2. 知识库内容写入Neo4j/文件系统
   ↓
3. diagnosis-engine-service检测到知识库更新（或收到通知）
   ↓
4. diagnosis-engine-service重新加载知识库内容
   ↓
5. 工具（鉴别诊断工具）可以使用新知识库内容
```

### 2. 与clinical-parsing-service的关系

**关系说明**：
- **数据提供者与使用者**：knowledge-management-service是归一化词表和配置的提供者，clinical-parsing-service是使用者
- **词表同步**：
  - 归一化词表导入后，clinical-parsing-service需要重新加载词表（从文件系统读取）
  - 可以通过文件系统监控或通知机制触发重新加载
- **配置同步**：
  - 基础标准配置更新后，需要通知clinical-parsing-service重新加载
  - 可以通过配置版本号或文件系统监控实现

**协作流程**：
```
1. knowledge-management-service导入归一化词表/基础标准配置
   ↓
2. 词表/配置写入文件系统
   ↓
3. clinical-parsing-service检测到文件更新（或收到通知）
   ↓
4. clinical-parsing-service重新加载词表/配置到内存
   ↓
5. 工具（病例理解工具）可以使用新词表/配置
```

### 3. 与其他服务的关系

**关系说明**：
- **配置分发**：配置文件导入后，需要分发到对应的服务
  - diagnosis-engine-service：主诉配置、疾病配置、证据配置、规则文件（第5-13项）
  - health-state-assessment-service：入口判定规则、健康管理路径规则、入口角度统一转换规则（第14-16项）
  - risk-assessment-service：风险识别规则、高危规则、安全兜底规则（第12、17-18项）

**配置分发机制**：
1. **文件系统共享**：所有服务共享配置文件目录，knowledge-management-service写入，其他服务读取
2. **版本通知**：knowledge-management-service导入新配置后，通知对应服务重新加载
3. **热加载支持**：各服务支持配置文件热加载，无需重启服务

### 4. 与主Agent架构的关系

**关系说明**：
- **不直接交互**：knowledge-management-service不直接与主Agent交互
- **间接关系**：knowledge-management-service管理知识库内容，知识库内容被工具调用，工具返回结果给主Agent
- **架构定位**：
  - knowledge-management-service：知识库数据的管理者（管理服务）
  - 工具（Tools）：知识库数据的使用者（诊断服务）
  - 主Agent：工具调用的决策者（诊断服务）

**架构关系图**：
```
知识库管理服务（knowledge-management-service）
  ↓ 管理知识库内容
知识库（Neo4j/文件系统）
  ↓ 被工具调用
工具（diagnosis-engine-service、clinical-parsing-service等）
  ↓ 返回结构化结果
主Agent（diagnosis-service）
  ↓ 写入CDP + 记录AuditTrail
CDP + AuditTrail
```
