## 一、主诉模板配置文件

### 1.1 配置文件总览

主诉相关的配置包含以下7个配置文件：

| 配置文件 | 对应表/字段 | 说明 |
|---------|-----------|------|
| `chief_complaint_key_fields.yaml` | 主诉表2 - 最小关键字段配置 | 关键字段配置（起病时间、部位、分布、性质、严重度等） |
| `chief_complaint_red_flags.yaml` | 主诉表1 - 字段10：危险信号清单引用 | 引用规则层ID |
| `chief_complaint_stop_conditions.yaml` | 主诉表1 - 字段11：收敛/停止条件引用 | 引用规则层ID |
| `chief_complaint_escalation_rules.yaml` | 主诉表1 - 字段12：升级/转诊触发引用 | 引用规则层ID |
| `chief_complaint_clarification_rules.yaml` | 主诉表3 - 主诉澄清规则 | 特定主诉组合的澄清规则 |
| `chief_complaint_differential_points.yaml` | 主诉表8 - 关键差异点配置 | 关键差异点信息（如果采用配置文件方案） |
| `chief_complaint_trigger_rules.yaml` | 主诉表10 - 回填/重排/收敛触发点 | 触发规则信息 |

**文件位置**：`诊断引擎服务/数据/主诉配置/`

**注意**：
- 主诉表1的其他字段（主诉定义、包含范围、排除范围、适用人群、适用场景、默认入口方向）存储在知识图谱中作为ChiefComplaint节点的属性
- 主诉表4、5、6、7、9存储在知识图谱中作为节点和关系

    trigger_chief_complaints:

      - "呼吸困难"

    clarification_question: "你主要是不够气/喘不上气，还是胸口压闷为主？"
    # 答案选项
    answer_options:
      - "不够气"
      - "压闷"
      - "两者都有"
      - "不确定"
    # 判定结果
    judgment_results:
      不够气:
        action: "进入主诉"
        target_chief_complaint: "呼吸困难"
        remaining_symptoms: "进入S（伴随症状）"
      压闷:
        action: "进入主诉"
        target_chief_complaint: "胸闷"
        remaining_symptoms: "进入S（伴随症状）"

        action: "并行保留"
        target_chief_complaints:
          - "呼吸困难"
          - "胸闷"
    # 不确定兜底
    uncertain_fallback:
      action: "并行保留"
      safety_handling: "先走危险信号兜底"
      target_chief_complaints:
        - "呼吸困难"
        - "胸闷"
  
  # 胸痛 + 气短组合
  CC_胸痛_CC_气短:
    rule_id: "CHEST_PAIN_SPECIFIC_001"

    trigger_description: "胸痛和气短同时出现"

### 1.9 配置文件使用说明

#### 1.9.1 配置文件索引

所有主诉配置文件都按主诉ID（`display_id`）索引，例如：
- `CC_001` - 水肿
- `CC_CHEST_PAIN` - 胸痛
- `CC_DYSPNEA` - 呼吸困难

#### 1.9.2 与知识图谱的关联

主诉配置文件通过主诉ID（`display_id`）关联到知识图谱中的ChiefComplaint节点：

```cypher
// 知识图谱中的ChiefComplaint节点
ChiefComplaint {
  chief_complaint_uuid: String,
  display_id: "CC_001",  // 用于索引配置文件
  name: "水肿",
  definition: "组织间液体增多导致的肿胀表现",  // 在知识图谱中
  included_scopes: ["下肢肿胀", "眼睑肿胀"],  // 在知识图谱中
  // ... 其他属性
}
```

#### 1.9.3 系统调用流程

1. **从知识图谱查询主诉**：根据症状推理到主诉，获取主诉实体信息
2. **加载主诉配置**：根据主诉的`display_id`加载对应的配置文件
3. **应用规则**：根据诊断流程阶段，应用相应的规则（关键字段、澄清、触发等）
4. **输出结果**：根据触发规则和收敛条件，生成诊断结果

#### 1.9.4 配置文件更新

- 配置文件支持热加载，修改后自动重新加载
- 每个配置文件包含版本号和更新时间
- 建议使用Git进行版本控制

### 7.10 配置文件使用说明

#### 7.10.1 配置文件索引

所有疾病配置文件都按疾病ID（`display_id`）索引，例如：
- `DIS_DVT` - 深静脉血栓形成
- `DIS_AMI` - 急性心肌梗死
- `DIS_ANGINA` - 心绞痛

#### 7.10.2 与知识图谱的关联

疾病配置文件通过疾病ID（`display_id`）关联到知识图谱中的Disease节点：

```cypher
// 知识图谱中的Disease节点
Disease {
  disease_uuid: String,
  display_id: "DIS_DVT",  // 用于索引配置文件
  name: "深静脉血栓形成",
  // ... 其他属性
}
```

#### 7.10.3 系统调用流程

1. **从知识图谱查询疾病**：根据症状推理到疾病，获取疾病实体信息
2. **加载疾病配置**：根据疾病的`display_id`加载对应的配置文件
3. **应用规则**：根据诊断流程阶段，应用相应的规则（验证、回填、升级等）
4. **输出结果**：根据输出规则和证据链构建规则，生成诊断结果

#### 7.10.4 配置文件更新

- 配置文件支持热加载，修改后自动重新加载
- 每个配置文件包含版本号和更新时间
- 建议使用Git进行版本控制

## 十一、配置文件使用说明

### 10.1 配置文件加载顺序

1. **系统启动时**：
   - 加载基础标准配置
   - 加载所有规则配置文件
   - 按需加载主诉配置文件（延迟加载）

2. **诊断流程中**：
   - 根据识别的主诉加载对应主诉配置
   - 根据流程阶段加载对应规则配置

### 10.2 配置文件版本管理

- 每个配置文件包含版本号和更新时间
- 支持配置文件热加载（修改后自动重新加载）
- 建议使用Git进行版本控制

### 10.3 配置文件验证

- 启动时验证配置文件格式和必填字段
- 运行时验证配置引用的规则ID是否存在
- 定期检查配置文件完整性
