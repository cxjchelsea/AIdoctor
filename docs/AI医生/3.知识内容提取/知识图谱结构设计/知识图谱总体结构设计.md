# AI医生系统 - 知识图谱总体结构设计

> **设计目标**：整合第0项（编码规范）、第3项（标准目录主数据）、第5项（主诉模板）、第6项（疾病模板）的知识图谱设计，形成统一的总体结构设计文档  
> **创建日期**：2026-01-28  
> **文档版本**：v1.0

---

## 📋 文档总览

### 设计范围

本文档整合了AI医生系统知识图谱的四个核心模块：

1. **第0项：医学概念本体与编码规范** - 编码信息存储
2. **第3项：标准目录主数据** - 基础目录实体
3. **第5项：主诉模板** - 主诉知识扩展
4. **第6项：疾病模板** - 疾病知识扩展

### 设计原则

1. **关系用图谱，配置用文件** - 实体和关系存储在知识图谱中，流程规则存储在配置文件中
2. **渐进式扩展** - 第3项提供基础实体，第5、6项在此基础上扩展属性和关系
3. **实体复用** - 避免重复创建实体，通过`display_id`关联复用
4. **双层Schema** - 语义层（业务实体）和工程层（数据追溯）分离
5. **证据追溯** - 所有关系边链接到证据chunk，支持可解释性查询
6. **版本管理** - 节点和关系都包含版本信息，支持版本管理和更新

## 二、双层Schema设计

### 2.1 语义层（Ontology/Concept Schema）

**定义**：语义层定义医学领域的核心概念、实体类型和关系类型，关注临床语义的正确性。

#### 2.1.1 核心实体类型汇总

| 实体类型 | 来源模块 | 说明 | 主要属性 |
|---------|---------|------|---------|
| **Symptom** | 第3项 | 标准症状 | display_id, name, category, symptom_code, icd10_code, snomed_code |
| **ChiefComplaint** | 第3项+第5项 | 标准主诉（第3项基础，第5项扩展） | 第3项：display_id, name, category<br>第5项扩展：definition, included_scopes, excluded_scopes, applicable_populations, applicable_scenarios |
| **Disease** | 第3项+第6项 | 标准疾病（第3项基础，第6项扩展） | 第3项：display_id, name, category, icd10_code, icd11_code, snomed_code<br>第6项扩展：definition, typical_manifestations, atypical_manifestations, tier_level, priority_tag |
| **Examination** | 第3项 | 标准检查 | display_id, name, category, examination_type, examination_code, snomed_code |
| **Evidence** | 第7项（待设计） | 证据条目 | display_id, name, evidence_type, strength |
| **ReasoningSubgroup** | 第6项 | 推理子组 | display_id, name, description, entry_triggers, promotion_target, priority_gaps, promotion_path（第5项扩展） |
| **DifferentialFrameworkSubclass** | 第5项 | 鉴别诊断框架子类 | display_id, framework_type, subclass_name, subclass_boundary, must_not_miss_diseases |
| **DifferentialPoint** | 第5项+第6项 | 关键差异点/鉴别点 | display_id, name/dimension, standard_question, answer_options, negative_restriction, uncertain_handling |
| **Category** | 第3项 | 分类 | display_id, name, category_type, parent_category, level, description |
| **Treatment** | 第0项 | 治疗（编码规范） | display_id, name, treatment_code, drug_code |
| **Sign** | 第0项 | 体征（编码规范） | display_id, name, sign_code, snomed_code |
| **Indicator** | 第0项 | 指标（编码规范） | display_id, name, indicator_code, loinc_code, snomed_code |
| **Drug** | 第0项 | 药物（编码规范） | display_id, name, drug_code, atc_code, snomed_code |

#### 2.1.2 核心关系类型汇总

| 关系类型 | 方向 | 头节点 | 尾节点 | 来源模块 | 说明 |
|---------|------|--------|--------|---------|------|
| **BELONGS_TO** | → | Symptom/Disease/Examination | Category | 第3项 | 实体属于分类 |
| **HAS_CATEGORY** | → | Category | Category | 第3项 | 分类包含子分类（分类层级关系） |
| **ALIGNED_WITH** | ↔ | Entity | Entity | 第0项 | 编码对齐关系（不同编码体系之间的映射，可选） |
| **HAS_CANDIDATE_DISEASE** | → | ChiefComplaint | Disease | 第5项 | 主诉有候选疾病（三层候选） |
| **HAS_REASONING_SUBGROUP** | → | ChiefComplaint | ReasoningSubgroup | 第5项 | 主诉有推理子组 |
| **HAS_DIFFERENTIAL_SUBCLASS** | → | ChiefComplaint | DifferentialFrameworkSubclass | 第5项 | 主诉有鉴别诊断框架子类 |
| **HAS_DIFFERENTIAL_POINT** | → | ChiefComplaint | DifferentialPoint | 第5项 | 主诉有关键差异点 |
| **RECOMMENDS_EXAMINATION** | → | ChiefComplaint | Examination | 第5项 | 主诉推荐检查 |
| **SUPPORTED_BY** | → | Disease | Evidence | 第6项 | 疾病被证据支持 |
| **OPPOSED_BY** | → | Disease | Evidence | 第6项 | 疾病被证据反对 |
| **REQUIRES** | → | Disease | Evidence | 第6项 | 疾病需要证据 |
| **DIFFERENTIAL_WITH** | ↔ | Disease | Disease | 第6项 | 疾病需要与另一疾病鉴别 |
| **REQUIRES_EXAMINATION** | → | Disease | Examination | 第6项 | 疾病需要检查 |
| **BELONGS_TO_SUBGROUP** | → | Disease | ReasoningSubgroup | 第6项 | 疾病属于推理子组 |
| **HAS_DIFFERENTIAL_POINT** | → | Disease | DifferentialPoint | 第6项 | 疾病有鉴别点 |
| **ESCALATION_TRIGGER** | → | Disease | Evidence | 第6项 | 疾病升级触发条件（可选） |
| **CONTAINS_DISEASE** | → | DifferentialFrameworkSubclass/ReasoningSubgroup | Disease | 第5项+第6项 | 子类/子组包含疾病 |
| **AFFECTS** | → | DifferentialPoint | ReasoningSubgroup/Disease | 第5项 | 差异点影响子组/疾病 |
| **IS_STANDARD_FOR** | → | Symptom/ChiefComplaint/Disease | Concept | 第3项 | 标准目录实体是某个概念的标准术语（可选） |

### 2.2 工程层（Ingestion & Retrieval Schema）

**定义**：工程层定义知识抽取、存储、检索所需的技术结构，关注可追溯性和可维护性。

#### 2.2.1 核心节点类型

| 节点类型 | 说明 | 主要属性 |
|---------|------|---------|
| **Document** | 源文档 | doc_id, name, type, version, source_url |
| **Chunk** | 文档片段（含向量嵌入） | chunk_id, text, embedding, doc_id, chunk_index |
| **Mention** | 实体提及 | mention_id, text, start_pos, end_pos, chunk_id |
| **Evidence** | 证据节点 | evidence_id, chunk_id, confidence |
| **Source** | 数据来源 | source_id, source_type, version, author |
| **Version** | 版本信息 | version_id, version_number, created_at, description |
| **ExtractionRun** | 抽取运行记录 | run_id, model_name, prompt_version, created_at, metrics |

#### 2.2.2 核心关系类型

| 关系类型 | 方向 | 头节点 | 尾节点 | 说明 |
|---------|------|--------|--------|------|
| **CONTAINS** | → | Document | Chunk | 文档包含词块 |
| **CONTAINS** | → | Chunk | Mention | 词块包含实体提及 |
| **REFERS_TO** | → | Mention | Entity | 提及指向实体 |
| **HAS_EVIDENCE** | → | Edge | Chunk | 关系边链接到证据chunk |
| **FROM_DOC** | → | Entity/Edge | Document | 实体/关系链接到来源文档 |
| **HAS_VERSION** | → | Entity/Edge | Version | 实体/关系有版本信息 |

### 2.3 两层Schema的关联

**关联方式**：
- 语义层的实体节点通过`Mention`节点链接到工程层的`Chunk`
- 语义层的关系边通过`source_chunk_id`属性链接到工程层的`Chunk`
- 工程层的`Source`和`Version`节点为语义层实体提供来源和版本信息

**示例结构**：
```
语义层：Disease(深静脉血栓) --[SUPPORTED_BY]--> Evidence(单侧肿胀)
         ↓                                    ↓
工程层：Mention --[IN_CHUNK]--> Chunk --[FROM_DOC]--> Document(指南v2.0)
```

- 支持多编码体系并存（ICD-10、ICD-11、SNOMED CT等）

## 八、数据导入流程

### 8.1 完整导入流程

```
步骤1：导入第0项编码规范
  - 从表格文件读取编码信息
  - 作为节点属性存储（不创建独立编码节点）
  ↓
步骤2：导入第3项标准目录主数据
  - 从表格文件读取标准目录数据
  - 创建基础实体节点（Symptom, ChiefComplaint, Disease, Examination, Category）
  - 设置编码属性（第0项）
  - 建立分类关系（BELONGS_TO, HAS_CATEGORY）
  - 实体归并：名称精确匹配、编码匹配、语义匹配
  - 编码对齐：与第0项编码规范对齐，支持多编码体系并存
  ↓
步骤3：导入第5项主诉模板
  - 从表格文件读取主诉模板数据
  - 通过display_id查找已有ChiefComplaint节点（第3项）
  - 更新ChiefComplaint节点属性（扩展属性）
  - 创建DifferentialFrameworkSubclass节点
  - 创建DifferentialPoint节点（可选）
  - 建立主诉关系（HAS_CANDIDATE_DISEASE, HAS_REASONING_SUBGROUP等）
  ↓
步骤4：导入第6项疾病模板
  - 从表格文件读取疾病模板数据
  - 通过display_id查找已有Disease节点（第3项）
  - 更新Disease节点属性（扩展属性）
  - 创建ReasoningSubgroup节点
  - 创建DifferentialPoint节点（可选）
  - 建立疾病关系（SUPPORTED_BY, OPPOSED_BY, REQUIRES等）
  ↓
步骤5：建立工程层链接
  - 为每个实体节点创建Mention节点
  - 为每个关系边创建Evidence节点
  - 链接到Chunk和Document节点
  ↓
步骤6：验证数据完整性
  - 验证所有display_id关联正确
  - 验证所有关系边都有source_chunk_id
  - 验证所有必需属性都已填充
```

## 九、查询接口设计

### 9.1 核心查询场景

#### 9.1.1 编码查询（第0项）

```cypher
// 根据症状编码查询症状实体
MATCH (s:Symptom {symptom_code: "C0008031"})
RETURN s.name, s.symptom_code, s.icd10_code, s.snomed_code

// 根据ICD-10编码查询疾病
MATCH (d:Disease {icd10_code: "I20.9"})
RETURN d.name, d.icd10_code, d.icd11_code, d.snomed_code
```

#### 9.1.2 标准目录查询（第3项）

```cypher
// 查询所有标准症状
MATCH (s:Symptom)
RETURN s.name, s.category, s.symptom_code
ORDER BY s.category, s.name

// 根据分类查询症状
MATCH (s:Symptom)-[:BELONGS_TO]->(c:Category {name: "心血管系统"})
RETURN s.name, s.symptom_code

// 查询分类层级结构
MATCH path = (parent:Category)-[:HAS_CATEGORY*]->(child:Category)
RETURN path
```

#### 9.1.3 主诉查询（第5项）

```cypher
// 根据主诉查询候选疾病（三层候选）
MATCH (cc:ChiefComplaint {display_id: "CC_001"})-[r:HAS_CANDIDATE_DISEASE {tier_level: "Tier2"}]->(d:Disease)
RETURN cc.name, d.name, r.tier_level, r.priority, r.selection_basis

// 根据主诉查询推理子组
MATCH (cc:ChiefComplaint {display_id: "CC_001"})-[:HAS_REASONING_SUBGROUP]->(sg:ReasoningSubgroup)
RETURN cc.name, sg.name, sg.display_id

// 根据主诉查询检查建议
MATCH (cc:ChiefComplaint {display_id: "CC_001"})-[r:RECOMMENDS_EXAMINATION]->(e:Examination)
RETURN cc.name, e.name, r.suggestion_timing, r.purpose
```

#### 9.1.4 疾病查询（第6项）

```cypher
// 查询疾病的支持证据
MATCH (d:Disease {display_id: "DIS_DVT"})-[r:SUPPORTED_BY]->(e:Evidence)
RETURN d.name, e.display_id, e.name, r.priority
ORDER BY r.priority

// 查询需要鉴别诊断的疾病
MATCH (d1:Disease {display_id: "DIS_DVT"})-[r:DIFFERENTIAL_WITH]->(d2:Disease)
RETURN d1.name, d2.display_id, d2.name, r.priority, r.differential_points
ORDER BY r.priority

// 查询疾病需要的检查
MATCH (d:Disease {display_id: "DIS_DVT"})-[r:REQUIRES_EXAMINATION]->(e:Examination)
RETURN d.name, e.name, r.value_level, r.prerequisite
ORDER BY r.value_level
```

#### 9.1.5 证据追溯查询（工程层）

```cypher
// 查询关系的证据来源
MATCH (d:Disease {display_id: "DIS_DVT"})-[r:SUPPORTED_BY]->(e:Evidence)
MATCH (c:Chunk) WHERE c.chunk_id IN r.source_chunk_id
MATCH (c)-[:FROM_DOC]->(doc:Document)
RETURN d.name, e.display_id, e.name, c.text, doc.name, doc.version
```

## 十一、模块集成说明

### 11.1 模块依赖关系

```
第0项（编码规范）
    ↓ 提供编码属性
第3项（标准目录主数据）
    ├─→ 第5项（主诉模板）依赖ChiefComplaint节点
    ├─→ 第6项（疾病模板）依赖Disease节点
    └─→ 第7项（证据模板）待设计
```

### 11.2 实体复用规则

1. **ChiefComplaint节点**：第3项创建基础节点，第5项扩展属性，不创建新节点
2. **Disease节点**：第3项创建基础节点，第6项扩展属性，不创建新节点
3. **ReasoningSubgroup节点**：第6项创建，第5项复用（通过display_id关联）
4. **DifferentialPoint节点**：第5项和第6项都可以创建，需要去重检查
5. **Examination节点**：第3项创建，第5项和第6项复用

### 11.3 关系建立规则

1. **主诉关系**：建立在第3项已有的ChiefComplaint节点上
2. **疾病关系**：建立在第3项已有的Disease节点上
3. **跨模块关系**：通过display_id关联不同模块的实体
