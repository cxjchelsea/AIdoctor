# 智能诊断系统 - 系统设计方案

> **文档定位**：本文档是智能诊断系统的**系统设计方案**，专注于业务逻辑、功能设计、流程设计等业务层面的设计。  
> **核心理念**：智能诊断是**医学判断引擎**，专门回答"是不是病？是否安全？"的问题，与智能家庭医生（照护执行引擎）协作，将被动、分散的模块整合成主动、整体的健康管理系统。  
> **技术实现**：请参考《智能诊断系统-技术架构方案.md》

---

## 一、系统定位与核心理念

### 1.1 系统定位

**智能诊断系统**是健康管理平台的**医学判断引擎**，作为整个健康管理平台的8个模块之一，专门提供专业的医学判断服务。

**核心定位**：
- **医学判断引擎**：专门回答"是不是病？是否安全？是否需要检查？"的问题
- **专科医生角色**：专门做诊断和健康检查，在诊断领域比家庭医生更专业、更深入
- **专业诊断**：基于症状、体征、检查结果，提供**专业的可能性分析**和**鉴别诊断**
- **健康检查**：提供专业的健康检查建议和检查结果解读
- **深度推理**：通过更专业的诊断引擎，提供更精准、更深入的诊断分析
- **像医生一样**：通过主动对话、自然语言交互、智能追问，提供人性化的诊断服务
- **处理"没病的人"**：对"没病的人"给出专业的医学判断依据，说明为什么安全，识别需要关注的风险

### 1.2 核心理念：像医生一样的交互体验

**系统要像真正的医生一样**：

1. **主动询问**：不是被动等待用户填写表单，而是主动询问关键信息
   - "您这个症状出现多久了？"
   - "除了这个症状，还有没有其他不舒服？"
   - "疼痛是持续的还是阵发性的？"

2. **自然对话**：使用自然语言，像医生和患者面对面交流
   - 不使用冰冷的表单
   - 不使用技术术语
   - 使用温暖、专业的语言

3. **智能追问**：根据已收集的信息，智能判断还需要什么信息
   - 信息不足时，主动追问
   - 信息冲突时，主动澄清
   - 发现相关症状时，主动探索

4. **专业分析**：像专科医生一样，进行深入的专业分析
   - 多维度分析（症状、体征、检查、病史）
   - 鉴别诊断（支持证据、反对证据）
   - 专业建议（检查建议、就医建议）

5. **人性化沟通**：像医生一样，关心患者，提供情感支持
   - 理解患者的担忧
   - 提供安慰和鼓励
   - 给出明确的指导

### 1.3 与智能家庭医生系统的关系

**核心公式**：
> **智能诊断 = 医学判断引擎**（回答"是不是病？是否安全？"）  
> **智能家庭医生 = 照护执行引擎**（回答"怎么管理？如何改善？"）

**协作关系**：
- **智能诊断（专科医生思维）**：进行医学判断，给出"是不是病"、"是否安全"的专业结论
- **智能家庭医生（全科照护思维）**：基于医学判断，制定照护计划，提供长期管理
- **两者协作**：智能诊断提供医学判断依据，智能家庭医生基于判断结果制定管理计划

**关键区别**：

| 维度 | 智能诊断（专科医生思维） | 智能家庭医生（全科照护思维） |
|------|------------------------|---------------------------|
| **核心问题** | "这个情况医学上是否安全？" | "这个人长期该怎么管理？" |
| **回答的问题** | "是不是病？是否安全？" | "怎么管理？如何改善？" |
| **时间视角** | 一次性/阶段性判断 | 长期连续管理 |
| **对"没病的人"的处理** | 给出"没病"的医学判断依据 | 给出"保持健康"的照护计划 |
| **输出形式** | 鉴别诊断、检查建议、风险提示 | 健康计划、随访任务、生活方式指导 |
| **决策性质** | 医学判断（是否安全、是否需要检查） | 照护决策（如何管理、如何改善） |
| **服务对象** | 需要医学判断的人（有病+没病） | 需要长期照护的人 |
| **典型场景** | "我体检指标有点异常，是不是病了？" | "我整体健康状态如何，该怎么保持？" |

**协作流程**：
```
用户提出问题/上传检查结果
         ↓
   智能诊断（专科医生思维）
   进行医学判断分析
         ↓
   输出医学判断结论
   （有病/没病/需要进一步检查）
         ↓
   智能家庭医生（全科照护思维）
   接收医学判断
         ↓
   制定照护计划/解释/随访
         ↓
   输出给用户
```

### 1.4 核心功能

#### 1.4.1 专业诊断分析（像医生一样）

**功能定位**：提供专科医生级别的诊断分析，通过主动对话收集信息，**包括对"没病的人"的专业判断**

**输入**：
- 症状描述（通过对话收集：主诉、伴随症状、症状特征）
- 体征数据（通过对话询问或设备采集：生命体征、体格检查结果）
- 检查结果（用户上传：检验单、影像报告等）
- 健康档案（自动获取：既往史、家族史、用药史等）

**输出**（对"有病的人"和"没病的人"都适用）：
- ✅ **专业的可能性分析**：按可能性排序的疾病方向（Top 3-5），比家庭医生更精准
- ✅ **详细的鉴别诊断**：支持证据、反对证据、鉴别要点
- ✅ **专业的检查建议**：建议做哪些检查、检查的优先级、检查的目的（包括"不需要做哪些检查"的建议）
- ✅ **专科就医建议**：建议去哪个专科、何时就医、需要带什么资料
- ✅ **诊断推理过程**：解释为什么考虑这些可能性，推理过程更专业
- ✅ **人性化沟通**：像医生一样，用自然语言解释，提供情感支持
- ✅ **对"没病的人"的专业判断**：
  - 给出"没病"的医学判断依据
  - 说明为什么安全
  - 识别需要关注的风险
  - 给出后续建议（是否需要复测、观察等）

#### 1.4.2 健康检查服务

**功能定位**：提供专业的健康检查建议和检查结果解读

**功能包括**：
- **检查建议**：根据症状、年龄、性别、既往史，建议需要做哪些检查
- **检查方案设计**：设计个性化的检查方案（体检套餐、专项检查等）
- **检查结果解读**：专业的检查结果解读，识别异常指标
- **检查结果分析**：分析检查结果的临床意义，可能的疾病方向
- **复查建议**：建议何时复查、复查哪些项目
- **避免过度医疗**：判断哪些检查不需要做，给出专业的"为什么不需要"的解释

## 二、系统整合：从被动分散到主动整体

### 2.1 整合前的问题

**现有模块的特点**：
- **被动**：用户填表、用户上传、用户主动操作
- **分散**：各个模块独立，没有统一引导
- **用户主导**：用户需要自己知道要做什么

**问题**：
- 用户不知道什么时候该做什么
- 各个模块之间缺乏协调
- 系统无法主动引导用户
- 缺乏整体性的健康管理方案

### 2.2 整合后的系统架构

**以智能家庭医生为核心，智能诊断为医学判断引擎，整合所有模块**：

```
┌─────────────────────────────────────────────────────────────┐
│              智能家庭医生（全科照护思维）                        │
│            - 主动引导、统一协调、整体管理                        │
│            - 基于智能诊断的医学判断，制定照护计划                 │
└─────────────────────────────────────────────────────────────┘
         │                    │                    │
         ▼                    ▼                    ▼
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│  智能诊断        │  │   健康中心       │  │   健康监测       │
│  (医学判断引擎)  │  │  (健康档案)      │  │  (实时监测)      │
└─────────────────┘  └─────────────────┘  └─────────────────┘
         │                    │                    │
         ▼                    ▼                    ▼
┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐
│   抗衰管理       │  │   风险评估       │  │   健康科普       │
│  (健康维护)      │  │  (风险预警)      │  │  (知识教育)      │
└─────────────────┘  └─────────────────┘  └─────────────────┘
```

### 2.3 主动引导机制

**智能家庭医生主动引导用户**：

1. **主动监测与提醒**
   - 监测用户健康数据，发现异常主动提醒
   - 提醒用户进行健康检查
   - 提醒用户完成健康评估

2. **主动触发诊断**
   - 发现异常指标 → 主动询问症状 → 触发智能诊断
   - 用户上传检查报告 → 自动解读 → 发现异常 → 触发智能诊断
   - 用户描述症状 → 主动收集信息 → 触发智能诊断

3. **主动制定方案**
   - 基于智能诊断的医学判断，主动制定照护计划
   - 整合健康中心、抗衰管理、预防干预等模块，给出综合方案
   - 主动设置随访任务、提醒事项

4. **主动协调各模块**
   - 根据用户情况，主动引导用户使用相关模块
   - 将分散的模块整合成完整的健康管理方案
   - 像完整的医生、医院一样，提供一站式服务

### 2.4 整体工作流程示例

**场景：用户体检发现血压130/85mmHg（正常高值）**

```
1. 健康监测模块检测到异常
   ↓
2. 智能家庭医生主动提醒："您的血压处于正常高值，值得关注"
   ↓
3. 智能家庭医生主动询问："您最近有什么不适症状吗？"
   ↓
4. 用户描述症状（或说"没有症状"）
   ↓
5. 智能家庭医生判断需要医学判断 → 触发智能诊断
   ↓
6. 智能诊断（专科医生思维）进行医学判断：
   - 当前不构成高血压诊断，医学上安全
   - 属于正常高值，需要关注但无需治疗
   - 建议3-6个月复测血压
   - 无需立即进行24小时动态血压监测
   ↓
7. 智能诊断输出医学判断结论给智能家庭医生
   ↓
8. 智能家庭医生（全科照护思维）基于医学判断，制定照护计划：
   - 解释为什么安全（帮助用户理解）
   - 制定3个月复测计划
   - 提供生活方式指导（饮食、运动、压力管理）
   - 设置随访提醒
   - 整合健康中心、抗衰管理模块，给出综合方案
   ↓
9. 用户收到完整的健康管理方案（不是分散的建议，而是整体方案）
```

### 2.5 对"没病的人"的整合处理

**关键理解**：
> **智能诊断面对的不是"有病的人"，而是"需要医学判断的人"；  
> 智能家庭医生面对的不是"健康或生病"，而是"一个需要被长期照护的人"。**

**处理流程**：

```
用户情况：完全健康，但想"确认没问题"
   ↓
智能家庭医生主动引导："我来帮您做一个全面的健康评估"
   ↓
整合健康中心、健康监测、风险评估等模块，收集数据
   ↓
智能诊断（专科医生思维）进行医学判断：
   - 当前医学上安全，无疾病状态
   - 风险评估：家族史为一级风险因素，但当前无疾病指征
   - 医学建议：目前无需进行XX检查，建议每年监测XX指标
   ↓
智能诊断输出医学判断结论给智能家庭医生
   ↓
智能家庭医生（全科照护思维）基于医学判断，制定照护计划：
   - 制定年度健康监测计划
   - 提供预防性生活方式指导
   - 设置年度体检提醒
   - 整合健康科普模块，推送相关知识
   ↓
用户收到完整的健康管理方案（保持健康的计划）
```

## 三、诊断触发机制

### 3.1 触发条件

诊断功能在以下情况下触发：

#### 条件1：用户明确请求诊断
- 用户说："我这是什么病？"
- 用户说："帮我分析一下可能是什么问题"
- 用户说："根据我的症状，可能是什么原因？"
- 用户说："我这些症状指向什么疾病？"

**意图识别**：通过现有AI服务的意图识别，识别为"诊断咨询"意图

#### 条件2：症状评估完成后自动触发
- 用户完成症状描述后，系统判断：
  - 症状信息足够（至少3个关键信息：主诉 + 起病时间 + 严重度/频率）
  - 非紧急情况（分诊等级L3或L4）
  - 用户健康档案完整度 > 60%
  - 用户未明确拒绝诊断

**触发流程**：
```
用户描述症状
    ↓
[模块4：症状评估与分诊] → 完成分诊评估
    ↓
分诊等级判断
    ├── L1/L2（紧急） → 不触发诊断，直接建议就医
    └── L3/L4（非紧急） → 检查触发条件
        ├── 症状信息足够（≥3个关键信息） → 触发诊断
        └── 症状信息不足 → 继续收集信息（主动追问）
```

#### 条件3：检查结果解读后触发
- 用户上传检查报告后
- 系统识别到异常指标
- 结合症状和健康档案，触发诊断分析

**触发流程**：
```
用户上传检查报告
    ↓
[报告解读模块] → 识别异常指标
    ↓
检查是否有症状描述
    ├── 有症状 → 结合症状+检查结果 → 触发诊断
    └── 无症状 → 主动询问："您有什么不适症状吗？"
```

#### 条件4：智能家庭医生主动触发
- 智能家庭医生监测到异常指标
- 智能家庭医生主动询问用户症状
- 智能家庭医生判断需要医学判断 → 主动触发智能诊断
- **这是系统整合后的关键触发方式**：从被动等待用户请求，变为主动引导和触发

**触发流程**：
```
智能家庭医生监测到异常（如血压升高）
    ↓
智能家庭医生主动提醒用户："您的血压有点高，有什么不适吗？"
    ↓
用户描述症状（或说"没有症状"）
    ↓
智能家庭医生判断需要医学判断 → 主动触发智能诊断
    ↓
智能诊断进行医学判断
    ↓
输出医学判断结论给智能家庭医生
    ↓
智能家庭医生基于医学判断，制定照护计划
```

#### 条件5：历史诊断更新触发
- 用户补充新信息（新症状、新检查结果）
- 系统判断：新信息可能改变诊断结果
- 自动触发诊断更新

### 3.2 触发优先级

```
紧急情况（L1/L2）
    ↓
[模块4：分诊模块处理] → 不触发诊断，直接建议就医

非紧急情况（L3/L4）
    ↓
[检查触发条件]
    ↓
满足条件 → [触发诊断]
不满足条件 → [继续收集信息（主动追问）]
```

### 3.3 不触发诊断的情况

**安全边界**：
1. **紧急情况**（分诊等级L1/L2）→ 直接建议就医，不触发诊断
2. **信息严重不足**（完整度 < 30%）→ 先收集信息，不触发诊断
3. **用户明确拒绝** → 尊重用户意愿，不触发诊断
4. **红旗信号触发** → 立即建议就医，不触发诊断

### 3.2 详细流程说明

#### 4.1 阶段1：主动询问（像医生一样主动收集信息）

**不是被动等待用户填写表单，而是主动询问**：

**数据来源**（从现有系统模块获取 + 主动询问）：

1. **当前症状**（通过主动对话收集）
   - 主诉（用户描述："我最近胸痛"）
   - 症状特征（主动询问："疼痛持续多久了？"、"疼痛程度如何？"）
   - 伴随症状（主动询问："除了胸痛，还有没有其他不舒服？"）
   - 症状评分（主动询问："0-10分，您觉得疼痛是几分？"）
   - 分诊等级（L1-L4）

2. **健康档案**（自动获取，必要时主动询问补充）
   - 基础信息：年龄、性别、身高、体重、BMI
   - 既往史：慢病、手术史、住院史（主动询问："您之前有没有类似的症状？"）
   - 家族史：遗传性疾病、家族慢病（主动询问："您家里有没有人得过类似的病？"）
   - 用药史：当前用药、用药依从性（主动询问："您最近有没有吃什么药？"）
   - 生活方式：饮食、运动、睡眠、烟酒
   - 风险标签：代谢风险、心血管风险、睡眠风险等

3. **生命体征**（主动询问或设备采集）
   - 当前测量值：血压、心率、血氧、体温（主动询问："您最近测过血压吗？"）
   - 基线数据：个体正常波动范围
   - 近期趋势：7天/30天趋势
   - 是否偏离基线：判断体征是否异常

4. **检查结果**（用户上传或主动询问）
   - 检验单：血常规、生化、肝肾功能、血脂、HbA1c等
   - 影像报告：X光、CT、MRI、超声等
   - 居家检测：试纸结果（尿、唾液、呼气等）

5. **历史诊断**（从诊断记录获取）
   - 历史诊断记录
   - 历史可能性分析
   - 历史就医结果（如果用户反馈）

**主动询问策略**（像医生一样）：

**优先级1：关键症状特征**
- "您这个症状出现多久了？"（起病时间）
- "症状严重程度如何？0-10分打几分？"（严重度）
- "什么情况下出现的？"（诱因）
- "什么情况下会缓解？"（缓解因素）

**优先级2：伴随症状**
- "除了这个症状，还有没有其他不舒服？"
- "有没有发热、咳嗽、胸闷等？"
- "有没有出汗、气短、头晕等？"

**优先级3：既往相关病史**
- "您之前有没有类似的症状？"
- "您有没有XX疾病史？"（根据当前症状，询问相关既往史）
- "您家里有没有人得过类似的病？"（家族史）

**优先级4：近期事件**
- "最近有没有外伤、用药改变、旅行等？"
- "最近有没有接触过传染源？"
- "最近有没有什么特殊的事情发生？"

**数据完整度计算**：
```
数据完整度 = (已有信息项数 / 总信息项数) × 100%

总信息项包括：
- 症状信息（主诉、起病时间、严重度、伴随症状）：4项
- 健康档案（年龄、性别、既往史、用药史）：4项
- 生命体征（血压、心率、体温）：3项
- 检查结果（如果有）：1项

最低要求：≥ 60% 才能进行诊断分析
理想状态：≥ 80% 诊断准确性更高
```

#### 4.2 阶段2：信息补全（智能追问，像医生一样追问细节）

**缺失信息识别**：
- 如果症状信息不足（< 3个关键信息），识别缺失项
- 如果健康档案不完整（< 60%），标记缺失字段
- 如果生命体征缺失，判断是否需要测量
- 如果数据有冲突，需要确认

**智能追问策略**（优先级排序，像医生一样）：

**优先级1：关键症状特征**
- 起病时间："症状出现多久了？"
- 严重度："症状严重程度如何？0-10分打几分？"
- 诱因："什么情况下出现的？"
- 缓解因素："什么情况下会缓解？"

**优先级2：伴随症状**
- "除了这个症状，还有没有其他不舒服？"
- "有没有发热、咳嗽、胸闷等？"
- "有没有出汗、气短、头晕等？"

**优先级3：既往相关病史**
- "您之前有没有类似的症状？"
- "您有没有XX疾病史？"（根据当前症状，询问相关既往史）
- "您家里有没有人得过类似的病？"（家族史）

**优先级4：近期事件**
- "最近有没有外伤、用药改变、旅行等？"
- "最近有没有接触过传染源？"

**追问方式**（通过对话服务，像医生一样自然）：
- 使用自然语言提问，一次问1-2个问题，避免信息过载
- 根据用户回答，动态调整后续问题
- 支持用户补充信息："我还想补充..."
- 使用温暖、专业的语言，像医生一样关心患者

**停止追问条件**：
- 信息完整度达到阈值（≥ 70%）
- 用户明确表示"不知道"或"不想回答"
- 追问轮次超过限制（最多3轮）
- 用户明确拒绝继续

**数据冲突处理**（像医生一样澄清）：
- 如果症状说"发热"，但体温正常 → 追问："您自己感觉发热，还是测过体温？"
- 如果症状说"胸痛"，但分诊等级是L4 → 追问："疼痛程度如何？有没有其他症状？"

**对话示例**（像医生一样的对话）：
```
用户："我最近胸痛"
系统："胸痛需要重视。请问疼痛持续多久了？"
用户："3天了"
系统："疼痛是持续的还是阵发性的？"
用户："一阵一阵的"
系统："疼痛时有没有其他症状，比如出汗、气短？"
用户："有点气短"
系统："您之前有没有类似的症状？"
用户："没有"
系统："您有没有高血压、心脏病等病史？"
用户："有高血压"
系统："好的，我了解了。让我为您分析一下可能的原因..."
[系统进行诊断分析]
系统："根据您的描述和健康档案，我考虑以下几个可能的方向：
1. 心绞痛（可能性较高）- 支持证据：胸痛、气短、有高血压史
2. 焦虑症（可能性中等）- 支持证据：阵发性胸痛
3. 胃食管反流（可能性较低）- 支持证据：胸痛

建议您尽快到心内科就诊，做心电图和心脏彩超检查。如果疼痛突然加重，或伴有大汗、恶心等症状，请立即就医。"
```

#### 4.3 阶段3：专业可能性分析（五引擎融合）

**分析方法**（5个引擎并行工作，比家庭医生更专业）：

**引擎1：专科规则引擎匹配**（权重25%）
- **特点**：比家庭医生的规则引擎更专业、更细化
- **规则库结构**：症状组合 → 疾病方向
- **匹配逻辑**：
  1. 提取用户症状列表
  2. 在规则库中查找匹配的症状组合
  3. 完全匹配 > 部分匹配（匹配度 > 70%）> 单个症状匹配
  4. 输出匹配的疾病方向及置信度
- **规则优先级**：
  - 高优先级规则：症状组合 + 体征组合
  - 中优先级规则：症状组合
  - 低优先级规则：单个症状
- **示例**：
  - {发热 + 咳嗽 + 胸痛} → {肺炎: 0.8, 支气管炎: 0.6, 胸膜炎: 0.4}
  - {胸痛 + 出汗 + 气短} → {心梗: 0.9, 心绞痛: 0.7, 焦虑: 0.3}

**引擎2：深度知识图谱推理**（权重25%）
- **特点**：比家庭医生的知识图谱推理更深入，考虑更多关系路径
- **图谱结构**（利用现有Neo4j知识图谱）：
  - 节点：症状、疾病、检查、体征、药物等
  - 边：关系（引起、诊断、治疗等）
- **推理逻辑**：
  1. 从症状节点出发
  2. 沿着"引起"关系，找到可能的疾病节点
  3. 考虑疾病节点的属性（年龄、性别、既往史匹配度）
  4. 计算路径权重，排序输出

**引擎3：专科统计模型预测**（权重20%）
- **特点**：使用专科级别的统计模型，考虑更多专业特征
- **模型输入**：
  - 症状特征向量（症状类型、严重度、持续时间等）
  - 用户画像向量（年龄、性别、既往史等）
  - 体征向量（血压、心率、体温等）
- **模型输出**：
  - 疾病可能性概率分布
  - 例如：{肺炎: 0.35, 支气管炎: 0.28, 胸膜炎: 0.15, ...}
- **模型训练**：
  - 基于历史诊断数据训练
  - 定期更新模型参数
  - 考虑用户反馈（实际诊断结果）

**引擎4：专业大模型分析**（权重25%）
- **特点**：使用更专业的医学大模型，提示词更专业
- **提示词设计**：
  ```
  你是一位经验丰富的医生，需要根据患者的症状、体征、健康档案等信息，
  分析可能的疾病方向。

  患者信息：
  - 年龄：{age}
  - 性别：{gender}
  - 既往史：{medical_history}
  - 当前症状：{symptoms}
  - 生命体征：{vital_signs}
  - 检查结果：{test_results}

  请分析：
  1. 可能的疾病方向（Top 3-5）
  2. 每个方向的支持证据
  3. 每个方向的反对证据
  4. 还需要哪些信息来进一步判断
  5. 建议做哪些检查

  注意：
  - 不要给出确诊结论
  - 使用"可能"、"考虑"等表述
  - 如果信息不足，明确说明
  ```
- **输出解析**：
  - 解析大模型返回的结构化结果
  - 提取可能性列表、支持证据、反对证据等
  - 转换为标准格式

**引擎5：鉴别诊断规则引擎**（权重5%，新增）
- **特点**：专门的鉴别诊断规则，帮助区分相似疾病
- **规则库**：相似疾病的鉴别要点
- **示例**：
  - 心绞痛 vs 心梗：疼痛持续时间、严重程度、伴随症状
  - 肺炎 vs 支气管炎：发热程度、咳嗽性质、胸痛特点

**结果融合逻辑**（比家庭医生更精细）：
```
最终可能性分数 = 
    专科规则引擎分数 × 0.25 +
    深度知识图谱分数 × 0.25 +
    专科统计模型分数 × 0.2 +
    专业大模型分数 × 0.25 +
    鉴别诊断规则分数 × 0.05

输出Top 3-5可能性列表（疾病方向 + 可能性分数 + 诊断推理过程）
注：代码实现中可返回Top 5候选，然后根据可能性分数筛选出Top 3-5展示给用户
```

**与家庭医生的区别**：
- 家庭医生：4个引擎，权重相对平均
- 智能诊断：5个引擎，增加了鉴别诊断规则引擎，权重更精细

**冲突解决**：
- 如果不同引擎结果差异很大，降低置信度
- 如果多个引擎指向同一方向，提高置信度
- 如果规则引擎匹配度很高（> 0.8），优先使用规则引擎结果

#### 4.4 阶段4：鉴别诊断（像医生一样，分析支持/反对证据）

**对每个可能性，进行支持/反对分析**：

**支持证据分析**：
- **症状支持**：哪些症状支持该可能性
  - 例如：胸痛 + 出汗 + 气短 → 支持心梗
- **体征支持**：哪些体征支持该可能性
  - 例如：血压升高 + 心率加快 → 支持心血管疾病
- **检查结果支持**：哪些检查结果支持该可能性
  - 例如：心电图异常 → 支持心脏病
- **用户画像匹配**：年龄、性别、既往史是否匹配
  - 例如：老年男性 + 有高血压史 → 支持心血管疾病

**反对证据分析**：
- **症状不支持**：哪些症状不支持该可能性
  - 例如：没有发热 → 不支持感染性疾病
- **体征不支持**：哪些体征不支持该可能性
  - 例如：体温正常 → 不支持感染
- **检查结果不支持**：哪些检查结果不支持该可能性
  - 例如：血常规正常 → 不支持严重感染
- **用户画像不匹配**：年龄、性别、既往史是否不匹配
  - 例如：年轻女性 → 不太可能是老年性疾病

**缺失信息识别**：
- 还需要哪些关键信息来进一步判断
- 哪些检查可以帮助确诊或排除
- 哪些症状需要进一步观察

**可能性重新排序**：
- 综合支持证据和反对证据，重新计算可能性分数
- 考虑证据强度（强证据权重更高）
- 输出最终的可能性列表（Top 3-5）

**证据强度分级**：
- **强证据**：特异性症状/体征（权重1.0）
  - 例如：胸痛伴出汗 → 强支持心梗
- **中证据**：常见症状/体征（权重0.7）
  - 例如：发热 → 中支持感染
- **弱证据**：非特异性症状/体征（权重0.4）
  - 例如：乏力 → 弱支持多种疾病

#### 4.5 阶段5：结果输出（像医生一样，用自然语言解释）

**输出结构**：

```
诊断分析结果
├── 一句话总结（像医生一样，用自然语言）
```

**人性化沟通**（像医生一样）：

## 五、对"没病的人"的专业处理

### 5.1 为什么"没病的人"也需要智能诊断？

**医学上的必要性**：

1. **"没病"不是默认状态，而是判断结果**
   - 用户说"我没事" ≠ 医学上确认安全
   - 只有经过医学分析，才能确认"没病"

2. **"没病"的判断需要专业依据**
   - 为什么安全？
   - 哪些指标支持这个结论？
   - 哪些风险需要关注？

3. **"没病"的判断需要给出后续建议**
   - 是否需要复测？
   - 复测周期是多久？
   - 什么情况下需要就医？

**产品上的价值**：

1. **解决用户焦虑**
   - 用户担心有问题，需要专业医生给出判断
   - "医生说没事"比"系统说没事"更可信

2. **避免过度医疗**
   - 专业判断哪些检查不需要做
   - 避免用户因为焦虑而做不必要的检查

3. **早期发现风险**
   - 虽然"没病"，但可能识别出需要关注的风险
   - 给出预防性建议

### 5.2 智能诊断处理"没病的人"的完整流程

**关键理解**：
> 智能诊断对"没病的人"做的不是"告诉你没病"，而是**"用医学方法证明你没病，并告诉你为什么安全"**。

这是一个**主动的医学判断过程**，而不是被动的"没发现问题"。

**处理流程**：

1. **信息收集与分析**
   - 收集症状、体征、检查结果、病史
   - 进行医学逻辑分析

2. **鉴别诊断思维**
   - 列出可能的疾病方向
   - 逐一排除或确认
   - 判断是否构成疾病

3. **风险分层**
   - 评估当前风险等级
   - 识别危险信号
   - 判断是否需要进一步检查

4. **给出医学结论**
   - 明确说明"目前不构成疾病"的依据
   - 说明为什么安全
   - 给出后续建议（是否需要复测、观察等）

5. **输出给智能家庭医生**
   - 提供医学判断依据
   - 提供后续管理建议
   - 提供风险提示

### 5.3 典型场景示例

#### 场景一：指标异常，但不构成疾病

**用户情况**：50岁女性，总胆固醇5.8mmol/L（正常上限5.7），其他正常

**智能诊断输出**：
```
医学判断结论：
- 指标分析：总胆固醇5.8，略高于正常上限，但未达到高胆固醇血症诊断标准（>6.2）
- 风险评估：50岁女性，轻度升高，需关注但非疾病状态
- 医学建议：
  * 当前无需药物治疗
  * 建议3个月后复测血脂全套
  * 若持续升高或合并其他危险因素，需进一步评估
- 结论：目前不构成高脂血症诊断，但需监测
```

**智能家庭医生基于此输出**：
- 制定3个月复测计划
- 提供降胆固醇的饮食建议
- 设置运动计划
- 解释为什么暂时不需要吃药

#### 场景二：有症状，但排除疾病

**用户情况**：40岁男性，偶发胸闷，心电图、心脏彩超正常

**智能诊断输出**：
```
医学判断结论：
- 症状分析：偶发胸闷，无典型心绞痛特征
- 检查结果：心电图、心脏彩超均正常，排除器质性心脏病
- 鉴别诊断：考虑功能性不适或焦虑相关，非心脏疾病
- 危险信号评估：无胸痛、无放射痛、无活动后加重，风险低
- 医学建议：
  * 当前无需进一步心脏检查（如冠脉CTA）
  * 可观察，若症状频繁或加重需就医
  * 若出现胸痛持续、放射至左臂等情况需立即就医
- 结论：目前不构成心脏疾病，医学上安全
```

**智能家庭医生基于此输出**：
- 解释为什么安全（帮助用户理解）
- 提供压力管理和放松技巧
- 设置症状观察提醒
- 制定生活方式改善计划

#### 场景三：完全健康，但想"确认没问题"

**用户情况**：28岁女性，体检全部正常，但担心家族有糖尿病史

**智能诊断输出**：
```
医学判断结论：
- 当前检查结果：血糖、糖化血红蛋白均在正常范围
- 风险评估：家族史为一级风险因素，但当前无糖尿病指征
- 医学建议：
  * 目前无需进行OGTT（口服葡萄糖耐量试验）
  * 建议每年监测空腹血糖和糖化血红蛋白
  * 若出现多饮、多尿、体重下降等症状，需及时就医
- 结论：当前医学上安全，无疾病状态
```

**智能家庭医生基于此输出**：
- 制定年度血糖监测计划
- 提供糖尿病预防的生活方式指导
- 设置年度体检提醒

## 六、数据模型设计

### 4.1 诊断记录表（diagnosis_record）

```sql
CREATE TABLE diagnosis_record (
    id BIGSERIAL PRIMARY KEY,
    user_id VARCHAR(64) NOT NULL,
    family_id VARCHAR(64),
    diagnosis_type VARCHAR(32) NOT NULL, -- 'symptom', 'examination', 'comprehensive'
    status VARCHAR(32) NOT NULL, -- 'collecting', 'questioning', 'analyzing', 'completed', 'cancelled'
    
    -- 症状信息（通过对话收集）
    chief_complaint TEXT,
    symptom_duration VARCHAR(64),
    symptom_severity INTEGER, -- 0-10
    symptom_frequency VARCHAR(32),
    symptom_location TEXT,
    accompanying_symptoms TEXT,
    symptom_features JSONB,
    
    -- 体征数据（通过对话询问或设备采集）
    vital_signs JSONB, -- {bp: {systolic: 130, diastolic: 85}, heart_rate: 75, ...}
    physical_exam JSONB,
    
    -- 检查结果
    examination_results JSONB, -- [{type: 'blood_test', data: {...}}, ...]
    
    -- 诊断结果
    diagnosis_result JSONB, -- {possibilities: [...], evidence: {...}, suggestions: {...}}
    
    -- 对话记录（像医生一样的对话）
    dialogue_history JSONB, -- [{role: 'user/system', content: '...', timestamp: '...'}, ...]
    questioning_count INTEGER DEFAULT 0, -- 追问次数
    
    -- 元数据
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    completed_at TIMESTAMP,
    
    -- 索引
    INDEX idx_user_id (user_id),
    INDEX idx_family_id (family_id),
    INDEX idx_status (status),
    INDEX idx_created_at (created_at)
);
```

### 4.2 检查记录表（examination_record）

```sql
CREATE TABLE examination_record (
    id BIGSERIAL PRIMARY KEY,
    user_id VARCHAR(64) NOT NULL,
    family_id VARCHAR(64),
    examination_type VARCHAR(32) NOT NULL, -- 'blood_test', 'imaging', 'physical', 'comprehensive'
    
    -- 检查方案
    plan_id BIGINT,
    plan_name VARCHAR(255),
    plan_items JSONB, -- [{item: 'blood_test', purpose: 'diagnosis', priority: 'high'}, ...]
    
    -- 报告信息
    report_type VARCHAR(32), -- 'image', 'pdf', 'text'
    report_file_path VARCHAR(512),
    report_ocr_result JSONB,
    report_structured_data JSONB, -- {indicators: [{name: 'WBC', value: 6.5, unit: '10^9/L', normal_range: '4-10', status: 'normal'}, ...]}
    
    -- 解读结果
    interpretation_result JSONB, -- {abnormal_indicators: [...], clinical_significance: {...}, possible_diseases: [...], suggestions: {...}}
    
    -- 元数据
    examination_date DATE,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    
    -- 索引
    INDEX idx_user_id (user_id),
    INDEX idx_family_id (family_id),
    INDEX idx_examination_type (examination_type),
    INDEX idx_examination_date (examination_date)
);
```

## 七、与其他模块的集成

### 5.1 与健康中心模块集成

**数据获取**：
- 获取用户健康档案（基本信息、既往史、家族史、用药史等）
- 获取健康数据（血压、血糖、体重等历史数据）

### 5.2 与健康监测模块集成

**数据获取**：
- 获取实时监测数据（血压、心率、血氧等）
- 获取监测设备数据

### 5.3 与风险评估模块集成

**数据共享**：
- 诊断结果反馈给风险评估模块
- 从风险评估模块获取风险标签

### 7.4 与智能家庭医生模块集成（关键）

**协作关系**：
- **智能诊断 → 智能家庭医生**：
  - 诊断结果（医学判断结论）反馈给家庭医生模块
  - 提供医学判断依据、风险评估、后续建议
  - 对"没病的人"提供"为什么安全"的专业解释
  
- **智能家庭医生 → 智能诊断**：
  - 从家庭医生模块获取基础健康档案
  - 接收家庭医生的诊断请求
  - 接收家庭医生收集的用户信息

**数据流转**：
```
智能家庭医生收集用户信息
   ↓
触发智能诊断
   ↓
智能诊断进行医学判断
   ↓
输出医学判断结论给智能家庭医生
   ↓
智能家庭医生基于医学判断，制定照护计划
   ↓
整合其他模块，输出完整方案给用户
```

### 7.5 与对话服务集成（关键）

**对话流程集成**：
- 诊断功能作为对话服务的一个"子流程"
- 当触发诊断时，对话服务切换到"诊断模式"
- 诊断模式下的追问，通过对话服务进行（像医生一样）

**上下文管理**：
- 诊断过程中的所有对话，记录到对话上下文
- 诊断结果，保存到对话历史
- 后续对话可以引用诊断结果："根据之前的诊断分析..."

**多轮对话支持**：
- 用户可以在诊断过程中补充信息
- 系统根据新信息，动态更新诊断结果
- 支持用户提问："为什么是这个病？"、"这个可能性高吗？"

## 八、安全边界与风险控制

### 6.1 触发边界

**不触发诊断的情况**：
- 紧急情况（分诊等级L1/L2）→ 直接建议就医
- 信息严重不足（完整度 < 30%）→ 先收集信息
- 用户明确拒绝诊断 → 尊重用户意愿
- 红旗信号触发 → 立即建议就医

### 6.2 输出边界

**输出格式**：
- ✅ **可能性列表**：按可能性排序的疾病方向（Top 3-5），更精准
- ✅ **支持证据**：详细的症状/体征/检查结果支持证据，更专业
- ✅ **反对证据**：详细的反对证据和鉴别要点
- ✅ **缺失信息**：还需要哪些关键信息来进一步判断
- ✅ **建议检查**：专业的检查建议（检查项目、优先级、目的）
- ✅ **专科就医建议**：建议去哪个专科、何时就医、带什么资料
- ✅ **诊断推理过程**：解释诊断推理过程，更透明

**不输出**：
- ❌ "您得了XX病"（确诊式表述）
- ❌ "一定是XX病"（绝对化表述）
- ❌ 具体的用药剂量和疗程（只提示药物类别，不替代医生处方）
- ❌ 手术建议（只提示"可能需要手术治疗"，具体方案由医生决定）

**必须包含**：
- ✅ 免责声明："本分析仅供参考，不替代医生诊断，最终诊断需由专业医生确定"
- ✅ 专科就医建议：明确建议何时、去哪个专科就医
- ✅ 危险信号：出现哪些情况立即就医

### 6.3 风险等级判断

**高风险情况**：
- 可能性列表中有严重疾病（如：心梗、脑梗、肿瘤等）
- 即使可能性不高，也要明确提示就医
- 输出时，严重疾病要特别标注

**中风险情况**：
- 可能性列表中有需要治疗的疾病
- 建议尽快就医（2-3天内）

**低风险情况**：
- 可能性列表主要是常见病、自限性疾病
- 可以建议观察或预约就医

## 九、总结

本文档详细描述了智能诊断系统的系统设计方案，包括：

1. **系统定位**：医学判断引擎，专门回答"是不是病？是否安全？"的问题
2. **核心理念**：与智能家庭医生（照护执行引擎）协作，将被动、分散的模块整合成主动、整体的健康管理系统
3. **系统整合**：以智能家庭医生为核心，智能诊断为医学判断引擎，整合所有模块，实现主动引导
4. **诊断触发机制**：明确什么情况下触发诊断（包括主动触发）
5. **诊断流程逻辑**：像医生一样的对话流程，主动询问、智能追问、专业分析
6. **对"没病的人"的处理**：给出专业的医学判断依据，说明为什么安全，识别需要关注的风险
7. **数据模型设计**：数据库表设计
8. **模块集成**：与其他7个模块的集成方案（特别是与智能家庭医生的协作）
9. **安全边界**：明确的边界和风险控制

**关键特点**：
- ✅ **医学判断引擎**：专门回答"是不是病？是否安全？"的问题
- ✅ **像医生一样**：主动对话、自然语言、智能追问
- ✅ **专业深度**：专科医生级别的诊断分析
- ✅ **人性化**：温暖、专业的语言，提供情感支持
- ✅ **安全合规**：明确的边界，不输出确诊结论
- ✅ **处理"没病的人"**：给出专业的医学判断依据，说明为什么安全
- ✅ **系统整合**：与智能家庭医生协作，整合所有模块，实现主动引导

**核心公式**：
> **智能诊断 = 医学判断引擎**（回答"是不是病？是否安全？"）  
> **智能家庭医生 = 照护执行引擎**（回答"怎么管理？如何改善？"）

**对"没病的人"的理解**：
> **智能诊断面对的不是"有病的人"，而是"需要医学判断的人"；  
> 智能家庭医生面对的不是"健康或生病"，而是"一个需要被长期照护的人"。**
