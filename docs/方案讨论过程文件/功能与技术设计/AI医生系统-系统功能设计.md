> **文档定位**：本文档是AI医生系统的**系统功能设计**，专注于业务功能、临床流程、能力模块等业务层面的设计。  
> **技术实现**：请参考《AI医生系统-技术架构设计.md》  
> **核心目标**：构建一个能够代替真人医生的AI医生系统，具备完整的医学推理能力、主动交互能力、可解释性和安全性。

## 一、系统定位与核心理念

### 1.1 系统定位

> **医生面对的，从来不是"有没有病"的人群，而是"不知道自己有没有病"的人群。**

**AI医生系统**必须同时面向"有病的人"和"没病的人"，否则它就不配叫医生，只能叫"诊断工具"。

**核心定位**：
- **不是假设用户是病人**，而是从"健康状态不确定"的人出发
- **先判断是否需要进入医学诊疗流程**
- **对未进入诊疗流程的人**，负责风险管理与随访
- **对进入诊疗流程的人**，执行受控、可解释的临床推理与决策支持

**两种工作态**：

#### 🟢 工作态一：健康管理态（Wellness / Monitoring Mode）

- **面向**：没病 or 不确定健康状态的人
- **核心任务**：
  - 判断是否需要升级到临床诊疗态
  - 管理风险与趋势（早期风险识别）
  - 主动问询与随访
  - 健康建议与生活方式指导
- **允许**：
  - 不下诊断
  - 只给观察建议
  - 提供安抚与解释

#### 🔴 工作态二：临床诊疗态（Clinical Reasoning Mode）

- **面向**：疑似/明确有病的人
- **核心任务**：
  - 鉴别诊断（DDx）
  - 检查/处置建议
  - 推理与证据链
- **使用**：
  - DR.KNOWS方法
  - 知识图谱路径推理
  - 强结构化推理

> **这不是两个系统，而是一个系统的两个"工作态"。**

### 1.2 核心设计原则

> **"医生的第一职责不是'下诊断'，而是'判断要不要下诊断'"**

系统设计遵循医生的工作流程，采用**单主Agent架构**，将AI医生的能力拆解为8个"临床工具"，每个工具都可以单独训练、评测、替换：

**主Agent（Clinical Agent Brain）**：
- 负责运行循环（Observe→Plan→Act→Update→Evaluate→Stop/Escalate）
- 负责工具调用决策和调度
- 负责证据融合和冲突解决
- 负责停止条件、升级策略、拒答策略的判断

**八大工具（Tools）**：

0. **健康状态判定工具**（Health State Assessment Tool, tool_0）
1. **病例理解工具**（Clinical Parsing Tool, tool_1）
2. **主动问诊工具**（Interview Tool, tool_2）
3. **鉴别诊断工具**（Differential Diagnosis Tool, tool_3）
4. **检查建议工具**（Workup Planner Tool, tool_4）
5. **治疗建议工具**（Management Planner Tool, tool_5）
6. **风险评估工具**（Risk Assessment Tool, tool_6）
7. **证据链工具**（Evidence Chain Tool, tool_7）

### 1.3 核心数据结构：Clinical Decision Package (CDP)

所有推理围绕一个中心产物：**Clinical Decision Package（CDP）**。它不是UI产物，而是系统内部一切推理的核心数据结构。

## 二、八大工具功能设计

### 2.0 工具0：健康状态判定工具（Health State Assessment Tool）- **关键分叉点**

> **对应技术架构文档**：4.0 工具0：健康状态判定工具 + 1.3 health-state-assessment-service  
> **工具ID**：`tool_0`  
> **工具类型**：Deterministic  
> **技术实现详情**：请参考《AI医生系统-技术架构设计.md》第4.0节和第1.3节

**职责**：判断"这个人，现在需要被当成'病人'对待吗？"

> **这是医生的第一职责，发生在"诊断之前"**

**输入**：
- 用户描述的症状/不适（初始主诉）
- 基本信息（年龄、性别等）
- 健康档案（如有）

**输出**：健康状态判定
- 是否需要进入诊疗流程（`needs_clinical_mode`：true/false）
- 工作态选择（`work_mode`：wellness_mode / clinical_mode）
- 风险等级（L1/L2/L3/L4）
- 判定依据（`assessment_reason`）

#### 2.0.1 AI诊断入口判定流程（P0模块）

**流程概述**：入口判定模块通过五个步骤完成用户意图识别、症状识别、方向澄清、危险信号检查和路径输出。

**Step 1｜接收用户输入**

**功能**：接收用户自然语言描述本次来访目的

**输入**：用户自然语言输入（文本/语音）

**处理**：
- 支持自然语言理解（NLU）
- 允许混合诉求（既想体检又有轻微不适）
- 不依赖选择题入口

**输出**：结构化的用户意图表达

**需求清单**：
- **输入接收能力**：
  - 支持用户用自然语言描述需求（不依赖选择题入口）
  - 允许用户输入"混合诉求"（既想体检又有轻微不适）

**Step 2｜识别用户是否"有症状/困扰"**

**功能**：系统对用户输入做一次判断，识别用户是否有症状/困扰

**判断结果**：

**情况 A：明确无症状**
- 用户表达的是"健康管理/体检规划/筛查/预防"
- 且没有任何不适描述
- **处理**：进入 Step 4（危险信号兜底）后，准备进入健康筛查路径（A）

**情况 B：存在症状/困扰**
- 用户描述任何身体不适、异常感觉、功能变化、心理困扰等（不论轻重）
- **处理**：进入 Step 4（危险信号兜底）后，准备进入症状诊断路径（B）

**情况 C：不确定/模糊/混合诉求**
- 用户说不清是否算不适
- 或同时说"想体检 + 有点不舒服"
- **处理**：进入 Step 3 做一次方向澄清

**需求清单**：
- **症状/困扰识别规则**：
  - 能识别"症状/不适/困扰/异常感觉/功能变化"等表达
  - 轻微问题也算"有困扰"，不要求严重程度
  - 能识别"明确无症状"的表达（纯筛查/纯体检规划）

**Step 3｜方向澄清（仅对"情况C"触发一次）**

**功能**：通过最小澄清确认用户当前的主要目标

**触发条件**：仅当 Step 2 判断为"情况C"时触发

**澄清目标**：确认用户主要目标是：
- **A**：健康筛查/体检规划
- **B**：症状咨询/问题排查

**处理原则**：
- 澄清后不得反复追问，避免入口卡顿
- 澄清结果只能落到两类：进入 A 或进入 B

**处理流程**：
- 生成最小澄清问题（仅一次）
- 根据用户回答确定方向（A 或 B）
- 澄清完成后，继续进入 Step 4

**需求清单**：
- **方向澄清机制（仅一次）**：
  - 当用户表达模糊或混合诉求时，触发一次澄清
  - 澄清结果只能落到两类：进入 A 或进入 B
  - 澄清后不得反复追问，避免入口卡顿

**Step 4｜危险信号检查（安全兜底，所有用户都要过一次）**

**功能**：无论用户走 A 还是 B，都必须判断是否存在危险信号

**检查逻辑**：
- **如果命中危险信号**：
  - 不进入线上流程
  - 输出"优先线下就医/急诊"的安全提示（结束）

- **如果未命中危险信号**：
  - 进入 Step 5 输出选路结果

**危险信号库**：维护一份危险信号清单（红旗库）

**检查原则**：
- 入口判定阶段只做"是否命中"，不做解释诊断
- 命中后输出固定的安全提示并结束线上流程

**需求清单**：
- **危险信号检查机制**：
  - 维护一份危险信号清单（红旗库）
  - 入口判定阶段只做"是否命中"，不做解释诊断
  - 命中后输出固定的安全提示并结束线上流程

**Step 5｜输出路径结果并跳转**

**功能**：根据前面的判断结果，输出明确的路径选择并跳转

**输出规则**：
- **无症状 + 无危险信号** → 进入健康筛查路径（A）
- **有症状/困扰 + 无危险信号** → 进入症状诊断路径（B）
- **危险信号命中** → 退出线上流程（安全提示）

**跳转规则**：
- 跳转到对应路径的第一个步骤
- **A路径**：进入健康筛查流程的起点（A1｜需求分类）
- **B路径**：进入症状诊断流程的起点（阶段1｜问诊）

**需求清单**：
- **选路输出与跳转规则**：
  - 输出必须明确：进入 A / 进入 B / 退出线上流程
  - 跳转到对应路径的第一个步骤
  - A：进入健康筛查流程的起点
  - B：进入症状诊断流程的起点

#### 2.0.2 路径切换支持（防止误入）

**功能**：允许用户在路径中切换，防止误入错误路径

**切换规则**：

**A路径 → B路径切换**：
- **触发条件**：若用户在 A 路径中后续出现症状描述
- **处理**：应允许切换到 B（症状诊断路径）

**B路径 → A路径切换**：
- **触发条件**：若用户在 B 路径中明确只是想筛查
- **处理**：应允许切换到 A（健康筛查路径）

**需求清单**：
- **路径切换支持（防止误入）**：
  - 若用户在 A 路径中后续出现症状描述，应允许切换到 B

**2.2.0 临床决策分析驱动的问诊（基于临床决策理论）**

**医疗理论依据**：临床决策分析（Clinical Decision Analysis, CDA）

**核心思想**：
问诊不仅是信息收集，更是临床决策过程。每个问题都应该能够：
1. 改变诊断概率（信息增益）
2. 影响临床决策（风险识别）
3. 考虑成本效益（患者负担）

**临床决策增益计算**：

```python
# 扩展的信息增益计算（基于临床决策理论）
IG_clinical(q|DDx, E) = IG_information(q|DDx, E) 
                      + α · IG_risk(q|DDx, E)
                      + β · IG_cost(q|DDx, E)

其中：
1. IG_information: 信息论的信息增益（原有）
   - 计算方式：IG_information = H(DDx|E) - E[H(DDx|E ∪ {answer})]
   - 衡量：问题能减少多少诊断不确定性

2. IG_risk: 风险相关的信息增益
   - 计算方式：IG_risk = Σ_{d ∈ DDx_high_risk} P(d) · I(q can exclude d)
   - 衡量：问题能排除多少高危诊断
   - 医疗依据：漏诊代价远大于误报代价（λ_FN >> λ_FP）
   - 例如：胸痛时优先问"是否伴出汗"（排除心梗）

3. IG_cost: 成本效益相关的信息增益
   - 计算方式：IG_cost = IG_information / Cost(q)
   - 衡量：问题的成本效益比
   - 考虑：时间成本、患者负担、心理成本
   - 医疗依据：临床决策分析中的"期望效用理论"

权重设置（基于医疗理论）：
- α = 0.5（风险权重较高，因为漏诊代价极大）
- β = 0.2（成本权重较低，但需要考虑患者体验）
- 信息增益权重 = 0.3（基础权重）
```

**医疗理论依据**：
- **临床决策分析**：考虑诊断的敏感性、特异性、预测值
- **期望效用理论**：考虑误诊的代价（漏诊代价 >> 误报代价）
- **诊断决策阈值理论**：优先排除高危诊断（治疗阈值以上的诊断）

**最优问诊策略**：
在临床决策理论下，最优问诊策略是：
```
q* = argmax_{q} [IG_clinical(q|DDx, E)]
```

**理论保证**：
- 优先问能排除高危诊断的问题（风险优先）
- 优先问信息增益高的问题（效率优先）
- 考虑问题的成本效益（患者体验优先）

**输出到CDP**：
- 更新 `uncertainty.missing_critical_info`
- 生成问诊计划（临时字段，不持久化）

**2.3.1 推理子组组织（基于诊断树理论）**

**职责**：将候选方向按最有效的维度组织为推理子组，把清单变成结构

**医疗理论依据**：
1. **诊断树理论**（Diagnostic Tree Theory）- 诊断学中的系统化诊断方法
2. **解剖学分类**（Anatomical Classification）- 基于解剖学/生理学系统的分类
3. **病理生理机制**（Pathophysiological Mechanism）- 基于疾病机制的诊断
4. **时间特征诊断**（Temporal Pattern Diagnosis）- 基于起病方式和病程的诊断

**核心思想**：
将候选诊断组织为树状结构，符合临床医生的思维模式：
- **根节点**：主诉/主要症状（Chief Complaint）
- **第一层**：系统分类（基于解剖学/生理学）- 决定"哪个系统的问题"
- **第二层**：病理生理机制 - 决定"什么类型的疾病"
- **第三层**：具体疾病 - 决定"具体是什么病"
- **叶节点**：最终诊断（Final Diagnosis）

**医疗理论优势**：
- **符合临床思维**：临床医生通常先确定系统，再确定机制，最后确定具体疾病
- **提高诊断效率**：一条关键问题能推动整个系统方向前移或后移
- **减少诊断遗漏**：系统化组织确保不遗漏重要诊断方向
- **支持分层问诊**：按照诊断树的层级进行问诊，逐步缩小诊断范围

**组织维度**（按诊断学优先级）：

1. **系统分类**（第一优先级）- 基于解剖学/生理学系统
   - **分类**：心血管系统、呼吸系统、消化系统、神经系统、代谢系统、心理系统、血液系统、泌尿系统、内分泌系统、免疫系统等
   - **医疗理论依据**：
     - 解剖学分类是诊断的基础（Anatomical Basis of Diagnosis）
     - 符合临床医生的思维习惯（Clinical Thinking Pattern）
     - 系统性疾病通常有特定的症状模式（System-Specific Symptom Patterns）
   - **优势**：
     - 一条关键问题能推动整个系统方向前移或后移
     - 例如："胸痛" → 心血管系统 vs 呼吸系统 vs 消化系统
   - **诊断学依据**：Harrison's Principles of Internal Medicine中的系统分类方法

2. **病理生理机制**（第二优先级）- 基于疾病机制
   - **分类**：炎症性、感染性、肿瘤性、代谢性、免疫性、遗传性、退行性、创伤性、中毒性等
   - **医疗理论依据**：
     - 理解疾病机制有助于诊断和治疗（Mechanism-Based Diagnosis）
     - 机制相同或相似的疾病有相似的临床表现（Mechanism-Clinical Correlation）
     - 病理生理机制决定疾病的自然病程（Natural History of Disease）
   - **优势**：
     - 机制相同或相似的疾病可以一起考虑
     - 例如：缺血性心脏病（心梗、心绞痛）vs 炎症性心脏病（心肌炎）
   - **诊断学依据**：Robbins and Cotran Pathologic Basis of Disease中的机制分类

3. **起病方式与病程**（第三优先级）- 基于时间特征
   - **分类**：
     - 急性（<1周）、亚急性（1-4周）、慢性（>4周）
     - 持续/间歇、进行性/缓解性、复发性
   - **医疗理论依据**：
     - 时间特征是重要的诊断线索（Temporal Pattern as Diagnostic Clue）
     - 不同疾病有不同的起病方式和病程（Disease-Specific Temporal Patterns）
     - 时间特征能帮助区分相似疾病（Differential Diagnosis by Temporal Pattern）
   - **优势**：
     - 时间特征能快速区分疾病类型
     - 例如：急性胸痛（心梗）vs 慢性胸痛（心绞痛）
   - **诊断学依据**：临床诊断学中的时间特征诊断方法

4. **严重程度与风险**（贯穿所有层级）- 基于临床严重性
   - **分类**：高危（必须立即排除）、中危、低危
   - **医疗理论依据**：
     - 风险分层是临床决策的核心（Risk Stratification in Clinical Decision Making）
     - 漏诊高危疾病的代价极大（High Cost of Missing High-Risk Diseases）
     - 风险优先原则（Risk-First Principle）：优先排除高危诊断
   - **优势**：
     - 优先处理高危诊断，避免漏诊
     - 例如：胸痛时优先排除心梗（高危），再考虑心绞痛（中危）
   - **诊断学依据**：急诊医学中的分诊理论（Triage Theory）

**诊断树结构**（基于诊断树理论）：

**医疗理论依据**：
- **诊断树理论**：将诊断过程组织为树状结构，符合临床医生的系统化思维
- **分层诊断**：按照系统→机制→疾病的层次进行诊断，逐步缩小诊断范围

```json
      "trigger_condition": "高危触发条件",
      "action": "立即进入验证/升级处理"
    }
  ]
}
```

**目标**：
- 一条关键问题能推动一个子组（系统或机制）整体前移或后移
- 优先处理高危诊断，避免漏诊
- 符合临床医生的思维模式（从系统到机制到疾病）

**医疗理论优势**：
1. **符合临床思维**：从系统分类开始，逐步细化到具体疾病
2. **支持分层问诊**：先问系统层面的问题，再问机制层面的问题
3. **风险优先**：高危诊断优先处理，符合临床决策原则
4. **可追溯性强**：诊断树结构清晰，便于追溯和解释

**2.3.2 分流路径设计**

**职责**：提炼关键差异点，形成可执行的分流路径，确保后续收缩不是"随便问"，而是沿着明确的逻辑分叉推进

**核心功能**：
1. **提炼关键差异点**：
   - 为每对子组或每个关键方向提炼"能最快区分"的差异点
   - 例如：是否突发、是否静息也出现、是否进行性加重
   - 这些差异点将成为证据采集的"第一层分叉"

2. **明确"必须优先处理"的路径**（高危先行）：
   - 对必须排除的高危方向建立优先路径
   - 一旦命中高危差异点或高危线索，直接进入升级/验证动作
   - 避免在高危尚未控制时继续在低危方向上细问

3. **形成分流路径清单**：
   - 第一层分叉问题（用于快速分流子组）
   - 命中高危时的处理指引（进入验证/升级的入口条件）
   - 未命中高危时的继续收缩方向（进入下一步证据采集）

**分流路径结构**：
```json
{
  "first_layer_questions": [
    {
      "question": "第一层分叉问题",
      "purpose": "快速分流子组",
      "answer_options": ["选项1", "选项2"],
      "next_action": {
        "if_option1": "进入子组A",
        "if_option2": "进入子组B"
      }
    }
  ],
  "high_risk_path": {
    "trigger_conditions": ["高危差异点", "高危线索"],
    "action": "进入优先处理与验证入口"
  },
  "normal_path": {
    "action": "进入下一步证据采集与排序收缩"
  }
}
```

**2.3.3 分流路径模板库**

**职责**：为每个高频主诉沉淀分流路径模板，提高问诊效率

**模板内容**：
- 推理子组结构
- 第一层分叉问题
- 高危触发条件与优先路径
- 继续收缩步骤

**维护策略**：
- 为每个高频主诉建立分流路径模板
- 持续迭代更新，基于实际问诊效果优化
- 支持模板复用和组合

**输出到CDP**：
- 更新 `ddx` 字段
- 更新 `evidence_graph` 字段
- 生成分流路径（临时字段，用于指导问诊）

### 2.4 工具4：检查建议工具（Workup Planner Tool）

> **对应技术架构文档**：4.4 工具4：检查建议工具 + 3.4 检查建议引擎  
> **工具ID**：`tool_4`  
> **工具类型**：Deterministic  
> **技术实现详情**：请参考《AI医生系统-技术架构设计.md》第4.4节和第3.4节

**职责**：基于当前DDx和已有证据，建议下一步检查，并评估检查的价值

**输入**：
- 当前CDP的 `ddx`
- 已有证据（`patient_state`）
- 风险等级（`triage`）

**输出**：检查建议
- 检查名称
- 检查目的（能确认/排除哪些DDx）
- 优先级（紧急/重要/可选）
- 预期信息增益（能区分哪些DDx）

**核心功能**：
1. **检查必要性评估**：判断是否需要进一步检查
2. **检查价值评估**：评估检查能提供多少信息增益
3. **检查优先级排序**：根据紧急程度和信息增益排序
4. **检查目的明确化**：明确每个检查能确认/排除哪些DDx

**避免"无脑开单"**：
- 必须评估检查的价值
- 优先推荐信息增益高的检查
- 避免重复检查
- 考虑检查的成本和风险

**2.4.1 验证计划制定**

**职责**：针对"最可能方向"和"必须排除方向"制定验证计划，回答三个问题：查不查、查什么、用什么标准判定

**验证计划结构**：
```json
{
  "verification_purpose": "确认/排除/升级判定",
  "verification_action": {
    "type": "补问/观察/测量/检查或就医",
    "content": "具体动作",
    "priority": "优先级"
  },
  "judgment_standard": {
    "if_support": "什么结果支持该方向",
    "if_not_support": "什么结果不支持该方向",
    "if_uncertain": "什么结果需要进一步验证"
  },
  "result_backfill_rule": {
    "if_support": "如何更新三层排序（上移/巩固）",
    "if_not_support": "如何更新三层排序（下移/排除）",
    "if_uncertain": "如何更新三层排序（保留/标记需线下排除）"
  }
}
```

**核心原则**：
- **验证计划必须能改变排序或触发升级处理**，避免"做了也不改变决策"的无效验证
- 针对"最可能方向"：验证计划用于确认诊断
- 针对"必须排除方向"：验证计划用于排除高危诊断

**验证计划类型**：
1. **补问验证**：通过追问关键问题验证
   - 例如："疼痛是否持续不缓解？"用于验证心梗
2. **观察验证**：通过观察体征验证
   - 例如：观察生命体征是否异常
3. **测量验证**：通过设备测量验证
   - 例如：测量血压、心率、体温
4. **检查验证**：通过医学检查验证
   - 例如：心电图、心肌酶等
5. **就医验证**：需要线下就医才能验证
   - 例如：需要专业医生检查才能排除

**输出到CDP**：
- 更新 `workup_plan` 字段（包含验证计划）

**职责**：识别高危情况，评估紧急程度，决定是否需要立即升级处理

**职责**：定义复评时间窗和升级触发条件，用于生成行动与随访建议

```json

    }

```

**复评时间窗**：

**2.7.1 证据清单结构化**

**职责**：将证据组织成结构化的证据清单，每条证据包含完整信息

**证据清单结构**：
```json
{
  "evidence_items": [
    {
      "evidence_name": "证据项名称（体征/症状/测量/检查结果）",
      "evidence_source": "追问/观察/设备测量/线下检查",
      "evidence_result": "具体数值或描述",
      "evidence_direction": "支持/不支持/不确定",
      "affected_direction": "推动哪个方向前移或后移",
      "evidence_strength": "强证据/中证据/弱证据",
      "timestamp": "证据获取时间"
    }
  ]
}
```

**证据方向**：
- **支持**：推动该方向前移（上移或巩固）
- **不支持**：推动该方向后移（下移或排除）
- **不确定**：需要进一步验证

**证据强度分级**：
- **强证据**：特异性症状/体征（权重≥0.8）
  - 例如：胸痛伴出汗 → 强支持心梗
- **中证据**：常见症状/体征（权重0.5-0.8）
  - 例如：发热 → 中支持感染
- **弱证据**：非特异性症状/体征（权重<0.5）
  - 例如：乏力 → 弱支持多种疾病

**证据来源**：
- **追问**：通过问诊获得的信息
- **观察**：通过观察获得的体征
- **设备测量**：通过智能设备测量的数据
- **线下检查**：通过医学检查获得的结果

**输出到CDP**：
- 更新 `evidence_graph` 字段（包含结构化证据清单）
- 更新 `uncertainty` 字段

### 3.2 健康管理态详细流程

#### 3.2.1 健康人筛查流程（A路径）概述

**目标**：面向无症状的健康人群，提供健康筛查、体检规划、健康管理等服务

**流程结构**：
```
A1｜需求分类 → A2｜通用最小健康档案 → A3｜进入对应分支执行 → A4｜统一结果页输出 → A5｜随访闭环
```

**核心原则**：
- 用户无症状或不确定健康状态
- 采集最低必要信息（缺失不阻塞）
- 按需求类型进入固定分支
- 所有分支收敛为统一结果展示结构

#### 3.2.2 A1｜需求分类

**目标**：把用户需求归入三类之一，后续严格对齐分支流程

**需求类型**：
1. **筛查建议**：用户无症状，只想知道"应该做哪些筛查/多久一次"
2. **健康目标管理**：用户无症状，但希望改善健康状态（减脂/睡眠/运动/精力）
3. **计划性健康需求**：用户无症状，但有明确场景任务（备孕/疫苗/差旅/材料等）

**处理流程**：
1. 三选一归类需求
2. 输出需求类型（1/2/3）

**需求清单**：
- **四类需求选项文案**
- **用户常见表达归类示例**
- **不确定时的引导话术**

#### 3.2.3 A2｜通用最小健康档案

**目标**：采集最低必要信息，为后续建议提供依据（缺失不阻塞）

**处理流程**：
1. 采集最小健康档案字段
2. 输出健康档案卡 + 可选补充的缺失字段清单

**健康档案字段**：
- 基本信息：年龄、性别、身高、体重
- 既往史：疾病史、手术史、过敏史
- 家族史：遗传疾病史
- 生活习惯：吸烟、饮酒、运动、饮食
- 用药史：当前用药、既往用药

**需求清单**：
- **健康档案采集字段清单**
- **低信息模式兜底话术**（缺失不阻塞仍能输出）
- **缺失字段提示与补充策略**（可选）

#### 3.2.4 A3｜进入对应分支执行

**目标**：按需求类型进入固定分支，输出该分支的标准结果

##### A3-1｜筛查建议分支（对应需求1）

**目标**：用户无症状，只想知道"应该做哪些筛查/多久一次"

**处理流程**：
1. **补充追问**（仅问会影响筛查决策的关键信息）
   - 年龄、性别、既往史、家族史等关键信息
   - 避免过度追问

2. **规则化生成两张清单**：
   - **推荐做的筛查清单**：
     - 按年龄段、性别、风险因素推荐筛查项目
     - 包含筛查频率和时机
   - **不建议做的筛查清单**：
     - 反过度筛查理由
     - 替代建议

3. **输出分支结果**：
   - 推荐筛查清单 + 频率/时机
   - 不建议筛查清单 + 理由
   - 下次更新时间点
   - 随访节奏

**需求清单**：
- **额外追问清单**（仅筛查决策关键项）
- **输出数量与排序规则**（推荐/不推荐各输出多少条）
- **条件触发筛查规则库**（什么条件→建议哪些筛查→大致频率/时机）
- **不推荐筛查清单**（反过度筛查理由与替代建议）
- **强烈要求检查时的标准回应话术**

##### A3-2｜健康目标管理分支（对应需求2）

**目标**：用户无症状，但希望改善健康状态（减脂/睡眠/运动/精力）

**处理流程**：
1. **固定追问**（目标/现状/资源/周期）
   - 目标：想要改善的具体目标（减脂/睡眠/运动/精力等）
   - 现状：当前状态和基线数据
   - 资源：可用的时间、精力、经济资源
   - 周期：期望的改善周期

2. **生成可执行行动计划**：
   - 行动计划：具体的行动步骤
   - 追踪指标：2-3个关键指标（如体重、睡眠时长）
   - 复盘节点：定期回顾和调整时间点

3. **输出分支结果**：
   - 行动计划 + 追踪指标 + 复盘节点
   - 随访节奏

**需求清单**：
- **固定追问清单**（目标/现状/资源/周期）
- **目标计划模板库**（按目标类型复用）
- **追踪指标建议库**（2–3个即可）
- **失败兜底调整话术**

##### A3-4｜计划性健康需求分支（对应需求4）

**目标**：用户无症状，但有明确场景任务（备孕/疫苗/差旅/材料等）

**处理流程**：
1. **追问场景必要信息**（场景/时间点/禁忌信息）
   - 场景：具体的场景任务（备孕/疫苗/差旅/材料等）
   - 时间点：任务的时间节点
   - 禁忌信息：是否有禁忌症或特殊情况

2. **输出清单 + 时间表 + 注意事项**：
   - 检查清单：需要完成的检查项目
   - 时间表：检查的时间安排
   - 注意事项：需要特别注意的事项

3. **输出分支结果**：
   - 清单 + 时间表 + 注意事项
   - 随访节奏

**需求清单**：
- **固定追问清单**（场景/时间点/禁忌信息）
- **场景清单库**（清单+时间表+注意事项）
- **场景节点提醒规则**（什么时候提醒更新）

#### 3.2.5 A4｜统一结果页输出

**目标**：所有分支收敛为同一种结果展示结构

**结果展示结构**：
1. **一句话总结**：总结本次咨询的核心建议
2. **现在建议做的事（清单）**：明确建议用户执行的事项
3. **暂时不建议做的事（清单）**：明确不建议的事项及理由
4. **下一次复查/更新时间点**：明确的随访时间
5. **退出A路径条件提示**：出现不适/危险信号→线下评估

**需求清单**：
- **一句话总结模板**（按需求类型）
- **推荐/不推荐展示话术模板**
- **退出A路径提醒文案**（出现不适/危险信号→线下评估）

#### 3.2.6 A5｜随访闭环

**目标**：给出明确随访节奏，形成流程结束点与再次进入入口

**随访节奏规则**（按需求类型）：

1. **筛查建议**：周期性更新档案
   - 按筛查项目的时间间隔提醒用户更新
   - 定期回顾健康档案

   - 轻度异常：3-6个月复查
   - 中度异常：1-3个月复查或进一步评估
   - 重度异常：立即就医，完成后随访

3. **目标管理**：按复盘节点回访更新
   - 按行动计划中的复盘节点提醒用户
   - 评估进展并调整计划

4. **计划性需求**：按场景节点提醒更新/完成任务
   - 按时间表提醒用户完成检查
   - 任务完成后关闭提醒

**需求清单**：
- **随访节奏规则**（按需求类型）
- **随访提醒话术**（按节点提醒用户更新/复查/复盘）

### 3.3 临床诊疗态详细流程（AI循证诊断流程）

> **参考文档**：《智能诊断A路径：AI循证诊断流程.md》  
> **对应技术架构文档**：5.3 临床诊疗态协作流程 + 3.3 5步AI循证诊断流程编排引擎  
> **技术实现详情**：请参考《AI医生系统-技术架构设计.md》第5.3节和第3.3节  
> **核心思想**：将临床诊疗态流程重构为5步AI循证诊断流程，确保诊断过程可推理、可复用、可审计。

#### 3.3.1 流程总览

临床诊疗态采用**5步AI循证诊断流程**：

```
Step 1: 识别问题
  ↓
Step 2: 构建鉴别诊断候选集并分层
  ↓
Step 3: 组织候选集并建立分流路径
  ↓
Step 4: 采集关键证据并形成排序与验证计划
  ↓
Step 5: 回填证据并输出终点结论包
```

**流程特点**：
- **可推理**：每个步骤都有明确的推理逻辑和依据
- **可复用**：问题清单、候选集、分流路径等可沉淀为模板库
- **可审计**：每个步骤的输出都有结构化记录，支持追溯和验证

#### 3.3.2 Step 1：识别问题

**目标**：把用户的自然语言描述，转化成可推理、可复用、可审计的结构化"问题清单"，作为后续候选方向生成与分流问诊的唯一输入。

**核心任务**：

1. **概念归一化（明确用户在说什么）**
   - 把"原话"翻译为医学可用的标准概念
   - 处理同义表达与歧义表达
   - 避免误解主诉含义

2. **形成完整问题清单**
   - 不仅记录主诉，还要同步记录伴随问题与关键背景
   - 进行分组组织，保证后续推理不会漏关键信息

3. **标记信息缺口（决定能不能进入下一步）**
   - 明确"当前已知什么、还缺什么、缺了会造成什么推理风险"
   - 按缺口等级决定是否允许进入 Step 2

**输出标准**：

**结构化问题清单**：

```json
{
  "主要问题": {
    "主诉名称": "归一化后的主诉",
    "持续时间": "持续时间与起病方式（突然/渐进）",
    "严重程度": "当前严重程度（对活动/睡眠/功能影响）"
  },
  "伴随问题": [
    {
      "症状名称": "与主诉同窗出现的关键伴随症状",
      "出现时间": "时间",
      "分流价值": "是否具有分流价值"
    }
  ],
  "关键背景": {
    "年龄": "年龄",
    "性别": "性别",
    "既往史": ["与当前主诉相关的重大疾病史"],
    "当前用药": ["会改变风险或表现者"],
    "过敏史": ["会改变风险或表现者"],
    "生理状态": "妊娠、近期手术、久坐久卧、感染接触等",

  },
  "信息缺口": {
    "必填缺口": ["缺失则不能进入 Step 2"],

  }
}
```

**参与工具**：
- **工具1：病例理解工具** - 执行概念归一化和结构化提取
- **工具2：主动问诊工具** - 识别信息缺口并生成追问

**完成条件**：
- 必填缺口已补齐，或已明确标记为"重要缺口"并提示风险
- 问题清单结构化完成，可进入 Step 2

**示例**：

#### 3.3.3 Step 2：构建鉴别诊断候选集并分层

> **参考文档**：《DR.KNOWS与5步诊断流程整合方案.md》  
> **核心原则**：**知识库优先，DR.KNOWS路径用于验证和补充**

**目标**：在 Step 1 的"问题清单"基础上，建立该主诉的鉴别诊断全集，并按临床风险与证据强度分成三层，形成后续问诊分流与检查决策的"候选集合"。

**整合目标**：**优先使用知识库中的权威医学内容**（主诉知识图谱、疾病知识图谱），DR.KNOWS路径用于验证和补充。

**核心任务**：

1. **知识库候选集检索阶段（优先）**
   - **从主诉知识图谱检索三层候选**：根据主诉标准名，从主诉表5（三层候选总览表）检索Tier1/Tier2/Tier3候选疾病
   - **从主诉表6（候选疾病明细表）检索详细信息**：
     - 默认层级（Tier1/Tier2/Tier3）
     - 入选依据（来自知识库的权威依据）
     - 当前支持线索（关键支持证据条目ID列表）
     - 当前反对线索（关键反对证据条目ID列表）
     - 待补齐缺口（必须补齐的关键信息条目ID列表）
   - **从疾病知识图谱检索疾病详细信息**：
     - 典型表现模式
     - 关键支持证据条目ID列表
     - 关键反对证据条目ID列表
     - 必须补齐的关键信息条目ID列表
     - 易混疾病ID列表
     - 关键鉴别点
     - 分流路径中的位置（Tier1/Tier2/Tier3）
     - 推理子组归属

2. **DR.KNOWS路径检索阶段（验证和补充）**
   - **提取症状CUI**：从问题清单中提取所有症状的CUI编码
   - **执行路径检索**：从Neo4j知识图谱检索所有从症状到疾病的推理路径（支持2-4跳）
   - **路径与知识库候选匹配**：
     - 检查检索到的路径是否指向知识库候选集中的疾病
     - 如果路径指向知识库候选，标记为"已验证"
     - 如果路径指向知识库候选外的疾病，标记为"补充候选"（用于知识库完善）

3. **候选集整合与验证阶段**
   - **知识库候选优先**：
     - 直接使用知识库中的候选集作为主要候选
     - 使用知识库中的默认层级（Tier1/Tier2/Tier3）作为初始分层
     - 使用知识库中的入选依据作为候选的入选依据
   - **DR.KNOWS路径验证**：
     - 为每个知识库候选匹配对应的DR.KNOWS路径
     - 如果知识库候选有对应的路径，标记为"路径已验证"
     - 如果知识库候选没有对应的路径，标记为"路径缺失"（但不影响候选入选，因为知识库是权威来源）
   - **补充候选处理**（可选）：
     - 如果DR.KNOWS路径指向知识库候选外的疾病，作为补充候选
     - 补充候选需要人工审核，确认是否应该加入知识库
     - 补充候选不参与主要排序，仅作为参考

4. **三层分层阶段（基于知识库权威内容）**
   - **Tier2（必须优先除外）选择**：
     - **直接使用知识库中的Tier2候选**（主诉表5、主诉表6中的默认层级为Tier2的疾病）
     - 使用知识库中的入选依据（如"漏诊后果严重且符合现有表现"）
     - 使用知识库中的支持线索和反对线索
     - **不依赖路径数量或路径结构特征**
   - **Tier1（最可能）选择**：
     - **直接使用知识库中的Tier1候选**（主诉表5、主诉表6中的默认层级为Tier1的疾病）
     - 使用知识库中的入选依据（如"常见方向组"）
     - 使用知识库中的支持线索和反对线索
     - 根据当前患者信息匹配知识库中的支持线索
     - **不依赖路径数量或路径结构特征**
   - **Tier3（积极备选）选择**：
     - **直接使用知识库中的Tier3候选**（主诉表5、主诉表6中的默认层级为Tier3的疾病）
     - 使用知识库中的入选依据（如"易混淆组"）
     - 使用知识库中的支持线索和反对线索
     - **不依赖路径数量或路径结构特征**

5. **信息缺口标记（基于知识库）**
   - **优先使用知识库中的待补齐缺口**：
     - 从主诉表6（候选疾病明细表）中获取"待补齐缺口"（必须补齐的关键信息条目ID列表）
     - 从疾病知识图谱中获取"必须补齐的关键信息条目ID列表"
     - 这些是知识库中定义的权威缺口清单
   - **DR.KNOWS路径补充缺口**（可选）：
     - 如果知识库中的缺口清单不完整，可以从DR.KNOWS路径中提取中间节点作为补充
     - 但知识库中的缺口清单优先
   - **缺口分级**（基于知识库）：
     - 必填缺口：知识库中标记为"必须补齐"的信息
     - 重要缺口：知识库中标记为"重要"的信息

#### 3.3.4 Step 3：组织候选集并建立分流路径

> **参考文档**：《DR.KNOWS与5步诊断流程整合方案.md》  
> **核心原则**：**优先使用知识库中的推理子组和关键差异点**，DR.KNOWS路径用于验证和补充

**目标**：把 Step 2 的"分层候选清单"组织成可推进的推理结构，并提炼出能在问诊与基础测量中快速收缩范围的分流路径，确保后续收缩不是"随便问"，而是沿着明确的逻辑分叉推进。

**整合目标**：**优先使用知识库中的推理子组和关键差异点**，DR.KNOWS路径用于验证和补充。

**核心任务**：

1. **关键差异点提取（基于知识库）**
   - **优先使用知识库中的关键差异点**：
     - 从主诉表8（关键差异点配置表）中获取关键差异点
     - 这些是知识库中定义的权威差异点，包含标准问法、答案选项、影响子组/疾病、动作等
   - **DR.KNOWS路径补充差异点**（可选）：
     - 如果知识库中的差异点不完整，可以从DR.KNOWS路径中提取中间节点作为补充
     - 但知识库中的差异点优先
   - **差异点分类**（基于知识库）：
     - 系统来源差异点（心血管/呼吸/消化等）
     - 病程差异点（急性/慢性）
     - 诱因差异点（活动/体位/进食等）
     - 分布差异点（局部/全身、单侧/双侧）

2. **推理子组组织（基于知识库）**
   - **优先使用知识库中的推理子组**：
     - 从主诉表7（推理子组清单表）中获取推理子组
     - 这些是知识库中定义的权威子组，包含子组名称、覆盖疾病、子组进入触发、推进目标等
   - **从疾病知识图谱获取推理子组归属**：
     - 从疾病知识图谱中获取"推理子组归属"字段
     - 确定每个疾病属于哪个推理子组
   - **DR.KNOWS路径验证子组**（可选）：
     - 如果知识库中的子组不完整，可以从DR.KNOWS路径中提取系统来源节点作为补充
     - 但知识库中的子组优先
   - **子组的高危触发条件**（基于知识库）：
     - 从疾病知识图谱中获取"升级触发条件（疾病级红旗）"
     - 从主诉表1中获取"危险信号清单引用"

3. **分流路径设计**
   - **第一层分叉问题设计**：
     - 基于关键差异点设计第一层分叉问题
     - 例如：是否静息也发作（区分急性/慢性）
     - 例如：是否伴发热（区分感染/非感染）
   - **高危路径设计**：
     - 识别高危触发条件
     - 设计高危路径：一旦命中高危条件，直接进入验证/升级
   - **分流路径结构**：
     - 第一层分叉问题 → 子组筛选
     - 高危触发条件 → 高危路径
     - 未命中高危 → 继续收缩方向

     - 路径中的关系就是线索类型
   - **线索分类**：
     - 关键差异点线索（用于区分方向）
     - 阳性线索（支持某一方向）
     - 关键阴性线索（排除某一方向）
   - **线索标准化**：
     - 线索名称（中文）
     - 线索类型（差异点/阳性/阴性）
     - 获取方式（追问/观察/测量）
     - 标准问法与答案选项
     - 判定规则（支持/不支持/不确定）

#### 3.3.5 Step 4：采集关键证据并形成三层排序与验证计划

> **参考文档**：《DR.KNOWS与5步诊断流程整合方案.md》  
> **核心原则**：使用DR.KNOWS路径约束推理，指导证据采集和排序

**目标**：沿着 Step 3 的分流路径，系统采集能够"推动排序变化"的关键证据，形成稳定的三层清单，并制定验证计划，明确下一步要用什么证据把"方向"推进到"可确认/可排除/需升级"。

**整合目标**：使用DR.KNOWS路径约束推理，指导证据采集和排序。

**核心任务**：

1. **证据提取**
   - **从路径中提取需要采集的证据**：
     - 路径中的节点就是需要采集的证据
     - 如果路径中的节点在当前证据中缺失，标记为需要采集
   - **证据分类**：
     - 阳性线索证据（路径中支持某一方向的节点）
     - 关键阴性线索证据（路径中排除某一方向的节点）
   - **证据采集顺序**（基于知识库，非优先级）：
     - **优先采集知识库中标记为"必须补齐"的信息**（来自知识库的待补齐缺口）
     - **优先采集Tier2候选路径中的证据**（必须优先除外）
     - **优先采集Tier1候选路径中的证据**（最可能）
     - **优先采集Tier3候选路径中的证据**（积极备选）

2. **路径约束推理**
   - **选择Top-N路径**（基于知识库候选，非路径结构特征）：
     - **排序依据是知识库中的内容**（Tier1/Tier2/Tier3），不是路径长度、数量、风险评估等级
     - 优先选择指向Tier1候选的路径
     - 优先选择指向Tier2候选的路径
     - 优先选择指向Tier3候选的路径
     - 总共选择Top-10路径用于约束LLM推理
   - **构建路径约束Prompt**：
     - 将Top-N路径格式化为自然语言描述
     - 将路径作为上下文注入Prompt
     - 明确要求LLM：**必须基于提供的路径推理，不得引入路径外的自由联想**
   - **LLM推理**：
     - LLM在路径约束下进行推理
     - 分析每个疾病的支持证据（必须来自路径）
     - 分析每个疾病的反对证据（必须来自路径）
     - 识别还需要哪些信息来进一步判断（路径中缺失的节点）
   - **推理结果验证**（关键步骤）：
     - **路径一致性验证**：检查LLM输出的诊断是否在路径中
     - **证据来源验证**：检查LLM输出的证据是否来自路径
     - **路径完整性验证**：检查LLM是否使用了所有Top-N路径
     - **医学逻辑验证**：检查LLM的推理是否符合医学逻辑
     - **降级策略**：如果验证失败，使用路径本身作为推理结果，并标记为"需要人工审核"

3. **证据采集执行**
   - **按采集顺序采集证据**（基于知识库，非优先级）：
     - **优先采集知识库中标记为"必须补齐"的信息**（来自知识库的待补齐缺口）
     - **优先采集Tier2候选路径中的证据**（必须优先除外）
     - **优先采集Tier1候选路径中的证据**（最可能）
     - **优先采集Tier3候选路径中的证据**（积极备选）
   - **证据采集方式**：
     - 追问：路径中的症状节点
     - 观察：路径中的体征节点
     - 测量：路径中的检查节点
   - **证据记录**：
     - 记录证据项名称
     - 记录证据来源（追问/观察/测量）
     - 记录证据结果
     - 记录证据方向（支持/不支持/不确定）
     - 记录影响对象（推动哪个方向前移或后移）

4. **三层排序形成**（基于知识库权威内容，非路径结构特征）
   - **基于知识库中的权威内容排序**：
     - **Tier2（必须排除方向）**：知识库中的Tier2候选，如果未完成排除则保留
     - **Tier1（最可能方向）**：知识库中的Tier1候选，根据当前支持线索和反对线索匹配情况
     - **Tier3（积极备选方向）**：知识库中的Tier3候选，需要进一步区分
   - **路径用于验证候选**：
     - 如果新证据支持某一方向的路径，验证该方向的知识库候选仍然有效
     - 如果新证据反对某一方向的路径，标记该方向的知识库候选为"需要重新评估"
     - **但排序不依赖路径数量，而是基于知识库中的权威内容**
   - **排序依据标注**：
     - 每个方向必须写清"一句话依据"
     - 依据**优先来自知识库**（知识库中的入选依据、支持线索、反对线索）
     - 路径作为补充依据（用于追溯和验证）

5. **验证计划制定**
   - **优先使用知识库中的验证计划**：
     - 从疾病知识图谱中获取"必须补齐的关键信息条目ID列表"
     - 从主诉表6（候选疾病明细表）中获取"待补齐缺口"（必须补齐的关键信息条目ID列表）
     - 这些是知识库中定义的权威验证计划
   - **DR.KNOWS路径补充验证计划**（可选）：
     - 如果知识库中的验证计划不完整，可以从路径中提取检查节点作为补充
     - 但知识库中的验证计划优先
   - **验证计划设计**：
     - 验证目的（确认/排除/升级判定）
     - 验证动作（补问/观察/测量/检查或就医）
     - 判定标准（什么结果支持/不支持）
     - 结果回填规则（结果出现后如何更新三层排序）
   - **验证计划执行顺序**（基于知识库，非优先级）：
     - **优先执行Tier2候选的验证计划**（必须优先除外）
     - **优先执行Tier1候选的验证计划**（最可能）
     - **优先执行Tier3候选的验证计划**（积极备选）

6. **路径更新与知识库验证**
   - **将新证据回填到路径**：
     - 如果新证据匹配路径中的节点，标记为已采集
     - 如果新证据支持路径，标记路径为"支持"
     - 如果新证据反对路径，标记路径为"反对"
   - **路径支持状态更新**：
     - 被支持的路径：保留，路径支持状态更新为"支持"

   - **路径用于验证知识库候选**（**关键作用**）：
     - 检查被支持的路径是否指向知识库中的候选疾病
     - 如果路径支持知识库候选，验证候选仍然有效
     - 如果路径强烈反对知识库候选，标记候选为"需要重新评估"
     - **但知识库候选的排序不依赖路径数量，而是基于知识库中的权威内容**
   - **路径筛选**（用于Step 5的证据链生成）：
     - 保留被支持的路径（用于Step 5的证据链生成）
     - 保留指向知识库候选的路径（用于验证和追溯）
     - 被强烈反对的路径标记为"已排除"，但保留用于审计

**输出标准**：

**必交付内容**：

#### 3.3.6 Step 5：回填证据并输出终点结论包

> **参考文档**：《DR.KNOWS与5步诊断流程整合方案.md》  
> **核心原则**：使用DR.KNOWS路径生成证据链和结论包

**目标**：将 Step 4 的验证结果回填到证据清单与问题清单中，更新三层排序，并输出可行动、可审计的终点结论包。该结论包既能对用户形成明确的"下一步怎么做"，也能对内部形成可追溯的证据链与复评规则，保证诊断过程可迭代。

**整合目标**：使用DR.KNOWS路径生成证据链和结论包。

**核心任务**：

1. **证据回填**
   - **回填新增证据**：
     - 将Step 4验证计划的结果回填到证据清单
     - 将新增问诊、测量、检查结果回填
   - **证据标记**：
     - 标记每条证据对各方向的作用（支持/不支持/不确定）
     - 标记每条证据来自哪个推理路径
   - **证据审计记录**：
     - 记录证据项
     - 记录来源（追问/观察/测量/检查）
     - 记录结果
     - 记录作用（支持/不支持/不确定）
     - 记录影响（推动哪个方向前移或后移）

2. **路径更新与知识库候选验证**
   - **将新证据回填到路径**：
     - 如果新证据匹配路径中的节点，标记为已采集
     - 如果新证据支持路径，标记路径为"支持"
     - 如果新证据反对路径，标记路径为"反对"
   - **路径用于验证知识库候选**（**关键作用**）：
     - 检查被支持的路径是否指向知识库中的候选疾病
     - 如果路径支持知识库候选，验证候选仍然有效
     - 如果路径强烈反对知识库候选，标记候选为"需要重新评估"
     - **但知识库候选的排序不依赖路径数量，而是基于知识库中的权威内容**
   - **路径筛选**（用于证据链生成）：
     - 保留被支持的路径（用于证据链生成）
     - 保留指向知识库候选的路径（用于验证和追溯）
     - 保留Top-N路径（用于证据链生成）

3. **三层排序更新（基于知识库）**
   - **基于知识库候选更新排序**：
     - **Tier2（必须排除方向）**：知识库中的Tier2候选，如果未完成排除则保留
     - **Tier1（最可能方向）**：知识库中的Tier1候选，根据当前支持线索和反对线索匹配情况
     - **Tier3（积极备选方向）**：知识库中的Tier3候选，需要进一步区分
   - **路径用于验证候选**：
     - 如果路径支持知识库候选，验证候选仍然有效
     - 如果路径强烈反对知识库候选，标记候选为"需要重新评估"
     - **但排序不依赖路径数量，而是基于知识库中的权威内容**
   - **排序依据更新**：
     - 更新每个方向的"一句话依据"
     - 依据**优先来自知识库**（知识库中的入选依据、支持线索、反对线索）
     - 路径作为补充依据（用于追溯和验证）

4. **证据链生成（基于知识库和路径）**
   - **优先使用知识库中的证据链**：
     - 从疾病知识图谱中获取"证据链构建规则"（输出解释时证据如何选取与排序）
     - 从疾病知识图谱中获取"关键支持证据条目ID列表"和"关键反对证据条目ID列表"
     - 这些是知识库中定义的权威证据链
   - **DR.KNOWS路径补充证据链**：
     - 选择被支持的路径（指向知识库候选的路径）
     - 将路径格式化为证据链描述
     - 例如：症状A → 系统来源B → 疾病C
     - 路径作为知识库证据链的补充和验证
   - **证据链完整性检查**：
     - 检查知识库中的证据链是否完整（关键支持证据是否都有证据支持）
     - 检查路径是否与知识库中的证据链一致
     - 如果路径与知识库证据链一致，验证证据链有效
   - **证据链标注**（基于知识库和路径）：
     - 标注哪些是阳性证据（**优先来自知识库的关键支持证据**，路径作为补充）
     - 标注哪些是关键阴性证据（**优先来自知识库的关键反对证据**，路径作为补充）
     - 标注证据来源（知识库/路径）

5. **终点结论包生成**
   - **终点分类**：
     - **可确证终点**：证据达到明确诊断标准，路径完整且一致
     - **不可确证终点**：证据不足以确证，但路径指向明确方向
   - **结论生成**：
     - **可确证**：输出具体疾病诊断（基于Top路径）
     - **不可确证**：输出最可能方向或最可能诊断倾向（基于Top路径）
   - **必须排除项状态**：
     - 已排除：路径被强烈反对，证据充分
     - 未排除：路径仍存在，证据不足
     - 需线下排除：需要线下检查才能排除
   - **关键依据**：
     - 至少三条证据（来自Top路径）
     - 明确哪些是阳性证据
     - 明确哪些是关键阴性证据
     - 每条证据都对应推理路径
   - **行动与随访**：
     - 立即行动（基于路径中的检查节点）
     - 复评时间窗（基于路径中的随访节点）
     - 升级触发条件（基于路径中的高危节点）

6. **复评与回退机制**
   - **回退触发条件**：
     - 证据冲突：新证据与现有路径强烈冲突
     - 症状演变：症状变化导致现有路径不再适用
     - 处理无效：按路径建议处理无效
   - **回退目标确定**：
     - 如果路径被强烈反对，回退到Step 2（重新检索路径）
     - 如果证据不足，回退到Step 4（重新采集证据）
     - 如果排序不稳定，回退到Step 3（重新组织分流路径）
   - **回退执行**：
     - 清除被反对的路径
     - 保留仍有效的路径
     - 重新执行相应步骤

**输出标准**：

**必交付内容**：

1. **证据回填记录**：
   - 每条证据包含：名称、来源、结果、作用、影响、相关路径

2. **更新后的三层清单**：
   - 最可能方向（1个）+ 一句话依据 + 推理路径

   - 积极备选方向（1-2个）+ 一句话依据 + 推理路径

5. **回退决策**（如适用）：
   - 回退原因、回退目标、保留的路径

#### 3.3.7 流程迭代与回退机制

**概述**：临床诊疗态流程支持动态迭代和回退，当出现证据冲突、症状演变或处理无效时，系统可以回退到之前的步骤重新处理，确保不会在错误结论上"锁死"。

**回退机制说明**：
- 系统支持回退到任意步骤（Step 1-5 或阶段0）
- 回退触发条件包括：证据冲突、症状演变、治疗无效、必须排除项未完成等
- 回退遵循医疗理论原则：假设可修正性、证据优先性、风险优先性、可追溯性

> **详细回退机制**：请参考 [3.4.7 回退机制（基于临床推理理论）](#347-回退机制基于临床推理理论) 章节，包含完整的回退条件清单、回退路径、医疗理论依据和理论保证。

### 3.5 终点结论包四要素（关键输出标准）

**职责**：确保所有诊断结果输出都包含四个要素，保证可行动、可审计

**四要素结构**：

#### 要素1：结论（Conclusion）

**可确证结论**：
- 输出具体疾病诊断（或最可能诊断）
- 诊断依据：支持证据链（至少3条）
- 疾病严重程度：轻度/中度/重度
- 诊断置信度：高/中/低

**不可确证结论**：
- 输出最可能方向或最可能诊断倾向
- 不确定性来源：为什么无法明确判断
- 缺失的关键证据：需要哪些证据来明确

#### 要素2：必须排除项状态（Must-Exclude Status）

**状态类型**：
- **已排除**：已通过验证明确排除的高危诊断
  - 排除理由：为什么已排除
- **未排除**：未完成排除，必须保留在候选清单中
  - 未排除原因：为什么未排除
- **需线下排除**：需要线下检查才能排除的高危诊断
  - 排除建议：需要做什么检查才能排除

**关键原则**：
- 未完成排除则必须保留，不能因为可能性低就忽略
- 必须明确告知患者必须排除项的状态

#### 要素3：关键依据（Key Evidence）

**证据要求**：
- **至少三条证据**，明确哪些是阳性证据，哪些是关键阴性证据
- **阳性证据**：支持诊断的证据（至少3条）
- **阴性证据**：排除其他诊断的证据
- **检查结果**：支持诊断的检查结果

**证据结构**：
```json
{
  "positive_evidence": [
    {
      "evidence": "证据名称",
      "source": "证据来源",
      "strength": "强证据/中证据/弱证据"
    }
  ],
  "negative_evidence": [
    {
      "evidence": "证据名称",
      "excluded_direction": "排除的诊断方向"
    }
  ],
  "check_results": [
    {
      "check_name": "检查名称",
      "result": "检查结果",
      "support_direction": "支持的诊断方向"
    }
  ]
}
```

#### 要素4：行动与随访（Action & Follow-up）

**立即行动**：
- 就医建议（科室、时间、需带资料）
- 检查建议（如需进一步确诊）
- 治疗方向（治疗方案方向，不给出具体用药剂量）
- 紧急情况处理建议

**复评时间窗**：
- 默认复评时间（根据疾病类型设定）
- 提前复评条件（症状加重、出现新症状等）
- 延迟复评条件（症状完全缓解等）

**升级触发条件**：
- 出现哪些情况必须立即升级（立即就医）
- 例如：症状突然加重、出现高危症状、处理无效等

```json

    "confidence": 0.75,
```

### 3.4 关键流程节点

#### 3.4.1 健康状态判定完成

**判定标准**：
- 已收集足够信息进行健康状态判定
- 明确是否需要进入诊疗流程
- 确定工作态（wellness_mode / clinical_mode）

**判定结果**：
- **进入健康管理态**：生成 `wellness_plan`，不生成 `ddx`
- **进入临床诊疗态**：启动诊断流程，生成 `ddx`

#### 3.4.2 健康管理态升级触发

**触发条件**：
- 症状加重或持续不缓解
- 出现新症状
- 识别到风险信号（红旗信号）
- 随访中发现异常

**升级动作**：
- 更新 `health_state_assessment.work_mode` = clinical_mode
- 启动诊断流程
- 主Agent重新调用相关工具

#### 3.4.3 Step 1 完成判断（识别问题）

**判断标准**：
- 问题清单已结构化（主要问题、伴随问题、关键背景）
- 必填缺口已补齐，或已明确标记为"重要缺口"并提示风险
- 概念已归一化，可进入 Step 2

**触发条件**：
- 必填缺口已补齐
- 或已明确标记为"重要缺口"并提示风险
- 问题清单结构化完成

**进入下一步**：
- 进入 Step 2：构建鉴别诊断候选集并分层

#### 3.4.4 Step 2 完成判断（构建鉴别诊断候选集并分层）

**判断标准**：
- 鉴别诊断全集已生成
- 三层分层已完成（至少有一个首要假设）
- 每个方向都有明确的入选依据

**触发条件**：
- 鉴别诊断全集已生成
- 三层分层已完成
- 下一步分流入口已标记

**进入下一步**：
- 进入 Step 3：组织候选集并建立分流路径

#### 3.4.5 Step 3 完成判断（组织候选集并建立分流路径）

**判断标准**：
- 推理子组结构已建立
- 关键差异点已提炼
- 分流路径清单已生成

**触发条件**：
- 推理子组结构已建立
- 关键差异点已提炼
- 分流路径清单已生成

**进入下一步**：
- 进入 Step 4：采集关键证据并形成排序与验证计划

#### 3.4.6 Step 4 完成判断（采集关键证据并形成排序与验证计划）

**判断标准**：
- 关键证据已采集（至少覆盖主要差异点）
- 三层排序已固化
- 验证计划已制定（针对最可能和必须排除方向）

**触发条件**：
- 关键证据已采集
- 三层排序已固化
- 验证计划已制定

**进入下一步**：
- 进入 Step 5：回填证据并输出终点结论包

#### 3.4.7 Step 5 完成判断（回填证据并输出终点结论包）

**判断标准**：
- 证据已回填
- 三层排序已更新
- 终点结论包已生成（包含四要素）

**触发条件**：
- 证据已回填
- 三层排序已更新
- 终点结论包已生成

**流程结束**：
- 输出终点结论包给用户
- 启动随访机制

#### 3.4.8 诊断更新触发（临床诊疗态）

**触发条件**：
- 新信息输入（新的症状、检查结果等）
- 信息冲突（需要重新评估）
- 随访反馈（症状变化）

**更新机制**：
- 根据新信息判断需要回退到哪个 Step
- 主Agent重新调用相关工具
- 更新CDP的相应字段

#### 3.4.5 高危升级触发（临床诊疗态）

**触发条件**：
- 工具6（风险评估工具）识别到高危情况
- `triage.risk_level` = L1 或 L2

**升级动作**：
- 立即建议就医
- 明确告知风险等级
- 提供紧急处理建议

**职责**：定义新信息出现后如何重新排序诊断方向，以及如何处理证据冲突

**重排规则**：
1. **新证据出现后的重排**：
   - 强支持证据 → 方向上移（权重+0.3）
   - 强反对证据 → 方向下移（权重-0.2）
   - 不确定证据 → 标记为不确定，需要进一步验证

2. **证据冲突时的回退规则**：
   - 如果新证据与原有证据明显冲突 → 标记为不确定并回退到 Step 4
   - 如果症状描述与检查结果冲突 → 回退到 Step 1 重新收集信息
   - 如果信息冲突，需要确认并标记为"待确认"状态

3. **三层排序更新规则**：
   - **最可能方向**：如果新证据强烈支持，巩固；如果新证据不支持，可能需要更换
   - **必须排除方向**：如果验证结果明确排除，标记为"已排除"；如果未排除，必须保留
   - **积极备选方向**：如果新证据支持，可能上移为最可能方向；如果新证据不支持，可能下沉或移除

**强调"排序可变"**：避免一旦形成初步结论就不再修正

#### 3.4.7 回退机制（基于临床推理理论）

> **对应技术架构文档**：6.5 回退机制引擎

1. **假设-验证模型**（Hypothesis-Testing Model）- Elstein的临床推理模型
2. **诊断修正理论**（Diagnostic Revision Theory）
3. **治疗性诊断**（Therapeutic Diagnosis）

- 诊断假设能够根据新证据动态调整
- 避免诊断锁定（Diagnostic Lock-in）
- 符合临床医生的思维过程

- **符合临床医生的思维过程**：临床诊断是一个动态的、迭代的过程
- **保证诊断的准确性**：通过回退机制及时纠正错误诊断

     - **疾病进展理论**（Disease Progression Theory）：新症状可能提示疾病进展或诊断方向错误
   - **医疗原则**：症状演变提示疾病状态改变，需要重新评估诊断

2. **回退到 Step 4**（采集关键证据并形成排序与验证计划）
   - **触发条件**：假设验证失败、治疗无效、必须排除项未完成、证据冲突
   - **医疗理论依据**：
     - **假设-验证模型**（Hypothesis-Testing Model）：如果假设与证据不符，回退到证据采集阶段

     - 治疗无效：说明诊断方向可能错误，需要重新诊断
     - 必须排除项未完成：高危诊断必须优先处理
   - **动作**：重新采集证据，重新制定验证计划，重新评估诊断概率

3. **回退到 Step 1**（识别问题）
   - **触发条件**：信息冲突、信息不完整、关键信息缺失
   - **医疗理论依据**：
     - **信息完整性原则**（Information Completeness Principle）：诊断需要完整、准确的信息
     - **信息一致性原则**（Information Consistency Principle）：信息冲突需要澄清
   - **医疗原则**：
     - 信息冲突：主观症状与客观体征不一致，需要重新验证
     - 信息不完整：关键信息缺失无法进行可靠诊断
   - **动作**：重新收集信息，澄清冲突，补全关键信息

4. **回退到阶段0**（健康状态判定阶段）
   - **触发条件**：症状突然加重、出现新的高危症状、生命体征异常
   - **医疗理论依据**：
     - **分诊理论**（Triage Theory）：高危情况需要重新评估健康状态
     - **风险升级原则**（Risk Escalation Principle）：症状恶化需要升级处理
   - **医疗原则**：症状突然加重或出现高危症状，需要重新评估是否需要紧急处理
   - **动作**：重新进行健康状态判定，重新评估风险等级，决定是否需要紧急就医

**理论保证**：
- **收敛性保证**：在回退机制下，诊断序列在有限步内收敛到稳定状态
- **误差界保证**：回退机制保证最终诊断的误差上界
- **安全性保证**：回退机制确保高危诊断不会被遗漏

**回退原则**（基于临床推理理论）：

1. **假设可修正性**：诊断假设应该能够根据新证据动态调整
   - 医疗依据：Elstein的假设-验证模型
   - 保证：避免诊断锁定（Diagnostic Lock-in）

2. **证据优先性**：新证据优先于旧假设
   - 医疗依据：循证医学原则
   - 保证：当新证据与旧假设冲突时，优先相信新证据

3. **风险优先性**：高危诊断优先处理
   - 医疗依据：风险优先原则（Risk-First Principle）
   - 保证：漏诊高危疾病的代价极大，必须优先排除

4. **可追溯性**：记录回退原因和动作
   - 医疗依据：临床决策的可审计性
   - 保证：便于审计和验证，支持临床决策的透明度

**理论保证**：
在临床推理理论下，回退机制保证：
- 诊断假设能够根据新证据动态调整（避免诊断锁定）
- 高危诊断优先处理（避免漏诊）
- 诊断过程符合临床医生的思维模式（可解释性强）

```
    - 主Agent调用工具0：判定是否需要进入诊疗流程
    - 更新 health_state_assessment
    - 设置 work_mode
    ↓
    ┌──────────────┬──────────────┐
    │ 健康管理态    │ 临床诊疗态    │
    └──────────────┴──────────────┘
         │                    │
         ▼                    ▼
CDP更新（健康管理）    CDP更新（信息收集）
    - 主Agent调用工具1   - 主Agent调用工具1更新 patient_state
      更新patient_state  - 主Agent调用工具2生成问诊计划
    - 生成 wellness_plan     ↓
    - 持续监控          CDP更新（诊断阶段）
         │              - 主Agent调用工具3更新 ddx
         │              - 主Agent调用工具4更新 workup_plan
         │              - 主Agent调用工具6更新 triage
         │                   ↓
         │              CDP更新（处置阶段）
         │              - 主Agent调用工具5更新 management_plan
         │              - 主Agent调用工具7更新 evidence_graph
         │                   ↓
         │              CDP持久化（诊断完成）
         │                   ↓
         │              CDP更新（随访阶段）
         │              - 主Agent重新调用相关工具
         │              - 更新CDP状态
         │
         └──────────→ 升级触发（症状加重/风险信号）
                      - 更新 work_mode = clinical_mode
                      - 进入临床诊疗态流程
```

### 4.2 CDP版本管理

**版本控制**：
- 每次CDP更新都创建新版本
- 保留历史版本，支持回放
- 记录每次更新的原因和来源

**审计信息**：
- `audit.model_version`：使用的模型版本
- `audit.prompt_version`：使用的提示词版本
- `audit.knowledge_version`：使用的知识版本
- `audit.timestamp`：更新时间戳
- `audit.reasoning_trace`：推理轨迹

## 五、评估与验证体系

### 5.1 三类离线评测集

#### 5.1.1 静态病例集（Static Case Set）

**用途**：评估"读病历 → 给DDx/计划"的能力

**输入**：固定的完整病历文本
**输出**：DDx列表、检查建议、处置方案
**评估**：可重复、可对比

**评估指标**：
- DDx Top-K命中率
- 检查建议合理性
- 处置方案合理性

#### 5.1.2 交互问诊集（Interactive Interview Set）

**用途**：评估"问对问题"的能力和问诊效率

**输入**：初始主诉，需要多轮对话
**输出**：问诊问题序列、最终诊断
**评估**：问诊质量、问诊效率

**评估指标**：
- "缺失信息"是否合理（问诊质量）
- 问诊轮次效率（完成诊断所需轮次）
- 信息增益有效性（问的问题是否有助于区分DDx）

#### 5.1.3 轨迹回放集（Trajectory Replay Set）

**用途**：评估"信息逐步揭示时修正DDx"的能力

**输入**：逐步提供信息
- 先给主诉
- 再给体征
- 再给检验
- 再给影像

**输出**：每个阶段的DDx更新
**评估**：是否能随着信息更新修正DDx

**评估指标**：
- DDx修正准确性
- 信息更新后的诊断更新及时性
- 证据链更新完整性

### 5.2 核心评估指标

#### 5.2.1 DDx准确性指标

- **DDx Top-1命中率**：最高可能性诊断是否正确
- **DDx Top-3命中率**：前3个可能性中是否包含正确诊断
- **DDx Top-5命中率**：前5个可能性中是否包含正确诊断

#### 5.2.2 安全性指标

- **红旗识别召回率**：宁可误报，不能漏报
- **高危升级及时性**：识别高危后是否及时建议就医
- **不确定性表达准确性**：低置信度时是否明确表达不确定性

#### 5.2.3 问诊质量指标

- **信息增益有效性**：问的问题是否有助于区分DDx
- **问诊轮次效率**：完成诊断所需轮次
- **缺失信息合理性**：识别的缺失信息是否合理

#### 5.2.4 可解释性指标

- **证据链完整性**：支持证据、反对证据、缺失证据是否完整
- **推理路径可追溯性**：诊断结论是否能追溯到证据
- **方案合理性**：基于路径/证据可解释

#### 5.2.5 健康状态判定指标

- **健康状态判定准确率**：是否正确判断是否需要进入诊疗流程
- **健康管理态升级及时性**：发现风险信号后是否及时升级到临床诊疗态
- **漏诊率**：应该进入临床诊疗态但误判为健康管理态的比例（必须极低）

## 六、知识演化与维护功能

> **设计目标**：在保持诊断责任链清晰的前提下，实现知识的自治演化与安全发布  
> **设计原则**：诊断决策单点负责；知识演化多点自治，但发布单点门禁  
> **详细技术设计**：请参考《知识演化与知识维护-完整设计方案.md》

### 6.1 功能概述

**核心思想**：
- **双层决策架构**：诊断域（主Agent）与知识域（知识演化Agent集群）分离
- **权限分离**：Read（生产知识）、Write（候选区）、Publish（发布门禁）、Rollback（回滚控制）
- **版本化管理**：类似CDP的写时复制思想，支持知识版本追溯和回滚

**功能定位**：
- **在线层**：知识查询服务（Knowledge Query Service），服务于通道1结构化推理，提供只读的知识库查询
- **离线层**：知识运维服务（Knowledge Operations Service），负责知识的抽取、验证、冲突处理、发布门禁

### 6.2 三个知识库区

#### 6.2.1 Sandbox（实验/构建区）

**功能**：
- 抽取Agent、解析Agent在这里生成结构化知识对象（KO）
- 与证据绑定
- 不影响任何线上推理

**特点**：
- 完全隔离，不影响生产环境
- 支持快速迭代和实验
- 可以随时清理和重建

#### 6.2.2 Staging（候选验证区）

**功能**：
- 验证Agent工作：证据一致性、冲突检测
- 冲突处理Agent工作：解决知识冲突
- 回归评测Agent工作：影子评测
- 产出"候选release（candidate_release）"

**特点**：
- 通过验证的知识才能进入Staging
- 支持完整的验证和测试流程
- 生成候选发布包

#### 6.2.3 Production（线上只读发布区）

**功能**：
- 只有通过Publish Gate的release才进入Production
- 生成 `kg_version`（v1, v2, v3...）
- 支持版本化管理和回滚

**特点**：
- 只读访问，不直接修改
- 版本化管理，支持回滚
- 对应CDP的写时复制思想

### 6.3 知识演化Agent集群

**Agent职责划分**：

| Agent | 职责 | 工作区域 |
|-------|------|---------|
| Extractor Agent | 从知识源中抽取结构化知识 | Sandbox |
| Verifier Agent | 验证知识的正确性和一致性 | Sandbox → Staging |
| Conflict Resolver Agent | 解决知识冲突 | Staging |
| Release Builder Agent | 打包发布候选 | Staging |
| Shadow Evaluator Agent | 在离线环境进行评测 | Staging |
| Rollback & Drift Monitor Agent | 监控生产环境的知识使用情况 | Production |

**Agent协作流程**：
```
新知识源
  ↓
Extractor Agent（抽取）→ Sandbox
  ↓
Verifier Agent（验证）→ Staging
  ↓
Conflict Resolver Agent（冲突解决）→ Staging
  ↓
Release Builder Agent（打包）→ candidate_release
  ↓
Shadow Evaluator Agent（影子评测）→ 评测报告
  ↓
Publish Gate（门禁）→ Production
  ↓
Rollback & Drift Monitor Agent（监控）→ 持续监控
```

### 6.4 Publish Gate：发布门禁机制

**定位**：非LLM、规则/测试驱动的发布控制器

**四道门禁**：

1. **Gate-1：结构合法性**
   - 检查KO schema完整
   - concept标准化字段齐全
   - 避免脏数据

2. **Gate-2：证据可追溯性**
   - 每条KO必须绑定provenance
   - 没有证据不允许进入发布候选

3. **Gate-3：回归评测与影子评测通过**
   - 必须跑最小回归集
   - 核心DDx场景测试
   - 红旗病种测试
   - 关键路径断裂测试

4. **Gate-4：风险分级审批（可选人工）**
   - 低风险：自动发布
   - 中风险：需要人工审批或双人签署
   - 高风险：必须人工审批+灰度发布

### 6.5 知识演化触发机制

#### 6.5.1 在线触发：只产生Proposal

**触发场景**：
- tool_3鉴别诊断候选为空/很弱（知识覆盖缺口）
- 冲突复核反复失败（图谱路径无法验证、证据互斥）
- 反复"证据不足"仍无法满足停止条件中的"证据链完整"

**处理方式**：
- 主Agent在Evaluate阶段可决定：向knowledge-ops提交 `proposal`（异步）
- **不阻塞当前会话闭环**
- 只产生提案，不直接更新生产知识

#### 6.5.2 离线触发：周期性扫描

**触发场景**：
- 新指南/新共识发布
- 内部规则变更
- 线上监控发现某类case回归，触发"修复提案"

**处理方式**：
- 定时任务扫描知识源
- 检测到更新后触发知识演化流程
- 自动生成提案

### 6.6 版本化管理与回滚

**版本生成**：
- 每次发布生成 `kg_version`（v1, v2, v3...）
- 对应CDP的写时复制思想
- 新版本、旧版本保留用于审计回滚

**回滚机制**：
- **全局回滚**：把默认kg_version指针回退（通过修改current_release指针）
- **局部回滚**：按ko_id局部回滚（利用downstream_bindings进行精确回滚）

**灰度发布**：
- 按会话分流
- 按机构分流
- 按病种分流

### 6.7 与诊断流程的集成

#### 6.7.1 主Agent集成

**主Agent职责不变**：
- 诊断与临床动作的唯一责任主体仍是主Agent
- 主Agent运行循环不变：Observe→Plan→Act→Update→Evaluate→Stop/Escalate
- 主Agent负责证据融合和冲突解决

**新增能力**：
- 主Agent可以触发知识演化提案（异步）
- 主Agent使用版本化知识进行推理
- 主Agent在CDP中记录知识引用

#### 6.7.2 工具服务集成

**工具服务职责不变**：
- 工具仍然无独立目标、无长期策略状态
- 工具只按主Agent调用执行并返回结构化结果
- 工具必须提供evidence引用和suggestedWrites

**新增能力**：
- 工具可以访问版本化知识
- 工具的evidence引用包含kg_version和ko_id
- 工具通过knowledge-query-service访问知识

#### 6.7.3 CDP集成

**CDP职责不变**：
- CDP仍然是病例事实的唯一事实源
- 所有工具从CDP读取，建议写回CDP
- CDP支持版本控制、回放、回退

**新增能力**：
- CDP记录知识引用（knowledge_refs）
- CDP的audit包含kg_version
- CDP支持知识版本追溯

### 6.8 功能优势

**优点**：
- ✅ 能真正做"知识演化"研究（触发策略、演化规则、漂移检测）
- ✅ 不会把生产知识库暴露给无门禁的自动更新
- ✅ 诊断责任链仍清晰（决策在主Agent，知识变更可追溯）
- ✅ 支持版本化管理和灰度发布
- ✅ 支持回滚和依赖分析

**注意事项**：
- ⚠️ 需要完整的治理设施（版本、影子评测、回滚、依赖分析）
- ⚠️ 系统复杂度上升
