# AI医生系统 - 技术架构设计（错误处理与异常场景设计）

> **文档定位**：本文档是AI医生系统的**技术架构设计**的错误处理与异常场景设计部分，包含系统级错误处理策略、异常场景处理流程、降级策略系统级设计、故障恢复机制等。  
> **业务功能**：请参考《AI医生系统-系统功能设计.md》  
> **核心目标**：详细说明系统在错误和异常场景下的处理策略，确保系统可靠性和安全性。

---

## 一、错误处理与异常场景概述

### 1.1 设计原则

**核心原则**：
1. **安全第一**：宁可误报，不能漏报，确保患者安全
2. **优雅降级**：系统在错误时能够优雅降级，不崩溃
3. **可追溯**：所有错误和异常都记录到AuditTrail
4. **可恢复**：系统在错误后能够恢复，不丢失关键数据
5. **用户友好**：错误信息对用户友好，不暴露技术细节

### 1.2 错误分类

**错误层级**：
- **工具层错误**：工具执行失败、超时、返回错误
- **服务层错误**：服务调用失败、服务不可用
- **系统层错误**：数据库连接失败、消息队列故障、网络故障
- **业务层错误**：CDP损坏、AgentState不一致、数据验证失败

**错误类型**：
- **技术错误**：超时、网络故障、数据库连接失败等
- **业务错误**：数据验证失败、业务规则违反等
- **逻辑错误**：算法执行失败、决策错误等

## 二、工具层错误处理

### 2.1 工具执行失败

**场景**：工具执行失败（status=failure）

**处理策略**：

```
1. 检查错误类型
   - timeout：超时错误
   - validation_error：验证错误
   - runtime_error：运行时错误

2. 根据错误类型处理
   - timeout：根据重试策略重试
   - validation_error：记录错误，使用降级策略
   - runtime_error：记录错误，使用降级策略

3. 更新AgentState
   - 更新 tried_tools 中的失败记录
   - 更新 failure_backoff 状态

4. 记录到AuditTrail
   - 记录工具调用失败
   - 记录错误类型和错误消息

5. 决定下一步
   - 如果工具是关键工具：触发升级或拒答
   - 如果工具是非关键工具：使用降级策略，继续执行
```

**处理流程**：

```
工具执行失败
  ↓
检查错误类型
  ↓
  ├─→ timeout
  │     ↓
  │   检查重试次数
  │     ↓
  │   如果未超过最大重试次数 → 重试
  │     ↓
  │   如果超过最大重试次数 → 使用降级策略
  │
  ├─→ validation_error
  │     ↓
  │   记录错误
  │     ↓
  │   使用工具降级策略
  │     ↓
  │   继续执行（如果工具非关键）
  │
  └─→ runtime_error
        ↓
      记录错误
        ↓
      使用工具降级策略
        ↓
      如果工具是关键工具 → 触发升级或拒答
      如果工具是非关键工具 → 继续执行
```

### 2.2 工具超时

**场景**：工具执行超时（status=timeout）

**处理策略**：

```
1. 检查工具重要性
   - 关键工具：tool_0（健康状态判定）、tool_3（鉴别诊断）、tool_6（风险评估）
   - 非关键工具：tool_2（主动问诊）、tool_5（治疗建议）、tool_7（证据链）

2. 根据工具重要性处理
   - 关键工具超时：立即使用降级策略，如果降级策略也失败，触发升级或拒答
   - 非关键工具超时：使用降级策略，继续执行

3. 重试策略
   - 检查重试次数：如果未超过最大重试次数，重试
   - 重试间隔：使用指数退避策略（exponential backoff）
   - 重试条件：只对关键工具和timeout错误重试

4. 更新AgentState
   - 更新 tried_tools 中的超时记录
   - 更新 failure_backoff 状态

5. 记录到AuditTrail
   - 记录工具调用超时
   - 记录重试次数和重试结果
```

**重试策略**：

```
重试次数：最多3次
重试间隔：指数退避
  - 第1次重试：1秒后
  - 第2次重试：2秒后
  - 第3次重试：4秒后

重试条件：
  - 只对关键工具重试
  - 只对timeout错误重试
  - 不对validation_error和runtime_error重试
```

### 2.3 工具返回部分成功

**场景**：工具返回部分成功（status=partial_success）

**处理策略**：

```
1. 评估部分成功的质量
   - 检查 quality.confidence
   - 检查 quality.completeness
   - 检查 errors 列表

2. 决定是否接受部分成功结果
   - 如果 confidence >= 0.6 且 completeness >= 0.7：接受结果
   - 如果 confidence < 0.6 或 completeness < 0.7：使用降级策略

3. 处理errors
   - 记录errors到AuditTrail
   - 根据errors类型决定是否继续执行

4. 更新CDP
   - 如果接受部分成功结果：写回CDP，但标记为"部分成功"
   - 如果不接受：使用降级策略
```

### 2.4 工具连续失败

**场景**：同一工具连续失败3次以上

**处理策略**：

```
1. 检测工具连续失败
   - 检查 tried_tools 中的失败记录
   - 如果同一工具连续失败3次以上，标记为"工具不可用"

2. 工具不可用处理
   - 如果工具是关键工具：触发升级或拒答
   - 如果工具是非关键工具：跳过该工具，使用降级策略

3. 更新AgentState
   - 更新 tried_tools 中的工具状态为"unavailable"
   - 记录工具不可用的原因

4. 记录到AuditTrail
   - 记录工具连续失败
   - 记录工具不可用状态

5. 通知运维
   - 如果工具连续失败，通知运维团队
   - 记录工具故障信息
```

## 三、服务层错误处理

### 3.1 服务调用失败

**场景**：主Agent调用工具服务失败（服务不可用、网络故障等）

**处理策略**：

```
1. 检查服务状态
   - 检查服务是否可用（健康检查）
   - 检查网络连接是否正常

2. 重试策略
   - 最多重试3次
   - 重试间隔：指数退避（1秒、2秒、4秒）
   - 只对关键服务重试

3. 服务降级
   - 如果服务不可用，使用服务降级策略
   - 服务降级：使用缓存结果、使用备用服务、使用简化逻辑

4. 更新AgentState
   - 更新服务状态
   - 记录服务调用失败

5. 记录到AuditTrail
   - 记录服务调用失败
   - 记录重试次数和重试结果
```

### 3.2 服务超时

**场景**：服务调用超时

**处理策略**：

```
1. 检查超时时间
   - 检查服务调用的超时时间设置
   - 检查服务响应时间

2. 超时处理
   - 如果服务是关键服务：立即使用降级策略
   - 如果服务是非关键服务：使用降级策略，继续执行

3. 重试策略
   - 只对关键服务和timeout错误重试
   - 最多重试2次（因为已经超时一次）

4. 更新AgentState
   - 更新服务调用超时记录
   - 更新服务状态

5. 记录到AuditTrail
   - 记录服务调用超时
   - 记录超时时间和重试结果
```

### 3.3 服务不可用

**场景**：服务完全不可用（服务宕机、服务维护等）

**处理策略**：

```
1. 检测服务不可用
   - 健康检查失败
   - 服务调用连续失败

2. 服务降级策略
   - 使用缓存结果（如果有）
   - 使用备用服务（如果有）
   - 使用简化逻辑（跳过该服务功能）

3. 如果服务是关键服务
   - 如果无法降级：触发升级或拒答
   - 如果可以降级：使用降级策略，继续执行

4. 更新AgentState
   - 更新服务状态为"unavailable"
   - 记录服务不可用的原因

5. 记录到AuditTrail
   - 记录服务不可用
   - 记录降级策略使用情况

6. 通知运维
   - 通知运维团队服务不可用
   - 记录服务故障信息
```

## 四、系统层错误处理

### 4.1 数据库连接失败

**场景**：MySQL/Oracle数据库连接失败

**处理策略**：

```
1. 检测数据库连接失败
   - 连接超时
   - 连接被拒绝
   - 连接池耗尽

2. 重试策略
   - 最多重试3次
   - 重试间隔：指数退避（2秒、4秒、8秒）
   - 使用连接池管理连接

3. 降级策略
   - 使用Redis缓存（如果数据在缓存中）
   - 使用只读模式（如果数据库只读可用）
   - 如果无法降级：触发升级或拒答

4. 数据一致性保证
   - 如果数据库连接失败，不更新CDP
   - 保留CDP在Redis缓存中
   - 等待数据库恢复后同步

5. 记录到AuditTrail
   - 记录数据库连接失败
   - 记录重试次数和重试结果

6. 通知运维
   - 通知运维团队数据库连接失败
   - 记录数据库故障信息
```

### 4.2 消息队列故障

**场景**：Redis消息队列故障

**处理策略**：

```
1. 检测消息队列故障
   - Redis连接失败
   - 消息队列不可用

2. 降级策略
   - 使用同步调用替代异步调用
   - 使用内存队列替代Redis队列（临时）
   - 如果无法降级：触发升级或拒答

3. 消息持久化
   - 如果消息队列故障，将消息持久化到数据库
   - 等待消息队列恢复后重放消息

4. 更新AgentState
   - 更新消息队列状态
   - 记录消息队列故障

5. 记录到AuditTrail
   - 记录消息队列故障
   - 记录降级策略使用情况

6. 通知运维
   - 通知运维团队消息队列故障
   - 记录消息队列故障信息
```

### 4.3 知识图谱连接失败

**场景**：Neo4j知识图谱连接失败

**处理策略**：

```
1. 检测知识图谱连接失败
   - Neo4j连接超时
   - Neo4j服务不可用

2. 降级策略
   - 使用知识库替代知识图谱（只使用知识库候选，不使用路径验证）
   - 使用缓存路径（如果路径在缓存中）
   - 如果无法降级：触发升级或拒答

3. 工具降级
   - tool_3（鉴别诊断工具）降级为只使用知识库模式
   - 标记路径验证为"未验证"

4. 更新AgentState
   - 更新知识图谱状态
   - 记录知识图谱连接失败

5. 记录到AuditTrail
   - 记录知识图谱连接失败
   - 记录降级策略使用情况

6. 通知运维
   - 通知运维团队知识图谱连接失败
   - 记录知识图谱故障信息
```

### 4.4 网络故障

**场景**：网络故障（服务间网络不通、外部API调用失败等）

**处理策略**：

```
1. 检测网络故障
   - 网络超时
   - 网络连接被拒绝
   - DNS解析失败

2. 重试策略
   - 最多重试3次
   - 重试间隔：指数退避（1秒、2秒、4秒）
   - 只对关键调用重试

3. 降级策略
   - 使用缓存结果（如果有）
   - 使用本地逻辑替代远程调用
   - 如果无法降级：触发升级或拒答

4. 更新AgentState
   - 更新网络状态
   - 记录网络故障

5. 记录到AuditTrail
   - 记录网络故障
   - 记录重试次数和重试结果

6. 通知运维
   - 通知运维团队网络故障
   - 记录网络故障信息
```

## 五、业务层错误处理

### 5.1 CDP损坏

**场景**：CDP数据损坏（JSON解析失败、字段缺失、数据不一致等）

**处理策略**：

```
1. 检测CDP损坏
   - JSON解析失败
   - 必填字段缺失
   - 数据格式不正确
   - 版本号不一致

2. CDP修复策略
   - 如果JSON解析失败：尝试从数据库重新加载CDP
   - 如果必填字段缺失：使用默认值填充（如果合理）
   - 如果数据格式不正确：尝试数据格式转换
   - 如果版本号不一致：使用乐观锁机制处理

3. 如果CDP无法修复
   - 从数据库重新加载CDP最新版本
   - 如果数据库也没有：创建新CDP，但保留用户输入

4. 更新AgentState
   - 更新CDP状态
   - 记录CDP损坏和修复过程

5. 记录到AuditTrail
   - 记录CDP损坏
   - 记录CDP修复过程

6. 通知用户
   - 如果CDP损坏严重，通知用户可能需要重新输入
```

### 5.2 AgentState不一致

**场景**：AgentState数据不一致（版本号不一致、状态不一致等）

**处理策略**：

```
1. 检测AgentState不一致
   - 版本号不一致
   - 状态字段不一致
   - 数据格式不正确

2. AgentState修复策略
   - 如果版本号不一致：使用乐观锁机制处理
   - 如果状态字段不一致：使用CDP状态同步AgentState
   - 如果数据格式不正确：尝试数据格式转换

3. 如果AgentState无法修复
   - 从CDP重新初始化AgentState
   - 如果CDP也没有：创建新AgentState

4. 更新AgentState
   - 更新AgentState状态
   - 记录AgentState修复过程

5. 记录到AuditTrail
   - 记录AgentState不一致
   - 记录AgentState修复过程
```

### 5.3 数据验证失败

**场景**：数据验证失败（工具返回的数据不符合预期、CDP数据不符合业务规则等）

**处理策略**：

```
1. 检测数据验证失败
   - 工具返回的数据不符合预期格式
   - CDP数据不符合业务规则
   - 数据值超出合理范围

2. 数据验证失败处理
   - 如果数据格式不正确：尝试数据格式转换
   - 如果数据值超出合理范围：使用默认值或拒绝数据
   - 如果数据不符合业务规则：拒绝数据，使用降级策略

3. 更新AgentState
   - 更新数据验证状态
   - 记录数据验证失败

4. 记录到AuditTrail
   - 记录数据验证失败
   - 记录验证失败的原因

5. 决定下一步
   - 如果数据是关键数据：触发升级或拒答
   - 如果数据是非关键数据：使用降级策略，继续执行
```

## 六、异常场景处理

### 6.1 工具连续失败场景

**场景**：多个工具连续失败，系统无法继续执行

**处理策略**：

```
1. 检测工具连续失败
   - 检查 tried_tools 中的失败记录
   - 如果关键工具连续失败3次以上，标记为"系统不可用"

2. 系统不可用处理
   - 触发升级策略：建议用户咨询专业医生
   - 记录系统不可用状态
   - 通知运维团队

3. 数据保护
   - 保存当前CDP状态到数据库
   - 保存AgentState状态
   - 保存AuditTrail记录

4. 用户通知
   - 通知用户系统暂时不可用
   - 建议用户稍后重试或咨询专业医生

5. 记录到AuditTrail
   - 记录系统不可用
   - 记录工具连续失败情况
```

### 6.2 预算耗尽场景

**场景**：AgentState中的budget耗尽（max_tool_calls、max_time_seconds、max_cost）

**处理策略**：

```
1. 检测预算耗尽
   - 检查 current_tool_calls >= max_tool_calls
   - 检查 current_time_seconds >= max_time_seconds
   - 检查 current_cost >= max_cost

2. 预算耗尽处理
   - 如果预算耗尽：停止运行循环，触发升级或拒答
   - 记录预算耗尽原因
   - 保存当前CDP状态

3. 用户通知
   - 通知用户诊断过程耗时较长，建议咨询专业医生
   - 提供当前诊断结果（如有）

4. 记录到AuditTrail
   - 记录预算耗尽
   - 记录预算使用情况

5. 优化建议
   - 分析预算耗尽原因
   - 提供优化建议（增加预算、优化算法等）
```

### 6.3 证据严重不足场景

**场景**：证据数量严重不足（evidence_count < 2），且无法通过工具补充

**处理策略**：

```
1. 检测证据严重不足
   - 检查 evidence_count < 2
   - 检查是否已尝试所有相关工具
   - 检查工具是否连续失败

2. 证据严重不足处理
   - 如果证据严重不足且无法补充：触发拒答策略
   - 记录证据不足原因
   - 保存当前CDP状态

3. 用户通知
   - 通知用户证据不足，无法完成诊断
   - 建议用户提供更多信息或咨询专业医生

4. 记录到AuditTrail
   - 记录证据严重不足
   - 记录证据不足原因

5. 优化建议
   - 分析证据不足原因
   - 提供优化建议（改进问诊策略、扩展知识库等）
```

### 6.4 诊断候选集为空场景

**场景**：tool_3（鉴别诊断工具）返回的候选集为空

**处理策略**：

```
1. 检测诊断候选集为空
   - 检查 cdp.ddx.rank_list 是否为空
   - 检查是否已尝试扩展检索

2. 诊断候选集为空处理
   - 如果候选集为空：触发扩展检索
   - 如果扩展检索仍为空：触发升级或拒答

3. 扩展检索策略
   - 调用 tool_3（鉴别诊断工具）- 扩展检索模式
   - 放宽检索条件（增加症状范围、减少路径长度限制等）

4. 如果扩展检索仍为空
   - 触发升级策略：建议用户咨询专业医生
   - 记录诊断候选集为空原因

5. 记录到AuditTrail
   - 记录诊断候选集为空
   - 记录扩展检索结果
```

### 6.5 系统资源耗尽场景

**场景**：系统资源耗尽（内存、CPU、磁盘等）

**处理策略**：

```
1. 检测系统资源耗尽
   - 检查内存使用率
   - 检查CPU使用率
   - 检查磁盘使用率

2. 系统资源耗尽处理
   - 触发资源清理：清理缓存、释放连接、终止非关键任务
   - 如果资源仍不足：触发升级或拒答

3. 数据保护
   - 保存当前CDP状态到数据库
   - 保存AgentState状态
   - 保存AuditTrail记录

4. 用户通知
   - 通知用户系统资源不足，建议稍后重试

5. 记录到AuditTrail
   - 记录系统资源耗尽
   - 记录资源使用情况

6. 通知运维
   - 通知运维团队系统资源耗尽
   - 记录资源使用情况
```

## 七、降级策略系统级设计

### 7.1 降级策略层级

**降级策略层级**：
- **工具层降级**：工具执行失败时的降级策略（见工具清单文档）
- **服务层降级**：服务调用失败时的降级策略
- **系统层降级**：系统故障时的降级策略
- **业务层降级**：业务逻辑失败时的降级策略

### 7.2 降级策略选择规则

**降级策略选择算法**：

```
function select_degradation_strategy(error: Error, context: Context) -> DegradationStrategy:
    # 1. 根据错误类型选择降级策略
    if error.type == "tool_failure":
        return select_tool_degradation_strategy(error, context)
    elif error.type == "service_failure":
        return select_service_degradation_strategy(error, context)
    elif error.type == "system_failure":
        return select_system_degradation_strategy(error, context)
    elif error.type == "business_failure":
        return select_business_degradation_strategy(error, context)
    
    # 2. 默认降级策略
    return default_degradation_strategy()
```

### 7.3 降级策略执行

**降级策略执行流程**：

```
1. 选择降级策略
   - 根据错误类型和上下文选择降级策略

2. 执行降级策略
   - 执行降级逻辑
   - 生成降级结果

3. 验证降级结果
   - 验证降级结果是否合理
   - 如果降级结果不合理，使用更激进的降级策略

4. 更新系统状态
   - 更新CDP状态（如果降级成功）
   - 更新AgentState状态
   - 标记降级策略使用情况

5. 记录到AuditTrail
   - 记录降级策略使用
   - 记录降级结果

6. 决定下一步
   - 如果降级成功：继续执行
   - 如果降级失败：触发升级或拒答
```

## 八、故障恢复机制

### 8.1 故障检测

**故障检测机制**：
- **健康检查**：定期检查服务健康状态
- **心跳检测**：定期检查服务心跳
- **错误监控**：监控错误率和错误类型
- **性能监控**：监控响应时间和资源使用率

### 8.2 故障恢复策略

**故障恢复策略**：

```
1. 自动恢复
   - 服务自动重启
   - 连接自动重连
   - 缓存自动清理

2. 手动恢复
   - 运维人员手动重启服务
   - 运维人员手动修复数据
   - 运维人员手动清理缓存

3. 数据恢复
   - 从数据库恢复CDP
   - 从数据库恢复AgentState
   - 从AuditTrail恢复历史记录

4. 状态同步
   - 同步CDP状态
   - 同步AgentState状态
   - 同步服务状态
```

### 8.3 故障恢复流程

**故障恢复流程**：

```
故障检测
  ↓
故障分类
  ↓
  ├─→ 自动恢复
  │     ↓
  │   执行自动恢复策略
  │     ↓
  │   验证恢复结果
  │     ↓
  │   如果恢复成功 → 继续执行
  │   如果恢复失败 → 手动恢复
  │
  └─→ 手动恢复
        ↓
      通知运维团队
        ↓
      执行手动恢复策略
        ↓
      验证恢复结果
        ↓
      如果恢复成功 → 继续执行
      如果恢复失败 → 系统维护
```

## 十、用户友好的错误提示

### 10.1 错误提示原则

**错误提示原则**：
- **用户友好**：错误提示对用户友好，不暴露技术细节
- **明确指导**：错误提示明确指导用户下一步操作
- **安全第一**：错误提示遵循"安全第一"原则，建议用户咨询专业医生

### 10.2 错误提示分类

**错误提示类型**：

| 错误类型 | 用户提示 | 建议操作 |
|---------|---------|---------|
| 工具执行失败 | "系统暂时无法处理，请稍后重试" | 稍后重试或咨询专业医生 |
| 服务不可用 | "系统暂时不可用，请稍后重试" | 稍后重试或咨询专业医生 |
| 系统故障 | "系统出现故障，请稍后重试" | 稍后重试或咨询专业医生 |
| 证据不足 | "当前信息不足以完成诊断，建议提供更多信息或咨询专业医生" | 提供更多信息或咨询专业医生 |
| 诊断候选集为空 | "当前情况超出系统诊断范围，建议咨询专业医生" | 咨询专业医生 |
| 预算耗尽 | "诊断过程耗时较长，建议咨询专业医生" | 咨询专业医生 |

### 10.3 错误提示生成

**错误提示生成算法**：

```
function generate_user_friendly_error_message(error: Error, context: Context) -> String:
    # 1. 根据错误类型生成基础提示
    base_message = get_base_error_message(error.type)
    
    # 2. 根据错误严重程度调整提示
    if error.severity == "high":
        message = base_message + "，建议立即咨询专业医生"
    elif error.severity == "medium":
        message = base_message + "，建议咨询专业医生"
    else:
        message = base_message + "，请稍后重试"
    
    # 3. 根据上下文添加具体建议
    if context.has_partial_result:
        message += "。当前诊断结果：" + context.partial_result
    
    return message
```
