## 二、推荐的开发流程

### 2.1 标准开发流程（6步法）

```
步骤1: 理解业务逻辑
    ↓
   必读文档：
   - 《AI医生系统-系统功能设计.md》- 理解系统整体功能
   - 《AI医生系统-业务逻辑详细设计.md》- 理解该服务对应的工具业务逻辑（核心）
   - 《AI医生系统-用户交互流程.md》- 理解用户交互流程（如需要）
   
   需要理解的内容：
   - 服务对应的工具及其职责
   - 输入数据格式和来源
   - 输出数据格式和目标
   - 业务处理流程
   - 业务规则和约束
    ↓
步骤2: 理解系统架构
    ↓
   必读文档：
   - 《AI医生系统-技术架构设计.md》- 技术架构总览
   - 《AI医生系统-技术架构设计-核心架构.md》- 理解双通道推理架构
   - 《AI医生系统-技术架构设计-智能体详细设计.md》- 理解对应工具的智能体设计
   - 《AI医生系统-技术架构设计-CDP数据与状态管理.md》- 理解CDP数据流转
   
   选读文档（根据服务需要）：
   - 《AI医生系统-技术架构设计-核心技术组件.md》- 理解技术组件
   - 《AI医生系统-技术架构设计-性能与评估.md》- 理解性能要求
   
   需要理解的内容：
   - 双通道推理架构（通道1：结构化推理，通道2：语言与策略）
   - 服务在架构中的位置
   - 服务间依赖关系
   - 数据流向（CDP流转）
   - 技术栈选择
    ↓
步骤3: 理解项目结构
    ↓
   必读文档：
   - 《AI医生系统-项目结构设计.md》- 了解目录结构、代码组织方式
   
   需要理解的内容：
   - 服务目录结构
   - 代码组织规范
   - 命名规范
   - 包/模块划分
    ↓
步骤4: 编写服务实现方案（新增，关键步骤）
    ↓
   参考文档：
   - 《AI医生系统-业务逻辑详细设计.md》- 业务逻辑（核心参考）
   - 《AI医生系统-技术架构设计.md》及相关子文档- 技术架构
   - 《AI医生系统-项目结构设计.md》- 项目结构
   - 《AI医生系统-数据模型设计.md》- 数据模型设计
   - 《AI医生系统-API接口规范.md》- API设计规范
   - 《AI医生系统-错误处理规范.md》- 错误处理规范
   - 《AI医生系统-最终输出格式规范.md》- 输出格式规范
   - 《AI医生系统-入口设计规范.md》- 入口相关服务参考
   - 《AI医生系统-技术架构设计-性能与评估.md》- 性能要求
   
   编写内容：
   - 服务概述（基于业务逻辑设计）
   - 技术实现设计（基于技术架构设计）
   - 接口设计（遵循API接口规范）
   - 数据流设计（基于数据模型设计）
   - 依赖关系（基于技术架构设计）
   - 实现步骤（分阶段实现计划）
   - 测试策略
    ↓
步骤5: 实现服务
    ↓
   参考文档：
   - 《AI医生系统-项目结构设计.md》- 代码组织规范
   - 《AI医生系统-API接口规范.md》- API设计规范
   - 《AI医生系统-错误处理规范.md》- 错误处理规范
   - 《AI医生系统-数据模型设计.md》- 数据模型设计
   - 《AI医生系统-技术架构设计-项目实现与部署.md》- 实现与部署要求
   
   实现过程：
   1. 创建服务目录结构（遵循项目结构设计）
   2. 实现核心业务逻辑（基于实现方案）
   3. 实现API接口（遵循API接口规范）
   4. 实现错误处理（遵循错误处理规范）
   5. 编写单元测试
    ↓
步骤6: 测试与验证
    ↓
   验证依据：
   - 《AI医生系统-业务逻辑详细设计.md》- 验证业务逻辑实现
   - 服务实现方案文档- 验证技术实现
   - 《AI医生系统-API接口规范.md》- 验证API接口
   - 《AI医生系统-最终输出格式规范.md》- 验证输出格式
   
   测试内容：
   - 单元测试（覆盖核心业务逻辑）
   - 集成测试（验证服务间调用）
   - 与业务逻辑设计文档对照验证
   - 与实现方案对照验证
```

## 四、为什么需要服务实现方案文档？

### 4.1 避免直接编码的问题

**问题1：理解不充分**
- 直接编码可能导致对业务逻辑理解不深
- 容易遗漏关键业务规则

**问题2：技术选型不当**
- 没有充分思考就选择技术方案
- 后期发现性能或扩展性问题

**问题3：返工风险高**
- 实现后发现不符合架构设计
- 需要大量重构

**问题4：团队协作困难**
- 不同开发者理解不一致
- 代码审查缺乏参考标准

### 4.2 服务实现方案的价值

**价值1：深度思考**
- 编写方案的过程就是深度思考的过程
- 提前发现潜在问题

**价值2：技术验证**
- 在编码前验证技术方案可行性
- 提前识别技术风险

**价值3：开发指南**
- 方案文档作为开发指南
- 减少开发过程中的决策时间

**价值4：知识沉淀**
- 方案文档记录设计思路
- 便于后续维护和扩展

```markdown
## 一、服务概述
```

- **在架构中的位置**：通道1（结构化推理通道）的核心组件
- **服务职责**：实现DR.KNOWS路径检索与评分，生成鉴别诊断候选集

### 1.2 输入输出
- **输入**：
  - 症状列表（CUI编码）
  - 体征信息
  - 患者基本信息
- **输出**：
  - 推理路径列表
  - 疾病候选集（三层分层：首要假设/主要备选/必须排除）
  - 置信度评分

### 1.3 业务价值
- 实现基于知识图谱的医学推理
- 提供可解释的诊断结果
- 支持多引擎融合诊断

## 二、技术实现设计

### 2.1 技术栈选择
- **编程语言**：Python 3.10+
- **框架**：FastAPI
- **核心依赖**：
  - `neo4j==5.14.0`：Neo4j图数据库客户端
  - `numpy==1.24.3`：数值计算
  - `scikit-learn==1.3.2`：机器学习（可选）

### 2.2 核心算法/方法

#### 2.2.1 多跳路径检索（DR.KNOWS方法）
- **算法描述**：在Neo4j知识图谱中检索症状到疾病的推理路径
- **实现思路**：
  1. 构建症状节点查询
  2. 使用Cypher查询多跳路径
  3. 路径过滤和排序
- **算法复杂度**：O(n²)，n为路径长度

#### 2.2.2 三层评分体系
- **先验概率评分**：基于疾病先验概率
- **似然评分**：基于症状-疾病关联强度
- **后验概率评分**：贝叶斯推理计算

#### 2.2.3 路径注入LLM
- **策略**：将推理路径作为上下文注入LLM
- **提示词设计**：结构化路径 + 自然语言描述

### 2.3 性能要求
- **响应时间**：< 5秒（单次路径检索）
- **并发处理**：支持10+并发请求
- **资源消耗**：内存 < 2GB

### 4.2 命名规范

#### Java命名规范

- **类名**：大驼峰（PascalCase），如 `DiagnosisService`
- **方法名**：小驼峰（camelCase），如 `startDiagnosis`
- **常量**：全大写下划线，如 `MAX_QUESTIONING_COUNT`
- **包名**：全小写，如 `com.aidoctor.diagnosis`

#### Python命名规范

- **类名**：大驼峰（PascalCase），如 `DiagnosisService`
- **函数名/变量名**：小写下划线（snake_case），如 `start_diagnosis`
- **常量**：全大写下划线，如 `MAX_QUESTIONING_COUNT`
- **模块名**：小写下划线，如 `diagnosis_service.py`

### 4.3 API设计规范

#### RESTful API设计

1. **URL设计**：
   ```
   GET    /api/v1/diagnosis/{id}           # 获取诊断记录
   POST   /api/v1/diagnosis                # 创建诊断
   PUT    /api/v1/diagnosis/{id}           # 更新诊断
   DELETE /api/v1/diagnosis/{id}           # 删除诊断
   ```

2. **统一响应格式**：
   ```json
   {
     "code": 200,
     "message": "success",
     "data": {},
     "timestamp": 1705123456789
   }
   ```

3. **错误响应格式**（参考《错误处理规范.md》）：
   ```json
   {
     "code": 400,
     "message": "请求参数验证失败",
     "data": null,
     "errors": [...],
     "traceId": "3f1a9b1d2c5a4b0e",
     "timestamp": 1705123456789
   }
   ```

### 4.4 错误处理规范

#### 错误码分配（参考《错误处理规范.md》）

| 范围 | 归属 | 说明 |
|------|------|------|
| 1000-1099 | health-state-assessment-service | 入口判定/健康状态判定 |
| 1100-1199 | clinical-parsing-service | 概念识别/归一化 |
| 1200-1299 | dialog-service | 信息缺口/追问生成 |
| 1300-1399 | workup-planner-service | 检查价值评估 |
| 1400-1499 | treatment-engine-service | 治疗方案推理 |
| 1500-1599 | risk-assessment-service | 风险评估 |
| 1600-1699 | explanation-service | 证据链/可解释性 |
| 1700-1799 | CDP管理（跨服务） | CDP创建/更新/版本 |
| 2000-2099 | diagnosis-service | 流程编排 |
| 3000-3999 | diagnosis-engine-service | DR.KNOWS核心 |

#### 异常处理原则

1. **统一异常处理**：使用全局异常处理器
2. **错误日志记录**：所有错误都要记录日志
3. **用户友好提示**：错误信息对用户友好，不暴露系统内部信息
4. **可追溯性**：错误必须包含traceId、cdpId等追踪信息

### 4.5 数据库设计规范

#### 表命名规范

- **表名**：小写下划线，如 `cdp`、`diagnosis_record`
- **字段名**：小写下划线，如 `patient_id`、`created_at`
- **索引命名**：`idx_表名_字段名`，如 `idx_cdp_patient_id`

#### CDP设计规范

- **版本控制**：使用乐观锁（version字段）
- **写时复制**：每次更新创建新版本
- **JSON字段**：使用JSONB类型（PostgreSQL）或JSON类型（MySQL 8.0+）

### 4.6 日志规范

#### 日志级别

- **ERROR**：系统错误，需要立即处理
- **WARN**：警告信息，可能的问题
- **INFO**：重要业务流程信息
- **DEBUG**：调试信息，开发环境使用

#### 日志格式

```
[时间] [级别] [服务名] [线程] [类名] [方法名] - [消息] [上下文信息]
```

示例：
```
2025-01-22 10:30:45.123 [INFO] [diagnosis-service] [http-nio-8084-exec-1] [DiagnosisService] [startDiagnosis] - 开始诊断流程 cdpId=cdp_123456, patientId=patient_001
```

#### 提交消息格式


## 八、常见问题与解决方案

### 8.1 开发环境问题

#### 问题1：数据库连接失败

**解决方案**：
1. 检查数据库服务是否启动
2. 检查配置文件中的数据库连接信息
3. 检查数据库用户权限

#### 问题2：服务启动失败

**解决方案**：
1. 检查端口是否被占用
2. 检查依赖服务是否启动
3. 查看日志文件定位问题

### 8.2 代码开发问题

#### 问题1：服务间调用超时

**解决方案**：
1. 检查网络连接
2. 增加超时时间配置
3. 检查下游服务是否正常

#### 问题2：CDP版本冲突

**解决方案**：
1. 使用乐观锁机制
2. 实现重试机制
3. 检查并发更新逻辑

### 8.3 测试问题

#### 问题1：测试数据污染

**解决方案**：
1. 使用独立的测试数据库
2. 每个测试用例执行后清理数据
3. 使用事务回滚
