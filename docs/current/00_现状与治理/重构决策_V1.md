# 1. 重构总原则

基于当前基线，AIdoctor 不适合采用：

```text
重新设计全部架构
↓
全部重写
↓
一次性切换
```

推荐：

```text
现有能力
↓
固定 Contract
↓
增加 Eval
↓
统一 State ownership
↓
接入 StateCommitter
↓
接入 Model / Python Runtime
↓
增加 explicit lifecycle
↓
逐业务单元替换旧主链
```

即：

> Strangler-style Incremental Refactoring。

---

# 2. 第一优先级不是 Agent 智能化

当前最大问题不是：

```text
Agent 不够自主
```

而是：

```text
同一系统中
业务能力
状态
运行时
异常语义
模型调用
Prompt
测试
安全边界
没有统一。
```

因此当前优先级应是：

```text
Correctness
↓
State
↓
Safety
↓
Recoverability
↓
Observability
↓
Eval
↓
Agent intelligence
```

---

# 3. 建议的核心目标架构

最终不建议采用纯 Agent-first。

推荐：

```text
Clinical Workflow Runtime
        │
        ├── Deterministic lifecycle
        │
        ├── Safety gates
        │
        ├── State transition
        │
        ├── Checkpoint / Resume
        │
        └── HITL
              │
              ▼
       Constrained Agent
              │
       决定有限范围内的
       next best action
              │
              ▼
        Capability Runtime
              │
        Tool / Model / KG
              │
              ▼
          StatePatch
              │
              ▼
        StateCommitter
              │
              ▼
             CDP
```

即：

> Workflow 决定允许发生什么，Agent 在允许空间内决定下一步做什么。

---

# 4. 建议的第一阶段重构顺序

不按微服务顺序重构。

按业务状态转换顺序重构。

推荐第一个完整核心闭环：

```text
用户首次输入
↓
安全入口
↓
临床信息解析
↓
判断是否需要继续询问
↓
WAITING_FOR_USER
↓
用户回复
↓
恢复
↓
重新判断
```

这是整个系统最适合成为第一个 Runtime 化闭环的部分。

原因：

1. 风险可控；
2. 当前真实能力已经存在；
3. 能覆盖 CDP；
4. 能覆盖 StateCommitter；
5. 能覆盖 Capability；
6. 能覆盖 WAITING；
7. 能覆盖 Resume；
8. 能验证事件幂等；
9. 不需要一开始就碰最终诊断和治疗；
10. 完成后后续 DDx / Workup / Treatment 都可沿用同一机制。

# 5. 建议的第一业务闭环拆分

## U1 — Session / CDP 创建

```text
S_in:
NO_SESSION

Event:
START_DIAGNOSIS

Action:
create CDP

S_out:
INTAKE_PENDING
```

---

## U2 — Safety Entry

```text
S_in:
INTAKE_PENDING

Capability:
Health State Assessment

Possible transition:

WELLNESS
CLINICAL_INTAKE
URGENT_ESCALATION
SAFETY_BLOCKED
CAPABILITY_FAILURE
```

关键：

```text
Health State capability failure
≠
automatic clinical continuation
```

---

## U3 — Clinical Parsing

```text
S_in:
CLINICAL_INTAKE

Capability:
Clinical Parsing

Output:
structured clinical facts
ambiguity
quality
evidence
suggested patch
```

Capability 不直接修改 CDP。

---

## U4 — State Commit

```text
Capability Result
↓
StatePatch
↓
StateCommitter
↓
CDP Version +1
```

这是 StateCommitter 第一次正式接管当前临床主链。

---

## U5 — Information Sufficiency

判断：

```text
Enough information?
```

不是只返回：

```text
completeness = 61
```

而应产生：

```text
ENOUGH_FOR_DDX
NEED_MORE_INFORMATION
SAFETY_UNCERTAIN
CAPABILITY_UNCERTAIN
```

---

## U6 — Ask Question

如果：

```text
NEED_MORE_INFORMATION
```

调用 Dialog Capability。

返回：

```text
question
questionPurpose
requiredFields
expiresAt
```

然后：

```text
state = WAITING_FOR_USER
checkpoint
```

---

## U7 — Resume

用户回复后：

```text
Event
answer
pendingQuestionId
baseVersion
```

Runtime 校验：

```text
session 是否仍在等待
question 是否匹配
event 是否重复
是否过期
baseVersion 是否一致
```

通过：

```text
WAITING_FOR_USER
→ CLINICAL_INTAKE
```

重新进入 Parsing。


# 9. 迁移原则

每次迁移一个 Business Development Unit 必须满足：

```text
旧路径行为已盘清
↓
Contract 已定义
↓
Failure Policy 已定义
↓
State Transition 已定义
↓
Unit Test PASS
↓
Integration Test PASS
↓
Eval PASS（AI Capability）
↓
旧路径与新路径行为对照
↓
切流
↓
观察
↓
旧路径移除
```

禁止：

```text
先删除旧代码
再补新能力
```

# 10. 最终决策

基于 Current State Baseline V1：

## 不重写

当前系统拥有足够多真实业务能力，不支持推倒重来。

## 不继续修补旧 Workflow

旧 Workflow 可以暂时维持兼容，但不应继续成为新增架构能力的宿主。

## 新 Runtime 不直接“大爆炸接管”

应从第一个业务状态闭环开始渐进接管。

## StateCommitter 应成为状态写入唯一入口

但通过 Adapter 渐进迁移，不一次性改完所有服务。

## Model Runtime 应成为所有正式临床模型调用唯一入口

Legacy LLM 不应恢复。

## Prompt Registry 应成为正式 Prompt 唯一所有者

Service-local Clinical Prompt 逐步退出。

## CDP 应继续作为临床业务事实源

不重新创造另一套业务状态数据库。

## Agent 应被限制在 Workflow 允许的动作空间中

不采用自由 Agent 驱动整个医疗流程。

## Clinical Eval 是正式启用任何 AI Capability 的前置条件

不再把 Demo、固定 confidence 或 Smoke Test 当成能力验证。

# 12. 建议实施路径 — Clinical Intake Runtime Migration

目标：

> 把“首次输入 → 安全入口 → 临床解析 → 信息不足 → 提问 → WAITING_FOR_USER → 回复 → Resume”做成第一个真正状态驱动、可恢复、可验证的业务闭环。

在 R1 完成并独立验证前，不进入 DDx / Treatment 等后续高风险临床链路的大规模迁移。
