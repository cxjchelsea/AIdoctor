继续盘点后，主链“后半段”已经压实了不少。现在可以把 Current State Assessment 再推进一层，而且这一轮发现的问题比上一轮更接近“为什么当前系统看起来很多东西都有，但实际上还不能当成完整可靠系统”。

### 1. 当前五步诊断流程的“完成”语义是不可信的

`DiagnosisWorkflowOrchestrator` 的 Step 4、Step 5 已经完整追出来。

Step 4 是：

```text
Dialog：采集关键证据
→ Diagnosis Engine：分析证据
→ Workup Planner：生成检查/验证计划
→ 写入 CDP
```

其中“关键证据采集失败”会直接让 Step 4 失败，但后面的“证据分析失败”和“检查计划生成失败”都只是记录日志然后继续。

Step 5 更明显：

```text
Clinical Parsing：证据回填
→ Diagnosis Engine：最终排序
→ Treatment Engine：生成治疗方案
→ Risk Assessment：最终风险评估
→ Explanation Service：生成终点结论包
→ cdpStatus = completed
```

但是前面五个关键能力中的多个都允许失败后继续：

```text
证据回填失败        → continue
最终排序失败        → continue
治疗方案失败        → continue
最终风险评估失败    → continue
终点结论包失败      → continue
```

最后仍然无条件：

```java
updates.put("cdpStatus", "completed");
```

所以这里可以正式登记：

```text
CSA-STATE-003
completed 状态不等价于业务闭环完成
Severity: HIGH
Evidence: CONFIRMED
```

当前 `completed` 的真实语义更接近：

> 编排器运行到了 Step 5 末尾。

而不是：

> 必要证据、风险判断、治疗建议和结论包全部成功生成并通过验证。

这以后必须拆成类似：

```text
EXECUTION_FINISHED
BUSINESS_COMPLETE
CLINICALLY_RELEASABLE
```

至少不能混成一个 `completed`。

### 2. Workup Planner 是真实实现，但本质仍是“小型规则原型”

检查计划模块不是 Stub。

当前 `WorkupPlanner` 有：

```text
ValueAssessor
InformationGainCalculator
VerificationPlanner
检查项目库
综合评分
检查优先级
验证计划
```

它确实会：

```text
DDx
↓
寻找相关检查
↓
检查价值评分
↓
信息增益
↓
紧急程度
↓
综合评分
↓
high / medium / low
↓
verificationPlan
```

所以这个能力应该归类为：

```text
IMPLEMENTED
+
WIRED
```

不能说它只是设计。

但是它的检查库目前只有类似：

```text
心电图
心肌酶谱
胸部 CT
胸部 X 光
血常规
尿常规
```

并且源码明确写着：

> “初期使用简单列表，后期可扩展为从数据库或知识库加载”
> “示例检查项目库”

也就是说：

```text
工程实现：有
通用检查规划能力：没有被证明
医学覆盖度：很低/未验证
临床知识来源：未绑定
Eval：未发现
```

所以更准确：

```text
Workup Planner =
REAL ENGINEERING IMPLEMENTATION
+
PROTOTYPE CLINICAL CONTENT
```

我建议后续判定为：

```text
KEEP 算法/接口思想
REPLACE 临床知识内容
REFACTOR Capability 接入
```

而不是整个模块删掉。

### 3. Workup 在 DDx 缺失时同样把“不知道”降成普通情况

如果：

```python
if not ddx:
```

它返回：

```text
workupItems = []
verificationPlan = {}
priority = normal
```

这和上一轮 Risk Engine 的问题是同一类：

```text
信息不足 / 上游失败
```

没有被表达成：

```text
CANNOT_ASSESS
INSUFFICIENT_EVIDENCE
BLOCKED
```

而被转换成：

```text
normal
```

因此可以合并为一个更大的系统性问题：

```text
CSA-SEMANTIC-001
Unknown / Failure / Insufficient Evidence
被多个服务错误投影成正常业务值
```

已确认至少包括：

```text
Diagnosis Engine failure → empty DDx
Risk Engine empty DDx → mild
Workup empty DDx → normal priority
```

这比单独修改某个 if 更重要。

# 6. 更危险的是：未知疾病也会生成“标准治疗”

如果没找到对应疾病规则：

```python
if not treatment_rule:
```

代码不是停止。

而是生成：

```text
name = "{disease}标准治疗"
description = "根据诊断结果制定个性化治疗方案"
priority = medium
```

这意味着：

```text
没有治疗知识
```

被转换成：

```text
存在一个“标准治疗”
```

虽然内容比较泛，但语义仍然是错误的。

正确状态应该更像：

```text
TREATMENT_KNOWLEDGE_UNAVAILABLE
→ 不生成治疗推荐
→ 仅允许转人工/就医建议/安全输出
```

而不是制造一个“标准治疗”。

所以：

```text
CSA-SAFETY-003
Missing treatment knowledge fabricates a treatment-plan shell
HIGH
CONFIRMED
```

# 9. Explanation Service 也存在和 Dialog 相同的“假写入”

Explanation Service 会：

```text
GET diagnosis-service /cdp/{id}
↓
构建 evidence chain
↓
构建 reasoning paths
↓
构建 conclusion package
↓
生成自然语言解释
↓
POST /diagnosis/cdp/{id}/update
```

问题还是那个接口：

```text
/api/v1/diagnosis/cdp/{id}/update
```

前面已经确认当前 DiagnosisController 没有这个端点。

而 Explanation Service 对失败的处理是：

```text
logger.warning(...)
# 不抛出异常，因为这不是关键路径
```

所以又可以增加一个实证：

```text
Dialog Service          → dead/invalid CDP write path
Explanation Service     → dead/invalid CDP write path
```

这说明不是单个开发遗漏。

而是旧架构里曾经存在一种设计：

```text
Python Tool
→ 自己回写 diagnosis-service CDP
```

但实际接口没有完整实现。

后来 Java Orchestrator 又自己：

```text
调用 Tool
→ parse response
→ CDPManager.updateCDP()
```

于是产生了两套写入思想。

这是一个非常重要的历史演化痕迹。

# 10. 这进一步解释了为什么 State Committer 很重要

现在可以看得更清楚：

旧代码其实同时出现过：

```text
模式 A
Java Orchestrator
→ Tool
→ Java 解析
→ CDPManager.updateCDP

模式 B
Python Tool
→ diagnosis-service /cdp/update
→ 自己修改 CDP

模式 C
AgentLoop
→ CDPFieldWriter

模式 D
New StatePatch
→ StateCommitter
```

目前：

```text
A = 当前真实主链
B = 部分代码存在但接口不通
C = Agent 历史实现
D = 新工程基础，尚未接管临床主链
```

所以你之前的新架构要求：

> 所有状态 mutation 必须经过唯一 State Committer

并不是“为了架构漂亮”。

而是在解决一个仓库里已经真实发生的**多写入模型冲突**。

# 24. 现在对旧系统的评价又可以更精确一点

我现在不会把旧系统描述为：

> “一个已经完整实现的医疗问诊系统，只是工程架构需要升级。”

更准确应该是：

> **一个已经搭出了相当完整业务骨架、拥有真实多服务实现和状态聚合，但临床内容、Schema 契约、失败语义、状态治理和端到端验证仍处于明显工程原型阶段的系统。**

这点很重要。

因为它决定重构方式不是：

```text
旧系统全部不要
```

也不是：

```text
旧业务已经正确，只换 Runtime
```

而应该是：

```text
业务骨架和已有能力资产保留
↓
逐能力验证“内容是否可信”
↓
逐接口验证“是否真接入”
↓
逐状态验证“失败语义是否正确”
↓
然后接入新 Runtime / State / Contract / Eval
```
