# AIdoctor 工程治理规则

> 状态：CURRENT GOVERNANCE
> 目的：从历史 refactoring plans/reviews 中抽取仍应继续执行的通用工程治理原则，避免依赖旧 Phase 计划才能理解当前约束。

## 1. 基本原则

- 当前设计与实现必须以 `main` 当前代码、测试、CI 和运行证据为事实基础；
- 历史文档、旧计划和旧审查记录不得自动升级为当前实现事实；
- 高风险临床、PHI、安全与核心 Runtime/状态变更需要更严格的授权和审查；
- 不允许因为某个基础设施模块已通过测试，就推导临床主链已通过；
- 工程完成、临床有效、生产可启用必须分别判断。

## 2. 变更流程

对结构性 Runtime、状态、契约、安全边界或临床主链变更，默认流程为：

```text
明确 Scope / Authorization
→ 实现
→ 测试与证据
→ 独立审查
→ 修复审查问题
→ 显式 Merge Authorization
→ Standard Merge Commit
→ Post-Merge Verification
```

## 3. Git / Merge 规则

- 不自动 merge；
- 不 squash；
- 不 rebase；
- 合并只允许 standard merge commit；
- 未获得显式 Merge Authorization 时，PR 保持未合并状态；
- post-merge verification 之前，不把候选状态描述为 durable complete。

## 4. 文档与证据规则

- `docs/current/`：当前设计权威；
- `docs/refactoring/evidence/`：历史工程证据，原样保留；
- `docs/refactoring/reviews/`：历史独立审查证据，原样保留；
- `docs/refactoring/plans/`：历史实施与授权计划，不再决定新 SOP 开发顺序；
- `docs/refactoring/extensions/`：未来扩展设计，不反向扩大 V1；
- `docs/AI医生/项目文档/`：Legacy Design Reference。

## 5. 完成语义

任何阶段至少要区分：

- CODE EXISTS；
- IMPLEMENTED；
- WIRED；
- VERIFIED；
- BUSINESS LOOP CLOSED；
- CLINICALLY EVALUATED；
- PRODUCTION AUTHORIZED。

不得用其中一个替代另一个。

## 6. Clinical Safety

- Safety / Risk 失败不能投射成 safe / low-risk；
- 临床能力失败不能通过空对象静默进入后续正常业务值；
- 未经正式医学评估的高风险输出不得默认进入患者正式交付；
- 任何模型、Agent、工具不得绕过状态、权限和安全治理。

## 7. 当前重构方法

新重构按照状态驱动 SOP：

```text
Current State Assessment
→ 需求与边界
→ 功能模块
→ 系统级状态主干
→ 模块级状态
→ 业务闭环
→ 开发单元
→ 能力按需建设
→ 集成验证
→ 发布与回滚
```

历史 Phase A/B/... 路线继续保留为工程历史，不再直接作为当前施工顺序。
