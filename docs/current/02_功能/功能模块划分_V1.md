# AIdoctor V1 功能模块划分

> 状态：FROZEN / V1
> 所属阶段：SOP Phase 2 — 功能模块划分
> 上游：`01_需求/需求与系统边界_V1.md`

本文件按用户/业务职责定义 V1 功能域，不按微服务、LLM、RAG、Agent、数据库或现有目录划分。

## 1. 总体功能版图

### 核心业务功能域

- F1 问诊建立与对象确认
- F2 临床信息理解与病例采集
- F3 主动问诊与信息充分性管理
- F4 医疗风险识别与安全分流
- F5 疾病方向、鉴别与必须排除项管理
- F6 证据缺口与进一步检查建议
- F7 问诊结果整合与用户解释
- F8 问诊连续性、更正与恢复

### 横向系统保障能力

- G1 临床范围、医学知识与规则治理
- G2 临床状态治理
- G3 AI 能力与模型治理
- G4 安全与权限治理
- G5 Trace / Audit / Eval / Observability
- G6 临床证据与来源治理

横向 G 类不是患者直接操作的业务模块，不应与 F1-F8 混为微服务拆分依据。

## 2. F1 问诊建立与对象确认

目标：建立一次明确的问诊，知道“正在问谁、处理哪个健康问题”。

职责：
- 创建问诊上下文；
- 确认本人/代他人问诊；
- 接收首次自然语言输入；
- 识别模糊或混合诉求；
- 通过最小必要澄清确定当前主要健康问题；
- 临床症状存在时不得被体检/健康管理等非临床诉求掩盖。

不负责：症状医学解析、疾病判断、最终风险结论。

当前资产：DiagnosisController、DiagnosisOrchestrationService.start、CDP 创建、Frontend session。

初始处置：`REFACTOR`，入口概念和 CDP 创建资产可保留。

## 3. F2 临床信息理解与病例采集

目标：把用户自然语言转成可用于后续判断的临床事实。

职责：
- 主诉、症状、体征、时间、部位、性质、程度、频率、诱因/缓解因素；
- 伴随信息、既往史、用药、过敏、检查结果、相关背景；
- 否定、未知、未测量、不确定信息；
- 医学概念归一化与模糊信息识别；
- 记录事实来源类型和数据质量。

约束：`UNKNOWN != NO`，模型推断不得直接写成患者事实。

当前资产：Clinical Parsing、Concept Recognition、Normalization、patientState。

处置：核心 `KEEP + REFACTOR`；schema、来源、signs、Eval 需补齐。

## 4. F3 主动问诊与信息充分性管理

目标：判断还需要知道什么，并提出下一项最有价值的问题。

职责：
- 识别信息缺口；
- 为缺口标记其决策影响，而非只记录“缺失”；
- 判断是否继续询问、已经足够、需要线下信息或当前无法继续；
- 选择下一关键问题；
- 防止重复询问；
- 处理“不知道/没测过”；
- 控制问诊深度。

不负责：最终疾病判断和高风险安全最终决策。

当前资产：Dialog、Gap Identification、Completeness、Adaptive Questioning。

处置：`REFACTOR`；单一 completeness 阈值和 Dialog 自有业务真值不保留。

## 5. F4 医疗风险识别与安全分流

目标：持续判断是否存在需要优先处理的危险，并决定普通在线问诊能否继续。

职责：
- 红旗、急症、高危识别；
- 新临床事实到达后的重新评估；
- 风险升级；
- 就医/急诊引导；
- 高风险情况下限制、暂停或结束普通问诊。

约束：

```text
NO_DDX != LOW_RISK
SAFETY_FAILURE != SAFE
UNKNOWN != NORMAL
```

当前资产：Health State Assessment、Risk Assessment、Triage、红旗规则。

处置：`REFACTOR`；Fail-open 和原型硬编码需替代，Clinical Eval 缺失。

## 6. F5 疾病方向、鉴别与必须排除项管理

目标：在证据允许时形成可解释的疾病方向，并持续维护“最可能方向”和“必须排除方向”。

职责：
- 形成和更新候选疾病方向；
- 候选分层、排序、增删；
- 支持证据、反对证据和未知证据关联；
- 维护 Must-Exclude 集合；
- 对 Must-Exclude 维护“已排除 / 未排除 / 需线下排除”等业务语义；
- 新证据到达后重新排序或使旧推断失效；
- 无可靠候选、范围外时安全退出。

不负责：确诊、治疗、处方。

当前资产：Diagnosis Engine、Rule/KG/Statistical/Differential/Fusion、Evidence Analyzer、DR.KNOWS。

处置：业务资产 `KEEP + REFACTOR`；Fusion policy、Legacy LLM、failure semantics、Clinical Eval 需重构。

## 7. F6 证据缺口与进一步检查建议

目标：在线已无法获得关键证据时，告诉用户还缺什么，以及进一步完善什么信息可能有助于判断。

职责：
- 识别影响鉴别的关键证据缺口；
- 区分可在线追问与只能线下获取的证据；
- 给出有正式规则/知识支持的检查方向或具体检查项目；
- 解释为何需要这些证据；
- 区分一般完善和必须尽快线下排除。

边界：不是检查医嘱、检查下单或跨天检查回流系统。

当前资产：Workup Planner、Examination planning、Evidence Gap。

处置：Workup `KEEP + REFACTOR`；重复 Examination planning 需合并/移除；跨天回流后置。

## 8. F7 问诊结果整合与用户解释

目标：把多模块内部结果整理为一个患者可理解、可行动、可追溯且不越界的输出。

职责：
- 当前问题理解；
- 关键已知事实、未知/缺失信息；
- 疾病方向；
- Must-Exclude 当前状态；
- 支持/反对依据；
- 风险提示；
- 进一步信息/检查建议；
- 就医建议；
- 适用范围、不确定性和局限。

要求：确定性安全依据、患者事实证据和医学文献 Citation 在语义上区分。

不负责：创造新临床事实、治疗方案、自动处方。

当前资产：Explanation Service、ConclusionPackageBuilder、Frontend renderer。

处置：deterministic builders `KEEP + REFACTOR`；Legacy LLM 与前端临床 fallback `REPLACE/REMOVE`。

## 9. F8 问诊连续性、更正与恢复

目标：保证多轮问诊在等待、刷新、中断、重复提交和用户更正情况下仍保持业务正确。

职责：
- 等待用户回答；
- 页面刷新/网络中断后的普通恢复；
- 重复事件防重；
- 过期回答识别；
- 用户更正/补充；
- 上游事实改变后使依赖的风险、DDx、证据和建议失效并重新计算。

V1 不要求跨天等待外部检查或医生审核。

当前资产：CDP version、Frontend state、Dialog Redis/memory、AgentState、Python Runtime checkpoint。

处置：CDP aggregate `KEEP`；整体恢复/状态所有权 `REFACTOR`；durable clinical resume 仍是缺口。

## 10. G1 临床范围、医学知识与规则治理

职责：
- 显式定义系统支持的临床场景/范围；
- 医学知识、规则、阈值、术语、适用范围、版本、来源；
- Sandbox/Staging/Review/Publish Gate；
- Capability Package 的临床内容治理。

原则：模型可能知道某知识，不等于系统正式支持。

主要历史资产：知识演化设计、Capability Package、知识图谱、成人呼吸道场景资产。

## 11. G2 临床状态治理

职责：
- Clinical Business State Source of Truth；
- 合法状态变化；
- 受控写入；
- version、idempotency、invalidate、resume；
- Capability 结果到 StatePatch 再到 Commit 的治理。

主要资产：CDP、StateCommitter、部分 AgentState/Checkpoint 思想。

## 12. G3 AI 能力与模型治理

职责：
- Model Runtime；
- Prompt Registry；
- 模型路由、结构化输出、Fallback；
- Model/Prompt/Config Version；
- AI Capability Eval 绑定。

原则：Legacy clinical LLM 不能恢复为正式路径。

## 13. G4 安全与权限治理

职责：
- Capability Authorization；
- Consent / Permission；
- 最小授权 Context；
- 高风险动作限制；
- Fail Closed；
- PHI 最小必要读取。

区别：F4 判断患者医学风险；G4 判断系统自身“允许做什么”。

## 14. G5 Trace / Audit / Eval / Observability

职责：
- 运行追踪；
- 状态变更审计；
- Agent/Runtime/Capability 事件；
- Static / Interactive / Trajectory Eval；
- 回归、异常定位、版本记录；
- PHI 最小化 Trace。

主要资产：Execution Trace、AuditTrail、AOP、旧评估验证体系、refactoring evidence/reviews。

## 15. G6 临床证据与来源治理

职责：
- 患者事实证据；
- 医学知识证据和 Claim-Level Citation；
- 支持 / 反对 / 未知关系；
- 证据作用对象；
- 来源、适用性、冲突、局限和版本；
- Evidence Ledger / Evidence Intelligence 的业务语义。

原则：Knowledge 回答“医学上依据是什么”；Evidence 回答“该依据如何支持/反对当前患者的某个判断”。二者不合并。

## 16. 明确不作为 V1 功能模块

- 完整 Wellness / 健康管理；
- Treatment / Medication；
- 正式医生 HITL；
- 检查执行/预约/下单；
- 跨天外部检查结果恢复诊断；
- Multi-Agent；
- 长期 Memory。

这些不能因为旧代码或旧文档存在就反向制造当前 V1 产品需求。

## 17. 完整性反查

- 开始问诊 → F1
- 临床事实理解 → F2
- 信息缺口/主动追问 → F3
- 红旗/高危 → F4
- 疾病鉴别与 Must-Exclude → F5
- 线下证据/检查建议 → F6
- 患者结果与解释 → F7
- 等待/恢复/更正/防重 → F8
- 范围、知识、规则 → G1
- 状态一致性 → G2
- 模型/Prompt/Eval → G3
- 权限/Fail Closed → G4
- 运行证据/评估 → G5
- 临床证据/Citation → G6

冻结需求目前均有归属，未发现必须新增第九个 V1 业务功能域的证据。

## 18. 阶段结论

`SOP Phase 2 = FROZEN / V1`。

下一阶段：`Phase 3 — 系统级状态主干`。进入 Phase 3 前，应按 Legacy Document Assimilation Matrix 读取 CDP、AgentState、Durable Execution、总体架构等状态相关历史资产；仍不得提前拆开发单元。
