> 文档状态：DRAFT FOR FREEZE  
> 所属阶段：复杂业务软件开发 SOP — Phase 6 可验证开发单元拆分  
> 上游权威：`01_需求/需求与系统边界_V1.md`、`02_功能/功能模块划分_V1.md`、`03_状态/系统级状态主干_V1.md`、`03_状态/模块级状态与状态所有权_V1.md`、`05_业务闭环/业务闭环设计_V1.md`

> 本文只把已冻结业务闭环拆成最小可独立验证的业务状态转换单元，并定义单元依赖、输入/事件/动作/输出/验证条件；不冻结 API、数据库表、类、微服务边界、具体 StatePatch Schema、模型、Prompt、RAG、KG 或 Runtime 实现。

---

## 1. Phase 6 目标

Phase 5 已冻结 12 个业务闭环。Phase 6 不再回答“完整用户场景怎么走”，而回答：

> 为了逐步实现这些闭环，哪些最小业务状态变化可以单独开发、单独验证，并在通过后安全组合成更大的闭环？

每个开发单元必须满足：

```text
明确输入状态
+
明确触发事件
+
明确业务动作/决策
+
明确输出状态
+
明确失败语义
+
明确验证条件
```

开发单元不是微服务、类、接口或 Capability 本身。

```text
一个开发单元
!=
一个微服务

一个开发单元
!=
一个旧 Tool

一个开发单元
!=
一个完整业务模块
```

---

## 2. 拆分原则

### UNIT-01 单元以状态变化为中心

优先按：

```text
S_in + Event -> Decision/Action -> S_out
```

拆分，而不是按代码目录拆分。

### UNIT-02 单元必须可独立验证

一个单元通过时，至少可以验证：

- 输入状态是否合法；
- 事件是否被正确接受或拒绝；
- 输出状态是否唯一、可解释；
- Failure 是否与合法业务结果分离；
- 是否违反 Safety / State Ownership / Product Boundary。

### UNIT-03 Capability 只作为依赖，不在 Phase 6 设计实现

例如：

```text
U03 风险评估单元
需要 Risk Capability
```

但 Phase 6 不决定：

- 使用规则、模型还是混合方式；
- Prompt 怎么写；
- Python/Java 怎么调用；
- 具体 Schema 如何定义。

这些属于后续 Capability / Contract / Runtime 阶段。

### UNIT-04 共享治理可以跨多个单元复用

G2 State Governance、G4 Safety Gate、Runtime Checkpoint 等可以被多个开发单元依赖，但不能因此把所有单元合成一个大单元。

### UNIT-05 不为了复用旧代码制造单元

当前旧 `DiagnosisController`、固定五步 Workflow、Dialog、Risk、Diagnosis Engine、Workup、Explanation 等只用于后续资产映射，不决定本次 U 的边界。

### UNIT-06 单元完成不等于完整业务闭环完成

例如：

```text
U06 成功生成问题并进入 WAITING_USER
```

只证明等待入口成立；还需要 U07 Resume 才能形成完整跨轮闭环。

---

## 3. Phase 6 单元总览

V1 第一版拆为 15 个可验证开发单元：

```text
U01 Consultation 建立与对象/问题框定
U02 临床事实形成与版本提交
U03 当前版本风险评估
U04 Safety Gate 决策
U05 Clinical Readiness 唯一求值
U06 关键问题选择与进入 WAITING_USER
U07 用户回答 Resume 与幂等恢复
U08 DDx / Must-Exclude 评估
U09 DDx 后 Gap 重评与循环路由
U10 线下证据需求与检查建议
U11 Safe Exit 结果组装与交付
U12 正常结果组装与 COMPLETED
U13 用户更正与依赖失效传播
U14 Capability / Runtime Failure 路由
U15 Consultation 取消与过期终止
```

这 15 个单元共同覆盖 Phase 5 的 12 个业务闭环。

# 4. U01 Consultation 建立与对象/问题框定

## 4.1 对应闭环

- BL-01 新问诊建立与入口澄清

## 4.2 S_in

```text
不存在可合法继续的同一健康问题 Consultation
```

或已有请求明确要求创建新 Consultation。

## 4.3 Event

```text
START_CONSULTATION
+ 首次用户健康诉求
+ 当前最低身份/授权上下文
```

这里是业务事件概念，不冻结事件 Schema。

## 4.4 Action / Decision

- 创建 Consultation；
- 建立 Subject Resolution；
- 判断 Problem Framing；
- 判断是否需要最小澄清；
- 判断是否明显 `OUTSIDE_V1_INTENT`；
- 已暴露风险线索时不得因 framing 未完成而跳过后续 Safety 路径。

## 4.5 S_out

合法输出至少包括：

```text
A. Consultation ACTIVE
   Subject = RESOLVED
   Problem = FRAMED

B. Consultation WAITING_USER
   Problem = CLARIFICATION_REQUIRED
   并进入 U06

C. OUT_OF_SCOPE input
   并进入 U11

D. 无法可靠建立主体/上下文
   → U14 或 U11
```

## 4.6 Failure 语义

```text
对象未确认
!=
随便猜测为本人
```

```text
OUTSIDE_V1_INTENT
!=
系统故障
```

## 4.7 验证标准

至少验证：

- 本人/代他人能够形成明确 Subject；
- 模糊/混合诉求触发最小澄清；
- 纯 V1 范围外诉求不会进入正常 DDx；
- 已出现危险线索时不会因为入口未完全 framing 而屏蔽 U03/U04；
- 同一首条输入不会被重复产生两次业务效果。

# 5. U02 临床事实形成与版本提交

## 5.1 对应闭环

- BL-02 临床事实采集与安全入口
- BL-03 Resume 后事实形成
- BL-11 用户更正后的事实更新

## 5.2 S_in

```text
Consultation = ACTIVE
或合法 Resume/Correction 正在应用
```

并存在待解释的新用户输入/补充/更正。

## 5.3 Event

```text
NEW_CLINICAL_INPUT
```

## 5.4 Action / Decision

F2：

- 提取 Clinical Observation；
- 归一化；
- 保留事实值语义；
- 区分来源；
- 判断 CONFIRMED / UNCERTAIN / CONTRADICTED / INVALIDATED。

G2：

- 验证正式状态变化；
- 合法时生成新的 Clinical State Version；
- 旧派生结果进入待失效/重算范围。

## 5.5 S_out

```text
A. 新 Clinical State Version
   + 当前有效 Clinical Facts
   → U03

B. 需要进一步澄清
   → U05/U06

C. 输入无法可靠形成事实且不能继续安全处理
   → U11/U14
```

## 5.6 强制语义

```text
UNKNOWN != NO
UNMEASURED != NORMAL
MODEL_INFERRED != PATIENT_REPORTED
```

Capability 结果不能直接绕过 G2 成为正式 Clinical State。

## 5.7 验证标准

- `YES/NO/UNKNOWN/UNMEASURED/NOT_ASKED/NOT_APPLICABLE` 不发生语义塌缩；
- 同一输入事件最多产生一次正式事实提交；
- 新事实生成新版本，而不是静默覆盖旧版本；
- 不确定/冲突事实不会被伪装成 CONFIRMED；
- 下游旧 Risk/DDx/Delivery 可以被标记为需要重评。

# 6. U03 当前版本风险评估

## 6.1 对应闭环

- BL-02
- BL-05
- BL-08
- BL-11

## 6.2 S_in

```text
存在当前有效 Clinical State Version
Risk Assessment = NOT_ASSESSED 或 STALE
```

## 6.3 Trigger

```text
CLINICAL_STATE_CHANGED
或
RISK_REEVALUATION_REQUIRED
```

## 6.4 Action / Decision

F4 针对当前版本形成：

```text
Risk Assessment = VALID / FAILED
```

若 VALID，再得到唯一：

```text
NO_HIGH_RISK_SIGNAL
CAUTION
HIGH_RISK
```

## 6.5 S_out

```text
A. VALID + Risk Disposition
→ U04

B. FAILED
→ U04 形成不得 ALLOW 的 Gate 输入
→ 同时进入 U14 Failure 处理
```

## 6.6 强制语义

```text
Risk FAILED
!= NO_HIGH_RISK_SIGNAL
```

```text
NO_HIGH_RISK_SIGNAL
!= 患者安全/无病
```

## 6.7 验证标准

- 新事实到达后旧 Risk 必须可进入 STALE；
- 高风险输入能够稳定得到 HIGH_RISK；
- Risk capability failure 不会变成低风险；
- Risk 结果绑定当前 Clinical State Version。

# 7. U04 Safety Gate 决策

## 7.1 对应闭环

- BL-02
- BL-08
- BL-09

## 7.2 S_in

存在当前版本的：

- Clinical Risk 输入；
- 必要 Safety Capability 可用性；
- 当前适用 Safety Policy / Scope 条件。

## 7.3 Trigger

```text
RISK_OR_SAFETY_INPUT_READY
```

## 7.4 Action / Decision

G4 形成唯一 Safety Gate：

```text
ALLOW
RESTRICTED
BLOCKED
UNAVAILABLE
```

## 7.5 S_out

```text
ALLOW / 合法 RESTRICTED
→ U05

HIGH_RISK + RESTRICTED/BLOCKED
→ Consultation SAFETY_ESCALATED
→ U11

UNAVAILABLE
→ 禁止普通临床继续
→ U11 或 U14
```

## 7.6 强制语义

```text
HIGH_RISK
→ Safety Gate 不得保持普通 ALLOW
```

```text
Safety capability unavailable
→ Gate != ALLOW
```

## 7.7 验证标准

- HIGH_RISK 能抢占普通 DDx；
- Safety capability failure 时普通临床路径被阻断；
- Frontend/Model/Agent 不能覆盖 Gate；
- Gate 结果具有唯一业务解释。

# 8. U05 Clinical Readiness 唯一求值

## 8.1 对应闭环

- BL-02
- BL-04
- BL-05
- BL-06
- BL-07
- BL-11

## 8.2 S_in

```text
Safety Gate 允许普通推进
+ 当前 F1/F3/F5/F6 readiness inputs
+ 当前 Clinical State Version
```

## 8.3 Trigger

```text
READINESS_REEVALUATION_REQUIRED
```

## 8.4 Action / Decision

Clinical Readiness Resolver 按 Phase 5 已冻结优先原则形成唯一结果：

```text
OUT_OF_SCOPE
NEEDS_OFFLINE_EVIDENCE
NEEDS_CLARIFICATION
CAN_ASK_MORE
READY_FOR_CLINICAL_ANALYSIS
NO_RELIABLE_DIRECTION
```

其中线下证据只有在阻断当前正常结论或 Must-Exclude 处置时，才优先于仍具有实际决策价值的线上关键问题。

## 8.5 S_out

```text
NEEDS_CLARIFICATION / CAN_ASK_MORE
→ U06

READY_FOR_CLINICAL_ANALYSIS
→ U08

NEEDS_OFFLINE_EVIDENCE
→ U10

OUT_OF_SCOPE / NO_RELIABLE_DIRECTION
→ U11
```

## 8.6 验证标准

- 同一 Clinical State Version 只能得到一个正式 Readiness；
- 多个 readiness input 冲突时结果确定且可解释；
- Safety BLOCKED/UNAVAILABLE 时不得运行普通 readiness 路由；
- 不把 Resolver 决策交给前端或自由 Agent。

# 9. U06 关键问题选择与进入 WAITING_USER

## 9.1 对应闭环

- BL-01
- BL-04

## 9.2 S_in

```text
Clinical Readiness = NEEDS_CLARIFICATION
或 CAN_ASK_MORE
```

并存在合法、可在线获得且具有预期决策价值的 Gap。

## 9.3 Trigger

```text
QUESTION_REQUIRED
```

## 9.4 Action / Decision

F3：

- 评估 Gap 的 Decision Impact；
- 排除已回答/失效/无价值问题；
- 选择下一项最有价值问题；
- 形成 Question；
- 将对应 Gap 标记为 ASKED；
- 将 Question 推进到 DELIVERED_TO_USER。

业务生命周期进入：

```text
Consultation WAITING_USER
```

Runtime 进入：

```text
Thread AWAITING_USER
```

## 9.5 S_out

```text
WAITING_USER
+ 当前 Pending Question
+ 关联 Clinical State Version
```

## 9.6 收敛约束

若已经不存在可以合理预期影响 Safety/DDx/Must-Exclude/Readiness/Delivery 的线上问题：

```text
不得继续生成问题
→ 返回 U05 重新求值合法出口
```

具体最大轮次/预算不在 Phase 6 冻结。

## 9.7 验证标准

- 一次只形成一个明确的下一业务问题；
- 已失效/已回答 Gap 不会被重复询问；
- USER_UNKNOWN 不会被当作 NO；
- UNMEASURED 不会被当作 NORMAL；
- Question 成功交付后 Consultation 与 Thread 等待状态一致；
- 无业务价值问题时能够停止，而不是无限追问。

# 10. U07 用户回答 Resume 与幂等恢复

## 10.1 对应闭环

- BL-03

## 10.2 S_in

```text
Consultation = WAITING_USER
Thread = AWAITING_USER
存在当前 Pending Question
```

## 10.3 Event

```text
USER_ANSWER / RESUME_REQUEST
```

## 10.4 Action / Decision

F8 判断事件：

```text
ACCEPTED
DUPLICATE
EXPIRED
REJECTED
```

若 ACCEPTED：

- Runtime 验证 Thread/Checkpoint；
- 验证事件与当前 Pending Question / Clinical State Version 的兼容性；
- 成功后 Resume；
- F8 标记该 Resume Event 已 APPLIED；
- Consultation 返回 ACTIVE；
- 用户答案进入 U02，而不是直接成为 Clinical Truth。

## 10.5 S_out

```text
ACCEPTED/APPLIED
→ ACTIVE
→ U02

DUPLICATE
→ 无第二次临床副作用
→ 返回幂等确认/原处理引用或当前权威业务状态

EXPIRED / REJECTED
→ 不写 Clinical State
```

## 10.6 强制语义

```text
Idempotent effect
!= replay stale clinical truth
```

## 10.7 验证标准

- 重复提交不会产生 Clinical State Version +2；
- 过期回答不会污染当前状态；
- 错误 Question/Version 关联不能被普通 Resume；
- 页面刷新/网络中断后合法回答可以恢复；
- Duplicate 响应不会把旧临床结果重新提升为当前真值。

# 11. U08 DDx / Must-Exclude 评估

## 11.1 对应闭环

- BL-05

## 11.2 S_in

```text
Clinical Readiness = READY_FOR_CLINICAL_ANALYSIS
Safety Gate = ALLOW 或明确允许当前动作的 RESTRICTED
当前 Clinical State Version 有效
```

## 11.3 Trigger

```text
CLINICAL_ANALYSIS_ALLOWED
```

## 11.4 Action / Decision

F5：

- 形成候选疾病方向；
- 形成 Candidate Tier；
- 建立支持/反对/未知证据关系；
- 识别并维护 Must-Exclude；
- 形成 DDx Assessment：

```text
VALID
NO_RELIABLE_DIRECTION
FAILED
```

## 11.5 S_out

```text
VALID
→ U09

NO_RELIABLE_DIRECTION
→ U09/U05 判断是否仍有合法获取路径

FAILED
→ U14
```

## 11.6 强制语义

```text
DDx FAILED
!= NO_RELIABLE_DIRECTION
```

```text
UNKNOWN / INSUFFICIENT_EVIDENCE
!= Must-Exclude EXCLUDED
```

## 11.7 验证标准

- 候选必须有当前允许的正式依据；
- 无可靠方向能够作为合法业务结果，不会伪造候选；
- Must-Exclude 不会因证据不足静默消失；
- DDx 结果绑定当前 Clinical State Version；
- Failure 不会输出空数组后继续正常完成。

# 12. U09 DDx 后 Gap 重评与循环路由

## 12.1 对应闭环

- BL-04 ↔ BL-05 核心循环

## 12.2 S_in

```text
U08 产生 VALID 或 NO_RELIABLE_DIRECTION
```

## 12.3 Trigger

```text
DDX_ASSESSMENT_UPDATED
```

## 12.4 Action / Decision

- F3 基于新的 Candidate/Must-Exclude 重新评估 Information Gap；
- 必要时触发 U03 重新评估 Risk；
- 判断新的问题是否具有实际决策价值；
- 将新的 readiness inputs 交给 U05；
- 不自行决定最终下一路径。

## 12.5 S_out

通过 U05 唯一路由到：

```text
U06 继续追问
U10 线下证据
U11 Safe Exit
U12 正常交付
或经 U03/U04 被 Safety 抢占
```

## 12.6 收敛规则

继续循环必须能够合理预期影响至少一个：

```text
Risk / Safety Gate
DDx / Candidate 排序
Must-Exclude
Clinical Readiness
Delivery eligibility
关键不确定性
```

否则不得再次进入 U06。

## 12.7 验证标准

- DDx 新增候选能够产生新的合法 Gap；
- 候选失效后相关 Gap 可 INVALIDATED；
- 没有决策价值的新 Gap 不会无限制造问题；
- 循环能够进入正常、线下补证、无可靠方向、安全或失败出口。

# 13. U10 线下证据需求与检查建议

## 13.1 对应闭环

- BL-06

## 13.2 S_in

```text
Clinical Readiness = NEEDS_OFFLINE_EVIDENCE
```

## 13.3 Trigger

```text
OFFLINE_EVIDENCE_REQUIRED
```

## 13.4 Action / Decision

F6：

- 完成 Offline Evidence Assessment；
- 区分 VALID / FAILED；
- VALID 时形成 JUSTIFIED 的 Offline Evidence Need；
- 有正式依据时形成检查方向/具体检查建议；
- 将合规建议标记为 DELIVERABLE。

## 13.5 S_out

```text
VALID + JUSTIFIED
→ U11 Safe Exit Delivery

FAILED
→ U14
```

## 13.6 强制语义

```text
Offline Evidence Assessment FAILED
!= NOT_NEEDED
```

```text
Suggestion
!= Medical Order
```

## 13.7 验证标准

- 线下证据必须能解释影响哪个 Gap/DDx/Must-Exclude/Risk；
- 没有正式依据时不能自由生成具体检查；
- Failure 不会被解释为“不需要检查”；
- V1 不产生检查订单，也不建立跨天检查 Resume。

# 14. U11 Safe Exit 结果组装与交付

## 14.1 对应闭环

- BL-06
- BL-07
- BL-08
- BL-09 的安全退出分支

## 14.2 S_in

至少一种合法 Safe Exit 原因已经成立：

```text
OUT_OF_SCOPE
NO_RELIABLE_DIRECTION
NEEDS_OFFLINE_EVIDENCE
HIGH_RISK / Safety BLOCKED
Safety capability UNAVAILABLE
不可继续普通分析但仍可形成最低安全交付的 Failure
```

## 14.3 Trigger

```text
SAFE_EXIT_DELIVERY_REQUIRED
```

## 14.4 Action / Decision

F7：

- 组装与当前 Clinical State Version 一致的 Safe Exit Delivery；
- 保留已知/未知/风险/边界/必要行动；
- 高风险时突出安全处置；
- 线下证据时解释缺口和进一步建议；
- 范围外时明确能力边界；
- 进行 Delivery Validation；
- 成功后正式交付。

## 14.5 S_out

```text
VALIDATED + DELIVERED
→ Delivery Readiness = DELIVERED
→ Consultation = SAFE_EXIT

VALIDATION_FAILED / DELIVERY_FAILED
→ U14
```

## 14.6 强制语义

```text
SAFE_EXIT
!= COMPLETED
```

只有真正交付了合法安全结果才能进入 SAFE_EXIT；流程跑到边界但没有完成最低安全交付，不得伪装为 SAFE_EXIT。

## 14.7 验证标准

- OUT_OF_SCOPE 不生成自由疾病方向；
- HIGH_RISK 不继续普通鉴别；
- 安全能力不可用不会显示“低风险”；
- Delivery failure 会进入 U14；
- Safe Exit 结果不包含处方/治疗越界内容。

---

# 15. U12 正常结果组装与 COMPLETED

## 15.1 对应闭环

- BL-10

## 15.2 S_in

至少满足：

```text
Consultation = ACTIVE
Safety Gate 允许正常交付
当前 Clinical State Version 有效
Risk Assessment 对当前版本有效
DDx Assessment = VALID
关键 Must-Exclude 已适当处置
不存在阻断正常交付的关键 Gap
```

## 15.3 Trigger

```text
NORMAL_DELIVERY_ALLOWED
```

## 15.4 Action / Decision

F7：

- 组装正式 Delivery Package；
- 引用当前事实、Risk、DDx、Must-Exclude、Evidence、Unknown/Uncertainty 和必要建议；
- 验证产品边界、Evidence、Safety、Scope 与 Version 一致性；
- 正式交付。

## 15.5 S_out

```text
VALIDATED + DELIVERED
→ Delivery Readiness = DELIVERED
→ Consultation = COMPLETED

VALIDATION_FAILED / DELIVERY_FAILED
→ U14
```

## 15.6 强制语义

```text
Thread COMPLETED
!= Consultation COMPLETED
```

```text
Workflow reached end
!= COMPLETED
```

## 15.7 验证标准

- 未完成 Must-Exclude 不能被静默删除后完成；
- UNKNOWN/UNMEASURED 不被改写成正常；
- 疾病方向不表达为确诊；
- 不输出自动处方/治疗方案；
- 结果绑定当前有效 Clinical State Version；
- Delivery failure 不会把 Consultation 置为 COMPLETED。

# 17. U14 Capability / Runtime Failure 路由

## 17.1 对应闭环

- BL-09
- 其他所有单元的失败出口

## 17.2 S_in

任一业务单元收到显式：

```text
Capability Failure
Runtime Failure
Delivery Validation/Execution Failure
State Governance Failure
```

## 17.3 Trigger

```text
BUSINESS_DEPENDENCY_FAILED
```

## 17.4 Action / Decision

必须判断：

- 是否存在允许的 Retry / Repair；
- 是否存在已批准且满足当前安全和产品边界的 fallback；
- 是否仍允许安全继续普通业务；
- 是否影响 Safety Gate；
- 是否还能形成最低合法 Safe Exit Delivery；
- 是否只能进入 FAILED_TERMINAL。

Phase 6 不冻结 retry 次数、timeout 数值或 fallback 技术类型。

## 17.5 S_out

```text
A. 恢复成功
→ 返回失败前合法业务单元重新求值

B. 普通临床不能继续，但可安全交付
→ U11

C. 无法形成最低合法安全交付
→ Consultation FAILED_TERMINAL
```

## 17.6 强制语义

```text
Failure
!= empty business result
```

```text
Thread FAILED_TERMINAL
!= Consultation FAILED_TERMINAL
```

Runtime 失败如果仍可重建或安全退出，不得自动把业务 Consultation 判为终止失败。

## 17.7 验证标准

- Risk/DDx/F6 failure 均不会被解释为合法阴性；
- 可恢复 failure 能回到原业务链；
- 不可继续但可安全交付时进入 U11；
- 连安全交付也不可完成时才进入 FAILED_TERMINAL；
- Failure reason 可关联对应 Clinical State Version / Run / Capability Version。

# 26. Phase 6 完成标准

Phase 6 应能够回答：

> V1 的完整业务闭环可以拆成哪些最小、可独立验证、可以逐步组合的业务状态转换单元？

当前形成 15 个单元，已覆盖全部 12 个 Phase 5 业务闭环，并明确了第一纵向切片和单元依赖关系。

当前状态：

```text
SOP Phase 6 — Verifiable Development Units
= DRAFT COMPLETE / NOT FROZEN
```

冻结前应独立审查：

1. 是否存在 Unit 过大，实际包含多个不可独立验证的状态变化；
2. 是否存在 Unit 过小，只是技术函数而没有业务效果；
3. 是否有 Phase 5 闭环无法由 Unit 组合完整还原；
4. 是否存在两个 Unit 重复拥有同一状态语义；
5. U02/G2、U03/F4、U04/G4、U05/Resolver 的 Owner 边界是否清楚；
6. U06/U07 是否真正构成 WAITING_USER/Resume 幂等闭环；
7. U08/U09 是否能够收敛而不会重新制造固定五步或无限循环；
8. U11/U12/U14 是否保证 Delivery Failure 不会伪装成终态成功；
9. 是否错误提前冻结 API、数据库、框架或 Capability 实现；
10. Slice A 是否适合作为后续第一正式实施候选，但没有被误写成施工授权。

通过独立审查后，Phase 6 才可标记 `FROZEN / V1`。
