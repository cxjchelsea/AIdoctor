# AIdoctor V1 可验证开发单元拆分

> 文档状态：FROZEN / V1  
> 所属阶段：复杂业务软件开发 SOP — Phase 6 可验证开发单元拆分  
> 上游权威：`01_需求/需求与系统边界_V1.md`、`02_功能/功能模块划分_V1.md`、`03_状态/系统级状态主干_V1.md`、`03_状态/模块级状态与状态所有权_V1.md`、`05_业务闭环/业务闭环设计_V1.md`  
> 当前事实依据：`00_现状与治理/Current_State_Baseline_V1.md`、`00_现状与治理/重构决策_V1.md`  
> 本文只把已冻结业务闭环拆成最小可独立验证的业务状态转换单元，并定义单元依赖、输入/事件/动作/输出/验证条件；不冻结 API、数据库表、类、微服务边界、具体 StatePatch Schema、模型、Prompt、RAG、KG 或 Runtime 实现。

---

## 1. Phase 6 目标

Phase 5 已冻结 12 个业务闭环。Phase 6 回答：

> 为了逐步实现这些闭环，哪些最小业务状态变化可以单独开发、单独验证，并在通过后安全组合成更大的闭环？

每个开发单元必须具备：

```text
明确输入状态
+ 明确触发事件
+ 明确业务动作/决策
+ 明确输出状态
+ 明确失败语义
+ 明确验证条件
```

开发单元不是微服务、类、接口或 Capability 本身。

```text
一个开发单元 != 一个微服务
一个开发单元 != 一个旧 Tool
一个开发单元 != 一个完整业务模块
```

---

## 2. 拆分原则

### UNIT-01 单元以状态变化为中心

优先按：

```text
S_in + Event -> Decision/Action -> S_out
```

拆分，而不是按代码目录拆分。

### UNIT-02 单元必须可独立验证

一个单元通过时至少可以验证：输入状态是否合法、事件是否被正确接受或拒绝、输出状态是否唯一且可解释、Failure 是否与合法业务结果分离，以及是否违反 Safety / State Ownership / Product Boundary。

### UNIT-03 Capability 只作为依赖，不在 Phase 6 设计实现

Phase 6 可以声明某 Unit 需要 Risk / Parsing / DDx 等 Capability，但不决定规则、模型、Prompt、Java/Python 调用、Schema 等实现方式。

### UNIT-04 共享治理跨单元复用

G2 State Governance、G4 Safety Gate、Runtime Checkpoint 等可以被多个单元依赖，但不能因此把所有单元合并成一个大单元。

### UNIT-05 不为了复用旧代码制造单元

旧 `DiagnosisController`、固定五步 Workflow、Dialog、Risk、Diagnosis Engine、Workup、Explanation 等只用于后续资产映射，不决定当前 Unit 边界。

### UNIT-06 单元完成不等于完整业务闭环完成

例如 U06 成功交付问题并进入 `WAITING_USER`，只证明等待入口成立；还需要 U07 Resume 才能形成完整跨轮闭环。

### UNIT-07 WAITING_USER 只能在合法 Question 已交付后进入

```text
Question DELIVERED_TO_USER
→ Consultation WAITING_USER
→ Thread AWAITING_USER
```

入口模块发现“需要澄清”本身不能提前把 Consultation 改成 `WAITING_USER`。

### UNIT-08 Failure 的安全权限后果先于恢复/降级路由

对于会影响 Safety 的失败，例如 Risk Assessment FAILED：

```text
Failure
→ 先完成 Safety Gate 后果求值
→ 普通临床路径被确定允许/限制/阻断
→ 再进入 Failure Routing 判断恢复、Safe Exit 或 FAILED_TERMINAL
```

不得同时分叉多个竞争业务路径。

---

## 3. Phase 6 单元总览

V1 拆为 15 个可验证开发单元：

```text
U01 Consultation 建立与对象/问题框定
U02 临床事实形成与版本提交
U03 当前版本风险评估
U04 Safety Gate 决策
U05 Clinical Readiness 唯一求值
U06 关键问题选择与进入 WAITING_USER
U07 用户回答 Resume 与幂等恢复
U08 DDx / Must-Exclude 评估
U09 DDx 后 Gap 重评与循环路由
U10 线下证据需求与检查建议
U11 Safe Exit 结果组装与交付
U12 正常结果组装与 COMPLETED
U13 用户更正事件验证与失效触发
U14 Capability / Runtime Failure 路由
U15 Consultation 取消与过期终止
```

15 个单元共同覆盖 Phase 5 的 12 个业务闭环。

# 4. U01 Consultation 建立与对象/问题框定

## 4.1 对应闭环

- BL-01 新问诊建立与入口澄清

## 4.2 S_in

```text
不存在可合法继续的同一健康问题 Consultation
```

或业务明确要求创建新的 Consultation。

## 4.3 Event

```text
START_CONSULTATION
+ 首次用户健康诉求
+ 当前最低身份/授权上下文
```

这里是业务事件概念，不冻结 Event Schema。

## 4.4 Action / Decision

- 创建 Consultation；
- 建立 Subject Resolution；
- 判断 Problem Framing；
- 判断是否需要最小澄清；
- 判断是否明显 `OUTSIDE_V1_INTENT`；
- 若首条表达已暴露风险线索，不得因 framing 未完成而屏蔽后续 Safety 路径。

## 4.5 S_out

```text
A. Consultation ACTIVE
   Subject = RESOLVED
   Problem = FRAMED
   → U02

B. Problem = CLARIFICATION_REQUIRED
   → 形成 F1 Clarification Requirement
   → 不进入 WAITING_USER
   → U06

C. OUT_OF_SCOPE input
   → U11

D. 无法可靠建立主体/上下文
   → U14 或 U11
```

U01 不创建 `WAITING_USER`。只有 U06 成功形成并交付合法 Question 后，Consultation 才能进入等待态。

## 4.6 Failure 语义

```text
对象未确认 != 随便猜测为本人
OUTSIDE_V1_INTENT != 系统故障
CLARIFICATION_REQUIRED != WAITING_USER
```

## 4.7 验证标准

- 本人/代他人能够形成明确 Subject；
- 模糊/混合诉求形成 Clarification Requirement；
- U06 尚未交付问题时不得出现 `WAITING_USER`；
- 纯 V1 范围外诉求不会进入普通 DDx；
- 危险线索不会因为入口未完全 framing 而被屏蔽；
- 同一首条输入不会产生重复业务效果。

# 5. U02 临床事实形成与版本提交

## 5.1 对应闭环

- BL-02 临床事实采集与安全入口
- BL-03 Resume 后事实形成
- BL-11 用户更正后的事实更新

## 5.2 S_in

```text
Consultation = ACTIVE
或合法 Resume / Correction Input 正在应用
```

并存在待解释的新用户输入、补充或更正。

## 5.3 Event

```text
NEW_CLINICAL_INPUT
```

## 5.4 Action / Decision

F2：提取并归一化 Clinical Observation，保留事实值语义、来源与确定性，并判断 `CONFIRMED / UNCERTAIN / CONTRADICTED / INVALIDATED`。

G2：验证正式状态变化；合法时创建新的 Clinical State Version；根据依赖关系正式提交需要失效或重评的下游派生状态。

## 5.5 S_out

```text
A. 新 Clinical State Version + 当前有效 Clinical Facts
   → U03

B. 当前事实仍需进一步澄清
   → U05 / U06

C. 输入无法可靠形成事实且不能继续安全处理
   → U11 / U14
```

若本次输入来自 U13 合法 Correction，U02/G2 成功提交后，可把对应 Correction Event 完成到 `APPLIED`；其具体回调或接口机制不在 Phase 6 定义。

## 5.6 强制语义

```text
UNKNOWN != NO
UNMEASURED != NORMAL
MODEL_INFERRED != PATIENT_REPORTED
```

Capability 结果不能绕过 G2 直接成为正式 Clinical State。

## 5.7 验证标准

- 所有事实值语义不发生塌缩；
- 同一输入事件最多产生一次正式事实提交；
- 新事实生成新版本，不静默覆盖旧版本；
- 不确定/冲突事实不会伪装为 CONFIRMED；
- Correction 后受影响派生状态可以正式失效；
- 下游旧 Risk/DDx/Delivery 不会在新版本下继续冒充当前真值。

# 6. U03 当前版本风险评估

## 6.1 对应闭环

- BL-02
- BL-05
- BL-08
- BL-11

## 6.2 S_in

```text
存在当前有效 Clinical State Version
Risk Assessment = NOT_ASSESSED 或 STALE
```

## 6.3 Trigger

```text
CLINICAL_STATE_CHANGED
或 RISK_REEVALUATION_REQUIRED
```

## 6.4 Action / Decision

F4 对当前 Clinical State Version 执行风险评估，形成：

```text
Risk Assessment = VALID / FAILED
```

若 VALID，再得到唯一：

```text
NO_HIGH_RISK_SIGNAL
CAUTION
HIGH_RISK
```

## 6.5 S_out

```text
A. VALID + Risk Disposition
→ U04

B. FAILED
→ 仅把 Risk Assessment FAILED 作为 U04 的安全输入
→ U04 必须先形成 Safety Gate 后果
→ 若形成 UNAVAILABLE / BLOCKED 等禁止普通继续的结果，再进入 U14 处理恢复/降级
```

禁止：

```text
U03 FAILED
→ 同时并发进入 U04 与 U14
```

## 6.6 强制语义

```text
Risk FAILED != NO_HIGH_RISK_SIGNAL
NO_HIGH_RISK_SIGNAL != 患者安全/无病
```

## 6.7 验证标准

- 新事实到达后旧 Risk 可进入 STALE；
- 高风险输入稳定得到 HIGH_RISK；
- Risk failure 不会变成低风险；
- Risk 结果绑定当前 Clinical State Version；
- Risk failure 必须先造成确定的 Gate 后果，再进入恢复/降级路由。

# 7. U04 Safety Gate 决策

## 7.1 对应闭环

- BL-02
- BL-08
- BL-09

## 7.2 S_in

当前版本可获得以下 Safety 输入：

- Clinical Risk 或显式 Risk Assessment FAILED；
- 必要 Safety Capability 可用性；
- 当前适用 Safety Policy / Scope 条件。

## 7.3 Trigger

```text
RISK_OR_SAFETY_INPUT_READY
```

## 7.4 Action / Decision

G4 形成唯一 Safety Gate：

```text
ALLOW
RESTRICTED
BLOCKED
UNAVAILABLE
```

## 7.5 S_out

```text
ALLOW / 合法 RESTRICTED
→ U05

HIGH_RISK + RESTRICTED/BLOCKED
→ Consultation SAFETY_ESCALATED
→ U11

Risk Assessment FAILED / 关键 Safety Capability 不可用
→ Safety Gate = UNAVAILABLE（或按已批准策略形成更严格 Gate）
→ 普通临床路径被禁止
→ U14 判断能否恢复、Safe Exit 或 FAILED_TERMINAL
```

U04 不与 U14 竞争同一个最终决策：U04 只回答“现在普通临床是否获准继续”；U14 回答“发生失败后如何恢复或收束”。

## 7.6 强制语义

```text
HIGH_RISK → Safety Gate 不得保持普通 ALLOW
Safety capability unavailable → Gate != ALLOW
Risk Assessment FAILED → ordinary continuation prohibited until resolved
```

## 7.7 验证标准

- HIGH_RISK 能抢占普通 DDx；
- Risk/Safety capability failure 时普通临床路径先被阻断；
- Frontend/Model/Agent 不能覆盖 Gate；
- Gate 结果具有唯一业务解释；
- Failure 后不会出现 U04/U14 双重竞争路由。

# 8. U05 Clinical Readiness 唯一求值

## 8.1 对应闭环

- BL-02
- BL-04
- BL-05
- BL-06
- BL-07
- BL-11

## 8.2 S_in

```text
Safety Gate 允许普通推进
+ 当前阶段已经存在且适用的 F1/F3/F5/F6 readiness inputs
+ 当前 Clinical State Version
```

关键规则：并非每次求值都要求 F1/F3/F5/F6 四类输入全部存在。

```text
尚未进入某业务阶段
→ 对应 readiness input = absent-by-design / not-yet-applicable
→ 不是 Capability Failure
→ 也不得被投射为 negative / NOT_NEEDED
```

例如首次 Intake 时，F5 尚未做 DDx、F6 尚未做 Offline Evidence Assessment，这是合法的阶段性缺席。

## 8.3 Trigger

```text
READINESS_REEVALUATION_REQUIRED
```

## 8.4 Action / Decision

Clinical Readiness Resolver 按 Phase 5 已冻结优先规则形成唯一结果：

```text
OUT_OF_SCOPE
NEEDS_OFFLINE_EVIDENCE
NEEDS_CLARIFICATION
CAN_ASK_MORE
READY_FOR_CLINICAL_ANALYSIS
NO_RELIABLE_DIRECTION
```

只有实际适用且已有业务判定的 input 才参与解析。线下证据只有在阻断正常结论或 Must-Exclude 处置时，才优先于仍具有实际决策价值的线上关键问题。

## 8.5 S_out

```text
NEEDS_CLARIFICATION / CAN_ASK_MORE
→ U06

READY_FOR_CLINICAL_ANALYSIS
→ U08

NEEDS_OFFLINE_EVIDENCE
→ U10

OUT_OF_SCOPE / NO_RELIABLE_DIRECTION
→ U11
```

## 8.6 验证标准

- 同一 Clinical State Version 只有一个正式 Readiness；
- 多输入冲突时结果确定且可解释；
- Safety BLOCKED/UNAVAILABLE 时不得执行普通 readiness 路由；
- 未进入 F5/F6 时不会误报 dependency failure；
- 缺席 input 不会自动转成 `NOT_NEEDED`、`NO_RELIABLE_DIRECTION` 等业务结论；
- Resolver 决策不会下放给前端或自由 Agent。

# 9. U06 关键问题选择与进入 WAITING_USER

## 9.1 对应闭环

- BL-01
- BL-04

## 9.2 S_in

U06 支持两类合法 Question Need：

```text
A. F1 Clarification Requirement
   - Subject / Problem Framing 需要澄清

B. F3 Information Gap
   - Clinical Readiness = CAN_ASK_MORE
   - 存在合法、可在线获得且具有预期决策价值的 Gap
```

当 `Clinical Readiness = NEEDS_CLARIFICATION` 时，对应输入可以来自 F1/F2 的合法澄清需求，不要求它必须先被建模成 F3 Information Gap。

## 9.3 Trigger

```text
QUESTION_REQUIRED
```

## 9.4 Action / Decision

对于 F1 澄清需求：

- 形成最小必要 Clarification Question；
- 不扩展为普通临床信息收集。

对于 F3 Gap：

- 评估 Gap Decision Impact；
- 排除已回答、失效、重复或无价值问题；
- 选择下一项最有价值问题；
- 将相关 Gap 标记到适当问询状态。

两类输入最终统一形成：

```text
Question PROPOSED
→ SELECTED
→ DELIVERED_TO_USER
```

只有在 `DELIVERED_TO_USER` 成功后：

```text
Consultation → WAITING_USER
Thread → AWAITING_USER
```

## 9.5 S_out

```text
Question DELIVERED_TO_USER
+ 当前 Pending Question
+ 关联 Clinical State Version / 当前合法业务上下文
+ Consultation WAITING_USER
+ Thread AWAITING_USER
```

若 Question 尚未成功交付，则不得产生 `WAITING_USER`。

## 9.6 收敛约束

若不存在可以合理预期影响 Safety/DDx/Must-Exclude/Readiness/Delivery 的线上临床问题，不得继续生成 F3 问题，应返回 U05 重新求值合法出口。F1 入口澄清同样只能做最小必要澄清，不允许形成无限入口追问。

具体最大轮次/预算不在 Phase 6 冻结。

## 9.7 验证标准

- F1 Clarification Requirement 可以在没有 F3 Gap 时合法形成 Question；
- F3 主动问诊仍要求具有实际决策价值的 Gap；
- 一次只形成一个明确下一业务问题；
- 已失效/已回答 Gap 不会重复询问；
- USER_UNKNOWN 不会被当作 NO；
- UNMEASURED 不会被当作 NORMAL；
- 只有 Question 成功交付后 Consultation/Thread 才进入对应等待状态；
- 无业务价值问题时能停止而不是无限追问。

# 10. U07 用户回答 Resume 与幂等恢复

## 10.1 对应闭环

- BL-03

## 10.2 S_in

```text
Consultation = WAITING_USER
Thread = AWAITING_USER
存在当前 Pending Question
```

## 10.3 Event

```text
USER_ANSWER / RESUME_REQUEST
```

## 10.4 Action / Decision

F8 判断事件：

```text
ACCEPTED
DUPLICATE
EXPIRED
REJECTED
```

若 ACCEPTED：Runtime 验证 Thread/Checkpoint 和 Pending Question / Clinical State Version 兼容性；成功后 Resume；F8 标记事件已 APPLIED；Consultation 返回 ACTIVE；用户答案进入 U02，而不是直接成为 Clinical Truth。

## 10.5 S_out

```text
ACCEPTED/APPLIED
→ ACTIVE
→ U02

DUPLICATE
→ 无第二次临床副作用
→ 返回幂等确认、原处理引用或当前权威业务状态

EXPIRED / REJECTED
→ 不写 Clinical State
```

## 10.6 强制语义

```text
Idempotent effect != replay stale clinical truth
```

## 10.7 验证标准

- 重复提交不会产生第二次 Clinical State 效果；
- 过期回答不会污染当前状态；
- 错误 Question/Version 关联不能普通 Resume；
- 页面刷新/网络中断后合法回答可恢复；
- Duplicate 不会把旧临床结果提升为当前真值。

# 11. U08 DDx / Must-Exclude 评估

## 11.1 对应闭环

- BL-05

## 11.2 S_in

```text
Clinical Readiness = READY_FOR_CLINICAL_ANALYSIS
Safety Gate = ALLOW 或明确允许当前动作的 RESTRICTED
当前 Clinical State Version 有效
```

## 11.3 Trigger

```text
CLINICAL_ANALYSIS_ALLOWED
```

## 11.4 Action / Decision

F5 形成候选疾病方向、Candidate Tier、支持/反对/未知证据关系、Must-Exclude，并形成：

```text
DDx Assessment = VALID / NO_RELIABLE_DIRECTION / FAILED
```

## 11.5 S_out

```text
VALID
→ U09

NO_RELIABLE_DIRECTION
→ U09，再由 U05 判断是否仍有合法获取路径

FAILED
→ U14
```

## 11.6 强制语义

```text
DDx FAILED != NO_RELIABLE_DIRECTION
UNKNOWN / INSUFFICIENT_EVIDENCE != Must-Exclude EXCLUDED
```

## 11.7 验证标准

- 候选必须有当前允许的正式依据；
- 无可靠方向不会伪造候选；
- Must-Exclude 不会因证据不足静默消失；
- DDx 绑定当前 Clinical State Version；
- Failure 不会输出空数组后继续正常完成。

# 12. U09 DDx 后 Gap 重评与循环路由

## 12.1 对应闭环

- BL-04 ↔ BL-05 核心循环

## 12.2 S_in

```text
U08 产生 VALID 或 NO_RELIABLE_DIRECTION
```

## 12.3 Trigger

```text
DDX_ASSESSMENT_UPDATED
```

## 12.4 Action / Decision

- F3 基于新的 Candidate/Must-Exclude 重新评估 Information Gap；
- 必要时触发 U03 重新评估 Risk；
- 判断新的问题是否具有实际决策价值；
- 将新的 readiness inputs 交给 U05；
- 不自行决定最终下一路径。

## 12.5 S_out

经 U05 唯一路由到：

```text
U06 继续追问
U10 线下证据
U11 Safe Exit
U12 正常交付
或经 U03/U04 被 Safety 抢占
```

## 12.6 收敛规则

继续循环必须能够合理预期影响至少一个：

```text
Risk / Safety Gate
DDx / Candidate 排序
Must-Exclude
Clinical Readiness
Delivery eligibility
关键不确定性
```

否则不得再次进入 U06。

## 12.7 验证标准

- DDx 新增候选可以产生新的合法 Gap；
- 候选失效后相关 Gap 可 INVALIDATED；
- 没有决策价值的新 Gap 不会制造无限追问；
- 循环能够进入正常、线下补证、无可靠方向、安全或失败出口；
- 不恢复固定 Step1→Step5 作为业务真值。

---

# 13. U10 线下证据需求与检查建议

## 13.1 对应闭环

- BL-06

## 13.2 S_in

```text
Clinical Readiness = NEEDS_OFFLINE_EVIDENCE
```

## 13.3 Trigger

```text
OFFLINE_EVIDENCE_REQUIRED
```

## 13.4 Action / Decision

F6 完成 Offline Evidence Assessment；区分 VALID / FAILED；VALID 时形成 JUSTIFIED 的 Offline Evidence Need；有正式依据时形成检查方向/具体检查建议，并将合规建议标记为 DELIVERABLE。

## 13.5 S_out

```text
VALID + JUSTIFIED
→ U11

FAILED
→ U14
```

## 13.6 强制语义

```text
Offline Evidence Assessment FAILED != NOT_NEEDED
Suggestion != Medical Order
```

## 13.7 验证标准

- 线下证据能说明影响哪个 Gap/DDx/Must-Exclude/Risk；
- 没有正式依据时不能自由生成具体检查；
- Failure 不被解释为“不需要检查”；
- V1 不产生检查订单，也不建立跨天检查 Resume。

# 14. U11 Safe Exit 结果组装与交付

## 14.1 对应闭环

- BL-06
- BL-07
- BL-08
- BL-09 的安全退出分支

## 14.2 S_in

至少一种合法 Safe Exit 原因已经成立：

```text
OUT_OF_SCOPE
NO_RELIABLE_DIRECTION
NEEDS_OFFLINE_EVIDENCE
HIGH_RISK / Safety BLOCKED
Safety capability UNAVAILABLE
不可继续普通分析但仍可形成最低安全交付的 Failure
```

## 14.3 Trigger

```text
SAFE_EXIT_DELIVERY_REQUIRED
```

## 14.4 Action / Decision

F7 组装与当前 Clinical State Version 一致的 Safe Exit Delivery，保留已知/未知/风险/边界/必要行动；根据原因突出高风险安全处置、线下证据需求或能力边界；进行 Delivery Validation 并正式交付。

## 14.5 S_out

```text
VALIDATED + DELIVERED
→ Delivery Readiness = DELIVERED
→ Consultation = SAFE_EXIT

VALIDATION_FAILED / DELIVERY_FAILED
→ U14
```

## 14.6 强制语义

```text
SAFE_EXIT != COMPLETED
Delivery failure != SAFE_EXIT
```

只有真正交付合法安全结果才能进入 SAFE_EXIT。

## 14.7 验证标准

- OUT_OF_SCOPE 不生成自由疾病方向；
- HIGH_RISK 不继续普通鉴别；
- 安全能力不可用不会显示“低风险”；
- Delivery failure 进入 U14；
- Safe Exit 不包含处方/治疗越界内容。

```text
Safety Gate 允许正常交付
当前 Clinical State Version 有效
Risk Assessment 对当前版本有效
DDx Assessment = VALID
关键 Must-Exclude 已适当处置
不存在阻断正常交付的关键 Gap
```

```text
NORMAL_DELIVERY_ALLOWED
```

```text
VALIDATED + DELIVERED

VALIDATION_FAILED / DELIVERY_FAILED
```

# 16. U13 用户更正事件验证与失效触发

## 16.1 对应闭环

- BL-11

## 16.2 S_in

```text
非终止态 Consultation
+ 用户提出对既有事实的更正/撤销/补充
```

终止态后的更正不按普通 Resume 自动重开。

## 16.3 Event

```text
CORRECTION_REQUEST
```

## 16.4 Action / Decision

U13 的唯一职责是 F8 对 Correction Event 的业务有效性进行判断：

```text
RECEIVED
→ VALIDATING
→ VALIDATED / REJECTED
```

F8：

- 验证更正是否针对当前可修改的非终止 Consultation；
- 验证事件是否重复、过期或不适用；
- REJECTED 时保证无 Clinical State 副作用；
- VALIDATED 时形成合法 `Correction Input`，交给 U02。

U13 不直接：

- 创建新的 Clinical State Version；
- 修改 Risk/DDx/Must-Exclude/F6/F7；
- 决定更正后的最终下一业务路径。

## 16.5 S_out

```text
VALIDATED
→ 合法 Correction Input
→ U02

REJECTED
→ 原 Clinical State 不变
→ 无新的临床副作用
```

之后由：

```text
U02/G2
→ 新 Clinical State Version
→ 正式提交依赖失效

U03/U04/U05
→ 重新完成 Safety 与下一路径决策
```

Correction Event 在 U02/G2 成功提交后可完成到 `APPLIED`，但其具体技术交接机制留到后续 Contract/Runtime 阶段。

## 16.6 验证标准

- 非法/重复/过期更正不会改变 Clinical State；
- 合法更正只进入 U02，不在 U13 内重复实现状态提交；
- 历史交付不被静默覆盖；
- 新版本提交后依赖旧事实的 Risk/DDx/Recommendation/Delivery 能进入失效/重评；
- 更正后 Safety 必须重新具有评估机会。

# 17. U14 Capability / Runtime Failure 路由

## 17.1 对应闭环

- BL-09
- 其他所有 Unit 的失败出口

## 17.2 S_in

任一业务单元收到显式：

```text
Capability Failure
Runtime Failure
Delivery Validation/Execution Failure
State Governance Failure
```

对于 Risk/Safety 类失败，进入 U14 前必须已经通过 U04 形成明确的 Safety Gate 后果，避免恢复逻辑先于安全权限判断。

## 17.3 Trigger

```text
BUSINESS_DEPENDENCY_FAILED
```

## 17.4 Action / Decision

判断：

- 是否存在允许的 Retry / Repair；
- 是否存在已批准且满足当前安全和产品边界的 fallback；
- 是否仍允许普通业务继续；
- 是否还能形成最低合法 Safe Exit Delivery；
- 是否只能进入 FAILED_TERMINAL。

Phase 6 不冻结 retry 次数、timeout 数值或 fallback 技术类型。

## 17.5 S_out

```text
A. 恢复成功
→ 返回失败前合法业务单元重新求值

B. 普通临床不能继续，但可安全交付
→ U11

C. 无法形成最低合法安全交付
→ Consultation FAILED_TERMINAL
```

## 17.6 强制语义

```text
Failure != empty business result
Thread FAILED_TERMINAL != Consultation FAILED_TERMINAL
```

Runtime 失败如果仍可重建或安全退出，不得自动把 Consultation 判为终止失败。

## 17.7 验证标准

- Risk/DDx/F6 failure 不会变成合法阴性；
- Safety-sensitive failure 在恢复判断前已经阻断普通路径；
- 可恢复 failure 能回到原业务链；
- 不可继续但可安全交付时进入 U11；
- 连安全交付也不能完成时才进入 FAILED_TERMINAL；
- Failure reason 可关联对应 Clinical State Version / Run / Capability Version。

# 18. U15 Consultation 取消与过期终止

## 18.1 对应闭环


- 终止态不被普通 Resume 自动重开。

# 21. 第一批可形成端到端价值的开发切片

Phase 6 可以冻结推荐施工切片，但这仍不是 Implementation Authorization。

## 21.1 Slice A — Intake / Wait / Resume Foundation

核心状态主链：

```text
U01
→ U02
→ U03
→ U04
→ U05
→ U06
→ U07
→ 回 U02
```

为了让该切片真正成为端到端闭环，而不是只有 happy path，以下横向单元属于 Slice A 的**必需闭合能力**：

```text
U11 — 支持 Slice A 会产生的 Safe Exit 原因
       （至少入口范围外、高风险、Safety UNAVAILABLE 等）

U14 — 支持 Slice A 中 Capability / Runtime / Delivery Failure 的恢复与收束

U15 — 支持 WAITING_USER 的取消与过期终止
```

因此 Slice A 的正式验收范围为：

```text
Core:
U01 U02 U03 U04 U05 U06 U07

Required closure:
U11 U14 U15
```

这不要求在 Slice A 中提前实现 U11 所有未来 DDx/Offline Evidence 型内容，只要求覆盖本切片真实可达的 Safe Exit 原因。

## 21.2 Slice A 可验证的端到端结果

至少能够形成：

```text
A. 正常：
新问诊 → 事实 → Safety → Readiness → Question → WAITING_USER
→ Resume → 新事实

B. 安全退出：
入口范围外 / HIGH_RISK / Safety UNAVAILABLE
→ 合法 Safe Exit Delivery
→ SAFE_EXIT

C. Failure：
依赖失败
→ 合法恢复，或 Safe Exit，或 FAILED_TERMINAL

D. 等待终止：
WAITING_USER
→ CANCELLED / EXPIRED
```

Slice A 能最早验证：Consultation lifecycle、Clinical State versioning、State Governance、Safety fail-closed、Clinical Readiness、WAITING_USER、durable Resume、idempotency、用户答案重新进入 F2，以及不再依赖旧 completeness-only progression。

```text
Slice A 推荐优先
!= 已获得施工授权
```

正式实现前仍需完成后续 Capability / Contract / Runtime / Verification 设计，并经过既有工程治理授权。
