## 1. Purpose and non-negotiable ownership

F8 is U07's deterministic Business Resume Decision owner. It decides whether a **canonical** USER_ANSWER event can lawfully resume one current or historically proven waiting business interaction. A valid Business Resume Decision is **not** proof that P02 can restore the Runtime or that U02 has formed Clinical Facts.

```text
RDP-01 admitted canonical event + immutable scoped binding
+ authoritative U06/F3/P01/Consultation/U15 business-state provenance
+ prior F8 decision / same-wait winner evidence
→ F8 owner decision: ACCEPTED | DUPLICATE | EXPIRED | REJECTED
→ durable F8 decision (never generated by generic event ledger)
→ only ACCEPTED may become an RDP-04 P02 resume candidate
→ only RDP-03/04 governed effects may later establish APPLIED
```

Authority:
- **F8 / U07 business owner:** business validity, ordered precedence, immutable decision ledger, duplicate equivalence and decision replay.
- **Foundation canonical ledger / RDP-01:** event identity, immutable payload/context binding and permission-admission result; never invents F8 verdict.
- **U06/F3:** sent Question, delivered-wait parent effect and Question/Gap lifecycle truth. F8 reads but cannot mark delivery or Question answered.
- **Consultation lifecycle + P01/G2:** authoritative WAITING_USER and Clinical State/Pending Question versions. F8 reads; no direct mutations.
- **U15:** expiry, cancellation and terminal/supersession authority; F8 cannot undo U15.
- **P02 / RDP-04:** checkpoint compatibility, rehydrate, resume failure. Runtime failure cannot rewrite business verdict.
- **RDP-03:** claim/fencing, effects, APPLIED, Consultation ACTIVE, F3 bridge and U02 handoff exactly-once.
- **U02:** interpreting user answer into clinical observations/facts. F8 must not judge medical correctness.
- **U14/D07:** failure and repair routing, not a second F8 policy owner.

No LLM/knowledge/model invocation is required or authorized to decide this gate.

### 3.2 Snapshot consistency invariant

F8 evaluation must bind owner-provided:
- Consultation lifecycle status/row version/current_wait_effect ID;
- Question F3 status `DELIVERED_TO_USER` and authoritative question identity/version;
- current Pending Question ref + source Clinical State Version;
- U06 confirmed delivery, matching parent effect / wait effect child commit;
- U15 terminal/cancel/expire/supersede decision ref, effective time and authoritative commit order;
- original U06 eligibility issuance/reconciliation proof where required;
- prior F8 terminal decision and prior applied resume effect for the same wait and exact canonical ID.

The supplied `U07AuthoritativeWaitEvidence` is a **read-only input**, not self-validating state. If owner versions are incoherent, missing, unreadable or provisional, return `F8_EVALUATION_DEFERRED` without a business verdict or side effects. This is operational deferral, **not a fifth business decision**. RDP-03 must fence/recheck the same versions before apply; an earlier F8 ACCEPTED cannot override subsequent U15 cancellation.

## 5. Strict deterministic precedence, including historical duplicate handling

Precedence is evaluated in **two tiers** to avoid changing an existing immutable decision based on later state.

### Tier 0 — previously resolved canonical event (identity precedence, before fresh state policy)

1. **Same canonical event, prior F8 terminal verdict exists** → **return same durable prior decision unchanged**. If prior ACCEPTED but not APPLIED, it remains ACCEPTED and downstream coordination reconciles the original intended effect; does **not** become DUPLICATE.
2. **Same canonical event, decision not yet terminal** → reattach to in-flight evaluation, or after crash reacquire same decision authority; no competing second decision.
3. **Same-key transport alias** already resolved by RDP-01 → never treat as new answer.
4. **RESUME_REQUEST** → attach original answer event and prior decision; if none yet, observe/continue the *same* target evaluation. No independent ACCEPTED.

Tier 0 return semantics distinguish **historical immutable F8 verdict** from permission to perform *new* effects now. An old ACCEPTED does **not** override a later U15 terminal barrier; RDP-03 must fence before any further apply.

### Tier 1 — first F8 verdict for a genuinely new canonical USER_ANSWER

Apply following ordered table, stopping at first **proved** condition. When necessary owner evidence is unavailable, **DEFER** rather than assuming a lower-precedence verdict.

| Order | Condition on authoritative evidence | Verdict | Why |
|---|---|---|---|
| P1 | Another answer **already APPLIED** for the same exact consultation+Question+parent wait and proven *same answer content equivalence* | **DUPLICATE** | Completed prior effect wins, including after Question/Consultation lifecycle moved on |
| P2 | U15 committed wait expiry or authoritative Question/answer window ended before this event's **trusted first ingress time** | **EXPIRED** | Explicit expiry cannot be hidden by a later generic mismatch |
| P3 | U15 committed cancel/terminal-other, or Question superseded *without expiry*, with no proved P1 duplicate | **REJECTED** | Wrong life-cycle authority, no ordinary resume |
| P4 | Consultation, Question, Pending Question, parent wait, authenticated actor/scope or delivery provenance do not match | **REJECTED** | Wrong binding cannot be repaired through Runtime |
| P5 | Another **different** answer already owns a terminal winning F8 ACCEPTED claim for the same wait, but apply is not complete | **DEFER (F8_COMPETING_WINNER_PENDING)**, **not DUPLICATE** | Await outcome; a pending winner could fail or be cancelled; do not falsely claim already applied |
| P6 | Same wait previously applied a **different** answer, not equivalent | **REJECTED (F8_CONFLICTING_ANSWER)** | Does not turn conflicting new answer into a duplicate |
| P7 | Present lawfully delivered Question, current Pending Question, Consultation WAITING_USER, matching parent effect, current U15 validity and trusted eligibility authority | **ACCEPTED** | Business validity only; P02 still separate |
| P8 | Positive proof cannot be established | **DEFER / BLOCKED_EVIDENCE**, no business verdict | Never optimistic ACCEPTED |

**Important guard on P1:** duplicate equivalence must require *the same logical answer content*, provenance and same wait identity; the hash of `binding_fingerprint` alone is **not** a sufficient content-equivalence test because it includes event-specific refs. For approved PROFILE-B, compare authenticated canonical **answer content digest** and applicable immutable question/wait identity under a versioned equivalence policy. Do not use LLM similarity or substring matching. Different content or uncertain digest cannot be DUPLICATE by guess.

**P1 before P2/P3** is only for an independently proven already-applied identical answer to preserve idempotent status. The response is a reference to original processing, **not** new patient continuation. A late, first-ever answer with no applied identical winner is still EXPIRED if deadline passed. A terminally cancelled wait with no prior identical APPLIED winner is REJECTED; an expired wait uses EXPIRED where owner source proves expiry.

**Expiry clock rule:** evaluate authoritative expiry decision and its effective instant, **server-trusted first durable ingress timestamp** of original canonical answer, and authoritative causal commit order. Do not rely on user-controlled `occurred_at` to backdate a late answer. If event and U15 expiry race in an unorderable manner, **DEFER for same-wait serialized/fenced evaluation**, never silently prefer ACCEPTED. Historical duplicate check P1 is still authoritative even if status is now terminal.

**Precedence of terminal states:** EXPIRED requires positive U15/Question expiry proof; CANCELLED is REJECTED; SUPERSEDED without expiry is REJECTED; malformed scope is RDP-01 BLOCKED; owner unavailable is DEFER, not EXPIRED.

## 7. Decision lifecycle and state machine

```text
Canonical USER_ANSWER durable + RDP-01 admission
  → RECEIVED
  → VALIDATING
  → ACCEPTED | DUPLICATE | EXPIRED | REJECTED

ACCEPTED
  ├─ P02 checkpoint compatibility / rehydrate (RDP-04)
  ├─ if runtime failure: ACCEPTED remains durable; failure separate
  └─ governed apply (RDP-03/04) → APPLIED only on verified effects

DUPLICATE / EXPIRED / REJECTED
  → terminal at F8 layer, with zero ordinary Runtime effects

VALIDATING + unavailable evidence
  → deferred (operational, not fifth verdict)
  → retry same canonical event against refreshed authoritative evidence
```

- `APPLIED` is a subsequent **execution/effect lifecycle milestone** associated with originally ACCEPTED event, not an additional business verdict. No `DUPLICATE` → `APPLIED` transition.
- `ACCEPTED` never silently changes to `REJECTED` because P02 fails or U02 later fails.
- Old ACCEPTED does not permit effects to continue after a newer U15 terminal change; recovery must re-evaluate permission for side effects without altering historical verdict. No fake APPLIED based solely on rehydration.
- An F8 decision once durable is immutable. Any later correction requires an explicitly versioned governed correction/reversal event and provenance, not overwrite of old verdict.

## 8. Durable identity, arbitration and physical design

### 8.1 F8DecisionLedgerV1 (proposed)

Logical persisted fields:
```text
decision_id = stable hash("u07-f8-decision-v1", canonical_answer_event_id, decision_contract_version)
canonical_answer_event_id UNIQUE
consultation_id, question_id, parent_delivered_wait_effect_id
decision_input_fingerprint
business_verdict
reason_code
duplicate_of_event_id?
original_applied_winner_ref?
snapshot_evidence_ref / snapshot_versions
decision_policy_version
decision_status = VALIDATING | FINAL
decided_at
trace_ref
```

**Selected V1 physical design**: dedicated U07 F8 decision table in the **same relational DB** as the RDP-01 synthetic canonical event/answer binding and relevant governed coordination facts, or fail closed if a single transaction owner/locking primitive cannot be established. Do not reuse Foundation CanonicalBusinessEventRecord for F8 verdict and do not treat generic CanonicalEffectLedger as validated F8 decision persistence without RDP-05 compatibility evidence.

Uniqueness:
- PK `decision_id`, UNIQUE `canonical_answer_event_id`; exactly one F8 decision per canonical answer.
- To prevent two independent ACCEPTED winners, a separate `F8WaitAnswerAuthority` row keyed by `(consultation_id, question_id, parent_delivered_wait_effect_id)` records `winner_canonical_event_id`, `winner_decision_id`, `winner_state`, `authority_row_version`. Row must be serialized/locked with the relevant governed wait state and terminalization fencing, or must rely on a reviewed equivalent CAS/unique winning claim shared with RDP-03. **F8 is allowed to select the business winner; it does not write Clinical State or claim APPLIED.**
- A pending winner remains authoritative pending successful or governed terminal reconciliation; new event cannot declare a second winner merely because original Runtime is slow/unavailable. A rollback/discard of an ACCEPTED winner is never inferred; explicit U14/U15/P01 authority required.
- Unique constraints + optimistic CAS/serialized lock prevent two F8 winners at the same wait; the real DB adapter/locking/fencing design must be jointly reviewed in RDP-03 and RDP-05 before implementation.
- F8 decision plus winning claim must be durably atomic for ACCEPTED; non-ACCEPTED decisions must be individually idempotent with decision-key uniqueness; never publish ACCEPTED before claim durability.

### 8.2 Two-phase evaluation/commit protocol

```text
read RDP-01 immutable canonical event binding
  + read authoritative owner state + prior applied answer effects
  + read authoritative U15 terminal/expiry
→ calculate candidate verdict with §5 precedence
→ acquire exclusive same-wait decision authority / versioned CAS
→ re-read versions / expiry / winner under fenced authority
→ persist F8 decision and winner atomically, or return deferred/conflict
→ commit
→ downstream P02 permitted only if decision persisted ACCEPTED and
   CURRENT governance barrier independently passes
```

If primary state and F8 decision live in different stores, this physical design is not applicable without independently accepted reconciliation and fencing design. No stale snapshot can win a race.

### 8.3 Crash windows

| Crash window | Recovery | Guarantee |
|---|---|---|
| After RDP-01 canonical commit before F8 starts | reattach canonical event; evaluate once | no second identity |
| After owner state read before decision lock | re-read/fence; if changed defer/recompute | no stale ACCEPTED |
| After decision winner claim prepared but before transaction commit | entire claim/decision rollback | no phantom winner |
| After decision commit before reply | retrieve same immutable decision | no second decision |
| After ACCEPTED before P02 rehydrate | retain ACCEPTED, reconcile downstream | no fake business REJECTED |
| After P02 fail or checkpoint lost | preserve ACCEPTED; RDP-04/U14 handles repair/failure | no new F8 verdict |
| After APPLIED before U02 handoff | RDP-03/04 repair exactly one downstream effect | F8 never repeats answer application |
| Unknown commit outcome | re-read by unique canonical event & wait key in new transaction | do not optimistically ACCEPTED |
