# AIdoctor V1 系统级状态主干

> 文档状态：DRAFT FOR FREEZE  
> 所属阶段：复杂业务软件开发 SOP — Phase 3 系统级状态主干  
> 上游权威：`01_需求/需求与系统边界_V1.md`、`02_功能/功能模块划分_V1.md`  
> 本文只定义系统级状态对象、一级状态语义、状态关系和全局约束；不定义模块内部细状态、API、数据库表、开发单元或具体框架实现。

---

## 1. Phase 3 要解决的问题

AIdoctor 不能继续用一个模糊的 `completed / not completed` 或一个大 JSON 中的若干字段，混合表达：

- 一次问诊是否仍有效；
- 当前是否正在执行；
- 是否正在等待用户；
- 当前安全判断是什么；
- 信息是否足够；
- 是否已经形成可交付结果；
- 是否因失败而停止。

因此 V1 的系统级状态采用：

```text
一个业务主生命周期
+
三个正交系统状态维度
+
一个版本化临床事实聚合
+
一个独立执行恢复对象
```

具体为：

```text
Consultation Lifecycle       一次问诊在业务上是否仍成立
Safety Disposition           当前是否允许继续普通临床流程
Clinical Readiness           当前信息是否允许继续问、分析或结束
Delivery Readiness           当前结果是否允许正式交付
Clinical State / CDP         当前版本化临床事实与推理产物
Execution Thread             Runtime 执行、暂停、恢复、重试
```

核心原则：这些状态互相关联，但不能互相替代。

# 2. 系统级核心对象

## 2.1 Consultation：业务生命周期主对象

`Consultation` 表示一次完整的智能问诊业务事件。

它回答：

> 这次问诊在业务上处于什么生命周期阶段？

它不是聊天窗口，不等于 HTTP Session，也不等于一次 Runtime Run。

V1 原则：

```text
一个独立健康问题
→ 一个 Consultation
→ 一个当前 Clinical State / CDP
→ 一个主要 Execution Thread
→ 多个 Turn
→ 多个 Run
→ 多个 Clinical State Version
```

如果用户提出明显独立的新主诉，原则上创建新的 Consultation，而不是无限累积进旧 Consultation。

---

## 2.2 Clinical State / CDP：临床事实聚合

CDP 延续旧设计中最有价值的定位：

> 本次 Consultation 的版本化临床事实与临床推理聚合视图。

但 V1 不再允许“所有工具自由读写整个 CDP”。

CDP 负责承载或引用：

- 当前患者事实；
- 事实来源与确定性；
- 当前信息缺口；
- 当前风险判断；
- 当前疾病方向与 Must-Exclude 状态；
- 当前支持/反对/未知证据；
- 检查或进一步信息建议；
- 当前不确定性；
- 当前可交付结果引用；
- 使用的知识、规则、模型和能力版本引用。

CDP 必须版本化。上游事实变化时，不允许静默覆盖旧结果，而应产生新版本并使依赖结果失效或重新计算。

---

## 2.3 Execution Thread：执行恢复对象

Execution Thread 负责回答：

> Runtime 执行到哪里？为什么暂停？如何安全恢复？

它不保存临床真值。

V1 必须明确：

```text
Clinical State / CDP
!=
Execution Checkpoint
```

Checkpoint 可以缓存执行上下文，但恢复时必须重新验证当前 CDP 版本，不能假设旧 checkpoint 中的临床快照仍然有效。

# 3. Consultation Lifecycle — 业务主状态

建议 V1 采用以下一级生命周期：

```text
CREATED
ACTIVE
WAITING_USER
SAFETY_ESCALATED
COMPLETED
SAFE_EXIT
CANCELLED
EXPIRED
FAILED_TERMINAL
```

## 3.1 CREATED

含义：

- Consultation 已创建；
- 问诊对象和基础上下文已经建立或正在建立；
- 尚未进入稳定的多轮问诊推进。

允许：

- 接收首条用户输入；
- 确认患者主体；
- 做入口澄清；
- 建立初始 CDP。

禁止：

- 在临床事实尚未建立前直接宣告正式疾病方向。

---

## 3.2 ACTIVE

含义：

> 当前问诊可继续进行，系统可以进行信息理解、风险判断、主动问诊、鉴别分析、证据评估或结果准备。

`ACTIVE` 不等于“Runtime 正在运行”。

例如用户刚提交答案、Runtime 尚未获得执行租约时，Consultation 仍可以是 ACTIVE。

因此：

```text
Consultation ACTIVE
!=
Thread RUNNING
```

---

## 3.3 WAITING_USER

含义：

- 当前继续问诊所需的下一关键事件是用户回答；
- 系统已经产生合法的问题或澄清请求；
- 当前执行应暂停，而不是持续轮询或继续猜测。

必须关联：

- 当前等待的问题/请求；
- 对应的 Clinical State Version；
- 可接受的回答范围或事件类型；
- 过期策略；
- 幂等标识或 Resume 语义。

用户关闭页面不改变业务语义：Consultation 仍然可以保持 WAITING_USER。

---

## 3.4 SAFETY_ESCALATED

含义：

> 当前存在已经识别的高风险/红旗情况，普通问诊推进受到 Safety Policy 限制。

它不是“诊断完成”。

进入后必须：

- 保留风险依据；
- 给出相应安全/就医引导；
- 阻止普通 Planner 把风险状态静默降级；
- 只允许执行不会延误安全处置的必要动作。

V1 不要求完整医生 HITL，因此 SAFETY_ESCALATED 的合法后继主要是：

```text
SAFE_EXIT
或
COMPLETED（仅当已完成符合边界的安全交付）
```

未来可扩展 `WAITING_CLINICIAN / UNDER_REVIEW`，但不作为 V1 正式状态。

---

## 3.5 COMPLETED

含义：

> 本次 Consultation 已满足 V1 的正常终止条件，并成功形成符合产品边界、证据要求和安全要求的正式交付结果。

`COMPLETED` 必须表示“业务完成”，而不是“代码跑到了最后一步”。

至少要求：

- 不存在阻断交付的 Safety Failure；
- 输出未越过确诊/处方/治疗边界；
- 关键疾病方向有可追溯依据，或系统明确交付了证据不足/范围外等合法结果；
- 关键不确定性没有被伪装成阴性或正常；
- Delivery 已通过必要验证。

因此：

```text
workflow reached end
!=
COMPLETED
```

---

## 3.6 SAFE_EXIT

含义：

> 系统主动结束本次线上自动问诊，因为继续推进不再安全、可靠或处于当前支持范围内，但已经向用户提供了符合边界的安全解释和下一步指引。

典型原因：

- 超出 Clinical Capability Scope；
- 必要安全能力不可用；
- 关键输入无法可靠确认；
- 证据不足且无法继续线上获得；
- 当前场景需要线下进一步评估。

SAFE_EXIT 不是系统错误，也不等同 FAILED_TERMINAL。

---

## 3.7 CANCELLED

含义：

- 用户或授权业务方明确取消本次问诊；
- 不再接受普通 Resume；
- 不允许继续产生新的临床副作用。

---

## 3.8 EXPIRED

含义：

- Consultation 因超过既定生命周期或等待有效期而关闭；
- 旧回答不能再直接写入当前临床状态；
- 用户若继续咨询，应创建新 Consultation 或经过明确恢复策略。

具体时长不是 Phase 3 决定内容。

---

## 3.9 FAILED_TERMINAL

含义：

> 因系统级不可恢复故障，本次 Consultation 无法继续，也无法形成完整合法的正常交付。

必须记录：

- failure reason；
- 最后已确认 Clinical State Version；
- 是否已经向用户提供安全降级提示；
- 是否允许重新发起新 Consultation。

FAILED_TERMINAL 不允许伪装为 COMPLETED。

# 4. Consultation 主状态转换

V1 一级主干：

```text
                 ┌───────────────┐
                 │    CREATED    │
                 └───────┬───────┘
                         │
                         ▼
                 ┌───────────────┐
          ┌─────▶│     ACTIVE    │◀─────┐
          │      └───┬─────┬─────┘      │
          │          │     │            │
          │          │     │            │ user answer / valid resume
          │          │     ▼            │
          │          │  WAITING_USER ───┘
          │          │
          │          ▼
          │   SAFETY_ESCALATED
          │          │
          │          ├──────────▶ SAFE_EXIT
          │          └──────────▶ COMPLETED
          │
          ├─────────────────────▶ COMPLETED
          ├─────────────────────▶ SAFE_EXIT
          ├─────────────────────▶ CANCELLED
          ├─────────────────────▶ EXPIRED
          └─────────────────────▶ FAILED_TERMINAL
```

通用终止约束：

```text
COMPLETED
SAFE_EXIT
CANCELLED
EXPIRED
FAILED_TERMINAL
```

均为 V1 终止态。

终止态默认禁止普通 Resume。

# 5. Safety Disposition — 安全状态维度

Safety 不应该仅是一个模块输出字段，而应成为贯穿 Consultation 的系统级正交状态。

建议一级语义：

```text
NOT_EVALUATED
CLEAR_FOR_CONTINUATION
CAUTION
HIGH_RISK
SAFETY_BLOCKED
SAFETY_UNAVAILABLE
```

说明：

- `NOT_EVALUATED`：当前版本尚未形成所需安全判断；
- `CLEAR_FOR_CONTINUATION`：在当前已知信息下没有触发阻断普通流程的条件，不代表“患者安全/无病”；
- `CAUTION`：存在需要持续关注但尚未触发强制中止的风险；
- `HIGH_RISK`：命中需要优先安全处置的高风险条件；
- `SAFETY_BLOCKED`：根据安全策略明确禁止继续普通临床路径；
- `SAFETY_UNAVAILABLE`：必要安全能力无法可靠执行。

全局约束：

```text
SAFETY_UNAVAILABLE
!= CLEAR_FOR_CONTINUATION

HIGH_RISK / SAFETY_BLOCKED
→ 普通疾病分析不得覆盖其优先级
```

`Safety Disposition` 的详细判定规则留到 Phase 4 和 Capability 设计。

---

# 6. Clinical Readiness — 临床推进状态维度

它回答：

> 根据当前临床事实，下一步在业务上允许做什么？

建议一级语义：

```text
NEEDS_CLARIFICATION
CAN_ASK_MORE
READY_FOR_CLINICAL_ANALYSIS
NEEDS_OFFLINE_EVIDENCE
OUT_OF_SCOPE
NO_RELIABLE_DIRECTION
```

说明：

### NEEDS_CLARIFICATION
当前问题主体、主诉或关键表达尚不明确，必须先澄清。

### CAN_ASK_MORE
存在可在线获得且具有临床价值的关键缺口，应继续主动问诊。

### READY_FOR_CLINICAL_ANALYSIS
当前证据达到进入疾病方向/鉴别分析的最低业务条件。

注意：

```text
READY_FOR_CLINICAL_ANALYSIS
!= READY_TO_COMPLETE
```

分析后仍可能产生新的信息缺口并回到 `CAN_ASK_MORE`。

### NEEDS_OFFLINE_EVIDENCE
关键缺口已经无法通过当前线上问诊获取，需要线下检查、测量或专业评估。

### OUT_OF_SCOPE
当前问题不属于已版本化的 Clinical Capability Scope。

### NO_RELIABLE_DIRECTION
当前已经无法获得更多必要线上信息，但现有证据又不足以形成可靠疾病方向。

此状态必须允许合法 Safe Exit，而不是强行产生 DDx。

---

# 7. Delivery Readiness — 交付状态维度

系统必须区分“已经有一些临床结果”和“可以正式展示给用户”。

建议一级语义：

```text
NOT_READY
DRAFTING
VALIDATION_REQUIRED
READY
BLOCKED
DELIVERED
```

说明：

- `NOT_READY`：当前尚不具备形成完整输出的条件；
- `DRAFTING`：正在整合结果；
- `VALIDATION_REQUIRED`：已有候选输出，但尚需安全/证据/边界验证；
- `READY`：已满足交付要求；
- `BLOCKED`：由于安全、证据、范围、失败等原因禁止正常交付；
- `DELIVERED`：已形成并交付正式结果包。

关键约束：

```text
Consultation COMPLETED
→ Delivery Readiness 必须已经达到 DELIVERED
```

但：

```text
Delivery BLOCKED
→ Consultation 不得进入 COMPLETED
```

---

# 8. Execution Thread — Runtime 执行状态

V1 只冻结执行状态的一级语义，不冻结具体框架。

建议：

```text
CREATED
RUNNING
AWAITING_USER
RETRY_SCHEDULED
SUSPENDED
DEGRADED
COMPLETED
CANCELLED
EXPIRED
FAILED_TERMINAL
```

其中：

- Thread `AWAITING_USER` 必须对应 Consultation `WAITING_USER`；
- Thread `RUNNING` 不改变 Consultation 是否 ACTIVE；
- Thread `FAILED_TERMINAL` 不必然立刻等于 Consultation `FAILED_TERMINAL`，如果存在安全降级或可重建执行上下文，业务层仍可选择恢复或 Safe Exit；
- Thread `COMPLETED` 只代表当前执行线程结束，不自动证明 Consultation 业务完成。

V1 不包含正式 `AWAITING_CLINICIAN`，但枚举空间必须允许未来扩展。

---

# 9. Run 与 Checkpoint

一个 Thread 可以有多个 Run。

Run 表示：

> 从一次开始/恢复，到下一次暂停、等待或结束的一段实际执行。

Checkpoint 表示：

> 某个可验证的执行恢复点。

关系：

```text
Consultation
  └─ Thread
      ├─ Run 1
      │   ├─ Checkpoint 1
      │   └─ Checkpoint 2
      ├─ Run 2
      │   └─ Checkpoint 3
      └─ ...

Consultation
  └─ CDP v1 → v2 → v3 → ...
```

Checkpoint 与 CDP Version 必须建立引用关系，但不能成为 CDP 的替代物。

Resume 时至少需要验证：

- Consultation 是否仍允许恢复；
- Thread 是否仍有效；
- Resume Event 是否重复/过期；
- Checkpoint 是否与当前 Runtime 兼容；
- 关联 CDP Version 是否仍是可接受基线；
- 当前 Safety/Capability/Consent 等关键约束是否仍然成立。

Consent 的具体产品范围以后续安全与权限设计为准，Phase 3 不展开。

---

# 10. Clinical State Version 与失效传播

V1 必须把临床状态视为版本化状态，而不是一个可随意覆盖的 Map。

基本规则：

```text
用户新回答 / 更正
→ 形成 Patient Fact Change
→ 生成新的 Clinical State Version
→ 标记依赖旧事实的结果可能失效
→ 必要时重新 Safety
→ 必要时重新 Information Gap
→ 必要时重新 DDx / Must-Exclude
→ 必要时重新 Delivery
```

因此必须建立“依赖结果失效”概念。

Phase 3 不规定具体 DAG 或字段级 dependency graph，但冻结如下原则：

```text
上游事实改变
!= 仅覆盖文本

上游事实改变
→ 下游派生结果必须可失效 / 重算 / 重新审核
```

---

# 11. Must-Exclude 状态不是 Consultation 状态

疾病方向中的 Must-Exclude 应保留自己的临床状态，例如：

```text
UNASSESSED
NOT_EXCLUDED
EXCLUDED
NEEDS_OFFLINE_EXCLUSION
```

但它属于 F5 内部临床状态，不进入 Phase 3 的 Consultation 一级生命周期。

原因：一个 Consultation 可以同时存在多个 Must-Exclude 候选，它们不能被压缩成一个全局主状态。

该部分留到 Phase 4 模块级状态设计。

---

# 12. Information Gap 状态不是 Consultation 状态

同理，单个信息缺口可以存在：

- 是否阻断；
- 是否可在线获取；
- 是否已经询问；
- 是否用户未知；
- 是否需要线下获得；
- 是否已经失效。

这些是 F3/F6 模块级状态。

Phase 3 只通过 `Clinical Readiness` 表达其对系统主流程的综合影响。

---

# 13. 为什么不采用“固定五步 current_step”作为系统状态

旧 AgentState 使用 `current_step = 1..5` 表示诊断步骤。

V1 不把它作为系统主状态，原因是：

1. 新证据可以要求回退或重新分析；
2. Safety 可以在任意轮触发；
3. 主动问诊和鉴别分析可能循环；
4. 用户更正会让旧结果失效；
5. `Step 5 reached` 不等于业务完成。

因此：

```text
固定步骤
可以成为某种 Workflow 实现
但不能成为系统唯一状态真值
```

---

# 14. 为什么不让 AgentState 成为第二套系统状态

旧 AgentState 中有价值的部分继续保留，但必须重新归属：

```text
budget
retry/backoff
tried actions/tools
runtime stop guard
```

属于：

> Execution / Runtime State

而：

```text
patient facts
risk
DDx
Evidence
information gaps
```

属于：

> Clinical State / CDP

因此目标设计中不允许：

```text
CDP.work_mode
AgentState.work_mode
Frontend.work_mode
Dialog.work_mode
```

多个所有者同时解释同一个业务事实。

---

# 15. 系统级状态组合规则

几个典型合法组合：

### 正常追问

```text
Consultation = WAITING_USER
Safety = CLEAR_FOR_CONTINUATION / CAUTION
ClinicalReadiness = CAN_ASK_MORE
Delivery = NOT_READY
Thread = AWAITING_USER
```

### 可以进入疾病方向分析

```text
Consultation = ACTIVE
Safety = CLEAR_FOR_CONTINUATION / CAUTION
ClinicalReadiness = READY_FOR_CLINICAL_ANALYSIS
Delivery = NOT_READY
Thread = RUNNING / CREATED
```

### 高风险安全退出

```text
Consultation = SAFETY_ESCALATED
Safety = HIGH_RISK / SAFETY_BLOCKED
ClinicalReadiness = 任意非优先状态
Delivery = VALIDATION_REQUIRED / READY
```

完成安全交付后：

```text
Consultation = SAFE_EXIT 或 COMPLETED
Delivery = DELIVERED
```

### 安全能力故障

```text
Safety = SAFETY_UNAVAILABLE
→ 普通临床推进禁止
→ Delivery 不能进入普通 READY
→ Consultation 应进入安全降级决策
```

### 当前范围外

```text
Consultation = ACTIVE
ClinicalReadiness = OUT_OF_SCOPE
→ 形成边界说明和就医指引
→ Delivery READY
→ Consultation SAFE_EXIT
```

# 16. V1 全局状态不变量

## STATE-INV-01

```text
COMPLETED
!= workflow reached end
```

## STATE-INV-02

```text
Clinical State / CDP
!= Runtime Checkpoint
```

## STATE-INV-03

```text
Thread RUNNING
!= Consultation ACTIVE 的唯一条件
```

## STATE-INV-04

```text
UNKNOWN / UNMEASURED
不得通过状态转换自动变成 NEGATIVE / NORMAL
```

## STATE-INV-05

```text
SAFETY_UNAVAILABLE
不得进入 CLEAR_FOR_CONTINUATION
```

## STATE-INV-06

```text
HIGH_RISK / SAFETY_BLOCKED
优先级高于普通鉴别分析推进
```

## STATE-INV-07

```text
Terminal Consultation
不得普通 Resume
```

## STATE-INV-08

```text
相同业务事件重复到达
不得产生重复临床效果
```

## STATE-INV-09

```text
Upstream Fact Changed
→ Dependent Derived State must be invalidatable
```

# 19. 从历史设计正式继承什么

## 保留

- CDP 作为病例临床聚合视图；
- CDP 版本化和历史不可变思想；
- Copy-on-Write / 可回放思想；
- 工具不应直接修改临床事实；
- AgentState 中预算、重试、尝试、停止保护思想；
- Durable Execution 中 Thread / Run / Checkpoint / Resume / Idempotency 的分离；
- Checkpoint 与临床状态分离；
- 中断恢复、重复提交、服务故障恢复思想。

## 不原样继承

- `current_step = 1..5` 作为系统主状态；
- AgentState 作为第二套临床状态；
- Redis 作为唯一恢复事实源；
- `completed` 表示“流程代码已经跑到底”；
- 工具/Agent 直接决定 CDP 写入；
- 健康管理态作为 V1 核心状态；
- V1 正式 `AWAITING_CLINICIAN`；
- Treatment/Medication 生命周期进入 V1 主状态。

# 20. Phase 3 完成标准

Phase 3 应能够回答：

> 系统从一次问诊开始到结束，最关键的一级业务状态是什么？临床真值、执行状态、安全状态、信息充分性和交付状态分别由什么对象表达？

当前设计回答为：

```text
业务生命周期：Consultation Lifecycle
临床事实真值：Versioned Clinical State / CDP
执行恢复状态：Execution Thread / Run / Checkpoint
安全状态：Safety Disposition
临床推进条件：Clinical Readiness
正式输出条件：Delivery Readiness
```

它们构成 V1 的系统级状态主干。

当前状态：

```text
Phase 3 System-Level State Backbone
= DRAFT COMPLETE / NOT FROZEN
```

冻结前应检查：

1. 一级状态是否覆盖所有 V1 核心生命周期；
2. 是否存在两个状态对象竞争同一事实所有权；
3. 是否仍有 Failure → Normal 的隐式路径；
4. 是否能够表达用户等待、恢复、更正和终止；
5. 是否为 Phase 4 模块级状态留下空间而没有提前设计过细。
