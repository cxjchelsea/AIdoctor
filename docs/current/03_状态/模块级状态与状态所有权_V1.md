## 1. Phase 4 目标

Phase 3 已冻结系统级主干：

```text
Consultation Lifecycle
Clinical Risk Disposition
Safety Gate
Clinical Readiness
Delivery Readiness
Versioned Clinical State / CDP
Execution Thread / Run / Checkpoint
```

Phase 4 进一步回答：

1. F1-F8 各自需要维护什么业务状态；
2. 哪个模块是这些状态的唯一业务 Owner；
3. 哪些模块只能提出结果，不能直接改写其他模块状态；
4. 某个模块内部状态变化时，哪些系统级状态可能需要重新评估；
5. 用户更正、新证据和失败如何使下游派生状态失效。

核心原则：

```text
模块拥有自己的业务判断
!=
模块可以任意写整个 Clinical State
```

所有正式临床状态更新仍必须经过 G2 临床状态治理。

## 2. 状态所有权总原则

### OWN-01 单一语义单一 Owner

同一个业务事实只能有一个最终解释 Owner。

例如：

```text
“当前患者是否高风险” → F4
“当前是否还需要追问” → F3
“当前疾病方向集合是什么” → F5
“当前结果是否允许正式交付” → F7 + Delivery Gate
```

其他模块可以提供证据或建议，但不能并行维护另一套同义状态。

### OWN-02 Capability 输出不是最终状态

Capability / Tool / Model 只能返回结构化结果或状态变更建议。

```text
Capability Result
→ 业务模块解释
→ G2 State Governance 验证
→ Clinical State Version
```

### OWN-03 Frontend 不拥有临床状态

前端可以拥有 UI State，但不得拥有：

- Risk；
- DDx；
- Must-Exclude；
- Clinical Readiness；
- Delivery clinical semantics。

### OWN-04 Runtime 不拥有临床状态

Thread/Checkpoint 只拥有执行恢复状态，不拥有患者事实、风险、DDx 或证据真值。

### OWN-05 派生状态必须可失效

上游事实变化后，依赖旧事实的模块状态不能静默继续有效。

# 3. F1 问诊建立与对象确认

## 3.1 F1 Owner

F1 拥有：

> 当前 Consultation 是否已经建立了明确的问诊对象和当前健康问题上下文。

## 3.2 F1 内部状态

### Subject Resolution

```text
UNRESOLVED
RESOLVING
RESOLVED
INVALID
```

- `UNRESOLVED`：尚未确认问诊对象；
- `RESOLVING`：正在确认本人/代他人及必要基础信息；
- `RESOLVED`：问诊对象已满足当前 V1 要求；
- `INVALID`：对象信息冲突或无法建立可靠主体。

### Problem Framing

```text
UNFRAMED
CLARIFICATION_REQUIRED
FRAMED
OUTSIDE_V1_INTENT
```

- `UNFRAMED`：当前健康问题尚未形成稳定上下文；
- `CLARIFICATION_REQUIRED`：模糊/混合诉求需要最小澄清；
- `FRAMED`：当前主要健康问题已明确；
- `OUTSIDE_V1_INTENT`：确认后属于当前 V1 非目标，例如纯健康管理诉求。

## 3.3 F1 对系统级状态影响

```text
Subject UNRESOLVED / Problem CLARIFICATION_REQUIRED
→ Clinical Readiness = NEEDS_CLARIFICATION

Subject RESOLVED + Problem FRAMED
→ Consultation 可由 CREATED 进入 ACTIVE

Subject INVALID
→ Safety/Boundary Decision
→ SAFE_EXIT 或 FAILED_TERMINAL（视原因）

Problem OUTSIDE_V1_INTENT
→ Clinical Readiness = OUT_OF_SCOPE
```

## 3.4 不拥有

F1 不拥有 Risk、DDx、问诊充分性或最终 Delivery。

# 4. F2 临床信息理解与病例采集

## 4.1 F2 Owner

F2 拥有：

> 输入信息被解析后形成的“候选临床观察”，以及这些观察被确认成何种患者事实语义。

## 4.2 Clinical Observation 状态

单条临床观察建议具备：

```text
EXTRACTED
NORMALIZED
CONFIRMED
UNCERTAIN
CONTRADICTED
INVALIDATED
```

- `EXTRACTED`：从用户输入/报告等提取出候选观察；
- `NORMALIZED`：已映射为系统支持的医学概念；
- `CONFIRMED`：达到当前来源类型要求，可进入 Clinical State；
- `UNCERTAIN`：存在歧义、来源不可靠或用户表达不确定；
- `CONTRADICTED`：与当前有效事实发生冲突，等待处理；
- `INVALIDATED`：因用户更正或来源撤销而失效。

注意：`CONFIRMED` 表示“确认这条信息是当前有效输入事实”，不表示医学上证实疾病。

## 4.3 Fact Value Semantics

F2 必须维护而不能混淆：

```text
YES
NO
UNKNOWN
UNMEASURED
NOT_ASKED
NOT_APPLICABLE
```

这些是事实值语义，不是 Observation lifecycle。

## 4.4 Source / Confidence

每条事实必须关联来源身份，例如：

```text
PATIENT_REPORTED
EXTERNAL_MEASUREMENT
OCR_EXTRACTED
MODEL_INFERRED
RULE_DERIVED
CLINICIAN_CONFIRMED   # future-compatible
```

F2 负责来源解释，但医学文献 Citation 由 G6 治理。

## 4.5 对系统级状态影响

新 `CONFIRMED` 或 `INVALIDATED` 事实形成新的 Clinical State Version，并可能触发：

```text
F3 重新评估 Gap/Readiness
F4 重新评估 Risk
F5 使旧 DDx / Must-Exclude 失效或重算
F6 使旧 Evidence Gap / Workup 建议失效或重算
F7 使未交付或旧 Delivery 失效
```

# 5. F3 主动问诊与信息充分性管理

## 5.1 F3 Owner

F3 拥有：

> 当前还缺什么信息、缺失对决策有什么影响、是否值得继续在线询问，以及下一问是否已经形成。

## 5.2 Information Gap 状态

单个 Gap 生命周期：

```text
IDENTIFIED
QUESTIONABLE_ONLINE
ASKED
ANSWERED
USER_UNKNOWN
UNMEASURED
OFFLINE_REQUIRED
WAIVED
RESOLVED
INVALIDATED
```

解释：

- `IDENTIFIED`：发现缺口；
- `QUESTIONABLE_ONLINE`：可通过线上追问获得；
- `ASKED`：已向用户提出；
- `ANSWERED`：已收到可处理回答，等待/完成事实更新；
- `USER_UNKNOWN`：用户明确不知道；
- `UNMEASURED`：该信息尚未测量；
- `OFFLINE_REQUIRED`：必须依赖线下测量/检查/专业评估；
- `WAIVED`：经规则判断当前不再阻断，可暂不获取；
- `RESOLVED`：已获得满足当前决策需要的信息；
- `INVALIDATED`：因候选/问题变化，该 Gap 不再适用。

## 5.3 Gap Decision Impact

每个 Gap 还必须有独立影响等级，概念上至少区分：

```text
BLOCKING
UNCERTAINTY_INCREASING
DEFERABLE
OFFLINE_ONLY
```

不强制沿用旧“必填/重要/可选”字段名。

## 5.4 Question 状态

```text
PROPOSED
SELECTED
DELIVERED_TO_USER
ANSWER_RECEIVED
EXPIRED
SUPERSEDED
```

F3 负责问题业务生命周期；Thread 只负责等待和 Resume。

## 5.5 对系统级状态影响

```text
存在可在线获取的 BLOCKING / 高价值 Gap
→ Clinical Readiness = CAN_ASK_MORE

Question DELIVERED_TO_USER
→ Consultation = WAITING_USER
→ Thread = AWAITING_USER

仅剩 OFFLINE_REQUIRED 的关键 Gap
→ Clinical Readiness = NEEDS_OFFLINE_EVIDENCE
```

# 6. F4 医疗风险识别与安全分流

## 6.1 F4 Owner

F4 是 `Clinical Risk Disposition` 的唯一临床业务 Owner。

F4 不直接拥有 `Safety Gate`；Safety Gate 由 F4 风险结果 + G4 Policy/Capability 可用性共同决定。

## 6.2 Risk Assessment 生命周期

```text
NOT_ASSESSED
ASSESSING
VALID
STALE
FAILED
```

- `VALID`：针对当前 Clinical State Version 已形成有效风险判断；
- `STALE`：新事实到达，旧风险判断不能继续作为当前判断；
- `FAILED`：风险评估未能可靠完成，不能投射为低风险。

## 6.3 Risk Disposition

F4 正式输出系统级：

```text
NOT_EVALUATED
NO_HIGH_RISK_SIGNAL
CAUTION
HIGH_RISK
```

## 6.4 Red Flag 状态

单条 Red Flag / High-risk condition 可表达：

```text
NOT_EVALUATED
NOT_TRIGGERED
TRIGGERED
UNCERTAIN
INVALIDATED
```

## 6.5 对 Safety Gate 的影响

F4 提供 Risk Result，但不能单独越权修改系统权限。

最小规则：

```text
Risk HIGH_RISK
→ G4 必须将 Safety Gate 评估为 RESTRICTED/BLOCKED

Risk Assessment FAILED
→ G4 不得产生 ALLOW
```

# 7. F5 疾病方向、鉴别与必须排除项管理

## 7.1 F5 Owner

F5 拥有：

- 当前疾病方向候选集合；
- 候选层级/排序；
- Must-Exclude 集合及排除状态；
- 候选与患者证据的业务关联；
- 当前是否能够形成可靠方向。

## 7.2 Candidate 生命周期

```text
PROPOSED
ACTIVE
SUPPORTED
WEAKENED
EXCLUDED
INVALIDATED
```

这里不是概率阈值定义，而是候选在当前 Clinical State Version 中的业务生命周期。

## 7.3 Candidate Tier

候选层级与生命周期分离。概念上可表达：

```text
LIKELY
ACTIVE_ALTERNATIVE
MUST_EXCLUDE
```

历史 Tier1/Tier2/Tier3 可作为映射参考，但 V1 不在 Phase 4 冻结旧编号含义。

## 7.4 Must-Exclude 状态

```text
UNASSESSED
NOT_EXCLUDED
EXCLUDED
NEEDS_OFFLINE_EXCLUSION
INVALIDATED
```

关键约束：

```text
UNKNOWN / INSUFFICIENT_EVIDENCE
!= EXCLUDED
```

`NEEDS_OFFLINE_EXCLUSION` 表示当前线上系统无法完成可靠排除。

## 7.5 DDx Assessment 生命周期

```text
NOT_READY
ASSESSING
VALID
STALE
NO_RELIABLE_DIRECTION
FAILED
```

- `STALE`：新事实/更正导致现有 DDx 不再可作为当前结果；
- `FAILED`：能力失败，不等于 `NO_RELIABLE_DIRECTION`；
- `NO_RELIABLE_DIRECTION`：能力正常工作，但现有证据无法形成可靠方向。

这一分离是强制语义。

## 7.6 对系统级状态影响

```text
DDx VALID
→ 可继续 F6/F7

DDx NO_RELIABLE_DIRECTION 且无更多线上 Gap
→ Clinical Readiness = NO_RELIABLE_DIRECTION

Must-Exclude 存在 NOT_EXCLUDED 且仅能线下排除
→ Clinical Readiness 可进入 NEEDS_OFFLINE_EVIDENCE
```

# 8. F6 证据缺口与进一步检查建议

## 8.1 F6 Owner

F6 拥有：

> 哪些剩余证据必须通过线下信息/测量/检查补充，以及当前进一步检查建议的业务状态。

F6 不拥有检查执行结果，也不拥有跨天外部检查 Resume。

## 8.2 Offline Evidence Need 状态

```text
IDENTIFIED
JUSTIFIED
NOT_NEEDED
SUPERSEDED
INVALIDATED
```

`JUSTIFIED` 表示该线下证据需求已有正式知识/规则或候选鉴别依据。

## 8.3 Examination Suggestion 状态

```text
PROPOSED
VALIDATED
REJECTED_BY_POLICY
SUPERSEDED
DELIVERABLE
```

- `VALIDATED`：临床依据和适用范围成立；
- `REJECTED_BY_POLICY`：因越界、风险或缺乏授权不能输出；
- `DELIVERABLE`：可作为患者侧“进一步完善信息建议”进入 F7。

## 8.4 约束

```text
Suggestion
!= Medical Order
```

F6 不创建检查订单、不预约、不把建议解释为必须执行的医嘱。

# 9. F7 问诊结果整合与用户解释

## 9.1 F7 Owner

F7 拥有：

> 当前患者侧 Delivery Package 的业务生成与验证状态。

它不拥有上游临床事实、Risk、DDx 或 Evidence 真值，只引用当前有效版本。

## 9.2 Delivery Package 内部状态

Phase 3 已将系统级 Delivery Readiness 简化为：

```text
NOT_READY
READY
BLOCKED
DELIVERED
```

F7 内部可以进一步拥有：

```text
NOT_STARTED
ASSEMBLING
VALIDATING
VALIDATION_FAILED
VALIDATED
SUPERSEDED
DELIVERED
```

## 9.3 Validation 关注点

正式 Delivery 至少需要验证：

- 当前引用的 Clinical State Version 未过期；
- Safety Gate 允许相应类型交付；
- Risk 与 Must-Exclude 没有被遗漏或降级；
- UNKNOWN/UNMEASURED 未被转成正常；
- 疾病方向未被表达为确诊；
- Treatment/Prescription 未越界；
- 引用的患者证据、规则依据和医学 Citation 语义分离；
- 当前 Scope/Knowledge/Rule/Capability Version 合法。

## 9.4 系统级映射

```text
F7 NOT_STARTED / ASSEMBLING / VALIDATING
→ Delivery Readiness = NOT_READY

F7 VALIDATION_FAILED
→ Delivery Readiness = BLOCKED

F7 VALIDATED
→ Delivery Readiness = READY

F7 DELIVERED
→ Delivery Readiness = DELIVERED
```

若是正常问诊交付完成：

```text
Delivery = DELIVERED
→ Consultation 可进入 COMPLETED
```

若是边界/高风险/线下证据等安全退出交付完成：

```text
Delivery = DELIVERED
→ Consultation 进入 SAFE_EXIT
```

# 10. F8 问诊连续性、更正与恢复

## 10.1 F8 Owner

F8 拥有业务层面的：

- 用户等待请求；
- Resume 请求有效性；
- 用户更正/补充事件；
- 重复/过期事件业务处理；
- 由事实改变触发的下游失效传播协调。

Execution Thread 仍拥有 Runtime checkpoint/run 状态。

## 10.2 Resume Request 状态

```text
RECEIVED
VALIDATING
ACCEPTED
DUPLICATE
EXPIRED
REJECTED
APPLIED
```

`APPLIED` 表示该 Resume 事件已产生一次合法业务效果。

## 10.3 Correction Event 状态

```text
RECEIVED
VALIDATED
APPLIED
REJECTED
SUPERSEDED
```

合法更正被 `APPLIED` 后：

```text
Clinical State Version +1
→ 下游依赖状态进入 STALE / INVALIDATED / SUPERSEDED
→ F3/F4/F5/F6/F7 按依赖重新评估
```

## 10.4 Duplicate / Expiry

```text
Same Business Event
→ at most one clinical effect
```

重复事件可以返回已有结果，但不得再次提交临床状态变化。

过期回答不得直接写进当前 Clinical State。

## 10.5 与 Thread 的边界

```text
F8 = 这个 Resume 在业务上是否有效、应产生什么业务效果
Thread = 从哪个 checkpoint/run 恢复以及怎么执行
```

两者不得合并。

# 11. F1-F8 状态所有权矩阵

| 状态/对象 | 唯一业务 Owner | 可提供输入的其他模块 | 不允许的并行 Owner |
|---|---|---|---|
| Subject Resolution | F1 | Frontend/Auth context | Dialog/Frontend 自建 patient state |
| Problem Framing | F1 | F2/F4 | Frontend work_mode |
| Clinical Observation | F2 | OCR/Model/External source | Model 直接写事实 |
| Information Gap | F3 | F2/F5/F6 | Dialog 自有完整 Clinical Truth |
| Question lifecycle | F3 | Runtime负责等待 | Thread 不定义临床问题语义 |
| Clinical Risk | F4 | F2/F5 evidence | Diagnosis/Frontend 自行决定 Risk |
| Safety Gate | G4（基于 F4 + capability/policy） | F4/G3/G1 | F4 单独越权、Frontend fallback |
| DDx Candidate | F5 | F2/F3/G1/G6 | LLM/Knowledge Retriever 直接定结论 |
| Must-Exclude | F5 | F4/G6 | Workup/Frontend 自行排除 |
| Offline Evidence Need | F6 | F3/F5 | Examination duplicate planner |
| Examination Suggestion | F6 | G1/G6/F5 | LLM 自由推荐 |
| Delivery Package | F7 | F1-F6/G1-G6 | Frontend 拼临床结论 |
| Resume business validity | F8 | Runtime/G4 | Thread 独立改变临床真值 |
| Correction / invalidation coordination | F8 + G2 | F2-F7 | 直接覆盖旧结果 |
| Clinical State Version | G2 | F1-F8 | 任意业务模块直接写版本 |
| Thread/Run/Checkpoint | Runtime | F8/G2 | CDP 替代 checkpoint |

# 12. 跨模块失效传播

Phase 4 冻结依赖方向，不冻结字段级 DAG。

基本传播：

```text
F1 对象/问题框架改变
→ F2-F7 相关派生状态全部需重新判定

F2 患者事实改变
→ F3 Gap
→ F4 Risk
→ F5 DDx/Must-Exclude
→ F6 Offline Evidence/Suggestion
→ F7 Delivery

F3 新问题回答
→ 先进入 F2 形成新事实
→ 再触发下游重新评估

F4 Risk 变化
→ Safety Gate
→ F5/F6 是否允许继续
→ F7 输出类型

F5 DDx/Must-Exclude 变化
→ F3 Gap 可新增/失效
→ F6 建议可新增/失效
→ F7 Delivery 失效

F6 建议变化
→ F7 Delivery 失效/重组

任何 F1-F6 的有效上游状态变化
→ 已生成但未交付的 F7 结果必须至少进入 SUPERSEDED 或重新验证
```

# 13. Failure 与 Business Negative 必须分离

每个核心模块都必须区分：

```text
业务上没有发现结果
vs
能力执行失败
```

例如：

```text
F4 NO_HIGH_RISK_SIGNAL
!= F4 Assessment FAILED

F5 NO_RELIABLE_DIRECTION
!= F5 Assessment FAILED

F6 NOT_NEEDED
!= F6 capability failed
```

这是 Phase 4 全局不变量。

# 14. 与历史设计的继承关系

## 吸收

- 旧临床流程的结构化问题清单、信息缺口、候选分层、支持/反对证据、验证计划和可回退思想；
- 旧 Tool 设计中入口澄清、主动问诊、风险评估、检查建议、Evidence 的职责边界；
- 旧 CDP 的版本化病例聚合思想；
- AgentState 的预算/重试/停止保护转入 Runtime；
- Durable Execution 的 Thread/Checkpoint/Resume 分离。

## 不继承

- tool_0..7 作为状态 Owner 编号体系；
- 固定 Step1..5 作为模块状态机；
- Tool/Agent 直接写完整 CDP；
- treatment/medication 进入 V1；
- wellness_mode 成为 V1 主模块状态；
- failure → empty object → normal business state；
- Frontend 或 Dialog 保存并解释第二套 Clinical Truth。

# 16. Phase 4 完成标准

Phase 4 应能够回答：
