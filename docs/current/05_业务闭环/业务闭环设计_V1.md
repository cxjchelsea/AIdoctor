# AIdoctor V1 业务闭环设计

> 文档状态：FROZEN / V1  
> 所属阶段：复杂业务软件开发 SOP — Phase 5 业务闭环设计  
> 上游权威：`01_需求/需求与系统边界_V1.md`、`02_功能/功能模块划分_V1.md`、`03_状态/系统级状态主干_V1.md`、`03_状态/模块级状态与状态所有权_V1.md`  
> 当前事实依据：`00_现状与治理/Current_State_Baseline_V1.md`、`00_现状与治理/重构决策_V1.md`  
> 本文只定义 V1 业务场景如何从触发走到合法终止，以及每个闭环涉及的业务模块、关键状态变化、失败/退出语义和闭环完成条件；不定义开发单元、API、数据库表、类、微服务、具体 StatePatch Schema 或框架实现。

## 1. Phase 5 目标

Phase 1–4 已经依次回答：

```text
系统解决什么问题
→ 系统提供哪些业务能力
→ 系统有哪些一级状态
→ 各模块内部有哪些状态以及谁拥有
```

Phase 5 进一步回答：

> 对一个真实用户场景，这些模块和状态如何组合成“从触发到合法终止”的完整业务闭环？

业务闭环必须满足：

```text
Trigger
→ Preconditions
→ Business Actions / Decisions
→ State Changes
→ User-visible Outcome
→ Legal Termination or Wait
```

本阶段不把闭环直接拆成 U1/U2/U3 等施工单元。`重构决策_V1.md` 中历史建议的 R1/U1-U7 只能作为后续 Phase 6 拆单元时的参考，不能替代本文。

## 2. V1 业务闭环总图

AIdoctor V1 的核心不是固定五步，而是一条允许循环、抢占、回退和安全退出的状态驱动闭环：

```text
用户发起问诊
↓
F1 建立对象与当前问题
↓
F2 理解并提交当前临床事实
↓
F4 强制风险评估
↓
G4 Safety Gate
↓
Clinical Readiness Resolver
├─ NEEDS_CLARIFICATION
│    → F3 形成澄清问题
│    → WAITING_USER
│    → Resume
│    → F2
│
├─ CAN_ASK_MORE
│    → F3 选择下一关键问题
│    → WAITING_USER
│    → Resume
│    → F2
│
├─ READY_FOR_CLINICAL_ANALYSIS
│    → F5 疾病方向 / Must-Exclude
│    → F3 重新判断 Gap
│    → F4 必要时重新评估 Risk
│    → 再次求值 Clinical Readiness
│
├─ NEEDS_OFFLINE_EVIDENCE
│    → F6 形成有依据的线下证据/检查建议
│    → F7 安全退出交付
│    → SAFE_EXIT
│
├─ OUT_OF_SCOPE
│    → F7 范围说明 + 安全引导
│    → SAFE_EXIT
│
└─ NO_RELIABLE_DIRECTION
     → F7 不确定性/能力边界说明
     → SAFE_EXIT

任何阶段
↓
Risk = HIGH_RISK / SafetyGate = BLOCKED|UNAVAILABLE
↓
安全抢占
↓
F7 安全交付
↓
SAFE_EXIT

正常证据充分且结果合法
↓
F7 正式交付
↓
COMPLETED
```

核心特点：

1. Safety 可以在任意新事实到达后重新触发；
2. F3 与 F5 可以循环，而不是单向 Step1→Step5；
3. 用户回答必须通过 F2 重新形成临床事实，不能直接改 DDx/Risk；
4. 新事实可以使 F3-F7 的旧派生结果失效；
5. V1 的跨轮等待属于正常业务，不是异常；
6. `COMPLETED` 只代表正常问诊目标完成；边界、风险、证据不足等合法退出进入 `SAFE_EXIT`；
7. 任何循环都必须满足业务收敛规则，不允许无限追问或无限分析；
8. 同一 Clinical State Version 下，Safety 与 Clinical Readiness 必须得到唯一、可解释的下一业务路径。

## 2.1 Clinical Readiness 唯一决策优先规则

Phase 4 已冻结：F1/F3/F5/F6 只提供 Readiness 输入，由 Clinical Readiness Resolver 综合，并由 G2 验证提交唯一结果。

Phase 5 进一步冻结其业务优先原则。具体算法、权重和字段留到后续阶段，但同一 Clinical State Version 下必须得到确定性的唯一下一路径。

第一层永远先执行 Safety：

```text
Risk = HIGH_RISK
或 Safety Gate = BLOCKED / UNAVAILABLE
→ 不再比较普通 Clinical Readiness
→ 直接进入 BL-08
```

在 Safety 允许普通推进时，Readiness 输入按以下业务原则解析：

```text
1. OUT_OF_SCOPE
   当前问题不属于已批准 Clinical Scope
   → BL-07

2. NEEDS_OFFLINE_EVIDENCE
   存在阻断当前正常结论、且只能线下获得的关键证据
   → BL-06

3. NEEDS_CLARIFICATION
   当前对象/问题/关键表达尚未可靠建立，且仍可在线澄清
   → BL-04

4. CAN_ASK_MORE
   存在可在线获得且预期具有实际决策价值的关键 Gap
   → BL-04

5. READY_FOR_CLINICAL_ANALYSIS
   已满足当前分析最低条件，且不存在更高优先级阻断项
   → BL-05

6. NO_RELIABLE_DIRECTION
   当前能力已正常工作，但不能形成可靠方向，且没有更高优先级的合法在线/线下获取路径
   → BL-07
```

其中：

```text
NEEDS_OFFLINE_EVIDENCE
```

只有在对应线下证据对当前正常结论或 Must-Exclude 处置具有阻断意义时，才优先于普通线上追问；若线下缺口并不阻断当前业务目标，而仍存在可以实质改变 Safety/DDx/Must-Exclude/Readiness/Delivery 的线上关键问题，则可以继续 BL-04。

强制约束：

```text
同一 Clinical State Version
→ 一个唯一 Clinical Readiness
→ 一个唯一普通下一业务路径
```

不得把冲突留给前端、自由 Agent 或任一单独 Capability 临时决定。

---

## 2.2 闭环收敛与停止原则

V1 允许 BL-04 ↔ BL-05 循环，但循环不是目标本身。

继续一次新的追问或重新分析，必须能够说明它预期会实质影响至少一个当前业务决策：

```text
Clinical Risk / Safety Gate
DDx Candidate / 排序
Must-Exclude 状态
Clinical Readiness
Delivery 是否合法
关键不确定性是否可降低到影响决策的程度
```

如果新的线上问题已不能合理预期改变上述任何结果，则不得仅为了“获得更多信息”继续追问。

循环必须具有终止保护。Phase 5 不冻结具体轮次、预算、时长或成本数值，但后续 Runtime / Capability / Policy 必须能够实现相应保护。

当继续循环不再具有足够业务价值，或触发受控终止保护时，只允许根据当前事实进入合法出口：

```text
正常分析目标已经满足
→ BL-10

关键证据只能线下获得
→ BL-06

无法形成可靠方向且没有合法进一步获取路径
→ BL-07

Safety 抢占
→ BL-08

能力/执行失败
→ BL-09

用户取消/等待过期
→ BL-12
```

禁止：

```text
循环停止
→ 为了“给一个结果”而编造 DDx

循环停止
→ 把 UNKNOWN 当 NO

循环停止
→ 自动把未排除 Must-Exclude 删除
```

# 3. BL-01 新问诊建立与入口澄清闭环

## 3.1 目标

从“用户第一次表达健康诉求”走到：

- 问诊对象与当前主要健康问题明确，并可进入临床主流程；或
- 明确属于当前 V1 范围外并安全退出；或
- 需要一次最小澄清并进入等待用户状态。

## 3.2 Trigger

```text
用户发起一次新的健康咨询
```

## 3.3 Preconditions

- 当前不存在可合法继续的同一健康问题 Consultation，或业务明确要求新建；
- 用户请求未被终止态 Consultation 误当作普通 Resume；
- 基础身份/授权条件满足当前 V1 最低要求。

## 3.4 主路径

```text
Consultation CREATED
↓
F1 Subject Resolution
├─ RESOLVED
│    ↓
│  F1 Problem Framing
│    ├─ FRAMED
│    │    → Consultation ACTIVE
│    │    → 进入 BL-02
│    │
│    ├─ CLARIFICATION_REQUIRED
│    │    → F3 创建最小澄清问题
│    │    → Question DELIVERED_TO_USER
│    │    → Consultation WAITING_USER
│    │    → Thread AWAITING_USER
│    │    → 进入 BL-03
│    │
│    └─ OUTSIDE_V1_INTENT
│         → Clinical Readiness Resolver = OUT_OF_SCOPE
│         → 进入 BL-07
│
└─ INVALID
     → 不能静默猜测问诊主体
     → 根据原因进入安全退出或不可恢复失败
```

## 3.5 关键规则

- 混合诉求必须优先保证临床症状/安全风险不被“体检、健康管理”等非 V1 意图掩盖；
- 模糊诉求允许最小必要澄清，但不应形成无限入口追问；
- F1 只拥有 Subject / Problem Framing，不拥有 Risk；
- 入口阶段如果已经发现可能的危险信号，仍必须进入 F4/G4 安全判断，不能仅以“问题尚未完全 framing”为理由延迟风险处置。

## 3.6 合法闭环结果

```text
A. ACTIVE + FRAMED
→ 转入临床主流程

B. WAITING_USER
→ 合法暂停，等待澄清答案

C. SAFE_EXIT
→ 当前 V1 范围外或无法可靠建立合法问诊对象

D. FAILED_TERMINAL
→ 只有真正不可恢复且无法形成安全交付的系统故障
```

# 4. BL-02 临床事实采集与安全入口闭环

## 4.1 目标

把用户当前输入变成可审计的 Clinical Observation / Fact，并在任何普通临床推进前完成当前版本所需的风险和 Safety Gate 判断。

## 4.2 Trigger

```text
首次已 framing 的用户描述
或
一次合法 Resume 后的新用户回答
或
一次合法用户补充/更正形成的新输入
```

## 4.3 主路径

```text
用户输入
↓
F2 Clinical Observation
EXTRACTED
→ NORMALIZED
→ CONFIRMED / UNCERTAIN / CONTRADICTED / INVALIDATED
↓
G2 提交合法事实变化
↓
Clinical State Version +1
↓
旧派生状态按依赖进入 STALE / INVALIDATED / SUPERSEDED
↓
F4 Risk Assessment
NOT_ASSESSED/STALE
→ ASSESSING
→ VALID 或 FAILED
↓
G4 Safety Gate
↓
若 Gate 允许普通推进
→ Clinical Readiness Resolver
→ 按 2.1 唯一决策规则进入 BL-04 / BL-05 / BL-06 / BL-07

若 Gate BLOCKED / UNAVAILABLE
→ BL-08
```

## 4.4 事实值语义

任何输入都必须保留：

```text
YES
NO
UNKNOWN
UNMEASURED
NOT_ASKED
NOT_APPLICABLE
```

并保证：

```text
UNKNOWN != NO
UNMEASURED != NORMAL
MODEL_INFERRED != PATIENT_REPORTED
Risk Assessment FAILED != NO_HIGH_RISK_SIGNAL
```

## 4.5 闭环完成条件

BL-02 不是以“解析服务返回 200”为完成，而是至少满足以下之一：

```text
A. 当前输入已形成有效 Clinical State Version
   + 当前版本 Safety Gate 已形成合法结论
   → 允许进入唯一下一临床决策

B. 输入仍需澄清
   → 进入 BL-04

C. Safety 阻断/不可用
   → 进入 BL-08

D. 输入无法可靠确认且不能继续安全处理
   → BL-07 / BL-09
```

# 5. BL-03 用户等待、回答与普通 Resume 闭环

## 5.1 目标

保证多轮问诊在页面刷新、网络中断、用户暂时离开后仍可恢复，且重复、过期或错误回答不会产生重复临床效果。

## 5.2 Trigger

```text
F3 Question DELIVERED_TO_USER
→ Consultation WAITING_USER
→ Thread AWAITING_USER
```

## 5.3 等待态必须保持

等待期间：

- Consultation 仍代表同一次有效问诊；
- 当前问题与 Clinical State Version 不因用户关闭页面而改变；
- Runtime 不应继续猜测用户答案；
- 不产生新的 DDx/Risk/Clinical Fact 副作用。

## 5.4 Resume 主路径

```text
用户返回并提交回答
↓
F8 Resume Event = RECEIVED
↓
VALIDATING
├─ DUPLICATE
│    → 不产生第二次临床效果
│    → 返回幂等确认、原事件处理引用或当前权威业务状态
│    → 不得把旧 Clinical State / 旧 Delivery 重新当成当前临床真值展示
│
├─ EXPIRED
│    → 不写当前 Clinical State
│    → 根据当前 Consultation 状态决定新问诊或安全提示
│
├─ REJECTED
│    → 不恢复 Thread
│
└─ ACCEPTED
     ↓
     Runtime 校验当前 Thread / Checkpoint 可恢复
     ↓
     Resume
     ↓
     F8 APPLIED（同一事件至多一次）
     ↓
     Consultation ACTIVE
     ↓
     回到 BL-02，由 F2 重新解释用户答案
```

## 5.5 关键不变量

```text
Same Business Event
→ at most one clinical effect

Idempotent effect
!= replay stale clinical truth

Resume accepted
!= answer directly becomes clinical truth

用户回答
→ F2
→ G2 commit
→ new Clinical State Version
```

## 5.6 合法闭环结果

- `ACTIVE`：成功恢复并进入下一轮事实处理；
- `WAITING_USER`：无有效回答，继续等待；
- `EXPIRED/REJECTED/DUPLICATE`：事件被正确处理但不产生错误副作用；
- `SAFE_EXIT`：Consultation 已不适合普通恢复但可安全收束；
- `FAILED_TERMINAL`：真正不可恢复的执行/状态损坏。

# 6. BL-04 主动问诊与信息补全闭环

## 6.1 目标

当当前信息不足时，不以固定 completeness 百分比粗暴前进，而是找到对当前决策最关键、且仍可在线获取的信息缺口，向用户提出下一项最有价值的问题。

## 6.2 Trigger

Clinical Readiness Resolver 形成：

```text
NEEDS_CLARIFICATION
或
CAN_ASK_MORE
```

## 6.3 主路径

```text
F3 汇总当前 Information Gaps
↓
区分 Decision Impact
BLOCKING / UNCERTAINTY_INCREASING / DEFERABLE / OFFLINE_ONLY
↓
筛选可在线获取且当前仍有实际决策价值的 Gap
↓
Question PROPOSED
→ SELECTED
→ DELIVERED_TO_USER
↓
对应 Gap = ASKED
↓
Consultation WAITING_USER
Thread AWAITING_USER
↓
BL-03 Resume
↓
BL-02 新事实形成
↓
F3 Gap 重新评估
↓
Clinical Readiness Resolver 重新求值
```

## 6.4 分支

### 用户给出有效答案

```text
Gap ANSWERED
→ F2 形成事实
→ Gap RESOLVED 或继续保留
```

### 用户明确不知道

```text
Gap USER_UNKNOWN
```

不能转换为 `NO`。

### 尚未测量

```text
Gap UNMEASURED
```

不能转换为 `NORMAL`。

### 只能线下获取

```text
Gap OFFLINE_REQUIRED
→ 若其对当前正常结论具有阻断意义
→ Clinical Readiness 输入 NEEDS_OFFLINE_EVIDENCE
→ BL-06
```

### Gap 已不再重要

```text
WAIVED / INVALIDATED
```

不得继续重复追问。

## 6.5 闭环退出条件

主动问诊循环只有在以下情况之一成立时退出：

```text
A. READY_FOR_CLINICAL_ANALYSIS
→ BL-05

B. NEEDS_OFFLINE_EVIDENCE
→ BL-06

C. OUT_OF_SCOPE / NO_RELIABLE_DIRECTION
→ BL-07

D. Safety 抢占
→ BL-08

E. 能力/执行失败
→ BL-09

F. 用户取消/超时
→ BL-12

G. 继续追问已无足够决策价值或触发受控终止保护
→ 根据 2.2 收敛到 BL-06 / BL-07 / BL-10 / BL-09
```

## 6.6 追问价值约束

F3 不得只因为“仍然存在未填写字段”就继续问。

每一个新问题至少必须能够合理预期影响：

```text
Safety
DDx
Must-Exclude
Readiness
Delivery eligibility
或关键不确定性
```

否则该 Gap 应被 `WAIVED / DEFERABLE / INVALIDATED`，或进入线下/边界出口，而不是继续制造轮次。

# 7. BL-05 疾病方向、Must-Exclude 与再问诊闭环

## 7.1 目标

在信息达到最低分析条件后形成有依据的疾病方向，并识别 Must-Exclude；分析结果若暴露新的关键缺口，应回到主动问诊而不是强行结束。

## 7.2 Trigger

```text
Clinical Readiness = READY_FOR_CLINICAL_ANALYSIS
Safety Gate = ALLOW / 合法 RESTRICTED 范围内允许
```

## 7.3 主路径

```text
F5 DDx Assessment
NOT_READY/STALE
→ ASSESSING
↓
基于当前 Clinical State
+ G1 已批准 Scope/Knowledge/Rules
+ G6 Evidence
↓
Candidate PROPOSED → ACTIVE
↓
形成 Candidate Tier
LIKELY / ACTIVE_ALTERNATIVE / MUST_EXCLUDE
↓
维护支持 / 反对 / 未知证据
↓
维护 Must-Exclude
UNASSESSED / NOT_EXCLUDED / EXCLUDED / NEEDS_OFFLINE_EXCLUSION
↓
DDx Assessment
├─ VALID
│    ↓
│  F3 根据当前候选重新评估 Information Gap
│    ↓
│  F4 对新推导出的风险相关事实/条件进行必要重评
│    ↓
│  Clinical Readiness Resolver
│    ├─ CAN_ASK_MORE → BL-04
│    ├─ NEEDS_OFFLINE_EVIDENCE → BL-06
│    ├─ OUT_OF_SCOPE / NO_RELIABLE_DIRECTION → BL-07
│    └─ 结果已满足正式交付条件 → BL-10
│
├─ NO_RELIABLE_DIRECTION
│    ↓
│  若仍有可在线、且具有实际决策价值的 Gap → BL-04
│  若存在阻断性线下 Gap → BL-06
│  若无更多合法获取路径 → BL-07
│
└─ FAILED
     → 不得解释为“没有疾病”
     → BL-09
```

## 7.4 Must-Exclude 强约束

```text
UNKNOWN / INSUFFICIENT_EVIDENCE
!= EXCLUDED
```

对 `MUST_EXCLUDE`：

- 未完成排除时必须保留；
- 若仍可线上补证且该问题有实际决策价值，进入 BL-04；
- 若只能线下排除，进入 BL-06；
- 不允许为了生成“干净结论”而静默删除高风险候选。

## 7.5 重要闭环特性

BL-05 与 BL-04 构成 V1 核心循环：

```text
分析
→ 发现新的关键缺口
→ 追问
→ 新事实
→ 风险重评
→ 重新分析
```

但该循环必须服从 2.2 的收敛与停止原则：只有下一轮仍具有实际决策价值时才允许继续。

因此固定 `Step 2 → Step 3 → Step 4 → Step 5` 不是当前业务真值，无限 `BL-04 ↔ BL-05` 也不是合法业务行为。

# 8. BL-06 线下证据/进一步检查建议闭环

## 8.1 目标

当关键证据无法通过当前线上问诊获得时，系统应明确“缺什么、为什么缺、可以进一步完善什么”，但不能伪装成已完成鉴别，也不能变成检查医嘱系统。

## 8.2 Trigger

```text
Clinical Readiness = NEEDS_OFFLINE_EVIDENCE
```

可能来源：

- F3 关键 Gap = OFFLINE_REQUIRED；
- F5 Must-Exclude = NEEDS_OFFLINE_EXCLUSION；
- F5 当前候选区分依赖线下测量/检查。

## 8.3 主路径

```text
F6 Offline Evidence Assessment
NOT_ASSESSED/STALE
→ ASSESSING
├─ VALID
│    ↓
│  Offline Evidence Need
│  IDENTIFIED → JUSTIFIED
│    ↓
│  需要具体检查/测量建议时
│  Examination Suggestion
│  PROPOSED → VALIDATED → DELIVERABLE
│    ↓
│  F7 组装安全退出型 Delivery
│    ↓
│  VALIDATING
│    ├─ VALIDATION_FAILED / 交付执行失败
│    │    → Delivery Readiness BLOCKED
│    │    → BL-09
│    │
│    └─ VALIDATED
│         → DELIVERED
│         → Consultation SAFE_EXIT
│
└─ FAILED
     → FAILED != NOT_NEEDED
     → BL-09
```

## 8.4 输出必须包含

- 当前仍缺失的关键证据；
- 该证据影响哪个疾病方向/Must-Exclude/风险判断；
- 为什么线上无法完成；
- 有正式依据时，可给出检查方向或具体检查项目；
- 明确其性质是“进一步完善信息/与医生沟通的建议”，不是系统下达医嘱。

## 8.5 V1 边界

本闭环在：

```text
建议已安全交付
→ SAFE_EXIT
```

即闭合。

V1 不继续实现：

```text
用户几小时/几天后完成检查
→ 上传结果
→ 自动恢复原 Consultation
→ 再次 DDx
```

该能力属于后续产品阶段，不得在 V1 Phase 5 中偷渡。

# 9. BL-07 范围外 / 无可靠方向 / 输入不足的安全退出闭环

## 9.1 目标

系统正常识别到“当前不适合继续给出疾病方向”时，形成一个合法、安全、可解释的终止，而不是制造答案或把它误报成系统故障。

## 9.2 Trigger

至少包括：

```text
Clinical Readiness = OUT_OF_SCOPE
Clinical Readiness = NO_RELIABLE_DIRECTION
关键输入无法可靠确认且不能继续线上澄清
```

## 9.3 主路径

```text
确认当前原因
↓
不得生成未经支持的疾病方向
↓
F7 形成 Safe Exit Delivery
- 当前系统能确认什么
- 当前无法确认什么
- 为什么不能继续
- 需要用户下一步做什么
- 必要就医/专业咨询建议
↓
F7 VALIDATING
├─ VALIDATION_FAILED / 交付执行失败
│    → Delivery Readiness BLOCKED
│    → BL-09
│
└─ VALIDATED
     → Delivery Readiness READY
     ↓
     交付
     → DELIVERED
     ↓
     Consultation SAFE_EXIT
```

## 9.4 区分 Failure

```text
OUT_OF_SCOPE / NO_RELIABLE_DIRECTION
= 合法业务结果

Capability FAILED
= 执行失败
```

两者不能共用空数组、null 或 `{}` 表达。

# 10. BL-08 高风险 / Safety Gate 抢占闭环

## 10.1 目标

任何新事实触发高风险或 Safety Gate 阻断时，安全路径必须抢占普通问诊/鉴别流程，避免为了“继续收集信息或提高准确率”延误安全处置。

## 10.2 Trigger

```text
Clinical Risk = HIGH_RISK
或
Safety Gate = BLOCKED
或
Safety Gate = UNAVAILABLE
```

## 10.3 主路径：高风险

```text
F4 Risk Assessment VALID
→ Risk HIGH_RISK
↓
G4 Safety Gate = RESTRICTED / BLOCKED
↓
Consultation SAFETY_ESCALATED
↓
冻结/阻断普通 F5/F6 推进
↓
只允许不会延误处置的必要动作
↓
F7 形成高风险安全交付
- 风险依据
- 明确就医/急诊方向
- 当前系统不继续普通鉴别的原因
↓
F7 VALIDATING
├─ VALIDATION_FAILED / 交付执行失败
│    → BL-09
│
└─ VALIDATED
     → Delivery DELIVERED
     → Consultation SAFE_EXIT
```

## 10.4 主路径：必要安全能力不可用

```text
Risk Assessment FAILED
或关键 Safety Capability 不可用
↓
Safety Gate = UNAVAILABLE
↓
不得形成 ALLOW
↓
不得继续普通 DDx
↓
F7 形成能力受限下的安全提示/就医建议
↓
若交付失败 → BL-09
若安全交付可完成 → SAFE_EXIT
若连最低安全交付都无法可靠完成 → FAILED_TERMINAL
```

## 10.5 强约束

```text
HIGH_RISK
!= diagnostic confidence low/high

NO_DDX
!= LOW_RISK

SAFETY_UNAVAILABLE
!= SAFE

普通 Planner / Agent
不得覆盖 Safety Gate
```

# 11. BL-09 Capability / Runtime 失败与业务降级闭环

## 11.1 目标

把“能力执行失败”作为显式业务输入处理，禁止再次出现：

```text
failure
→ empty result
→ downstream interprets as normal/negative
```

## 11.2 Trigger

例如：

- F2 关键解析能力失败；
- F4 Risk Assessment FAILED；
- F5 DDx Assessment FAILED；
- F6 Offline Evidence Assessment FAILED；
- F7 Validation / Delivery 执行失败；
- Model/Knowledge/Rule Capability 当前不可用；
- Runtime 当前 Run 失败。

## 11.3 处理原则

失败后必须先区分：

```text
是否允许 Retry / Repair
是否存在已批准、满足当前安全和产品边界的 fallback
是否仍可安全继续收集用户信息
是否影响 Safety Gate
是否影响结果交付合法性
是否必须 Safe Exit
是否已经不可恢复到 FAILED_TERMINAL
```

Phase 5 不冻结 fallback 的技术类型，也不冻结重试次数、超时时长或具体实现。后续可能采用何种规则、能力、模型或 Runtime 方式，必须由对应 Capability / Runtime / Failure Policy 文档决定。

## 11.4 闭环结果

### 可恢复

```text
失败被修复 / 已批准 fallback 成功
→ 对应模块形成新的有效状态
→ 返回原业务闭环
```

返回原闭环后必须重新检查当前 Clinical State Version、Safety Gate 和相关派生状态是否仍有效，不能默认沿用失败前的旧结果。

### 不可继续普通临床分析，但可安全交付

```text
→ F7 安全降级说明
→ F7 必须完成合法验证与交付
→ SAFE_EXIT
```

若 F7 在安全降级交付本身继续失败：

```text
若仍存在另一条已批准的最低安全交付路径
→ 仅允许该最低安全路径

否则
→ FAILED_TERMINAL
```

### 无法形成最低合法安全交付

```text
→ FAILED_TERMINAL
```

## 11.5 关键规则

- `Thread FAILED_TERMINAL` 不自动等于 Consultation `FAILED_TERMINAL`；若可重建执行上下文或形成安全退出，业务层仍可恢复/Safe Exit；
- Capability failure 不得直接写成 `NO_HIGH_RISK_SIGNAL`、`NO_RELIABLE_DIRECTION`、`NOT_NEEDED`；
- F7 failure 不得直接进入 `COMPLETED` 或 `SAFE_EXIT`；只有实际完成合法交付后才能进入对应 Consultation 终态；
- Failure reason 必须可追溯到对应 Clinical State Version / Run / Capability Version。

# 12. BL-10 正常结果整合与完成闭环

## 12.1 目标

当正常问诊目标已达到时，生成一个不越界、证据可追溯、与当前状态版本一致的正式患者侧结果，并把 Consultation 合法结束为 `COMPLETED`。

## 12.2 Preconditions

至少满足：

```text
Consultation = ACTIVE
Safety Gate 允许正常交付
当前 Clinical State Version 有效
F4 Risk Assessment 对当前版本有效
F5 DDx Assessment = VALID
关键 Must-Exclude 已得到适当处置
不存在仍阻断正常结果的在线/线下关键 Gap
```

不是要求“所有字段都完整”，而是当前业务目标已经满足合法交付条件。

## 12.3 主路径

```text
F7 Delivery Package
NOT_STARTED
→ ASSEMBLING
↓
引用当前有效：
- Clinical Facts
- Risk
- DDx / Must-Exclude
- Evidence
- Unknown / Uncertainty
- 必要进一步建议
- Scope / Knowledge / Rule / Capability Versions
↓
VALIDATING
├─ VALIDATION_FAILED / 交付执行失败
│    → Delivery Readiness BLOCKED
│    → 修复/重新计算/BL-09
│
└─ VALIDATED
     → Delivery Readiness READY
     ↓
     正式交付用户
     ↓
     F7 DELIVERED
     → Delivery Readiness DELIVERED
     ↓
     Consultation COMPLETED
```

## 12.4 输出边界

正式结果可包含：

- 当前问题理解；
- 关键已知事实；
- 未知/未测量/不确定项；
- 疾病鉴别方向；
- Must-Exclude 当前状态；
- 支持/反对依据；
- 当前风险；
- 必要信息/检查建议；
- 就医建议；
- 当前支持范围与局限。

不得变成：

- 自动确诊；
- 自动处方；
- 个性化治疗方案；
- 长期健康管理计划。

## 12.5 Completion 强约束

```text
Workflow end
!= COMPLETED

Thread COMPLETED
!= Consultation COMPLETED

Delivery DELIVERED
+ 正常业务目标满足
→ Consultation COMPLETED
```

# 13. BL-11 用户更正、事实失效与重新计算闭环

## 13.1 目标

用户发现前面信息说错、补充新的关键事实或撤销旧信息时，系统必须对受影响的派生判断进行失效传播和重新计算，而不是只覆盖文本。

## 13.2 Trigger

```text
用户更正 / 撤销 / 补充既有事实
```

## 13.3 主路径

```text
F8 Correction Event RECEIVED
↓
VALIDATED / REJECTED
↓
合法更正
→ F2 重新解释涉及的 Clinical Observation / Fact
↓
G2 提交新的 Clinical State Version
↓
受影响下游状态：
F3 Gap → INVALIDATED / 重新识别
F4 Risk → STALE → 重新评估
F5 DDx/Must-Exclude → STALE / INVALIDATED → 重算
F6 Offline Evidence → STALE / SUPERSEDED → 重算
F7 Delivery → SUPERSEDED / 重新验证
Clinical Readiness Resolver → 重新求值
↓
Safety 再次优先判断
↓
按照 2.1 的唯一决策规则返回 BL-04 / BL-05 / BL-06 / BL-07 / BL-08 / BL-10
```

## 13.4 特别规则

如果更正发生在结果已经交付之后：

- 已交付历史不能被静默篡改；
- 原 Delivery 与对应 Clinical State Version 继续保留历史追溯；
- 是否允许在同一 Consultation 内重新开放，不在 V1 默认普通 Resume 语义中自动成立；
- 若 Consultation 已是终止态，默认新建 Consultation 或采用后续明确设计的修订机制。

Phase 5 不扩大终止态普通 Resume 边界。

# 14. BL-12 取消与过期闭环

## 14.1 用户取消

```text
用户明确取消
↓
Consultation CANCELLED
↓
Thread 停止接受普通 Resume
↓
未完成问题/派生操作不再产生新的临床副作用
```

## 14.2 等待过期

```text
Consultation WAITING_USER
↓
超过正式有效期
↓
Consultation EXPIRED
↓
旧回答不得直接写入当前 Clinical State
```

继续咨询时原则上创建新的 Consultation，除非后续版本明确支持某种受控恢复策略。

# 17. 闭环级全局不变量

```text
LOOP-INV-01 每次有效用户事实变化后，Safety 必须能够重新评估
LOOP-INV-02 用户回答必须经 F2/G2 后才能成为 Clinical State
LOOP-INV-03 WAITING_USER 是正常业务状态，不是 failure
LOOP-INV-04 Duplicate/Expired Resume 不得产生新的临床副作用
LOOP-INV-05 Capability Failure 不得被投射为合法阴性/空业务结果

LOOP-INV-07 Must-Exclude 未完成排除不得因证据不足自动消失
LOOP-INV-08 线上仍有高价值可获取 Gap 时，不应过早 Safe Exit
LOOP-INV-09 无可靠方向时不得为了完成流程而强行生成 DDx
LOOP-INV-10 上游事实变化必须使依赖的派生状态可失效/重算

LOOP-INV-12 Frontend 不得在任何闭环中创建 Clinical Truth
LOOP-INV-13 Thread/Checkpoint 决定如何恢复执行，不决定临床真值
LOOP-INV-14 OUT_OF_SCOPE / NEEDS_OFFLINE_EVIDENCE / NO_RELIABLE_DIRECTION 的合法终止是 SAFE_EXIT，不是 COMPLETED
LOOP-INV-15 只有正常问诊目标完成并成功交付才进入 COMPLETED
LOOP-INV-16 BL-04 ↔ BL-05 每次继续必须有实际预期决策价值，并具有终止保护
LOOP-INV-17 同一 Clinical State Version 的 Clinical Readiness 必须解析为唯一普通下一业务路径
LOOP-INV-18 F7 Validation/Delivery Failure 不得直接进入 COMPLETED 或 SAFE_EXIT，必须进入失败处理
LOOP-INV-19 Idempotent Duplicate 不得重放陈旧 Clinical Truth
LOOP-INV-20 Phase 5 只要求 fallback 已批准且安全，不冻结其 deterministic/model/tool 等技术类型
```

# 18. 与 Current State / 重构决策的关系

当前现状中的旧固定 Workflow、completeness 阈值、直接 Map 写入、前端临床 fallback、Fail-open 等，都不能成为 Phase 5 的业务闭环规则。

`重构决策_V1.md` 中建议的第一个迁移路径：

```text
首次输入
→ 安全入口
→ 临床解析
→ 信息不足
→ 提问
→ WAITING_FOR_USER
→ 回复
→ Resume
```

现在可以在 Phase 5 中正式映射为：

```text
BL-01
→ BL-02
→ BL-04
→ BL-03
→ BL-02
```

因此它确实是一个很适合后续优先实现的候选子闭环，但是否成为第一个正式开发单元集合，要等 Phase 6 基于完整业务闭环再拆分，不能在 Phase 5 直接把历史 U1-U7 升格。

# 21. Phase 5 完成标准

Phase 5 应能够回答：

> 对 V1 的每类真实用户业务场景，从什么事件开始，经过哪些业务状态和模块，在哪些条件下循环、等待、被 Safety 抢占、正常完成、安全退出或失败终止？

当前设计形成 12 个业务闭环：

```text
BL-01 新问诊建立与入口澄清
BL-02 临床事实采集与安全入口
```
