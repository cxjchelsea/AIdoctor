## 一、服务概述

> **参考文档**：《AI医生系统-业务逻辑详细设计.md》

### 1.1 服务定位

- **对应工具**：tool_1（病例理解工具）
- **在双通道推理架构中的位置**：通道1（结构化推理通道）的起点，为后续诊断提供标准化输入
- **服务职责**：将非结构化的患者信息转换为结构化的临床要素

**核心价值**：
- 作为结构化推理通道的入口，负责将用户的自然语言输入转换为系统可理解的结构化数据
- 为后续的诊断引擎、问诊服务等提供标准化的医学概念输入
- 支持多模态输入（文本、图片等），提升用户体验

### 1.2 输入输出

#### 1.2.1 输入数据格式和来源

**输入来源**：
- **上游服务**：diagnosis-service（流程编排服务）
- **直接输入**：用户对话内容、病历文本、检查报告等

**输入数据格式**：
```json
{
  "userId": "user_123",
  "sessionId": "session_456",
  "cdpId": "cdp_789",
  "text": "我最近胸口闷，走几步就喘，之前有高血压",
  "input": {
    "modality": "text",  // 或 "image", "mixed"
    "images": [],  // 图片URL列表（可选）
    "vitalSigns": {},  // 生命体征（可选）
    "medicalHistory": {}  // 既往史（可选）
  }
}
```

**输入数据类型**：
- 病历自由文本
- 对话内容
- 检查单
- 生命体征
- 既往史

#### 1.2.2 输出数据格式和目标

**输出目标**：
- **下游服务**：diagnosis-engine-service（诊断引擎）、dialog-service（对话服务）
- **CDP更新**：更新 `patient_state` 字段

**输出数据格式**：
```json
{
  "code": 200,
  "message": "success",
  "data": {
    "concepts": [
      {
        "originalText": "胸口闷",
        "normalizedSymptom": "胸闷样不适",
        "cui": "C0232118",
        "confidence": 0.95,
        "conceptType": "symptom"
      }
    ],
    "structuredData": {
      "symptoms": [
        {
          "name": "胸闷样不适",
          "cui": "C0232118",
          "duration": "recent",
          "severity": "moderate",
          "trigger": null
        },
        {
          "name": "活动后气促",
          "cui": "C0030193",
          "duration": "recent",
          "severity": "moderate",
          "trigger": "activity"
        }
      ],
      "signs": [],
      "examinations": [],
      "medicalHistory": [
        {
          "disease": "高血压病",
          "icd": "I10",
          "status": "ongoing"
        }
      ],
      "medications": [],
      "allergies": []
    },
    "ambiguousExpressions": [
      {
        "text": "胸口闷",
        "type": "ambiguous",
        "suggestedQuestions": ["请描述一下胸闷的具体性质？是压迫感还是疼痛？"]
      }
    ]
  }
}
```

**输出数据结构**：
- **归一化概念列表**：原始文本 → 标准术语（CUI/ICD/SNOMED编码）
- **结构化数据**：
  - 症状（症状名称、持续时间、严重度、诱因）
  - 体征（客观检查结果）
  - 既往史（疾病史、手术史）
  - 用药史（当前用药、既往用药）
  - 过敏史
  - 检验异常（检查项目、异常值、异常程度）
- **歧义表达列表**：需要进一步追问的模糊表达

#### 1.2.3 数据流转关系

**CDP数据流转**：
1. **输入**：从CDP获取 `patient_state` 中的原始文本数据
2. **处理**：进行概念识别、归一化、结构化提取
3. **输出**：更新CDP的 `patient_state` 字段，写入结构化数据

**服务间数据流转**：
```
用户输入 → diagnosis-service → clinical-parsing-service
                                    ↓
                        结构化临床要素
                                    ↓
                    diagnosis-engine-service / dialog-service
```

### 1.3 业务价值

**解决的核心业务问题**：
1. **自然语言理解**：将用户的口语化表达转换为医学标准术语
2. **多模态理解**：支持文本、图片等多种输入形式
3. **结构化提取**：从非结构化文本中提取结构化临床要素
4. **歧义处理**：识别模糊表达，生成追问问题

**业务价值**：
- 为后续诊断引擎提供标准化的输入数据
- 提升系统对用户自然语言的理解能力
- 支持多模态输入，提升用户体验
- 通过歧义识别，引导用户提供更准确的信息

### 2.1 技术栈选择

#### 2.1.1 编程语言和框架

- **编程语言**：Python 3.10+
- **Web框架**：FastAPI 0.104.1+
  - **选择理由**：
    - 高性能异步框架，适合处理并发请求
    - 自动生成API文档（Swagger/OpenAPI）
    - 类型提示支持，提升代码可维护性
    - 与Python生态集成良好

#### 2.1.2 核心依赖库

**自然语言处理**：
- **spaCy 3.7.2+**：用于文本分词、词性标注、命名实体识别
  - **选择理由**：成熟的NLP库，支持中文处理，性能优秀
- **transformers 4.35.0+**：用于BERT等预训练模型
  - **选择理由**：支持中文医学BERT模型，可用于医学概念识别

**数据处理**：
- **pydantic 2.5.0+**：用于数据验证和序列化
- **httpx 0.25.1+**：用于调用下游服务（OCR服务等）

**其他**：
- **uvicorn**：ASGI服务器
- **python-multipart**：支持文件上传（多模态输入）

#### 2.1.3 技术选型理由

| 技术 | 优势 | 劣势 | 适用场景 |
|------|------|------|----------|
| FastAPI | 高性能、自动文档、类型提示 | 相对较新，生态不如Django成熟 | API服务，适合微服务架构 |
| spaCy | 性能优秀、支持中文 | 需要额外配置中文模型 | 文本预处理、基础NLP任务 |
| transformers | 支持预训练模型、效果好 | 资源消耗较大 | 医学概念识别、语义理解 |

### 2.2 核心算法/方法

#### 2.2.1 医学概念识别

**算法描述**：
- 从非结构化文本中识别医学概念（症状、疾病、药物、检查等）
- 使用规则匹配 + 机器学习模型（BERT）相结合的方法

**实现思路**：
1. **文本预处理**：
   - 使用spaCy进行分词、词性标注
   - 文本清洗（去除标点、特殊字符）
2. **规则匹配**：
   - 基于归一化词表进行精确匹配
   - 支持同义词、别名匹配
3. **机器学习识别**：
   - 使用医学BERT模型进行命名实体识别（NER）
   - 识别症状、疾病、药物等实体
4. **结果融合**：
   - 合并规则匹配和模型识别结果
   - 去重、排序、置信度计算

**算法复杂度**：O(n×m)，n为文本长度，m为归一化词表大小

#### 2.2.2 概念归一化

**算法描述**：
- 将识别到的医学概念转换为标准术语（CUI/ICD/SNOMED编码）
- 支持6类归一化词表：症状、疾病、药物、过敏源、检查项目、指标

**实现思路**：
1. **词表加载**：
   - 加载归一化词表（CSV/JSON格式）
   - 构建倒排索引（同义词 → 标准术语）
2. **匹配策略**：
   - **精确匹配**：完全匹配标准术语或同义词
   - **模糊匹配**：使用编辑距离、相似度计算
   - **上下文匹配**：结合上下文信息提升匹配准确率
3. **编码映射**：
   - 映射到CUI（UMLS概念唯一标识符）
   - 映射到ICD-10（疾病编码）
   - 映射到SNOMED CT（临床术语）
4. **置信度计算**：
   - 基于匹配方式、上下文信息计算置信度

**归一化词表结构**（参考《AI医生系统-知识内容需求具体.md》）：
- **1.1 症状归一化词表**：口语化表达 → 标准术语（CUI编码）
- **1.2 疾病名称归一化词表**：常见表达 → 标准术语（ICD编码）
- **1.3 药物名称归一化词表**：商品名/别名 → 标准名称（ATC编码）
- **1.4 过敏源归一化词表**：常见表达 → 标准术语
- **1.5 检查项目归一化词表**：不同医院名称 → 标准名称（LOINC编码）
- **1.6 指标名称归一化词表**：不同表达 → 标准术语

**算法复杂度**：O(m×log(m))，m为归一化词表大小（使用倒排索引）

#### 2.2.3 结构化提取

**算法描述**：
- 从文本中提取结构化的临床要素（症状、体征、检查等）
- 提取属性信息（持续时间、严重度、诱因等）

**实现思路**：
1. **实体关系抽取**：
   - 识别症状及其属性（持续时间、严重度、诱因）
   - 识别疾病及其状态（既往史、当前疾病）
   - 识别药物及其用法（当前用药、既往用药）
2. **模板匹配**：
   - 使用正则表达式匹配常见表达模式
   - 例如："最近3天" → duration: "3天"
3. **信息补全**：
   - 从CDP中获取已有信息，避免重复提取
   - 合并新提取的信息和已有信息

**算法复杂度**：O(n)，n为文本长度

#### 2.2.4 多模态理解

**算法描述**：
- 支持文本、图片等多种输入形式
- 调用OCR服务识别图片中的文字

**实现思路**：
1. **输入类型判断**：
   - 判断输入类型（text/image/mixed）
2. **图片处理**：
   - 调用ocr-service进行OCR识别
   - 获取图片中的文字内容
3. **文本融合**：
   - 将OCR识别的文字与原始文本合并
   - 进行统一的医学概念识别和归一化

**依赖服务**：ocr-service（可选）

#### 2.2.5 歧义表达判定与追问

**算法描述**：
- 识别模糊、歧义的表达
- 生成追问问题，引导用户提供更准确的信息

**实现思路**：
1. **歧义规则匹配**：
   - 使用歧义表达判定规则库（1.8）
   - 识别常见的歧义表达（如"胸痛"需要进一步追问性质）
2. **追问生成**：
   - 基于歧义类型生成针对性的追问问题
   - 例如："胸痛" → "请描述一下疼痛的性质？是压迫感还是刺痛？"
3. **结果返回**：
   - 在响应中返回歧义表达列表和追问建议
   - 由dialog-service进一步处理追问

**算法复杂度**：O(m)，m为歧义规则库大小

### 2.3 性能要求

> **参考文档**：《AI医生系统-技术架构设计-性能与评估.md》

#### 2.3.1 响应时间要求

- **单次解析响应时间**：< 2秒（P95）
- **概念识别时间**：< 500ms
- **概念归一化时间**：< 800ms
- **结构化提取时间**：< 500ms
- **多模态处理时间**：< 3秒（包含OCR调用）

#### 2.3.2 并发处理能力

- **目标QPS**：100+ 请求/秒
- **并发连接数**：支持500+并发连接
- **资源限制**：单实例内存 < 4GB，CPU < 2核

#### 2.3.3 资源消耗限制

- **内存消耗**：< 4GB（包含模型加载）
- **CPU消耗**：< 80%（平均负载）
- **磁盘IO**：最小化（词表加载到内存）

### 2.4 关键技术点

#### 2.4.1 关键技术难点

**难点1：中文医学概念识别准确率**
- **问题**：中文医学文本复杂，口语化表达多样
- **解决方案**：
  - 使用医学BERT模型（如BERT-Base-Chinese + 医学领域微调）
  - 结合规则匹配提升准确率
  - 使用归一化词表进行后处理

**难点2：归一化词表规模大，匹配效率低**
- **问题**：归一化词表可能包含数万条记录，线性匹配效率低
- **解决方案**：
  - 使用倒排索引（Trie树或哈希表）
  - 使用缓存机制（Redis）缓存常用匹配结果
  - 异步加载词表，避免启动时阻塞

**难点3：多模态输入处理**
- **问题**：需要调用OCR服务，可能影响响应时间
- **解决方案**：
  - 异步调用OCR服务
  - 设置超时和重试机制
  - 支持OCR结果缓存

**难点4：歧义表达判定准确性**
- **问题**：如何准确识别需要追问的歧义表达
- **解决方案**：
  - 使用规则库 + 机器学习模型
  - 结合上下文信息判断
  - 与dialog-service协作，由问诊服务进一步处理

#### 2.4.2 技术风险及应对

| 风险 | 风险等级 | 应对措施 |
|------|---------|---------|
| 归一化词表更新频繁 | 中 | 支持热更新，使用版本控制 |
| OCR服务不可用 | 中 | 降级处理，仅处理文本输入 |
| 模型推理性能不足 | 高 | 使用模型量化、模型蒸馏优化 |
| 内存占用过高 | 中 | 使用模型缓存、按需加载 |

### 3.1 API端点定义

#### 3.1.1 病例理解接口（核心接口）

**接口路径**：`POST /api/v1/parsing/parse`

**说明**：这是原有的业务接口，保持向后兼容。

#### 3.1.1.1 统一工具调用接口（新增）

**接口路径**：`POST /api/v1/tools/tool_1/invoke`

**接口描述**：统一的工具调用接口，符合《工具调用协议.md》规范。主Agent通过此接口调用工具。

**请求方法**：POST

**请求头**：
```
Content-Type: application/json
```

**请求体**（ToolContext格式）：
```json
{
  "trace_id": "string",  // 必填：追踪ID
  "cdp_reference": {
    "cdp_id": "string",  // 必填：CDP ID
    "version": 0,  // 必填：CDP版本号
    "read_fields": ["string"]  // 必填：需要读取的CDP字段路径列表
  },
  "agent_state_summary": {
    "current_step": 0,  // 必填：当前诊断步骤（1-5）
    "work_mode": "string"  // 必填：工作态（wellness_mode/clinical_mode）
  },
  "constraints": {
    "max_time_seconds": 0,  // 必填：最大执行时间（秒）
    "max_cost": 0.0,  // 必填：最大成本
    "risk_level_limit": "string"  // 可选：风险等级限制（L1/L2/L3/L4）
  },
  "call_params": {}  // 可选：工具调用参数（工具特定）
}
```

**响应体**（ToolResult格式）：
```json
{
  "trace_id": "string",  // 追踪ID（与请求中的trace_id一致）
  "tool_id": "tool_1",  // 工具ID
  "status": "string",  // 执行状态（success/partial_success/failure/timeout）
  "payload": {},  // 输出payload（工具特定结构）
  "evidence": [
    {
      "source": "string",  // 证据来源（knowledge_base/kg_path/rule/llm）
      "reference": "string",  // 证据引用（CUI/路径ID/规则ID/LLM prompt）
      "strength": "string",  // 证据强度（strong/medium/weak）
      "affected_direction": "string",  // 可选：受影响方向
      "evidence_direction": "string",  // 可选：证据方向
      "evidence_name": "string"  // 可选：证据名称
    }
  ],
  "quality": {
    "confidence": 0.0,  // 置信度（0.0-1.0）
    "completeness": 0.0,  // 完整度（0.0-1.0）
    "accuracy": 0.0  // 可选：准确度（0.0-1.0）
  },
  "suggested_writes": [
    {
      "field_path": "string",  // 字段路径（如：cdp.patient_state.parsed_concepts）
      "value": {},  // 字段值
      "reason": "string"  // 写回原因
    }
  ],
  "errors": [
    {
      "error_type": "string",  // 错误类型（timeout/validation_error/runtime_error）
      "error_message": "string",  // 错误消息
      "error_details": {}  // 错误详情
    }
  ],
  "duration_ms": 0,  // 执行时间（毫秒）
  "metadata": {}  // 可选：元数据（工具特定）
}
```

**实现方式**：
1. 从ToolContext中提取CDP引用信息
2. 通过HTTP调用diagnosis-service的CDP查询接口获取数据
3. 根据read_fields提取指定字段的数据
4. 构建现有服务的请求格式（ClinicalParsingRequest）
5. 调用现有业务逻辑服务（ClinicalParsingService）
6. 将业务结果转换为ToolResult格式
7. 构建evidence引用和suggested_writes建议

**代码位置**：
- 接口实现：`app/api/routes.py` 的 `invoke_tool_1()` 函数
- 数据模型：`app/models/tool_context.py`、`app/models/tool_result.py`
- CDP读取工具：`app/utils/cdp_reader.py`

**接口描述**：将非结构化的患者信息转换为结构化的临床要素

**请求方法**：POST

**请求头**：
```
Content-Type: application/json
```

**请求体**：
```json
{
  "userId": "string",  // 必填：用户ID
  "sessionId": "string",  // 必填：会话ID
```

## 四、数据流设计

> **参考文档**：
> - 《AI医生系统-数据模型设计.md》
> - 《AI医生系统-技术架构设计-CDP数据与状态管理.md》
> - 《AI医生系统-最终输出格式规范.md》

### 4.1 数据输入来源

#### 4.1.1 上游服务

- **diagnosis-service**（流程编排服务）
  - **调用方式**：同步HTTP调用
  - **调用时机**：诊断流程Step 1（病例理解阶段）
  - **传递数据**：用户输入文本、CDP ID

#### 4.1.2 数据格式

**输入数据格式**（参考数据模型设计）：
- **文本输入**：用户自然语言描述
- **CDP数据**：通过CDP ID获取已有的患者状态信息
- **多模态输入**：图片URL列表（可选）

#### 4.1.3 数据获取方式

**CDP数据获取**：
1. 如果提供 `cdpId`，从CDP服务获取 `patient_state` 字段
2. 合并已有信息和新增信息，避免重复提取
3. 如果未提供 `cdpId`，仅处理当前输入文本

### 4.2 数据处理流程

#### 4.2.1 数据处理步骤

**Step 1：文本预处理**
- 文本清洗（去除标点、特殊字符）
- 分词、词性标注（使用spaCy）
- 文本标准化（统一编码、大小写等）

**Step 2：多模态处理**（如果输入包含图片）
- 调用ocr-service进行OCR识别
- 获取图片中的文字内容
- 与原始文本合并

**Step 3：医学概念识别**
- 规则匹配（基于归一化词表）
- 机器学习识别（使用BERT模型）
- 结果融合和去重

**Step 4：概念归一化**
- 匹配归一化词表（6类词表）
- 映射到标准编码（CUI/ICD/SNOMED）
- 计算置信度

**Step 5：结构化提取**
- 提取症状及其属性（持续时间、严重度、诱因）
- 提取疾病、药物、检查等信息
- 提取既往史、过敏史等

**Step 6：歧义表达判定**
- 匹配歧义表达判定规则库
- 生成追问建议

**Step 7：结果整合**
- 整合所有提取的结构化数据
- 与CDP已有信息合并
- 生成最终响应

#### 4.2.2 数据转换逻辑

**文本 → 结构化数据转换**：
```
"我最近胸口闷，走几步就喘，之前有高血压"
    ↓
{
  symptoms: [
    {name: "胸闷样不适", cui: "C0232118", duration: "recent"},
    {name: "活动后气促", cui: "C0030193", duration: "recent", trigger: "activity"}
  ],
  medicalHistory: [
    {disease: "高血压病", icd: "I10", status: "ongoing"}
  ]
}
```

#### 4.2.3 数据验证规则

**输入验证**：
- 文本长度：1-10000字符
- 图片URL格式验证
- CDP ID格式验证

**输出验证**：
- 概念列表非空验证
- 结构化数据格式验证
- 编码格式验证（CUI/ICD格式）

### 4.3 数据输出格式

#### 4.3.1 输出数据结构

**输出到CDP**：
- 更新 `patient_state` 字段
- 写入结构化数据（symptoms、signs、examinations等）

**输出到下游服务**：
- 返回完整的结构化数据
- 包含归一化概念列表、结构化数据、歧义表达列表

#### 4.3.2 数据格式规范

**遵循最终输出格式规范**：
- 使用标准编码（CUI/ICD/SNOMED/LOINC/ATC）
- 结构化数据格式统一
- 时间格式：ISO 8601格式

#### 4.3.3 数据存储方式

**CDP存储**：
- 通过diagnosis-service更新CDP
- 使用乐观锁机制避免并发冲突
- 支持版本控制

**缓存策略**（可选）：
- 缓存常用归一化匹配结果（Redis）
- 缓存OCR识别结果（避免重复识别）

### 4.4 CDP数据流转

#### 4.4.1 CDP字段更新

**更新的CDP字段**：
- `patient_state.symptoms`：症状列表
- `patient_state.signs`：体征列表
- `patient_state.examinations`：检查列表
- `patient_state.medicalHistory`：既往史
- `patient_state.medications`：用药史
- `patient_state.allergies`：过敏史

**更新方式**：
- 通过diagnosis-service更新CDP
- 使用CDP更新接口，传递结构化数据

#### 4.4.2 CDP版本控制

**版本管理**：
- 每次更新创建新版本（写时复制）
- 使用乐观锁（version字段）避免冲突
- 记录更新历史

#### 4.4.3 CDP状态流转

**状态流转**：
- 输入：从CDP获取 `patient_state`
- 处理：进行概念识别和归一化
- 输出：更新CDP的 `patient_state`，状态流转到下一步（诊断引擎）

## 八、风险评估

### 8.1 技术风险

| 风险 | 风险等级 | 影响 | 应对措施 |
|------|---------|------|---------|
| 归一化词表规模大，匹配效率低 | 中 | 响应时间增加 | 使用倒排索引、缓存机制 |
| 医学概念识别准确率不足 | 高 | 影响后续诊断准确性 | 结合规则匹配和机器学习，持续优化 |
| OCR服务不可用 | 中 | 多模态功能失效 | 降级处理，仅处理文本输入 |
| 模型推理性能不足 | 中 | 响应时间增加 | 使用模型量化、模型蒸馏 |
| 内存占用过高 | 中 | 服务稳定性问题 | 使用模型缓存、按需加载 |

### 8.2 业务风险

| 风险 | 风险等级 | 影响 | 应对措施 |
|------|---------|------|---------|
| 归一化词表更新频繁 | 中 | 需要频繁更新服务 | 支持热更新，使用版本控制 |
| 用户表达多样化，识别困难 | 高 | 识别准确率下降 | 持续扩充归一化词表，优化识别算法 |
| 歧义表达判定不准确 | 中 | 影响用户体验 | 优化歧义规则库，结合上下文判断 |

### 8.3 时间风险

| 风险 | 风险等级 | 影响 | 应对措施 |
|------|---------|------|---------|
| 归一化词表数据准备延迟 | 中 | 开发进度延迟 | 提前准备测试数据，使用模拟数据开发 |
| 模型训练/微调时间超预期 | 中 | 功能实现延迟 | 先使用规则匹配，模型作为优化项 |
| 集成测试问题多 | 中 | 上线时间延迟 | 提前进行集成测试，及时发现问题 |

## 九、后续优化方向

### 9.1 性能优化

**优化方向**：
1. **模型优化**：
   - 使用模型量化（INT8）减少内存占用
   - 使用模型蒸馏（Distillation）提升推理速度
   - 使用TensorRT等推理加速框架

2. **缓存优化**：
   - 扩大缓存范围（缓存更多匹配结果）
   - 使用分布式缓存（Redis Cluster）
   - 实现缓存预热机制

3. **并发优化**：
   - 使用异步处理提升并发能力
   - 使用连接池优化HTTP调用
   - 使用消息队列处理批量请求

### 9.2 功能扩展

**扩展方向**：
1. **多语言支持**：
   - 支持英文医学文本识别
   - 支持多语言归一化词表

2. **模型升级**：
   - 使用更先进的医学BERT模型
   - 使用大语言模型（LLM）进行概念识别

3. **知识图谱集成**：
   - 使用知识图谱验证概念识别结果
   - 使用知识图谱进行概念关系推理

4. **实时学习**：
   - 支持用户反馈学习
   - 支持归一化词表自动更新

### 9.3 可观测性增强

**增强方向**：
1. **监控指标**：
   - 响应时间监控（P50/P95/P99）
   - QPS监控
   - 错误率监控
   - 资源使用监控

2. **日志增强**：
   - 结构化日志（JSON格式）
   - 链路追踪（TraceID）
   - 业务日志（概念识别结果、归一化结果）

3. **告警机制**：
   - 响应时间告警
   - 错误率告警
   - 服务不可用告警
